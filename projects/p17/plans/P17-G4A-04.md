# P17-G4A-04 Ready plan

## Outcome and corrected scope

G4A-04 closes the current Phase-4A declaration-group transaction boundary without adding another
writer, coordinator, journal format, or runtime planner. Saving install and uninstall continue to
plan exact immutable whole-file manifest/lock images. Multiple declaration groups that select the
same artifact pair form one deterministic collision lane: every group retains its own tool-pair
transactions and results, but the next colliding group is explicitly gated by the preceding
group's terminal `write-lock`. A failed, cancelled, or dependency-skipped predecessor therefore
leaves later same-pair groups unstarted. A fresh same-command rerun reads current revisions and
converges the remaining work.

The corrected immutable primary scope is exactly two entities:

- phase task `EWP-P4A-T03`; and
- phase selector `EWP-P4A-TS02`.

## Normative transaction boundary

The retained hierarchy is:

```text
Invocation
└── source/declaration group
    ├── exact manifest/lock intent
    ├── Claude placement transaction
    └── Codex placement transaction
```

The following rules are immutable:

1. Invocation syntax, option conflicts, global state, selection ambiguity, capability, and
   approval preflight complete before any write.
2. A source that fails before identity/reference resolution writes nothing.
3. A resolved install group persists its complete requested declaration and exact lock intent;
   local tool failures never shrink portable tools.
4. Every selected tool/scope pair has an independent journal and result. A started group reports
   every pair unless cancellation stops it; a sibling failure never rolls back a terminal success.
5. Saving uninstall retains one declaration and its lock entry until every selected removal in
   that declaration group succeeds or is acceptably absent.
6. A portable transition becomes an available prefix only when its final required artifact
   operation succeeds. For normal saving work this is `write-lock`. A saving uninstall group is
   also unsuccessful until that point because its artifact work follows all removals. A saving
   install group can still fail later at a tool pair after its portable prefix is already durable.
7. There is no whole-invocation, cross-group, or cross-tool atomicity promise and no `--atomic`
   surface.
8. Default fail-fast skips later groups after failure. Continue schedules later independent groups
   and preserves the original nonzero result. Cancellation always stops remaining work.
9. Groups colliding on the one selected artifact pair are not independent. Continue does not
   authorize them to execute against an unavailable immutable prefix.
10. Same-command rerun always plans from a fresh snapshot and current revisions. It does not reuse
    mutable in-memory ledger or artifact state from the failed invocation.

This clarification makes “later independent groups” concrete. No-save acquisition groups and
noncolliding current mutator groups retain the signed continuation behavior. Saving acquisition
groups in one invocation select one artifact pair, so their portable operations share a collision
lane even though their tool-pair journals remain declaration-local.

## Same-pair collision lane

For two saving uninstall declarations ordered canonically as alpha then beta, the plan is:

```text
alpha Claude remove ----\
alpha Codex remove ------> alpha write-manifest -> alpha write-lock
                                                     |
                                                     | artifact-prefix collision barrier
                                                     v
beta Claude remove -----\
beta Codex remove -------> beta write-manifest -> beta write-lock
```

The barrier is explicit operation dependency metadata, not a hidden executor policy. Once a group
plans a same-pair artifact transition, its terminal `write-lock` is added to every operation in
each later saving group until another successful planned transition advances that prefix. A group
with no artifact transition does not advance the chain, but still waits for any prefix it observed
from an earlier group. Group-local dependencies remain explicit as well. Consequently:

- alpha pair failure skips alpha artifact writes; every beta operation is dependency-skipped;
- alpha manifest failure or alpha lock failure dependency-skips every beta operation;
- alpha terminal success advances the exact artifact prefix and permits beta to start;
- fail-fast and continue produce the same beta skip for a failed colliding alpha group, because
  beta is not independent;
- a later truly independent group still follows the selected batch policy; and
- every skipped operation receives an ordinary `skipped-after-failure` result in plan order and
  emits no started-operation event.

The same rule applies to multiple resolved saving install source groups. Install retains its
existing group-local chain:

```text
migrate? -> write-manifest -> write-lock -> every selected placement
```

The next pair-changing install group depends on the preceding pair transition's `write-lock`, not
on the preceding group's live pairs. If that lock succeeds and a later placement fails, default
fail-fast skips the next source group while continue may run it from the now-durable exact prefix.
If the lock itself fails or is skipped, neither policy can start the later colliding transition.
An unchanged install group creates no new artifact-prefix terminal, but it still depends on the
latest earlier transition whose after-image its plan observed. Under continue, its pair result
cannot invalidate that already durable prefix. The planner derives the prefix terminal from the
immutable transition set; execution does not infer it.

For saving uninstall the terminal is always the final required `write-lock`. A tool removal never
serves as the cross-group terminal because portable retention is part of the declaration-group
contract.

## Narrow cross-group dependency amendment

Generic arbitrary cross-group DAGs remain invalid. Planning and execution accept only one closed
collision-barrier shape:

- groups are already in canonical deterministic order;
- the predecessor is the latest earlier `write-lock` that advances the same exact artifact pair;
- every operation in the dependent group names the same predecessor;
- no operation may depend on a later group or more than one external group;
- within-group dependencies remain acyclic and topological;
- the predecessor and dependent groups belong to the same command plan;
- acquisition additionally proves both groups select the same exact artifact pair and that the
  predecessor is the latest prefix terminal observed by the dependent saving group; and
- no saved-plan command or execution path is activated in G4A-04. Existing plan codecs and
  repositories remain byte-frozen; G4B-02 must independently decide and test how an exact saved
  plan validates this already-versioned dependency metadata.

`orderExecutableOperationsTopologically` may order this closed forward barrier but still rejects
every other cross-group edge. `validateExecutionPlanShape` repeats the exact structural validation
on the canonical plan. The scheduler uses its existing exact-success dependency check: it adds no
retry, branch selection, speculative execution, or resource-aware replanning.

The acquisition artifact controller retains its continuous role-image validation. Its current
prior-artifact-group success check becomes a defense that verifies the explicit dependency result;
it is not an independent scheduling rule. The existing artifact group/member/ledger/live lock
hierarchy and sole artifact coordinator remain unchanged.

## Immutable multi-declaration uninstall planning

`prepareUninstallArtifactPlanning` groups requested declaration intents by canonical operation
group ID and sorts them before constructing any transition. Duplicate command occurrences retain
their request indices but do not create duplicate declaration groups. One declaration selected for
Claude and Codex remains one group.

Planning owns local copies only:

1. Start from the one immutable observed manifest and lock image.
2. For the current declaration, identify every selected tool removal in that exact declaration.
3. Apply one lossless declaration edit to the prior planned manifest bytes:
   remove only selected tools, or remove the declaration when none remain.
4. Derive the exact correlated lock image: retain the lock entry while declared tools remain;
   remove it only with the final declaration; always update the root manifest semantic hash.
5. Record exact full before/after images and the fixed lossless edit/lock-replacement actions.
6. Carry those planned after-images as the next declaration group's immutable before-images.
7. Preserve nonselected declarations, defaults, registries, comments, whitespace, mode, and every
   unrelated lock entry.

No action is rebased onto whichever bytes happen to exist at execution. Exact under-lock revision
and actual-before validation must match the planned branch. A missing prefix dependency-skips the
later group rather than manufacturing another after-image.

Legacy project migration occurs at most once, before the first saving group, and its canonical
after-image becomes the first transition prefix. Multiple legacy migration operations, split
ownership, dual owners, a malformed/future artifact, or an incoherent lock remain pre-write
refusals. Force and continue cannot override them.

## Exact manifest-to-lock crash handoff

Manifest and lock remain separately journaled logical operations under one lease. A process may
therefore stop after a manifest operation is terminal and before its dependent lock operation
starts. G4A-04 closes only the exact fresh-snapshot handoff needed by saving uninstall.

Destination recovery is bounded. An explicit file/lock pair is reused exactly. Without explicit
selectors, remove-mode selection computes one combined owner set before choosing a destination:
ordinary manifest owners for every requested name plus sibling-lock handoff candidates from the
already-bounded project/user manifest candidates. A lock candidate is eligible only when its
canonical lock contains a requested name now absent from that manifest. All requested normal and
handoff owners must collapse to one exact artifact pair. Owners split across two pairs refuse before
snapshot planning or writes, even when one name has an ordinary manifest owner and another has only
a stale-lock owner. Exactly one pair selects; zero owners preserve the normal no-owner result. This
is not a filesystem crawl and never invents a new manifest. The existing role-based selectedBy
value (`selected-project-owner`, `project-root-owner`, or `user-owner`) remains truthful because
the selected artifact pair owns the exact normal/recovery entries; the later strict handoff proof
decides whether a stale entry may mutate. A custom lock override remains invocation-only and
therefore requires the same explicit selectors on rerun.

A lock-only repair is permitted when all of the following are true:

- the current manifest is canonical and already contains the exact planned selected-tool reduction
  or final declaration removal for the requested target;
- every manifest declaration other than that exact selected delta correlates with its current lock
  entry;
- for a reduced declaration, the selected lock entry is otherwise exact and only the root
  `manifestHash` is stale;
- for a removed declaration, the only extra lock entry is the requested removed target and the
  only other mismatch is the stale root `manifestHash`;
- live/ledger observations show that every selected removal for that declaration is already
  terminal or acceptably absent; and
- there is no unrelated entry, source, ref, SHA, content hash, schema, canonical-byte, or
  semantic mismatch.

That selected-removal proof is reconstructive and fail-closed; absence alone is never evidence.
The stale lock entry may locate a candidate but is never authority for its own `resolvedSha` or
`contentHash`. The planner combines current CLI target/tool/scope bounds and current adapter roots
with one exact authority shape for the recovery mode:

- **selected-tool reduction:** every selected pair is terminally absent. Authority comes from at
  least one retained unselected sibling pair for the same current declaration, never from the
  absent selected pair. Every retained sibling for that skill/scope must agree with the manifest's
  source/ref and with each other. Its origin and pinned records must be exact, including lowercase
  full-40 `origin.refResolved === pinned.gitSha`, and its pinned content hash must equal the freshly
  observed live content revision. Missing, non-pinned, custom, internally inconsistent, or
  disagreeing siblings refuse;
- **final declaration removal:** authority is proven separately for every selected tool pair from
  the ledger history array's append order. For each exact skill/tool/scope/project-root pair, the
  newest pair-affecting record must itself be a committed forward `remove`; filtering backward to
  an older uninstall is forbidden. Its intent and actual before/after live images must agree on
  pair identity, path, portable source/ref/full SHA/content, present before state, terminal absent
  after state, and committed disposition. Any active transaction, pending/nonterminal record,
  rollback, later install/repair/update/promote/remove disagreement, pruned/missing history, or
  intent/actual mismatch refuses. All selected-pair terminal histories must agree on the old
  declaration's portable source/ref/full SHA/content.

The current store may corroborate content bytes but its SHA-truncated path cannot prove the full
40-hex revision by itself. History array position is the only supersession order; timestamps and
filtered operation kinds are not substitutes. Recovery never performs source resolution, fetch,
Git/network access, or any resolver port call.

Only after that independent SHA/content proof may planning reconstruct the remaining bounded
fields. It enumerates a finite candidate set whose source/ref match the proven authority and whose
tools, scope, placement, and path are bounded by the request plus terminal history. It may not
invent a custom path. Inserting a candidate back into the current manifest must reproduce the stale
lock's exact prior `manifestHash`, and its source/ref/SHA/content fields must match the independent
authority exactly. Exactly one candidate may match. Zero or multiple candidates, an unbounded
custom path, lost required history, mixed scope, unsupported adapter, or another old field that
cannot be reconstructed uniquely refuses rather than guessing. A history-free declared-only
default-root removal therefore refuses: finite manifest-hash enumeration does not independently
prove the stale entry's SHA/content fields. Manual manifest deletion plus a stale lock likewise
cannot qualify solely because current live state is absent.

The repair emits `write-lock` only, against the exact observed stale lock and current manifest.
It never rewrites the human manifest, repeats a completed live removal, guesses a missing source,
or repairs unrelated drift. The repaired lock image may then serve as the immutable prefix for a
later colliding declaration group. Any broader mismatch refuses statefully and leaves recovery to
the existing diagnostic/recovery authorities.

Final-declaration removal intentionally leaves no manifest copy of the old tools/scope/placement.
The repair therefore uses an internal artifact-only uninstall recovery intent, not a fabricated
tool pair. It carries only the requested name, exact selected artifact pair/context, current
manifest/lock revisions, and the fixed lock repair. It plans one null-pair `write-lock`, reports no
live/ledger result, and derives a fresh recovery group/operation identity from the current request
and selected pair role/effective scope. It does not claim to resume the prior live operation ID or
invent the removed declaration fields. Existing ordinary uninstall intents remain tool/scope
specific and unchanged. This internal union stays inside acquisition planning and adds no command,
wire, saved-plan, or public package-root surface.

A crash after `write-lock` but before cleanup is handled by the existing coordinator recovery. A
crash within a live pair remains the existing pair-journal recovery case. G4A-04 adds no
cross-operation invocation journal.

## Result, revision, and exit truth

Every planned operation retains one result. Only a succeeded physical/logical commit advances the
touched resource revision. Failed, rolled-back, skipped, cancelled, and unstarted operations keep
their expected revision. A durable-after-error artifact outcome must be recovered/classified by the
existing coordinator before acquisition returns; it cannot be reported as an ordinary failed
operation while silently advancing the artifact cursor.

The current install/uninstall v2 report shapes remain sufficient and unchanged. They already expose
group/pair IDs through operation results, artifact effects, batch policy, skipped outcomes, save
mode, selected pair, and desired-state/live drift. Human and JSON renderers must preserve the
existing exit precedence:

```text
130 cancellation
then usage/state/capability/source/execution error
then drift 7 only after otherwise successful evaluation
then success 0
```

Continue never changes a failed batch to success. Dependency-skipped collision groups do not hide
the causal earlier error. Status reads fresh repositories and must report the exact declared,
locked, ledger, and live state after every partial boundary.

12. reporting/help: immutable revision receipts, status truth, human/JSON group/result parity, and

## Rejected designs and exclusions

exist, branch-dependent full bytes behind one published after-image, exponential conditional
after-image variants, a combined invocation finalizer, a second coordinator, a cross-domain
invocation journal, arbitrary cross-group DAGs, and whole-invocation rollback. Each would either
weaken immutable planning or materially expand architecture to make a colliding group appear
independent.

The group does not implement or register apply, sync, update, undo, GC, another adapter, another
artifact schema, saved-plan execution, new JSON versions, retry flags, `--atomic`, parallel writes,
or cross-filesystem rollback. It does not edit the normative WF13 assertions to fit current code.
It moves their terminal executable ownership to the first dependency-complete group.
