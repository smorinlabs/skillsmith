# P17-G5-05 mapped/Ready candidate plan

## State and coherent boundary

P17-G5-05 closes Phase 5 by composing already-signed sync, update, undo, apply, scheduler,
approval, artifact-pair, and transaction authorities. Its only missing product behavior is the
deliberately deferred update-to-undo seam: a successful update must retain enough exact artifact
lineage for `undo` to restore the prior manifest/lock intent together with the prior live
resolution, including a custom selected artifact pair.

The group does not add a command, option, scheduler, approval adapter, output format, recovery
engine, or transaction schema. It activates six planned validation owners and replays eight signed
dependency validations as one dependency-complete matrix.

Primary ownership is exactly seven entities:

- `EWP-CMD-UNDO-TS03`;
- `EWP-CMD-UPDATE-TS07`;
- `EWP-OPT-TS08`;
- `EWP-P5-TS05`;
- `EWP-WF09`;
- `EWP-WF13`; and
- `P1-04`.

Required-now is exactly 14 validations:

- the six primary selectors above; and
- signed dependency replays `EWP-CMD-APPLY-TS09`, `EWP-CMD-APPLY-TS11`,
  `EWP-CMD-APPLY-TS13`, `EWP-CMD-SYNC-TS09`, `EWP-CMD-UPDATE-TS06`,
  `EWP-CMD-UPDATE-TS08`, `EWP-CMD-UPDATE-TS09`, and `EWP-P4A-TS02`.

There is no downstream coverage. G5-05 must leave no planned Phase-5 catalog entity.

## Existing implementation audit

The dependency implementation already supplies:

- deterministic groups and `--continue-on-error` across apply, sync, update, and undo;
- exact bulk approval and noninteractive refusal through shared interaction/application policy;
- cancellation that stops unstarted groups and exit selection that preserves the real error;
- update artifact operations followed by independent tool-pair placement operations;
- prior-store retention in each committed update placement journal;
- custom-pair update selection and exact selected-pair output;
- scope/tool/target/all undo selection and committed reversal for dev, promote, install, and
  uninstall; and
- strict update and undo v1 reports with shared immutable operations/results.

The bounded missing seam is explicit in `undo/observe.ts`: an update candidate is recognized and
then refused as `undo-update-unavailable`. A committed update placement journal retains the live
before/after and prior store, but update artifact operations currently have no durable logical
history carrier. Guessing the artifact pair from cwd, deriving a sibling lock after a custom-pair
update, or reconstructing prior portable intent from current files would violate CF-040 and the
no-guessing undo contract.

Eight already-owned dependency selectors are green on the current baseline when serialized. An
attempt to run all stateful CLI fixture processes concurrently caused UPDATE-TS06 and TS09 to
collide at ledger-directory bootstrap; each passed immediately in serialized replay and both pass
inside the complete `--max-concurrency 1` terminal gate. G5-05 public-process fixtures therefore run
serially. Pure unit/static checks may still run concurrently.

## Durable update artifact lineage

### Forward update carrier

Every changing update declaration already has one deterministic operation group containing zero or
one manifest write, zero or one lock write, and one live operation per selected tool. G5-05 makes
the changing artifact operations durable logical history members of that same group:

- each artifact journal uses the existing strict logical-journal v1 shape;
- `pairId` remains null internally for the forward artifact carrier;
- intent and actual images contain the exact selected machine-bound artifact location and strict
  canonical manifest/lock before and after snapshots already present on the approved operation;
- command/workflow remain `update`; operation and group IDs remain those in the approved update
  plan;
- the pending carrier is durable before the artifact coordinator mutates a file;
- artifact-coordinator recovery and logical-journal phase advance converge together under the
  canonical ledger lock; and
- the carrier enters bounded committed history only after the exact physical after-image is
  authoritative.

The implementation must not add optional fields to the journal codec, persist CLI selectors in a
manifest/config, copy credentials/local paths into portable files, or create a second artifact
recovery record. Existing pre-G5-05 update history without an exact artifact carrier is visibly
non-reversible for artifacts and refuses with state remediation; undo never guesses or silently
restores only live state.

Manifest history is required when update changed requested ref/pin intent. Lock history is required
whenever update changed the selected resolution. A normal moving update commonly has only a lock
carrier; `--ref ... --pin` may have both. No-op artifact rows manufacture no carrier.

### Observation and lineage closure

Undo continues to select placement/history pairs through status. For an update source group it
additionally correlates sibling committed artifact carriers by exact group ID and validates:

- the selected live journals are committed forward updates or their exact rollback children;
- every artifact carrier has one unambiguous selected path and exact before/after image;
- its current physical artifact equals the expected after-image, or already equals the exact prior
  image after a committed rollback child;
- no newer committed or pending artifact operation supersedes that path/group lineage;
- a custom manifest/lock pair comes only from the recorded carrier, never sibling derivation;
- all selected pair journals and artifact carriers agree on source group, command/workflow, and
  project/scope identity; and
- malformed, missing, future, ambiguous, stale, partially observed, or permission-denied state
  refuses before approval or writes.

One selected update history group may contain multiple tool pairs but only one artifact transition.
Tool filtering may select a subset of pairs; artifact restoration is then explicit shared group
work and any remaining updated pair is reported as ordinary declared/live drift. An unfiltered
`undo <skill>` restores all selectable pairs and the artifact pair together.

### Pure inverse plan

The immutable undo planner adds the exact inverse manifest/lock operations to the already-selected
update group by swapping the recorded forward artifact before/after images. It does not parse live
files during planning, allocate a new source candidate, or invoke the update planner.

- inverse artifact operations use fresh deterministic rollback operation/transaction IDs and point
  internally to their exact forward parent operation IDs;
- operations remain in the existing undo operation vocabulary (`write-manifest`, `write-lock`);
- each artifact operation is assigned to the first actionable canonical pair in its update group so
  the existing strict `undo@1` pair/group operation coverage remains exact;
- the public pair retains its live source/active/parent lineage; artifact parent linkage remains in
  the private logical journal and exact operation images;
- an already-restored artifact transition contributes no operation;
- a group with all live pairs and artifacts already reversed remains `already-reversed` with zero
  mutation; and
- dry-run and execution expose byte-identical operations, dependencies, checks, selected group IDs,
  and artifact locations.

No field or enum is added to `undo@1`. Existing operations already carry manifest/lock images and
mutation flags. Existing effect projection remains schema-frozen; artifact truth is visible in the
operation/result vectors. If implementation cannot stay inside this signed shape, work stops for an
explicit contract amendment before product code continues.

## Execution, crash, and rerun contract

Approved update reversal uses one scheduler and the two signed physical authorities:

1. reacquire the canonical ledger lock and reobserve the exact update group, artifact carriers,
   selected live/store state, and expected revisions;
2. recover any same-operation artifact or placement record before new work;
3. publish rollback logical authority for the exact artifact parent before artifact mutation;
4. restore the exact selected manifest/lock pair through the artifact coordinator;
5. reverse each selected committed placement through the existing committed placement-reversal
   path, retaining pair independence and prior-store validation;
6. append committed rollback children without editing/removing forward history; and
7. clean private recovery state only after every corresponding terminal image is durable.

Artifact restoration precedes live rollback. This guarantees there is no state in which every live
pair appears terminally reversed while the artifact restoration has never become authoritative.
If a later pair fails, the restored artifact plus still-updated pair is truthful drift; the failure
remains nonzero, successful reversals remain committed, and a fresh rerun skips the already-restored
artifact and already-reversed pairs while converging only remaining work.

Cancellation before a durable boundary performs no write. Cancellation after a boundary leaves one
strict pending record and stops all later operations/groups. Permission and external-writer errors
retain their exact exit classes. Fail-fast marks later groups `skipped-after-failure`; explicit
continuation runs independent later groups but never hides the original failure. Invocation-level
syntax, ambiguity, state, artifact-lineage, approval, and no-prompt failures abort before mutation
under both policies.

## Shared bulk approval and scheduling closure

P1-04 is satisfied by composition, not a new facade:

- each command prepares one complete immutable selection and operation set;
- changing human execution receives one exact bulk prompt for that set;
- JSON, `--no-prompt`, and non-TTY execution require `--yes` where the command contract requires
  approval;
- `--yes` conflicts with dry-run/check before discovery or I/O;
- refusal/cancellation creates no artifact, ledger, live, store, backup, or recovery write;
- group order is deterministic and pair results remain independently visible;
- default fail-fast and explicit continuation have identical within-group semantics; and
- cancellation always stops regardless of continuation.

EWP-P5-TS05 proves this across sync, update, and undo. EWP-WF13 completes the dependency-scheduled
install/apply/sync/update/promote multi-tool matrix while retaining P4A-TS02 as its signed crash and
partial-failure foundation.

## Uniform artifact-option closure

EWP-OPT-TS08 is characterization plus cross-command integration, not a new option implementation.
It asserts, from live command declarations and spawned commands, that:

- status, doctor, check, install, uninstall, export, plan, fresh apply, sync-save, and update derive
  a sibling lock by default and accept one explicit advanced lock override only with one file;
- explicit paths are reported exactly, are never persisted, and must be repeated on later direct
  invocations;
- repeated singular file/lock selectors refuse before discovery;
- init rejects lockfile; no-save install/uninstall reject either selector; unsaved sync rejects
  either selector; and saved-plan apply rejects both;
- ordinary omission after a custom-pair command deliberately returns to sibling derivation; and
- portable-relative versus machine-bound absolute custom paths retain the signed plan behavior.

No command or option relation is changed unless this executable matrix identifies a real divergence
from CF-040. Any such divergence is corrected at the existing shared selector/registry authority,
not patched per command.

## Implementation order

1. Add the six primary selectors and hermetic fixture boundary; record honest red/characterization
   results and the eight serialized dependency baselines.
2. Add strict forward artifact-history projection and codec/history validation around approved
   update artifact operations.
3. Bind pending/committed artifact lineage to artifact-coordinator execution and recovery under the
   ledger lock.
4. Correlate update artifact lineage during undo observation and reject missing/stale/ambiguous
   history before approval.
5. Build pure inverse artifact operations and exact pair/group reductions without changing
   `undo@1` shape.
6. Execute inverse artifact operations through external scheduler bindings and committed placement
   reversal through the signed swap authority.
7. Close application approval/mutation accounting, output parity, custom-pair, partial-failure,
   cancellation, and crash/rerun matrices.
8. Refactor only after all primary and required-now selectors are green.

## Validation policy

Inner loops run the changed core suites, one primary selector at a time, and `bun run test:smoke`.
Because ledger, recovery, artifact barriers, cancellation, and crash behavior are in scope, every
recovery-affecting iteration also runs `bun run test:smoke:p2-ts04:recovery`. Stateful CLI fixture
selectors run serially; pure unit/static suites may run concurrently.

Targeted green requires all six primary selectors as separate processes. Impacted green requires
all 14 frozen commands, also as separate serialized processes, with exact receipts and no required
skip. Typecheck, boundary lint, catalog/package/plan structure, and diff checks are mandatory. A
full serialized terminal `bun run check -- --timeout 60000 --max-concurrency 1` runs only after
fresh independent GO and all proportional gates pass.

## Non-goals and stop conditions

- no new command, option, alias, output schema version, journal schema field, or recovery format;
- no undo of arbitrary current files or pre-lineage update history by inference;
- no global “latest operation” lookup or cross-project crawl;
- no change to saved-plan authorization, GC, distribution, help/completion, or Phase 6;
- no second scheduler, approval loop, artifact writer, or placement reversal engine;
- no parallel execution of stateful public-process fixtures; and
- no public-contract widening discovered during implementation without an explicit amendment,
  structural validation, fresh adversarial review, and user authorization.

## Ready-review questions

The independent reviewer must attempt to falsify at least:

- whether strict journal v1 can truthfully carry artifact operations without a schema change;
- whether artifact logical history and artifact recovery can diverge at any crash boundary;
- whether custom-pair identity survives update-to-undo without guessing;
- whether manifest intent must reverse together with lock/live for ref/pin transitions;
- whether assigning shared artifact inverse operations to one canonical pair keeps strict
  `undo@1` coverage and partial-result truth;
- whether artifact-first reversal and fresh rerun converge after every pair failure/cancellation;
- whether old update history refuses safely and actionably;
- whether the 47-path boundary omits a real shared authority or includes unnecessary scope; and
- whether the six primary selectors plus eight dependency replays completely prove P1-04,
  EWP-WF09, EWP-WF13, CF-026, and CF-040 without weakening signed tests.
