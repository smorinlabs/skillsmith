## Durable update artifact lineage

### Forward update carrier

Every changing update declaration already has one deterministic operation group containing zero or
one manifest write, zero or one lock write, and one live operation per selected tool. G5-05 makes
the changing artifact operations durable logical history members of that same group:

- each artifact journal uses the existing strict logical-journal v1 shape;
- `pairId` remains null internally for the forward artifact carrier;
- intent and actual images contain the exact selected machine-bound artifact location and strict
  canonical manifest/lock before and after identities already present on the approved operation;
- command/workflow remain `update`; operation and group IDs remain those in the approved update
  plan;
- each changing artifact operation is `conditional` with exactly one deterministic retained
  resource ID; the shared scheduler admits that shape only for update/undo `write-manifest` and
  `write-lock` null-pair operations and continues to reject retention on every other artifact
  prerequisite;
- the pending carrier is durable before the artifact coordinator mutates a file;
- artifact-coordinator recovery and logical-journal phase advance converge together under the
  canonical ledger lock; and
- the carrier enters bounded committed history only after the exact physical after-image is
  authoritative.

The implementation must not add optional fields to the journal codec, persist CLI selectors in a
manifest/config, copy credentials/local paths into portable files, or create a second artifact
recovery record. Existing pre-G5-05 update history without an exact artifact carrier is visibly
non-reversible for artifacts and refuses with state remediation; undo never guesses or silently
restores only live state.

Manifest history is required when update changed requested ref/pin intent. Lock history is required
whenever update changed the selected resolution. A normal moving update commonly has only a lock
carrier; `--ref ... --pin` may have both. No-op artifact rows manufacture no carrier.

### Exact retained preimages

An operation image proves semantic and byte identity but does not contain losslessly authored TOML
bytes or filesystem mode. G5-05 therefore does not attempt to reconstruct a manifest from its
normalized snapshot. A new private `retained-preimage@1` codec has one canonical UTF-8 JSON
encoding with exact keys and field order:

- `kind: "skillsmith.retained-artifact-preimage"` and `version: 1`;
- the exact forward operation ID, source role (`manifest` or `lock`), and absolute selected path;
- `before.mode` in the closed integer range `0..0o7777` and canonical padded-base64 `before.bytes`;
- `after.digest`, in the role's existing `manifest-bytes` or `lock-canonical` domain, and
  `after.mode` in the same closed range; and
- one trailing LF and no unknown keys, alternate base64, duplicate keys, trailing data, non-UTF-8,
  symlink, non-regular file, or over-limit payload.

Decode must re-encode byte-identically, parse/normalize manifest payloads, decode lock payloads,
and prove the embedded role/path/operation against the journal before returning bytes. The retained
row stores `repositoryRevision.kind: resource` with the resource-domain digest of the complete
canonical envelope, while `contentHash` is the role-specific digest of the decoded preimage
payload. `status/read.ts` and bounded-history cleanup use this same codec and verify both digest
domains; neither treats the wrapper itself as a manifest or lock. Cleanup additionally rechecks
the owner-private `0700` directory, `0600` regular envelope, link count, identity stability, and
last-reference rule before deletion.

Before each changing artifact operation, while the existing artifact-group, member, and ledger
locks are held, one update-history binding performs every adjacent journal phase:

1. append the strict pair-null logical journal in `prepared`, with the approved operation's one
   conditional retention resource declared in intent and `actual.retained` still empty;
2. create or authenticate the deterministic owner-private envelope, fsync its `0600` file and
   `0700` parent chain, then advance `prepared -> staged` while adding exactly one retained row;
3. advance `staged -> backed-up` with the identical retained row;
4. invoke the existing artifact-pair coordinator for the approved forward action;
5. observe its authoritative after-image, then advance `backed-up -> live -> committed` with the
   retained row unchanged; and
6. retain the envelope until the complete update occurrence leaves the undo window and restartable
   history cleanup removes its final reference.

The only transaction-identity exception is the one `prepared -> staged` enrichment above. It is
accepted only for a forward, pair-null `write-manifest`/`write-lock` journal whose intent declares
one matching conditional resource, whose previous retained vector is empty, and whose staged
vector is exactly one codec-authenticated backup with the matching role, operation, deterministic
path, and digests. Every other intent/context/disposition/before fact remains byte-identical;
`staged -> backed-up -> live -> committed`, all placement journals, and rollback children retain
the existing exact-identity rule. Omission, a second row, wrong phase/role/path/resource/digest, or
enrichment after `staged` is invalid.

This envelope is retained restoration material, not a recovery record. A crash in `prepared`
derives its one possible path from transaction ID and role: absent material is recreated only when
the locked physical artifact still exactly matches intent-before; present material must decode and
match that same bytes/mode observation before the staged row is published. A crash after envelope
fsync authenticates and adopts the deterministic copy. `staged` authenticates it before advancing;
`backed-up` reconciles the existing artifact-coordinator record and physical before/after image;
`live` verifies after and commits. No forward mutation occurs before `backed-up`. Abort and bounded
cleanup also discover a prepared-phase orphan by that deterministic path. Conflicting bytes, type,
identity, receipt, mode, ownership, permission, missing backup, or unmatched recovery state refuses
without guessing.

The private backup may contain losslessly authored portable content, so it stays under the existing
owner-private data boundary, is never emitted in normal human/JSON output, and is covered by the
existing secret/redaction and history-cleanup rules. The approved public operation continues to
carry only hashes, normalized values, and its already-authorized machine-bound artifact location.

### Transition-specific identity and one history occurrence

`updateGroupIdV1` currently hashes the resulting source but not the prior artifact state, so
A->B, B->C, C->B can reuse the B group and operation identities. G5-05 changes only update's group
identity input: the existing `target` fact becomes a versioned digest of the exact manifest and lock
before/after identities. It contains no raw bytes or path. Dry-run and execution remain identical,
while A->B and C->B no longer collide.

Group ID is still not treated as a globally unique historical occurrence. Correlation starts from
the exact selected placement source transaction, then walks commit order to the nearest unconsumed
forward artifact carriers with the same transition-specific group, exact role/path/image chain,
and matching update command/workflow. A later exact repeat selects its later carrier; rollback
children consume only their exact parent transaction. Missing, duplicated, crossed, or superseded
occurrences refuse. Tests include A->B->C->B, an exact repeated transition, different prior
manifest trivia, two tools, intervening history, and sibling/custom pairs.

### Observation and lineage closure

Undo continues to select placement/history pairs through status. For an update source group it
additionally correlates sibling committed artifact carriers by exact source transaction,
transition-specific group ID, commit order, and artifact image chain, and validates:

- the selected live journals are committed forward updates or their exact rollback children;
- every artifact carrier has one unambiguous selected path, exact before/after image, and readable
  exact retained preimage with the original mode;
- its current physical artifact equals the expected after-image, or already equals the exact prior
  image after a committed rollback child;
- no newer committed or pending artifact operation supersedes that path/group lineage;
- a custom manifest/lock pair comes only from the recorded carrier, never sibling derivation;
- all selected pair journals and artifact carriers agree on one historical occurrence, source
  group, command/workflow, and project/scope identity; and
- malformed, missing, future, ambiguous, stale, partially observed, or permission-denied state
  refuses before approval or writes.

One selected update history group may contain multiple tool pairs but only one artifact transition.
Tool filtering may select a subset of pairs; artifact restoration is then explicit shared group
work and any remaining updated pair is reported as ordinary declared/live drift. An unfiltered
`undo <skill>` restores all selectable pairs and the artifact pair together.

For each artifact path, a multi-group selection must form one contiguous suffix of unconsumed
forward transitions. Planning orders that suffix newest-first. Selecting an older transition while
omitting a newer transition on the same path refuses with remediation to undo the newer group or
select the complete suffix. Distinct recorded custom pairs never collapse into sibling derivation;
if one invocation selects incompatible pair authorities that cannot share the signed lock topology,
it refuses before approval and names the conflicting recorded paths rather than partially mutating.

### Pure inverse plan

The immutable undo planner creates one fresh deterministic undo-occurrence group from a versioned
digest of the exact ordered forward placement and artifact transaction/operation IDs. It swaps the
recorded forward artifact before/after images and binds a private exact-retained action to the
validated envelope. It does not parse current portable intent as restoration material, allocate a
new source candidate, or invoke the update planner.

- every selected live operation is remapped to that fresh group, a pair ID recomputed from the
  fresh group plus the unchanged live resource/tool, and an operation ID recomputed from the full
  fresh identity; source group/pair/operation IDs survive only in existing parent/source lineage;
- inverse artifact operations use the same fresh group, remain pair-null, receive new semantic
  operation/transaction IDs, and point internally to their exact forward parent operation IDs;
- operations remain in the existing undo operation vocabulary (`write-manifest`, `write-lock`);
- artifact operations remain group-level with `pairId`, skill, source, tool, and scope all null;
- `group.operations` exactly partitions into the canonical group-level artifact prefix plus the
  concatenated live-only `pair.operations`; omission, duplication, reordering, or pair-binding is
  invalid;
- the public pair retains its live source/active/parent lineage; artifact parent linkage remains in
  the private logical journal and exact operation images;
- an already-restored artifact transition contributes no operation;
- a group with all live pairs and artifacts already reversed remains `already-reversed` with zero
  mutation; and
- dry-run and execution expose byte-identical operations, dependencies, checks, selected group IDs,
  and artifact locations.

No field or enum is added to `undo@1`. Its validator admits the already-existing `write-manifest`
and `write-lock` operation vocabulary for this group-level partition. Pair outcomes reduce only
their live operations. Group outcome/failure reduces every group operation in deterministic result
order, so an artifact failure is never hidden behind a pair `not-run` result. Existing effect
projection remains schema-frozen; artifact truth is visible in the operation/result vectors. If
implementation cannot stay inside this shape, work stops for an explicit contract amendment before
product code continues.

### Schema-preserving artifact rollback lineage

Journal v1 already admits pair-null manifest/lock operations, but its fresh-rollback resolver and
logical-transaction helpers currently require a placement inverse with a legacy pair shadow. G5-05
adds an explicit artifact branch without changing serialized fields:

- a forward `write-manifest` or `write-lock` parent is eligible only when committed, pair-null,
  path-exact, and backed by the declared digest-authenticated preimage envelope;
- a rollback child keeps the parent's intent images and retained facts, names a fresh transaction
  and operation, names the exact parent operation in context, and advances actual state from the
  parent's after-image back to its before-image;
- no legacy placement shadow is required or written for an artifact child;
- a placement rollback child additionally carries the freshly recomputed group and pair IDs; its
  retained resource IDs remain the exact parent's retained authority, while ledger validation
  proves the child pair from child group plus the unchanged live resource/tool and resolves the
  parent from `context.parentOperationId`;
- one parent has at most one exact child, and resume finds the child by transaction lineage rather
  than operation ID alone; and
- wrong role/path/image, missing backup, duplicate child, future shape, stale phase, or mismatched
  command/workflow makes the ledger invalid before mutation.

Prepared through committed phases, pending resume/abort, duplicate and hostile parents, and child
cleanup are covered at the logical-transaction, ledger-codec, and history layers.

### Atomic bounded-history unit

History retention treats one update occurrence as an indivisible dependency unit: its forward
artifact carriers, every placement journal correlated to the occurrence, every rollback child, and
every retained preimage. If any member is newest for a placement/artifact anchor, is a pending
parent, has live retention, or is otherwise protected, the complete unit is protected and effective
capacity expands. When excluded, cleanup preflights retained resources and removes the complete
dependency unit through the existing restartable victim protocol. It never evicts an artifact
carrier while leaving its update placement selectable.

Occurrence units derive from transaction/commit-order and exact image-chain facts, not group ID
alone, so a later identical transition does not retain or delete the wrong earlier unit. Coverage
includes more than 256 history entries, two tools, custom pairs, pending children, cleanup restart,
an exact repeated transition, and safe backup deletion only after the final reference leaves the
window.

## Execution, crash, and rerun contract

Approved update reversal uses one scheduler and the two signed physical authorities:

1. reacquire the canonical ledger lock and reobserve the exact update group, artifact carriers,
   selected live/store state, and expected revisions;
2. recover any same-operation artifact or placement record before new work;
3. publish rollback logical authority for the exact artifact parent before artifact mutation;
4. restore the exact selected artifact preimages through a private exact-retained pair-coordinator
   action with the expected-current role digest/mode and exact target bytes/mode from the envelope;
   when both changed, restore manifest then lock so the final lock is validated against the already
   restored manifest;
5. reverse each selected committed placement through the existing committed placement-reversal
   path, retaining pair independence and prior-store validation;
6. append committed rollback children without editing/removing forward history; and
7. clean private recovery state only after every corresponding terminal image is durable.

Artifact restoration precedes live rollback. This guarantees there is no state in which every live
pair appears terminally reversed while the artifact restoration has never become authoritative.
Each durable artifact sub-boundary has a pending rollback child, so a failure between lock and
manifest restoration is truthful recoverable state, not an unjournaled inconsistency. If a later
artifact or pair fails, the failure remains nonzero, successful reversals remain committed, and a
fresh rerun skips exact committed children while converging only remaining work.

The private exact-retained action is internal to core and is not added to `HumanManifestAction`,
`GeneratedLockAction`, the artifact barrel, or public types. It accepts only a validated retained
envelope plus the exact inverse operation. The pair coordinator reobserves the current regular file,
requires its role digest and mode to equal the envelope's authenticated forward-after receipt,
requires target bytes to project exactly to the inverse after-image, and passes those bytes/mode to
the existing desired-role, staging, recovery-record, install, verify, and cleanup machinery. The
existing recovery record already carries after digest/mode, so its serialized format does not
change. Exact lock restore must decode canonically and correlate with the restored manifest.

Cancellation before a durable boundary performs no write. Cancellation after a boundary leaves one
strict pending record and stops all later operations/groups. Permission and external-writer errors
retain their exact exit classes. Fail-fast marks later groups `skipped-after-failure`; explicit
continuation runs independent later groups but never hides the original failure. Invocation-level
syntax, ambiguity, state, artifact-lineage, approval, and no-prompt failures abort before mutation
under both policies.

## Approved implementation compatibility amendment

Minimal implementation and the complete serialized dependency rerun exposed one shared-authority
omission in the accepted Ready manifest. Manifest operation images now use the role-specific
`manifest-bytes` digest required by retained-preimage authority, while acquisition snapshot
revisions intentionally remain in the generic `resource` domain. Reusing either digest for both
purposes makes one side untruthful: retained history loses its role-domain proof, or every
present-manifest install/uninstall rerun falsely reports a stale transition.

The private acquisition transition envelope therefore carries the already-observed resource-domain
manifest revision alongside its role-domain operation image. Planning validates the former against
the snapshot and the latter against the operation/action chain. This adds no serialized field,
public schema, command, option, output, recovery record, or portable artifact content.

The same implementation pass also requires the existing application/placement execution seam to
pass the signed artifact coordinator into undo, carry the retained placement override through swap,
and reread the ledger after the exact private rollback-artifact prerequisite commits. Those are
integration authorities, not a second scheduler, artifact writer, or reversal engine.

1. Add the six primary selectors and hermetic fixture boundary; record honest red/characterization
   results and the eight serialized dependency baselines.

   projection, the private retained-preimage codec, dual-domain status/cleanup validation, and the
   narrow scheduler retention shape around approved artifact operations.
3. Bind `prepared -> staged -> backed-up -> live -> committed` lineage, including the sole staged
   retention-enrichment exception, to existing artifact-coordinator execution/recovery under the
   ledger lock.
4. Add the internal exact-retained coordinator action and generalize artifact rollback
   parent/child lineage and whole-occurrence bounded-history units without changing journal v1 or
   the public artifact actions.
5. Correlate update artifact lineage from exact placement source transactions during undo
   observation and reject missing/stale/ambiguous/non-contiguous history before approval.
6. Derive one fresh undo-occurrence group, remap all live pair/operation identities, build pair-null
   inverse artifact operations, and retain exact group-level/pair-level `undo@1` reductions without
   changing its serialized fields or enums.
7. Execute retained-preimage artifact operations through external scheduler bindings and committed
   placement reversal through the signed swap authority.
8. Close application approval/mutation accounting, output parity, custom-pair, partial-failure,
   cancellation, history pressure, and crash/rerun matrices.
9. Refactor only after all primary and required-now selectors are green.

## Validation policy

Inner loops run the changed core suites, one primary selector at a time, and `bun run test:smoke`.
Because ledger, recovery, artifact barriers, cancellation, and crash behavior are in scope, every
recovery-affecting iteration also runs `bun run test:smoke:p2-ts04:recovery`. Stateful CLI fixture
selectors run serially; pure unit/static suites may run concurrently.

Targeted green requires all six primary selectors as separate processes. Impacted green requires
all 14 frozen commands, also as separate serialized processes, with exact receipts and no required
skip. Typecheck, boundary lint, catalog/package/plan structure, and diff checks are mandatory. A
full serialized terminal `bun run check -- --timeout 60000 --max-concurrency 1` runs only after
fresh independent GO and all proportional gates pass.

## Non-goals and stop conditions

- no new command, option, alias, output schema version, journal schema field, or recovery format;
- no normalized reconstruction where a retained exact artifact preimage is required;
- no undo of arbitrary current files or pre-lineage update history by inference;
- no global “latest operation” lookup or cross-project crawl;
- no change to saved-plan authorization, GC, distribution, help/completion, or Phase 6;
- no second scheduler, approval loop, artifact writer, or placement reversal engine;
- no parallel execution of stateful public-process fixtures; and
- no public-contract widening discovered during implementation without an explicit amendment,
  structural validation, fresh adversarial review, and user authorization.

- whether artifact logical history and artifact recovery can diverge at any crash boundary;

- whether bounded history retains and evicts one exact update occurrence atomically;
- whether transition-specific identity plus source-transaction/commit-order correlation separates
  A->B->C->B and exact repeated occurrences;

- whether artifact-first reversal and fresh rerun converge after every pair failure/cancellation;

- whether the six primary selectors plus eight dependency replays completely prove P1-04,
