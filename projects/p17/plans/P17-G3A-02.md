# P17-G3A-02 implementation plan

## Outcome and exact scope

P17-G3A-02 completes the three existing non-mutating inventory commands: `agents`, `list`, and
`commands`. It introduces one immutable inventory product for installed skills and slash commands,
one shared collision authority, deterministic registry-derived capability presentation, bounded
compact human output, complete versioned JSON, and the planned filters. It performs local reads
only and never writes, locks, prompts, verifies, accesses the network, or executes a lifecycle
operation.

The primary entities are exactly 24: the three command coverage entities; `EWP-P3A-T01`,
`EWP-P3A-T04`, and `EWP-P3A-T05`; the 14 agents/commands/list command selectors;
`EWP-P3A-TS01`, `EWP-P3A-TS03`; and recommendations `P1-01`, `P1-03`. Required-now and impacted
validations are the same exact 16 selectors, and downstream coverage is empty. The sole direct
dependency is signed G3A-01.

Strict exclusions are:

- G3A-01 retains desired/locked/ledger/live reconciliation, drift, journals, check exits, its
  signed status-local project/user shadow projection, and recovery remediation. List reads only
  the local ledger facts required to describe a live inventory row; it does not read a manifest or
  lock, create a status product, or retroactively change the `status@1` contract.
- G3B and later groups retain operation planning, mutation, lifecycle placement behavior, locks,
  transactions, ledger writes/migration, recovery, enable/disable execution, and future commands.
- No generic module gains a known-tool switch or a second capability matrix. Adapter roots and the
  signed registry remain the tool-specific authorities.
- No network, generic subprocess, verification, prompt, clock, ID, writable-directory, lock, or
  filesystem-write port enters the inventory boundary. Agents may reuse only the existing narrowly
  scoped local `runVersion` detection subprocess; generic execution remains forbidden.

## Shared selection and validation boundary

All option relationships are validated before project/config resolution, ledger reads, detection,
plugin discovery, or root scanning. Unknown tools and enum values are usage exit 2. A known tool
whose registered `inventory-skills` or `inventory-commands` operation is unavailable is capability
exit 4. A syntactically known scope that the selected command/tool capability does not support is
also capability exit 4; an unknown scope token remains usage exit 2. For list and commands,
malformed or unsupported local configuration/ledger state is state exit 3, permission and
filesystem access retain exit 6, and other inventory failure retains exit 1. Agents normalizes
every selected adapter detection failure to exit 1 while retaining its redacted diagnostic code;
it does not reinterpret a detection error as permission exit 6.
Cancellation wins with 130. A valid filter-to-zero result is exit 0 and is explicitly represented
as `filter-noop` in both application products and current wire DTOs; these commands never use drift
exit 7.

Only selected tools and roots are touched. Selected roots are observed independently, but any
selected detection/root/plugin/ledger failure prevents partial human or JSON output and is never
converted to absence. Cancellation stops outstanding work. When multiple actual list/commands
errors have already accumulated, the existing shared exit selector chooses the outcome; no command
adds another precedence table. Agents uses registry order only to select a deterministic diagnostic
after normalizing non-cancellation detection failures to exit 1.

The current numeric selector is extracted unchanged from `application/lifecycle-services.ts` into
`application/exit-policy.ts`; lifecycle and read services import that one authority. Its existing
order remains cancellation, permission, source, capability, state, usage, failure, success/drift.
This is a mechanical ownership move, not a new command-local error rule.

Selected tools are ordered by `toolRegistry.adapters`, regardless of CLI/config spelling order.
Selection precedence for list and commands is explicit repeatable CLI tools, then the effective
configuration tools, then every registered tool. Agents always defaults to every registered tool;
an explicit repeated selection is deduplicated and restored to registry order.

List accepts one scope through `--scope` or the four consistency-checked sugar flags. An unscoped
list inside a selected project reads system, user, project, and managed in canonical `SCOPES`
order. Outside a selected project it omits project and reads system, user, and managed. An exact
explicit project scope outside Git uses the shared canonical effective cwd as the non-Git project
root and identity, matching install and signed status behavior. Commands applies the same rule to
its user/project universe: unscoped is user plus project when a project exists and user only when
one does not; exact project scope outside Git uses the canonical effective-cwd fallback. A nested
manifest or explicit artifact never relocates either live root.

List filters are:

```text
list [glob...]
  [-t, --tool <name>]...
  [-s, --scope <system|user|project|managed> | --system | --user | --project | --managed]
  [--mode <dev|pinned|unmanaged>]
  [--source <glob>] [--revision <glob>] [--description <glob>]
  [--verified | --unverified]
  [--enabled | --disabled | --unconfigured]
  [--duplicates] [-l, --long] [--json]
```

Multiple positional name globs are OR. Repeated tool selectors are OR. Every other selector is
singular, and different filter dimensions are AND. Source, revision, and description globs are
case-sensitive and match only nonnull values. Empty/NUL or non-compilable patterns are usage exit 2
before I/O. `--verified` means exactly `passed`; `--unverified` means warned, skipped, or
unrecorded. The enabled trio and verified pair are mutually exclusive. Duplicate analysis happens
inside the selected tool/scope product before attribute filters, so a visible shadow can still name
its filtered winner without widening the displayed rows.

Commands retains its existing name globs, repeatable tools, singular user/project scope, enabled
trio, `--long`, and `--json`. Name globs are OR and dimensions are AND. List and commands use only
bounded-default selection; an empty positional list never means an implicit mutation-style all.

Agents retains repeatable tools, `--detected-only`, and `--format <markdown|json>`, and adds
`--json` plus `--capabilities`. `--json` is an alias for format JSON; combining it with explicit
markdown is usage exit 2, while combining it with explicit JSON is idempotent. Capabilities never
change detection. Both `--detected-only` and `--capabilities` are human presentation controls;
versioned JSON always retains every selected detection and capability fact.

## Immutable inventory products

The new inventory boundary lives below the application service and above a new internal
all-observations seam in the existing scanner modules. Public `listSkills()` and `listCommands()`
retain their historical realpath-deduplicated behavior and signatures. Internal
`observeSkillPlacements()` and `observeCommandPlacements()` return every logical observation before
legacy dedupe/filtering; they are not exported from the package root. New inventory readers consume
that seam, return deeply frozen arrays and records, and never mutate raw entries, filters, ledger
projections, registry data, or fixtures.

```ts
type InventoryMode = 'dev' | 'pinned' | 'unmanaged';
type InventoryPlacement = 'symlink' | 'copy' | 'unknown';
type InventoryVerification = 'passed' | 'warned' | 'skipped' | 'unrecorded';

type InventoryVisibility =
  | Readonly<{ state: 'unique'; winner: null; members: readonly InventoryMember[] }>
  | Readonly<{ state: 'winner'; winner: string; members: readonly InventoryMember[] }>
  | Readonly<{ state: 'shadowed'; winner: string; members: readonly InventoryMember[] }>
  | Readonly<{ state: 'duplicate'; winner: null; members: readonly InventoryMember[] }>;

interface SkillInventoryEntry {
  readonly name: string;
  readonly tool: SupportedTool;
  readonly scope: Scope;
  readonly path: string;
  readonly realpath: string;
  readonly root: string;
  readonly frontmatter: Frontmatter | null;
  readonly origin: Origin;
  readonly enabled: EnabledState;
  readonly mode: InventoryMode;
  readonly placement: InventoryPlacement;
  readonly source: string | null;
  readonly revision: string | null;
  readonly store: string | null;

  readonly description: string | null;
  readonly visibility: InventoryVisibility;
}

interface InventorySelection {
  readonly source: 'bounded-default';
  readonly tools: readonly SupportedTool[];
  readonly scopes: readonly Scope[];
  readonly filters: Readonly<Record<string, string | boolean | readonly string[] | null>>;
  readonly outcome: 'selected' | 'filter-noop';
}

interface SkillInventory {
  readonly selection: InventorySelection;
```

Canonical comparison is unsigned UTF-16 code-unit comparison, never locale comparison. Skill rows
sort by registry tool order, canonical `SCOPES` order, name, then path. Command rows use registry
tool order, user/project order, name, then path. Detection records sort by path, version, then
install method. Origin objects and frontmatter values are copied before freezing.

## Local ledger enrichment and known mode

List reads the version-discriminating ledger repository exactly once from
`ledgerPathOf(resolveDataDir(...))` through a focused read-only port. Version 1 is normalized in
memory; no migration is written. Transactions, history, retained resources, manifest, lock, and
journal semantics are not projected. The reader indexes user and the selected exact project only,
then correlates a record by project identity/null, tool, name, and exact logical placement path.
Name alone never transfers metadata between roots.

The live placement representation comes from one bounded node observation per normalized row:
directory is `copy`, symlink is `symlink`, and an observation race or unsupported node is `unknown`.
Mode is intentionally ledger-owned rather than inferred from symlink shape: an exact correlated
pair supplies its recorded `dev` or `pinned` mode, and every row without an exact pair is
`unmanaged`. This keeps list out of status live classification and prevents an arbitrary unmanaged
symlink from being described as Skillsmith-managed dev state.

Long metadata is mode-aware and filters consume these exact same projected values. A current dev
pair supplies source from `dev.remote`, otherwise its canonical resolved/source path; revision and
store are null and verification is `unrecorded`, even if the ledger retains an older origin or
pinned record. A current pinned pair supplies source from `origin.source`, otherwise a retained
current dev `remote`, otherwise its canonical resolved/source path. Its revision is
`origin.refResolved`, otherwise pinned `gitSha`, otherwise pinned `rev`, plus its current store and
verification. This source fallback covers a valid promote of a dev-only pair without exposing a dev
revision as pinned. An unmanaged row receives no ledger source, revision, store, or verification
facts. Description is the parsed frontmatter description or null. All displayed and encoded values
pass through recursive sensitive value redaction followed by strict codec reparse.

Malformed or unreadable ledger state fails list even in compact mode because pinned versus
unmanaged is part of the compact contract. An absent ledger is valid. Foreign projects,
unselected scopes/tools, and path-mismatched pairs are not read into a row. Plugin and policy rows
without an exact pair are unmanaged; enabled state remains an observed fact and never authorizes a
settings edit.

## Duplicate and shadow authority

Each inventory bundle may first project a pure adapter-owned runtime identity name; the conservative
fallback is the raw scanned name. For Claude plugin observations, the namespace is the nonempty
substring of `origin.pluginId` before its final `@`; a malformed ID is state exit 3. The exposed
human/JSON name and collision key are exactly `<plugin-name>:<raw-name>`, while provenance retains
the complete `plugin-name@marketplace` ID. Thus qualified plugin and standalone names do not collide
without a generic tool branch. Raw observation identity is `(tool, scope, runtime name, canonical
non-dereferenced logical path)`. Observations at that same logical placement collapse only when all
rendered/encoded raw facts agree, including origin, enabled, realpath, and recursively normalized
frontmatter/description. Any disagreement is inventory state exit 3, never enumeration-order
selection. Two names or two logical paths that resolve to one physical target remain distinct
placements. Realpath is diagnostic metadata, not an alias key. Equivalent observations are ordered
by a canonical origin tuple including origin kind, plugin ID/version/scope, then realpath, so plugin
enumeration cannot select a retained fact. Collision identity is exactly
`(tool, runtime skill-name)`; the same name in different tools is never a duplicate. Every
multi-row group preserves every member scope and logical path.

Identity and precedence are adapter-owned through optional pure `inventoryIdentity` and
`resolveInventoryCollision` members on a registered inventory bundle. Generic inventory passes only
frozen surface, name, scope, origin, root ordinal, path, and realpath candidates, validates the
projected name and that any returned winner is a member, and never switches on tool ID. The registry
validates and freezes these functions when present; third-party/fixture adapters without them remain
source-compatible, retain raw names, and conservatively return an ambiguous duplicate.

The built-in skill resolvers freeze the repository's researched tool behavior:

- Claude Code: managed/enterprise beats user/personal, which beats project. Plugin skills retain
  their namespace and therefore do not collide with standalone names. Unsupported synthetic scope
  combinations are ambiguous.
- Codex: every multi-placement identity is ambiguous. Repo, user, admin/system, current, and
  deprecated roots all contribute; current or earlier enumeration never guesses a winner.
- Kilo Code: a unique project-native `.kilo` candidate beats user-native `.kilo` candidates only.
  Any group containing a compatibility root, or multiple candidates at the highest native scope,
  is ambiguous because the shared compatibility pool has no documented tiebreaker.
- OpenCode: every collision is ambiguous because names are required to be unique and no tiebreaker
  is documented.

A unique authoritative winner is marked `winner`, every other member is `shadowed`, and all members
name the same ordered member list. An unresolved top rank marks every member `duplicate` with null
winner. These inventory semantics intentionally do not rewrite G3A-01's signed `status@1`
compatibility projection; a future status contract change must be mapped and versioned separately.
`--duplicates` retains both resolved shadow groups and ambiguous groups and the human diagnostic
names every scope/path and the winner or `ambiguous`.

The collision implementation is map-indexed and `O(n log n)` including final sort. It never performs
an all-pairs scan and never calls an adapter, ledger reader, project resolver, or filesystem port per
collision comparison.

## Agents product and capability presentation

Agents returns an immutable registry-ordered array of selected tools and sorted installation
records. Each human section labels `not detected`, `one installation`, or `multiple installations
(N)` explicitly. `--detected-only` removes only not-detected sections. Paths and versions are
escaped as table cells. Detection failure is not converted to absence. A new strict
selected-detection reader is used by the agents application service while public `detectAll()`
retains its historical best-effort behavior. After concurrent bounded detection, cancellation
wins; otherwise every selected adapter failure normalizes to exit 1, registry order selects the
diagnostic, and no partial report is fabricated.

With `--capabilities`, human output appends every selected tool's 16 registered operations with
supported state, exact scopes, and remediation. The source is exactly
`toCapabilitySnapshotV1Dto({ adapters: selectedAdapters })`; renderer code cannot restate the
Claude/Codex full-lifecycle or Kilo/OpenCode read-only matrix. The default unfiltered projection is
four tools and 64 operation facts.

Agents JSON advances from `agents@1` to `agents@2`. It contains registry-ordered detection rows and
the complete exact `skillsmith.capabilities@1` projection for the selected adapters on every JSON
request. `--json` and `--format json` are byte-identical for the same request. Detected-only and
capabilities remain human-only presentation controls, so machine output is always complete.

## List and commands presentation

Compact list begins with the unambiguous `Installed skills` label and contains exactly tool, scope,
known mode, name, and enabled state. Enabled `on` is the default and renders blank; `off` and
`unset` render `disabled` and `unconfigured`. Tool boundaries are visually separated while every
row retains the five-column contract. Long list is complete and adds placement, logical and real
paths, root, origin/provenance, source, revision, store, verification, description, and visibility.
It never adds desired, lock, drift, journal, recovery, or convergence facts.

Commands is always labeled `Installed slash commands`, never as the Skillsmith command index.
Compact rows contain tool, scope, name, and non-default enabled state. Long rows add logical and
real paths, root, plugin/standalone provenance, version/frontmatter, and description. Empty states
are exactly `No skills installed.` and `No slash commands installed.`. Active filters with no rows
add one explanation that the selected inventory was reduced to zero.

Default compact human list and commands output is capped at the first 100 canonically sorted data
rows. If truncated, the exact final line is
`... N more entries; narrow with filters or use --long or --json.` with locale-independent decimal
digits. Compact output for the frozen fleet fixtures must remain below 64 KiB. Explicit `--long`
and every JSON request are complete and untruncated.

The in-memory 10,000-skill and 4,096-command fixture runs must each sort and render under five
seconds on the test lane. Read-port instrumentation is bounded by `8N + 128`, project/config/ledger
and plugin discovery occur at most once per request, and no status or adapter lookup occurs per
entry.

## Versioned JSON compatibility

Historical `agents@1`, `commands@1`, and `list@2` codecs remain registered and byte-stable. Current
command mappings advance to `agents@2`, `commands@2`, and `list@3`. Commands@2 owns canonical order,
selection/filter-noop facts, summary, and complete rows; changing the semantic order of commands@1
would violate the signed conservative codec policy. No migration is declared: old agents,
commands, and list products do not contain facts required to reconstruct the new versions.

The three new codecs reject recursive unknown fields and future versions, use two-space canonical
JSON plus the descriptor's fixed terminal-LF rule, and accept only codec-owned DTO mappers.
Commands@2 and list@3 contain selection, total summary, and complete ordered rows; list@3 also
contains collision membership/visibility. Human
`--long` never changes JSON: plain `--json` and `--long --json` are byte-identical. Internal root
ordinals, ledger records, mutable maps, ports, errors, and raw sensitive values are
unrepresentable.

The new `@skillsmith/core/contracts/v3` package export is explicit. P1-TS10 current-wire goldens and
public DTO fixtures advance atomically; P2-TS08 retains the historical codecs and verifies the new
codec inventory without changing the six persisted artifact identities.
