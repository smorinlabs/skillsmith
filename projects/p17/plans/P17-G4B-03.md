## Terminal lock policy

The selected artifact pair remains the whole portable-lock authority. The terminal policy is:

- a current canonical lock supplies immutable pins without source resolution or a lock operation;
- default mode may resolve a selected missing, incomplete, source-mismatched, ref-mismatched, or
  path-mismatched pin, but it must either construct one safe complete replacement lock or refuse;
- a safe replacement is a visible `write-lock` operation with exact before/after canonical hashes,
  and live operations depend on that exact lock operation;
- resolution never changes the manifest declaration or requested ref, and planning never writes;
- a bounded selection does not fetch or drop unrelated declarations or retained undeclared pins;
  if a whole-lock rewrite would require either action, it refuses instead of widening authority;
- `--locked` is whole-pair strict: every invocation, including a bounded or filter-to-zero
  selection, requires one current complete canonical lock entry for every manifest declaration,
  no extra entry, and the current manifest relationship; it never resolves or produces a
  `write-lock`; and
- saved plans retain their recorded `options.locked`; saved apply has no option that can weaken or
  replace that policy.

Default lock resolution therefore has only three truthful results: current/no lock operation,
visible complete replacement, or refusal. It never silently mutates or silently claims a stale
selected pin is current.

## Commit and recovery boundary

Apply continues to use the existing signed hierarchy: stable apply-ledger bootstrap lock, artifact
group lock, exact manifest/lock compatibility members, then placement ledger lock. Under those
locks it revalidates the approved snapshot, executes the canonical dependency graph, and advances
durability revisions only after a commit receipt.

Manifest migration and lock replacement each commit through the existing artifact-pair recovery
record and authenticated lease. Ledger and live placement each commit through the existing
placement journal/writer and swap recovery state. The lock operation is an explicit dependency of
every live operation that consumes newly resolved pins, so a live/ledger mutation cannot start
before the reviewed lock after-image is durable. Failures before a durable boundary retain the
before image; failures after a durable boundary report or recover the exact after image. A rerun
must recover retained residue and converge or refuse if current bytes cannot be proved. It must
never invent a third mixed state.

`EWP-P4B-TS05` exercises apply through each existing manifest, lock, ledger, and live commit seam.
It may use the existing barrier hooks and a bounded child process to model hard death, but it may
not add a production-only crash hook. Every case proves the visible approved operation IDs, the
legal durable image after interruption, same-operation recovery, idempotent rerun, empty recovery
inventory, and absence of stage/backup/journal/secret residue after convergence.
