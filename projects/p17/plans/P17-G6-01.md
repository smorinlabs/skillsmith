# P17-G6-01 plan: single-lineage native and package-manager distributions

## State and coherent boundary

P17-G6-01 is the dependency-ready distribution group after signed G6-02B and G6-03. It builds
four native artifacts once, derives direct-download, Homebrew, npm, and Bun packages from those
same bytes, produces checksums, and proves clean installation from local release-candidate
artifacts. It does not publish anything or advance the exact-release-SHA gate owned by G6-04.

Primary ownership is exactly four entities:

- `EWP-P6-T01` — native release assets and checksums;
- `EWP-P6-T02` — Homebrew and npm/Bun distribution;
- `EWP-P6-TS01` — clean-machine install smoke per distribution; and
- `P1-12` — distribution.

The only required-now executable validation is `EWP-P6-TS01`. `EWP-WF01` remains downstream,
release-tier, planned, and primarily owned by G6-04. G6-01 may establish the package and
clean-install portion of that future workflow, but it may not create, target, execute, or sign off
the holistic workflow early.

## One build, multiple channels

Add one release model and one thin executable builder. The model owns the exact four-target matrix,
artifact names, package names, archive layout, completion paths, manifest schema, checksum order,
and formula rendering. The executable accepts an explicit output root plus `host` or `all` target
selection and refuses an existing nonempty output, invalid version, unsupported target, duplicate
asset name, or path outside its owned staging root.

The public contract is closed and ordered as follows; implementation must not invent any name or
field:

| Order | Target ID | Bun target | `os` | `cpu` | `libc` |
|---:|---|---|---|---|---|
| 1 | `darwin-arm64` | `bun-darwin-arm64` | `darwin` | `arm64` | absent |
| 2 | `darwin-x64` | `bun-darwin-x64` | `darwin` | `x64` | absent |
| 3 | `linux-arm64` | `bun-linux-arm64` | `linux` | `arm64` | `glibc` |
| 4 | `linux-x64` | `bun-linux-x64` | `linux` | `x64` | `glibc` |

For version `<version>`, the four direct archives are
`skillsmith-v<version>-<target>.tar.gz`. The five npm tarballs are
`smorinlabs-skillsmith-<version>.tgz` and
`smorinlabs-skillsmith-<target>-<version>.tgz`. The remaining public files are exactly
`skillsmith.rb`, `release-manifest.json`, and `SHA256SUMS`. The formula's four URLs are exactly
`https://github.com/smorinlabs/skillsmith/releases/download/v<version>/skillsmith-v<version>-<target>.tar.gz`.
All four archives, all five npm tarballs, the formula, manifest, and checksum file are immediate
children of the public release output root; no checksum-covered path is nested.

`release-manifest.json` is canonical UTF-8 JSON with two-space indentation and one trailing LF.
Objects use the field order shown below, targets use the table order above, and completions use
Bash/zsh/Fish order. `sourceRevision` is an explicit 40-character lowercase Git object ID, not an
inference from a tag or dirty working tree. SHA-256 values are 64 lowercase hexadecimal characters,
byte sizes are nonnegative JSON integers, and executable mode is a four-character string:

```json
{
  "schemaVersion": 1,
  "name": "skillsmith",
  "version": "<SemVer>",
  "sourceRevision": "<40-lowercase-hex>",
  "targets": [
    {
      "id": "<target>",
      "bunTarget": "<bun-target>",
      "os": "<os>",
      "cpu": "<cpu>",
      "libc": null,
      "binary": { "sha256": "<sha256>", "bytes": 1, "mode": "0755" },
      "archive": { "path": "<archive-name>", "sha256": "<sha256>", "bytes": 1 },
      "npm": {
        "name": "@smorinlabs/skillsmith-<target>",
        "path": "<npm-tarball-name>",
        "sha256": "<sha256>",
        "bytes": 1
      }
    }
  ],
  "launcher": {
    "name": "@smorinlabs/skillsmith",
    "path": "<launcher-tarball-name>",
    "sha256": "<sha256>",
    "bytes": 1
  },
  "formula": { "path": "skillsmith.rb", "sha256": "<sha256>", "bytes": 1 },
  "completions": [
    { "shell": "bash", "path": "completions/skillsmith.bash", "sha256": "<sha256>", "bytes": 2610 },
    { "shell": "zsh", "path": "completions/_skillsmith", "sha256": "<sha256>", "bytes": 7729 },
    { "shell": "fish", "path": "completions/skillsmith.fish", "sha256": "<sha256>", "bytes": 9200 }
  ]
}
```

The sample target's `libc` value is `null` for Darwin and `"glibc"` for Linux. The shown size
values are type examples; generated values record the actual bytes. `SHA256SUMS` has exactly 11
LF-terminated lines: four archives, the launcher plus four platform npm tarballs, the formula, and
the manifest. Each line is `<64-lowercase-hex><two ASCII spaces><relative POSIX path>`, sorted by
raw path bytes. It neither hashes itself nor includes raw staging binaries or internal directories.

For each selected target, the pipeline is strictly ordered:

1. compile `packages/cli/src/index.ts` once with `bun build --compile --bytecode --env=disable
   --no-compile-autoload-dotenv --no-compile-autoload-bunfig` into an immutable target staging
   directory;
2. run `file`/header validation and, only for the current host target, execute `version`, `help`,
   and all three completion commands;
3. capture Bash, zsh, and Fish from the signed CLI once and require exact equality with direct
   source execution;
4. create one executable-mode-preserving `.tar.gz` containing `skillsmith`, `LICENSE`, and the
   three completion files;
5. place the same unmodified binary bytes in that target's npm payload package;
6. pack the npm payload with `bun pm pack` and never rebuild inside packing; and
7. record byte size and SHA-256 from the actual produced payload.

After all target payloads exist, generate the launcher package, Homebrew formula candidate,
`release-manifest.json`, and raw-path sorted `SHA256SUMS`. Checksums cover every publishable
archive/package/formula payload plus the manifest; the checksum file does not recursively hash
itself. Formula SHA values must equal the corresponding archive entries. No channel may rebuild or
download its own copy of the CLI.

Every raw binary must be strictly smaller than 128 MiB (`134217728` bytes) before any archive or
npm fan-out. The model accepts `134217727`, rejects `134217728`, and rejects `134217729` without
allocating boundary-sized test buffers. Packaging cannot make an oversized compile acceptable.

## Hermetic build environment and leak refusal

The builder starts from an empty environment, not an inherited environment with a denylist. Its
recorded allowlist is only a `PATH` containing pinned Bun and required system `tar`/`file`, isolated
`HOME`, `TMPDIR`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, and `XDG_DATA_HOME`, plus
`LANG=C.UTF-8`, `LC_ALL=C.UTF-8`, `TZ=UTC`, and `NO_COLOR=1`. It builds from a fixed isolated
working/staging directory outside the source tree, drops all credential, registry, proxy, signing,
cloud, and GitHub variables, and never prints the ambient environment.

TS01 injects unique secret and absolute-path canaries into the parent environment and creates
canary dotenv/bunfig/config files. After the build, exact-byte scans must find none of the secret,
isolated-home/path, or absolute repository-path canaries in builder stdout/stderr, raw or extracted
binaries, direct archives, npm tarballs, formula, manifest, or checksums. The complete release
staging directory also passes `gitleaks dir` with the repository configuration and redaction
enabled. Any leak is a hard failure; logs may name the failed canary class but must not echo secret
values.

Two identical Bun 1.3.14 Linux-arm64 compiles produced different SHA-256 values during mapping.
Reproducible native bytes are therefore not claimed. Integrity comes from build-once fan-out:
direct archives, Homebrew, and npm packages all contain the exact binary produced in one lineage,
and G6-04 later binds that lineage to the exact release SHA and provenance.

## npm and Bun package model

Generate five publishable package directories under the ignored release output; do not mutate the
workspace packages into release payloads.

The launcher package:

- declares exact-version `optionalDependencies` on all four native payload packages;
- exposes only `skillsmith` through a tracked POSIX/CommonJS polyglot launcher with these exact
  two bootstrap statements after `#!/bin/sh`:

  ```text
  ':' //; runtime="$(command -v bun 2>/dev/null || command -v node 2>/dev/null)" || { echo "skillsmith requires Bun or Node.js" >&2; exit 1; }
  ':' //; exec "$runtime" "$0" "$@"
  ```

  A POSIX shell therefore re-executes the same file with Bun first or Node second, while Bun/Node
  parse the two statements as inert string literals followed by comments;
- selects exactly one package from `process.platform` and `process.arch`;
- spawns that package's binary with untouched argv, inherited stdin/stdout/stderr, exit status, and
  signal settlement, forwarding a received signal to the child and settling the launcher with the
  same signal;
- emits one actionable error for an unsupported platform or a missing/omitted payload;
- contains the three generated completion files under documented `share/completions` paths; and
- has no install/postinstall script, network fetch, shell mutation, source runtime, or workspace
  dependency.

The exact two-line POSIX/CommonJS bootstrap conflicts with Biome 1.9.4's mandatory semicolon
formatter: formatting inserts a semicolon between the string literal and `//`, changing the frozen
bytes. `biome.json` therefore has one G6-01-owned override that disables formatting only for
`packaging/npm/bin/skillsmith.cjs`. Biome linting remains enabled for that file and every other
formatter/linter setting remains unchanged. This is not a generic generated-file exclusion.

Its packed entries are exactly `package/package.json`, `package/README.md`, `package/LICENSE`,
`package/bin/skillsmith.cjs`, `package/share/completions/skillsmith.bash`,
`package/share/completions/_skillsmith`, and `package/share/completions/skillsmith.fish`. The
launcher is mode `0755`; every other launcher-package file is `0644`.

Each native package contains exactly `package.json`, `README.md`, `LICENSE`, and
`bin/skillsmith`. Its `os`, `cpu`, and Linux `libc: glibc` metadata select one platform, its version
equals the launcher and CLI version exactly, and it exposes no public JS API or competing bin.
Packed paths carry the `package/` prefix; `package/bin/skillsmith` is `0755` and the other three
entries are `0644`. Tests inspect all tarball entries and metadata, including the negative
`--omit=optional` path.

Clean-package smoke uses a test-only `Bun.serve` registry bound to `127.0.0.1`. It serves only five
exact package metadata documents and their packed tarballs, records every request, and rejects any
unknown route. npm and Bun install only the launcher name and exact version from that registry;
they must choose the host payload through the real exact-version `optionalDependencies` plus
`os`/`cpu`/`libc` metadata, never through an explicitly side-loaded payload.

Each lane uses empty isolated home, prefix, cache, config, temp, and working roots with no repository
`node_modules` visibility. Registry configuration points only to loopback; HTTP(S) proxy variables
point to a local deny listener, and any denied or non-fixture request fails the test. The installed
tree must contain the launcher and exactly one host payload, with no other platform payload or
source/workspace dependency. The npm-only lane exposes a private PATH with shell, Node, and npm but
no Bun; the Bun-only lane exposes shell and Bun but no Node. Both run `version`, `help`, and all
completion commands and prove argv, stdin/stdout/stderr, numeric exit, and signal propagation.
`--omit=optional`, missing payload, unsupported OS/architecture, and absence of both runtimes fail
with the frozen actionable errors.

Upgrade evidence has two intentionally separate lanes. The real-candidate lane installs the actual
release-please-managed version once and checks that compiled `skillsmith version`, package metadata,
and the manifest all match; it makes no synthetic upgrade claim. The lifecycle lane uses immutable
test-only versions `0.0.0-g6-fixture.1` and `0.0.0-g6-fixture.2`. TS01 embeds the two tiny
deterministic POSIX executable fixture byte strings and their frozen SHA-256 values; each prints its
own version and supports only the commands the lifecycle harness requires. The normal release model
packages those bytes with matching metadata and tests direct, npm, Bun, and Homebrew
install/upgrade/uninstall. These artifacts are explicitly `fixture: true` inputs, never enter the
candidate manifest/checksum/docs, and never edit root, CLI, core, release-please, or changelog
versions.

The two executable byte strings are exactly the following UTF-8/LF templates, substituting only the
shown literal version; there is one final LF and no other substitution:

```sh
#!/bin/sh
if [ "${1-}" = "version" ]; then
  printf '%s\n' '0.0.0-g6-fixture.1'
  exit 0
fi
printf '%s\n' 'G6 lifecycle fixture 0.0.0-g6-fixture.1' >&2
exit 64
```

The `.1` file is 160 bytes with SHA-256
`d2e29c65bd9afe1235f3105cbe297bd84c564a9c0026cc6320f059cd987797a6`. Replacing both `.1`
literals with `.2` produces the 160-byte `.2` file with SHA-256
`70f27666626752210b31be697cd63ff6554a6342936ea2ca435e1c5d53c7c3e9`. Any byte or hash drift
fails before lifecycle packaging.

and reject every unknown or proxy-deny request. They run formula syntax/audit plus install, formula
