# P17-G6-01 plan: single-lineage native and package-manager distributions

## State and coherent boundary

P17-G6-01 is the dependency-ready distribution group after signed G6-02B and G6-03. It builds
four native artifacts once, derives direct-download, Homebrew, npm, and Bun packages from those
same bytes, produces checksums, and proves clean installation from local release-candidate
artifacts. It does not publish anything or advance the exact-release-SHA gate owned by G6-04.

Primary ownership is exactly four entities:

- `EWP-P6-T01` — native release assets and checksums;
- `EWP-P6-T02` — Homebrew and npm/Bun distribution;
- `EWP-P6-TS01` — clean-machine install smoke per distribution; and
- `P1-12` — distribution.

The only required-now executable validation is `EWP-P6-TS01`. `EWP-WF01` remains downstream,
release-tier, planned, and primarily owned by G6-04. G6-01 may establish the package and
clean-install portion of that future workflow, but it may not create, target, execute, or sign off
the holistic workflow early.

- root scripts cross-compile all four declared Bun targets but overwrite the same

- CI builds and executes one host-selected binary per runner;
- release-please updates version/changelog metadata and creates a tag/GitHub Release, but uploads no

  not a standalone npm/Bun distribution payload;

- README truthfully says source checkout is the only currently published installation path.

The current branch is 661 commits beyond ancestor tag `v0.7.0`; its three linked package manifests
remain `0.7.0`, while a non-ancestor `v0.7.1` exists on another release line. G6-01 therefore
builds version-parameterized candidates and never infers publishability from a nearby tag. G6-04
must bind the eventual release-please version and exact merged SHA.

## One build, multiple channels

Add one release model and one thin executable builder. The model owns the exact four-target matrix,
artifact names, package names, archive layout, completion paths, manifest schema, checksum order,
and formula rendering. The executable accepts an explicit output root plus `host` or `all` target
selection and refuses an existing nonempty output, invalid version, unsupported target, duplicate
asset name, or path outside its owned staging root.

For each selected target, the pipeline is strictly ordered:

1. compile `packages/cli/src/index.ts` once with `bun build --compile --bytecode` into an immutable
   target staging directory;
2. run `file`/header validation and, only for the current host target, execute `version`, `help`,
   and all three completion commands;
3. capture Bash, zsh, and Fish from the signed CLI once and require exact equality with direct
   source execution;
4. create one executable-mode-preserving `.tar.gz` containing `skillsmith`, `LICENSE`, and the
   three completion files;
5. place the same unmodified binary bytes in that target's npm payload package;
6. pack the npm payload with `bun pm pack` and never rebuild inside packing; and
7. record byte size and SHA-256 from the actual produced payload.

After all target payloads exist, generate the launcher package, Homebrew formula candidate,
`release-manifest.json`, and lexically sorted `SHA256SUMS`. Checksums cover every publishable
archive/package/formula payload plus the manifest; the checksum file does not recursively hash
itself. Formula SHA values must equal the corresponding archive entries. No channel may rebuild or
download its own copy of the CLI.

Two identical Bun 1.3.14 Linux-arm64 compiles produced different SHA-256 values during mapping.
Reproducible native bytes are therefore not claimed. Integrity comes from build-once fan-out:
direct archives, Homebrew, and npm packages all contain the exact binary produced in one lineage,
and G6-04 later binds that lineage to the exact release SHA and provenance.

## Archive and completion placement

Use the runner's standard POSIX `tar` implementation for direct archives. A mapping spike showed
that `Bun.Archive` generated deterministic gzip bytes but restored an executable input as mode
`0600` under pinned Bun 1.3.14. It remains suitable for read-only inspection in tests, but it must
not create the public executable archive unless Bun gains and the plan reviews an explicit mode
API. No third-party archive dependency is needed.

Each target archive has this exact closed layout:

```text
skillsmith
LICENSE
completions/skillsmith.bash
completions/_skillsmith
completions/skillsmith.fish
```

The three completion entries must equal the signed G6-02B command output byte-for-byte. Archive
creation preserves `skillsmith` executable mode. Extraction rejects extra, missing, duplicate,
absolute, traversal, symlink, device, or oversized entries before clean-install smoke.

## npm and Bun package model

Generate five publishable package directories under the ignored release output; do not mutate the
workspace packages into release payloads.

The launcher package:

- declares exact-version `optionalDependencies` on all four native payload packages;
- exposes only `skillsmith` through a small tracked CommonJS launcher;
- selects exactly one package from `process.platform` and `process.arch`;
- spawns that package's binary with untouched argv, inherited stdin/stdout/stderr, exit status, and
  signal settlement;
- emits one actionable error for an unsupported platform or a missing/omitted payload;
- contains the three generated completion files under documented `share/completions` paths; and
- has no install/postinstall script, network fetch, shell mutation, source runtime, or workspace
  dependency.

Each native package contains exactly `package.json`, `README.md`, `LICENSE`, and
`bin/skillsmith`. Its `os`, `cpu`, and Linux `libc: glibc` metadata select one platform, its version
equals the launcher and CLI version exactly, and it exposes no public JS API or competing bin.
Tests inspect all tarball entries and metadata, including the negative `--omit=optional` path.

Clean-package smoke installs local launcher and host-payload tarballs into isolated npm and Bun
global prefixes, with fresh home/cache/config roots and no repository `node_modules` visibility.
It runs `skillsmith version`, `help`, and completion, then upgrades between two locally generated
fixture versions and uninstalls. Selection-matrix tests use npm/Bun's standard `os`/`cpu` metadata;
no local registry or postinstall downloader is introduced merely to simulate publication.

## Homebrew candidate model

Render one formula candidate for `smorinlabs/tap/skillsmith`. It selects the exact matching archive
for macOS/Linux and arm64/x64, declares the archive SHA from the release manifest, installs the
binary with `bin.install`, and places completion bytes with Homebrew's Bash, zsh, and Fish
completion helpers. Its `test do` runs a noninteractive, credential-free orientation command and
asserts the expected version.

G6-01 validates Ruby syntax, the four URL/SHA branches, archive equality, install/upgrade/uninstall
against a disposable prefix, and an actual local-tap install on a Homebrew-bearing macOS runner.
The always-runnable selector uses the same archive/formula model without skipping when Homebrew is
absent; the supported-platform receipt is separately mandatory before G6-01 sign-off. No edit or
push to the external tap occurs in this group.
