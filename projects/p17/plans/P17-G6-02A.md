# P17-G6-02A mapped plan: shared command metadata, help, workflows, and docs

## State and coherent boundary

P17-G6-02A is the first implementation group after formal Phase 6 entry. It makes the already
shipped 23-command CLI easier to learn without changing the command set, aliases, option spellings,
application routing, output DTOs, or mutation semantics. It also performs the approved Commander
12-to-15 compatibility upgrade before generated completion consumes the parser in G6-02B.

The group has two deliberately ordered product slices:

1. upgrade Commander to 15.x behind characterization and preserve the signed parser contract; then
2. make `CommandSpec` the single source for five-group root help, progressive command help,
   workflows, topics, README orientation, and a generated current command reference.

Primary ownership is exactly 17 entities:

- `COMMAND:help`;
- `EWP-CF-013` and `EWP-CF-032`;
- `EWP-CMD-HELP-TS01` through `EWP-CMD-HELP-TS07`;
- `EWP-OPT-TS05` and `EWP-OPT-TS07`;
- `EWP-P6-T04`, `EWP-P6-TS04`, and `EWP-P6-TS05`;
- `EWP-WF16`; and
- `P2-05`.

Required-now is exactly 15 executable validations:

- `EWP-CMD-HELP-TS01` through `EWP-CMD-HELP-TS07`;
- `EWP-OPT-TS05` and `EWP-OPT-TS07`;

## Existing implementation and gap audit

The current CLI already has one 28-node declarative registry (root, 23 top-level commands, and four
`config` children), exact aliases, argument/option metadata, primary-question strings, examples,
exit meanings, applications, and one generic Commander attachment path. Current generated command
help appends aliases, a question, examples, and exits to Commander's flat option output.

The remaining gaps are bounded:

- root help is Commander's alphabetical wall rather than the canonical five intent groups;
- several current questions differ from the final 23-row Section 13.4 matrix;
- examples have no workflow title, safety classification, or canonical minimal invocation;
- options have no help-family or common/advanced classification;
- command help lacks the required stable progressive section order and inherited-global section;
- `help workflows`, `help lock`, and `help plan` do not exist;
- the manifest topic still describes the pre-Phase-2 state as current;
- unknown `help` topics fail safely but do not suggest a close known name;
- README is hand-maintained and there is no current generated command reference under `docs/`;
- no executable selectors exist for the 12 G6-02A-owned validation entities; and
- Commander remains 12.1.0 even though the approved Phase-6 amendment selected 15.x.

`research/commands/` remains historical shipped/draft evidence. It is not converted into the new
current authority. The new generated current reference is `docs/commands.md`; README remains the
short orientation surface.

## Approved Commander 15 compatibility slice

The upgrade is intentionally first so later help and completion work targets one final parser API.
The isolated pre-entry spike established:

- Commander 15 is ESM-only and declares Node `>=22.12`; Skillsmith is an ESM, Bun-only CLI and the
  repository's Node compatibility runtime is 22.23.1;
- 387 of 388 broad tests passed without source changes;
- the only failure was the existing inherited negated-default preparse contract;
- Commander 15 delays the implicit `true` default for a lone negated option until parse preparation,
  while Skillsmith's signed pre-parse contract exposes that semantic default immediately;
- the isolated `Option.default(defaultValue)` candidate restored focused parsing but full registry
  validation later proved it changes declared `Option.defaultValue` metadata, so it is not the
  accepted implementation;
- 41 parser/completion characterization tests, typecheck, smoke, and native x64/ARM64 compilation
  passed in the spike;
- Commander 12 and 15 ARM64 binaries were both 114,010,256 bytes; and
- a direct `@bomb.sh/tab` adapter increased that spike binary by 196,608 bytes (0.172%), but its
  live attachment is deferred to G6-02B because its default `complete` command and PowerShell/
  alias/value behavior do not match Skillsmith's 1.0 contract.

Repository implementation order:

1. record the existing negated-default and command-tree characterization;
2. update `packages/cli/package.json` and `bun.lock` to Commander 15.x;
3. observe the existing negated-default failure on the real updated dependency;
4. keep ordinary defaults on public `Option.default`, and seed a negated option's explicit semantic
   default through public `Command.setOptionValueWithSource(..., 'default')` immediately after
   attachment so pre-parse values and declared option metadata both remain exact;
5. rerun options, help, eager global parsing, completion characterization, typecheck, smoke, and
   native x64/ARM64 compilation; and
6. prove that command paths, aliases, flags, choices, defaults, parse results, help exits, version,
   and compiled-artifact behavior have not changed.

No Commander private field, prototype patch, CommonJS bridge, dual parser, Node runtime requirement,
or parser-visible compatibility command is permitted.

## Shared metadata design

### Command documentation metadata

Each `CommandSpec` gains declarative documentation metadata:

- one exclusive `primaryQuestion` (already present, corrected to the exact Section 13.4 wording for
  the 23 top-level commands);
- one or two `minimalInvocations` (two only for `update`, whose bounded check and selected mutation
  are both normative);
- two or three `commonWorkflows`, each with a short label, invocation, explanation, and execution
  safety/prerequisite classification; and
- existing examples migrate into or are replaced by those common workflows so help and docs cannot
  drift between two independent invocation lists.

Root and nested `config` nodes retain truthful metadata for their own help pages. Generated public
indexes select only paths exactly one segment below `skillsmith`, which yields the canonical 23
rows and presents `config` once.

The exact five groups and order are:

1. Discover — agents, list, commands, status;
2. Manage — install, uninstall, update, undo;
3. Develop — dev, verify, promote;
4. Declarative — init, export, plan, apply, sync; and
5. Maintain — doctor, check, gc, config, completion, version, help.

Aliases are rendered adjacent to their canonical command and never become additional rows.

### Progressive option metadata

Every `CommandOptionSpec` gains exactly one stable help family and one common/advanced
classification. The family order is:

1. targets and scope;
2. source, destination, and artifacts;
3. behavior and verification;
4. safety and approval;
5. automation and output; and
6. inherited globals.

The classifier is declarative in `spec/options.ts`, validates every current option, and rejects an
unclassified or multiply classified option. It may share semantic defaults by canonical long flag,
but command-specific overrides are explicit records, not formatter conditionals.

For a leaf command, local `--help` appears once under automation/output. Other root options are
rendered once under inherited globals; the root `--help` spelling is not repeated there. Advanced
options are headed separately inside their owning family but never hidden. Defaults, choices,
conflicts, destructive effects, and relevant exit meaning stay adjacent to the owning metadata or
description rather than being inferred from prose.

### Rendering boundary

Commander 15's public `Command.helpGroup`, `Option.helpGroup`, `commandsGroup`, `optionsGroup`, and
`configureHelp` APIs own the mechanical grouping and global-option visibility. Skillsmith does not
reimplement Commander's wrapping, option terms, command terms, choice/default descriptions, or help
width calculation. New pure helpers under `packages/cli/src/help/` supply the product-specific
metadata, section order, and generated documentation for:

- root group summaries;
- progressive command help;
- the workflows topic;
- cross-cutting topics; and
- Markdown command-reference/index sections.

They consume immutable specs and Commander's public `Command`/`Help` APIs. `command-spec.ts` remains
the only construction/attachment owner. `current-renderers.ts` remains the output routing owner.
No helper writes streams, exits, parses argv, discovers state, or imports a command module.

The stable command-help section order is primary question, usage, common workflows, targets/scope,
source/destination/artifacts, behavior/verification, safety/approval, automation/output, inherited
globals, examples-equivalent workflow details, and exit codes. Empty option families are omitted
without reordering the remaining families.

### Topics and suggestions

Canonical topic metadata contains `workflows`, `manifest`, `lock`, `plan`, `source`, `environment`,
`scope`, `exit-codes`, and `formatting`. This follows the explicit normative source/scope topic
spellings. The currently shipped plural spellings `sources` and `scopes` remain accepted only as
compatibility aliases that resolve to the canonical singular page; they are not additional command
aliases, canonical topic rows, or generated-index entries. Topic aliases live beside their
canonical topic in the same metadata registry and participate in safe lookup/suggestion coverage.

Topic content is updated to current manifest/lock/plan behavior and generated workflow content.
`help <near-miss>` computes one deterministic close-name suggestion from the known command/topic
set, emits it with exit 2, and never invokes the suggested target. Inputs with no safe close match
retain the plain unknown-name error. Commander handles unknown command suggestions through its
public error behavior; both routes are covered without autocorrection.

## Generated documentation contract

`packages/cli/src/help/reference.ts` produces the canonical Markdown fragments from the same specs.
`scripts/generate-command-reference.ts` has `--write` and `--check` modes and owns two outputs:

- `docs/commands.md`, a generated current reference containing the exact five groups and 23 command
  rows plus per-command question, minimal invocation, workflows, aliases, arguments, option
  families, and exits; and
- one delimited generated command-orientation region in `README.md` containing the five-group
  command index and a link to the full reference.

The script writes deterministic LF UTF-8, is idempotent, and reports a nonzero check result on byte
drift. It never rewrites prose outside the README markers. The generated file says how it is
generated and must not be edited by hand.

Runnable examples carry metadata rather than relying on fence-text heuristics. WF16 materializes
placeholders only inside an owner-private temporary home and local fixture remotes, uses injected
fake tools/application seams where a real remote would be unsafe, and proves zero mutation of the
developer checkout and real fleet. README shell blocks not explicitly marked runnable remain
illustrative and are still parser-checked for live command/flag names by P1-TS05.

## Explicit exclusions

G6-02A does not:

- add, remove, rename, nest, or alias a command;
- add, remove, rename, or change the semantics/defaults of an option;
- add `help-all`, a command namespace, a completion installer, or PowerShell completion;
- attach `@bomb.sh/tab`, emit shell scripts, edit startup files, or claim downstream completion;
- change application services other than the bounded unknown-help suggestion message;
- change DTOs/codecs, human result rendering, color policy, logging, observation, interaction,
  scheduling, mutation, or exit precedence;
- perform the G6-03 dependency cleanup or install/upgrade documentation;
- build/package/publish binaries, checksums, Homebrew, npm, or release artifacts;
- rewrite historical research pages as current authority; or
- use public network access, live credentials, the developer's real home, or the real installed
  skill fleet in tests.
