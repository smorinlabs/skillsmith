# P17-G4A-02 Ready plan

## Outcome and exact scope

G4A-02 activates the dedicated `skillsmith export` command. Export observes one bounded live
fleet scope, classifies every selected placement from signed inventory/ledger/Git/source-content
facts, and creates or safely merges one portable manifest/lock pair. It never changes live
placements. It changes the placements ledger only through the canonical v1-to-v2 migration when a
real portable artifact mutation depends on legacy provenance. By default it skips observations that
cannot be represented portably with explicit warnings; `--strict` turns any such skip into a
zero-write failure. Bounded `--force` resolves only selected portable declaration conflicts and
never changes this portability gate, deletes declarations, or takes whole-file ownership.

The immutable catalog scope is exactly 15 primary entities:

- command `COMMAND:export`;
- decision `D-005`, finding `EWP-CF-011`, and retained recommendation `P1-06`;
- command selectors `EWP-CMD-EXPORT-TS01..TS09`; and
- phase task/selector `EWP-P4A-T02` and `EWP-P4A-TS03`.

The validation partition is exactly ten required-now validations: the nine export command
selectors and P4A-TS03. `EWP-WF04` remains one immutable downstream obligation owned required-now
by dependency-complete G4B-03 because that workflow invokes `plan` and `apply` and proves Machine-B
reproduction. G4A-02 does not create or run a WF04 owner.

Signed G3B-03 through G3B-05 remain authoritative for ledger-v2 and recovery, immutable observed
snapshots and pure planning, and registry-owned tool behavior. Signed Phase-2 artifact discovery,
lossless manifest editing, portable lock encoding, repositories, semantic hashing, pair
coordination, canonical source/path identity, and source-content hashing remain authoritative.
Signed G4A-01 supplies artifact-operation sequencing and the lease-bound coordinator seam. This
group composes and narrowly generalizes those authorities; it does not replace them.

All work is credential-free and hermetic. Tests use temporary homes, project roots, ledgers,
placements, stores, manifests, locks, local Git repositories/remotes, deterministic ports, and
synthetic canaries only.

## Approved export-default amendment

The consolidated plan previously did not determine what bare `skillsmith export` selects. The user
approved this exact correction on 2026-07-18, and Section 8.12 records it:

- without a scope selector, use current project scope when a project context exists and user scope
  otherwise;
- the automatic pair follows that scope: discovered/current project manifest plus sibling lock, or
  XDG user manifest plus sibling lock;
- `--file` selects only output and never changes the live scope or project identity;
- explicit system or managed scope is readable but not representable in the v1 portable manifest,
  so every such observation warns and skips, `--strict` fails without writes, and no observation is
  remapped to user/project;
- no portable selection creates no empty pair; and
- Kilo Code and OpenCode are valid readable export inputs. Their unavailable mutation capability
  is not an export error; only an unavailable required inventory/read capability exits 4.

The amendment changes no command name, option, entity, dependency, workflow, artifact schema, or
cross-machine behavior. It closes source-scope and automatic-pair defaults before implementation.

## Architecture verdict

The implementation adds one export domain and activates existing seams:

1. an application service resolves grammar, project context, readable tool/scope selection, and
   the exact output pair;
2. `export/observe.ts` builds one immutable snapshot by reading selected inventory, ledger, live
   content, and Git facts once;
3. pure `export/classify.ts` produces closed portable/nonportable facts;
4. pure `export/merge.ts` computes lossless manifest edits and a complete canonical lock model;
5. pure `export/plan.ts` emits the existing migrate-ledger/migrate-project-config/write-manifest/
   write-lock vocabulary;
6. `export/run.ts` binds those operations to the shared artifact execution authority; and
7. one v1 wire codec plus human/JSON renderers project the domain report.

The existing acquisition-specific artifact controller is extracted into
`artifacts/execution.ts` as a pair-only authority. The canonical ledger-migration execution binding
moves beside its preparation in `place/ledger-migration.ts`; acquisition retains a compatibility
alias. Acquisition and export each compose the shared pair controller with the existing ledger
tail. The physical pair coordinator, lease type, repositories, execution scheduler, operation
vocabulary, and recovery format remain unchanged.

The design rejects a reverse-sync engine, generic classifier registry, second manifest model,
second pair writer/coordinator, exporter plug-in interface, tool-specific export branches, a new
ledger schema, network resolver, live mutation, and plan/apply implementation.

## Command grammar and early preflight

The shared command registry activates the already-cataloged surface:

```text
skillsmith export
  [--file <path>] [--lockfile <path>]
  [-t, --tool <name>]...
  [-s, --scope <user|project|system|managed> | --user | --project | --system | --managed]
  [--strict] [-f, --force] [--dry-run] [--json]
```

There are no positionals, aliases, `--include-unmanaged`, approval, deletion, prune, locked,
network, or confirmation options. Exact preflight rules are:

- `--file` and `--lockfile` are singular; repeated singular options exit 2;
- `--lockfile` requires `--file` and is invocation-only;
- any two scope forms conflict even when equivalent, before project/tool discovery or I/O;
- unknown tool/scope exits 2; repeated tools deduplicate in registry order;
- a known tool missing required inventory/read capability exits 4 before artifact writes;
- `--strict`, `--force`, and `--dry-run` may combine because each changes classification, merge,
  or execution preview independently;
- force never grants approval and export never prompts; and
- global cd/config/output/verbosity/color semantics remain shared runtime authority.

Help, completion, option relations, target-ledger comparison, live command introspection, and JSON
mapping all consume the same command registry. No command module duplicates grammar.

## Live selection and automatic artifact pair

### Tools

Explicit tools select only those readable registries. They are unique and ordered by the canonical
registry. Without explicit tools, use configured effective tools when nonempty, otherwise every
known readable tool in registry order. Kilo Code and OpenCode are included when selected/readable;
export does not mistake their read-only lifecycle status for missing inventory capability. A valid
tool filter that observes no placements is an explained exit-0 no-op and creates no pair.

### Source scope

Exactly one source scope is observed:

- bare export: current project when `ProjectContext` has a project, otherwise user;
- explicit user: user roots and the user ledger tree only;
- explicit project: only the current stable project identity; outside Git, effective cwd is the
  explicit project root;
- explicit system or managed: only that readable scope, with every observation nonportable because
  manifest v1 has no such scope.

Scope filters before classification and same-name merge. It never rebases placement roots, changes
an inventory identity, selects another registered project, or converts system/managed state to a
writable scope.

### Output pair

Pair resolution is deterministic:

1. explicit `--file`, resolved from effective cwd, with sibling lock unless `--lockfile` is also
   explicit;
2. user source scope selects `$XDG_CONFIG_HOME/skillsmith/skillsmith.toml` plus sibling lock;
3. project source scope selects the discovered/current project manifest or
   `<projectRoot>/skillsmith.toml` plus sibling lock; and
4. system/managed or a filter-to-zero invocation reports no automatic writable pair unless an
   explicit file was named, but still writes nothing when no portable candidate survives.

An explicit output file never changes source scope, project identity, or live root selection. A
custom lock path is reported exactly, is never persisted into the manifest/config, and must be
repeated on a later direct call. No portable candidate means no new empty manifest or lock;
existing pair bytes remain unchanged.

## Immutable observation boundary

The runner builds one owned snapshot before pure classification. It contains only the facts needed
for the selected scope/tools:

- stable `ProjectContext` and effective source scope;
- registry-ordered inventory identities, root ordinals, physical representation, and duplicates;
- one discriminated ledger read state, its byte/semantic revision when present, selected logical
  pair records, current transaction, and pending migration/recovery journals;
- selected live byte/content revisions and placement paths;
- for dev candidates only, one `GitPort.inspectWorktree` result plus source-content revision per
  unique repository root; and
- the selected manifest and lock repository envelopes/revisions.

Every physical inventory root, ledger, artifact member, Git repository, and content tree is read at
most once per snapshot and deduplicated by canonical identity. Inputs are cloned/frozen and hostile
objects, proxies, accessors, cycles, invalid strings, or oversized collections refuse before
planning. Classification and merge do no filesystem, Git, network, clock, or environment reads.

Every ledger consumer discriminates v1 from v2. An unresolved current transaction, pending legacy
journal, or recovery journal refuses an otherwise mutating export rather than letting artifact
writes race or obscure recovery. A v1 ledger is still sufficient immutable provenance for pure
classification, but its canonical migration becomes the first planned operation only when a real
artifact mutation survives every preflight gate.

Export never fetches or resolves a moving remote ref. Managed records already contain their exact
resolution; clean dev export pins the inspected HEAD SHA. Existing requested refs are preserved only
when the live/existing intent relationship is compatible.

## Portable classification

Classification is deterministic by canonical `(name, tool, scope, root ordinal)` and yields a
closed reason code rather than embedding local paths.

### Managed remote candidate

A candidate is `portable-managed` only when all of these are proven together:

- one unambiguous selected inventory placement correlates to the exact ledger tool/scope/name pair;
- the ledger record is terminal pinned state with canonical install origin and pinned content;
- origin source, requested ref, full resolved SHA, source-relative skill path, content hash,
  placement representation, and selected live bytes are coherent;
- the live path is the adapter-owned default or maps to one permitted portable custom token; and
- canonical source/path normalization and the secret gate both pass.

The declaration uses the origin's credential-free source, its human requested ref (including null),
the selected scope, the proven symlink/copy representation, and its portable custom path. The lock
uses the exact resolved SHA, source path, content hash, and final manifest semantic hash.

### Clean Git dev candidate

A dev candidate is `portable-dev` only when the exact ledger/live record identifies a Git checkout,
`inspectWorktree` proves a full HEAD SHA, clean status, a canonical credential-free origin remote,
and a contained source-relative skill path, and current source content hashes successfully. The
manifest ref becomes the exact inspected SHA because export cannot infer the user's moving branch
intent. Source, source path, content hash, placement, scope, and portable custom path otherwise use
the same canonical gates as managed state.

### Nonportable candidate

These facts are never exported:

- dirty Git or non-Git dev state;
- unmanaged, ambiguous, duplicate, stale-ledger, incomplete-provenance, or live/content-mismatched
  placement state;
- system or managed source scope;
- credential-bearing, file, plain-HTTP, Git-protocol, store, ledger, journal, dev-source, or other
  local-only source identity;
- arbitrary absolute, escaping, traversal, drive, UNC, store-owned, ledger-owned, dev-owned, or
  otherwise unrepresentable placement path; and
- invalid source/name/ref/SHA/source-path/content-hash/schema data.

Default mode records a sanitized warning and skips the entry. `--strict` promotes any skip to
failure and makes the entire invocation zero-write. `--force` cannot alter classification. A
default adapter root omits `path`; a project-contained project custom target becomes `./...`; a
home-contained user custom target becomes `~/...`; custom location never changes scope.

## Same-name candidate merge

One manifest name owns one source/ref/scope/placement/path and a unique nonempty tool list. Selected
portable observations with the same name merge only when those shared fields and exact lock facts
agree and the resulting declaration has no custom `path`. Tools union in registry order only for
adapter-default locations. Canonical custom paths remain limited to one source and one tool even
when two observations normalize to the same token. Duplicate same-tool observations, any attempted
multi-tool custom-path union, or incompatible source, requested ref, scope, placement, portable
path, resolved SHA, source path, or content hash are a selected conflict and block every write.

Without force, a selected conflict exits 2. With force, a single deterministic portable live
candidate may become authoritative only when doing so does not rewrite intent owned by an unselected
tool. Force therefore:

- may add selected compatible tools and refresh selected exact resolution;
- may update shared declaration fields only when every existing tool in that declaration is part of
  the selected portable candidate set;
- may not add a second tool to a declaration carrying a custom path or retain a custom path while
  changing that declaration to multiple tools;
- never removes a tool or declaration, selects among ambiguous live candidates, or rewrites shared
  fields still used by an unselected tool; and
- never bypasses strict, capability, portability, artifact-shape, revision, lock-correlation,
  permission, or cancellation failures.

If bounded authority is insufficient, export refuses with remediation to narrow/select all related
tools or use a separate manifest. No order-dependent last-writer behavior is permitted.

## Safe existing-pair merge

Export obtains exact manifest/lock repository revisions before planning and applies only targeted,
lossless edits.

- An absent pair is created only when at least one portable candidate survives.
- Matching declarations preserve their requested ref, comments, order, defaults, registry content,
  optional fields, and unselected tools; selected compatible tools may be added.
- Exact live resolution refreshes only the matching lock entry and the root manifest hash.
- Unselected declarations and their valid lock entries remain semantically unchanged and in
  canonical lock order.
- A selected declaration conflict refuses all writes unless the bounded force rules above apply.
- Exact supported legacy project config may migrate losslessly only as a visible prerequisite to a
  real portable selected edit; it never migrates merely because all observations skipped.
- A ledger-v1 source may migrate losslessly to canonical v2 only as a visible prerequisite to a
  real portable artifact mutation. Dry-run previews it, while filter-to-zero, no-portable,
  strict/conflict/preflight refusal, and already-exact no-op paths neither lock nor migrate it.
- Any pending ledger journal or transaction refuses before pair planning. Migration preparation,
  journal recovery, persistence, and semantic verification reuse the canonical shared authority;
  export does not define a second ledger converter.
- Mixed, empty, malformed, nonportable, unknown, or future manifest state refuses with exit 3.
- Malformed, future, unknown-hash, noncanonical, extra-entry, or otherwise invalid lock state
  refuses with exit 3; export does not usurp doctor repair authority.
- A missing/incomplete lock may be created only when exact lock facts are available for every
  manifest declaration after the merge. Export never invents or drops an unselected entry.
- A valid unchanged rerun emits no operations and preserves both files byte-for-byte.

There is no full-file manifest serializer, declaration deletion, unselected replacement, implicit
lock-path persistence, or `--include-unmanaged` fallback.

## Pure operation plan and execution

`CurrentMutatorCommand` is widened only to admit `export`; the existing operation kinds, images,
identities, diagnostics, checks, and results stay closed. Export plans one artifact group and these
exact chains:

```text
migrate-ledger? -> migrate-project-config? -> write-manifest -> write-lock
migrate-ledger? -> migrate-project-config? -> write-lock  # manifest semantics already match
no operations                                              # pair already exact or no portable rows
```

Every operation has immutable before/after images, exact selected-pair preconditions, stable IDs,
null live pair identity, no force conflict model beyond the already-resolved merge decision, and
mutation flags only for its artifact role. The planned canonical lock always hashes the final
manifest semantics. Dry-run returns this identical plan/effect projection but binds no locks and
writes nothing.

`LedgerMigrationCommand` is likewise widened to `export`, and
`createAcquisitionLedgerMigrationBinding` becomes a compatibility alias for a generic shared
binding colocated with `prepareLedgerMigration`. A planned `migrate-ledger` is present exactly when
the observed ledger is v1 and at least one later artifact operation will execute. System/managed
all-skipped and other no-operation outcomes return a report without encoding an `OperationPlan`,
because its selection model admits only writable user/project scopes.

Execution uses the signed stable topological scheduler and extracted pair-only artifact controller.
Locks are acquired in existing order:

```text
artifact central/group -> exact manifest/lock compatibility members -> ledger
```

Dry-run, no-op, no-portable, and preflight-refused paths acquire no lock. A mutating export holds the
artifact group/member locks and ledger lock through every provenance-dependent artifact write. Under
that full hierarchy it reobserves ledger schema, semantic revision, current transaction and journals;
selected logical/live content and representation; manifest/lock revisions; and, for clean-dev
candidates, Git root, HEAD, dirty state, canonical remote, and source-content hash. Any mismatch
refuses before the first write.

When migration is planned, the shared binding journals, commits, and verifies canonical v2 under the
ledger lock, then advances the execution revision cursor so downstream artifact preconditions expect
the verified v2 after-image. The migration is an independently committed prerequisite and is
reported truthfully if a later artifact operation fails; its failure leaves the original ledger and
both artifacts unchanged. Acquisition retains byte-compatible public/internal aliases. The shared
pair controller validates exact pair/revision/action/image coherence, holds one authenticated group
lease, uses the existing lease-bound coordinator commit body, and performs sequential logical
artifact operations without peer-writer interleaving. Cancellation, contention, permission failure,
external-writer CAS refusal, crash recovery, and byte/mode preservation remain existing authority.
Execution never replans under lock.

G4A-04 retains exhaustive injected inter-operation and cross-domain crash matrices. G4A-02 proves
ordinary manifest-to-lock ordering, no-write preflight, exact revisions, concurrent-writer refusal,
cancellation, and recovery compatibility without adding a second durability model.

## Domain report, wire contract, and output

G4A-02 adds one strict `export@1` wire contract and current mapping. The domain report is owned,
frozen data with these bounded facts:

```ts
interface ExportReport {
  readonly reportVersion: 1;
  readonly dryRun: boolean;
  readonly requested: {
    readonly tools: readonly BuiltInToolId[];
    readonly explicitTools: boolean;
    readonly scope: "user" | "project" | "system" | "managed";
    readonly explicitScope: boolean;
    readonly strict: boolean;
    readonly force: boolean;
  };
  readonly artifactSelection:
    | {
        readonly outcome: "selected";
        readonly selectedBy: "explicit-file" | "project" | "user";
        readonly manifestPath: string;
        readonly lockPath: string;
        readonly lockSource: "sibling" | "explicit";
      }
    | {
        readonly outcome: "none";
        readonly reason: "no-portable-candidates" | "filter-noop";
      }
    | { readonly outcome: "refused"; readonly reason: string };
  readonly results: readonly ExportResult[];
  readonly effects: readonly ExportEffect[];
  readonly summary: {
    readonly observed: number;
    readonly portable: number;
    readonly skipped: number;
    readonly conflicts: number;
    readonly changed: number;
    readonly unchanged: number;
  };
}
```

Each portable result exposes name, registry-ordered tools, portable scope, canonical source object,
requested ref, exact SHA/source path/content hash, placement, portable path, classification
`portable-managed|portable-dev`, merge action, and closed reason code. Skipped/conflict results
expose only validated name/tool/scope plus sanitized classification/reason codes—never placement,
store, ledger, repository-root, dev-source, credential, or raw exception strings.

Effects expose role `ledger|manifest|lock`, action
`create|migrate|update|refresh|unchanged|not-written`, operation ID when present, and outcome
`planned|succeeded|failed|cancelled|not-run`. They are a bounded projection, not the whole internal
plan. Ledger migration is therefore visible without exposing its path. The selected output artifact
paths may be reported because the user selected or implicitly addressed them; no other machine path
crosses the domain/wire/output boundary. All strings pass the existing sensitive-material/redaction
gate.

The v1 DTO adds `schemaVersion: 1`, `kind: "skillsmith.export"`, mirrors the closed domain facts,
rejects unknown fields, and has no implicit migration. The codec is exported from the contracts/v1
subpath and package declarations, registered once, and bound to `skillsmith export` in the current
wire registry.

Human output and JSON derive from the same report:

- create/update/dry-run headings name the exact selected pair;
- every exported, skipped, conflict, unchanged, and not-written result is visible;
- warnings/errors use sanitized codes/remediation on stderr;
- JSON writes exactly one strict report value to stdout for a completed classification/plan,
  including strict/conflict outcomes, while parse/pre-observation failure uses the standard error
  contract;
- quiet/verbose/debug/color behavior remains shared runtime authority; and
- no success heading is printed for a refused or failed write.

Exit classes map through existing CLI policy:

- 0: successful create/update/noop, filter-to-zero, or default warn-and-skip completion;
- 1: strict promotion of one or more nonportable skips, or ordinary migration/artifact/coordinator
  execution or integrity failure;
- 2: grammar/selection error or unresolved selected portable conflict;
- 3: invalid or unreadable persisted artifact/ledger state, or stale revision/precondition;
- 4: required readable tool capability unavailable;
- 6: permission denial; and
- 130: cancellation.

There is no normal export source/network resolution exit because the command never fetches;
unusable source identity is a skip or strict failure.
