# P17-G3B-02 Ready plan

## Outcome and exact scope

G3B-02 introduces one neutral execution foundation for canonical operation groups and tool/scope
pairs, then migrates the current install and dev/promote execution paths that can truthfully expose
its scheduling outcomes. The foundation owns deterministic fail-fast/continue scheduling,
within-started-group partial-pair reporting, cancellation, a ranked mutation-lock hierarchy,
under-lock precondition validation, and exact prepared-plan execution without replanning.

The group has exactly four primary entities: `EWP-CF-005`, `EWP-CF-026`, `EWP-P3B-T02`, and
`EWP-P3B-TS03`. Its Ready validation partition is 80 impacted, 16 required-now, and 64 downstream.
The 16 current selectors are dev TS01..TS06, promote TS01..TS06, OPT-TS04, P3B-TS01, P3B-TS03,
and the signed WF15 extension. P3B-TS01 is a Ready-discovered required compatibility replay because
the new runtime outcome extends its exhaustive current-action matrix. All install, uninstall,
apply, sync, update, undo, P4A, P5, and future workflow selectors retain their catalog owners and
are not claimed here.

The accepted implementation is defensive local CLI lifecycle coordination. Subprocess fixtures use
only parent-created temporary homes and repository code; they accept no network endpoint, ambient
credential, arbitrary executable, arbitrary filesystem root, or external target.

## Cross-group and current-command boundary

- Install already exposes `--continue-on-error`, has a legacy `skipped` compatibility row, and is
  migrated to the shared scheduler. The migration corrects its current operation-level fail-fast
  loop so a started resolved-source group attempts and reports every tool/scope pair before policy
  affects later source groups.
- Dev and promote gain one real non-repeatable boolean `--continue-on-error` option. The application
  service forwards it to `FlipOptions`; the plan records `continue-on-error`; actual scheduling,
  output, and exit behavior are exercised through both command families.
- Uninstall planning remains a consumer-ready neutral-scheduler adapter boundary, but its public
  option and skipped-result contract remain G4A-01-owned. The immutable target registry assigns
  `option:skillsmith uninstall:--continue-on-error` to G4A-01 and `EWP-CMD-UNINSTALL-TS01`, while
  uninstall@1 has no truthful skipped action. G3B-02 characterizes it and does not encode an
  unstarted target as noop, refusal, failure, cancellation, or a missing row. G4A-01 must version
  that public result before enabling the option.
- Apply, sync, update, and undo use the neutral foundation only in their owning downstream groups.
  Saved-plan apply continues to reject continuation because reviewed authorization fixes its
  execution semantics.
- G3B-01's dev/promote TS04 trace is closed substantively: both selectors gain real multi-group
  default-skip and continue cases through the application/CLI seam. The other ten dev/promote
  selectors are mandatory compatibility replays rather than duplicate scheduler suites.

This sequencing does not claim that all 64 downstream validations pass. It closes the reusable
foundation and current required slice without shipping a no-op option or weakening a historical
wire contract.

## Scheduling domain

`packages/core/src/execution` is a neutral one-way domain. It may import planning types/order,
errors/results, and capability port types. It never imports acquire, place, application, CLI,
artifact writers/coordinators, or wire DTOs. Acquire and place may import execution.

The coordinator alone constructs a `ValidatedExecutionBinding` after every under-lock precondition
passes. It contains the exact operation/group/pair identity, the operation observer's freshly
validated `actualBefore`, an immutable `unstartedForce` projection, and the execution callback.
The scheduler accepts exactly one such binding per planned operation and returns one
`OperationExecutionResult` per operation. Construction rejects missing, extra, duplicate,
reordered, or mismatched bindings before any binding is invoked.

This slice accepts exactly one operation per non-null pair ID and requires every operation's
versioned `dependencyMetadata.operationIds` to be empty. A multi-operation pair or nonempty
dependency list refuses before any callback. Current groups are therefore independent; execution
of multi-operation pairs requires a reviewed P17-G4A-04 amendment, and dependency-bearing saved
execution requires a reviewed P17-G4B-02 amendment. The scheduler derives canonical contiguous
group and pair buckets from the already-canonical plan; it never sorts on locale, array arrival,
time, randomness, path casing, or raw secrets.

Execution rules are exact:

1. Invocation-level syntax, selection, source/state ambiguity, plan construction, preconditions,
   and approval fail before scheduling and before writes.
2. A started group attempts every not-yet-cancelled pair even after a sibling pair fails. Each
   accepted pair has one operation and the existing pair journal is its transaction boundary.
   There is no cross-pair rollback.
3. A group fails when any attempted pair result fails. Under `fail-fast`, only later groups receive
   `skipped-after-failure`; under `continue-on-error`, later independent groups start, while the
   original failure keeps the batch unsuccessful and the exit nonzero.
4. Cancellation stops new pairs/groups regardless of policy. A binding already at a durable
   journal boundary uses the existing same-operation recovery contract; every unstarted remaining
   operation receives `cancelled`, never `skipped-after-failure`.
5. The output has exactly one result per planned operation in plan order. Earlier successes remain
   truthful; no result rewrites the immutable plan or appends a diagnostic after planning.

`skipped-after-failure` is a scheduling result, not an operation kind, failure, cancellation, noop,
or planning diagnostic. Its six fields are `operationId`, `outcome`, `actualBefore`, `actualAfter`,
`force`, and `error`. Both actual images reuse the binding's same freshly validated under-lock
`actualBefore`; error is null. Force is the binding's `unstartedForce`: null when unsupported, or a
valid bounded force effect that preserves requested/conflict facts and requires `applied:false`.
A cancelled unstarted result uses the same unchanged-image and not-applied force rules with outcome
`cancelled`.

## Runtime and wire versioning

`OperationExecutionOutcome` gains the fifth closed value `skipped-after-failure`. The constructor
continues to require an error exactly for `failed`; all other outcomes require null. A skipped
result additionally requires structurally equal actual-before/actual-after images and, when force
is present, `applied:false`. The flip@4 codec independently enforces the equal-image/null-error rule;
flip operations retain null force. Type, creation, deep-freeze, exact-key, ordinary-data, and
mutation-trap tests cover the new value.

The enum expansion is breaking under ADR 0008's conservative compatibility policy. Therefore:

- flip@2 and flip@3 remain separately addressable historical codecs;
- flip@3 is narrowed explicitly to its four historical outcomes rather than deriving a widened
  result union from `FlipReport`; its mapper refuses a report containing the new outcome and its
  existing golden bytes remain unchanged;
- flip@4 has the same ten top-level fields and the same exact nested shapes as flip@3, except
  `schemaVersion: 4` and the five-value result outcome; it keeps exact one-result-per-operation
  order, empty dry-run results, recursive unknown-field refusal, two-space JSON, and no terminal LF;
- no v3-to-v4 migration is registered. Both are CLI output contracts, not persisted input; current
  dev/promote command mappings and the default renderer advance to flip@4;
- the v4 package subpath has a Zod-free declaration facade. Contract inventory, public type/runtime
  parity, version isolation, mapper canaries, and historical v3 golden tests advance together.

Dev/promote human and current flip@4 JSON output expose deterministic group IDs and policy through
the immutable plan, one pair-correlated result per operation, distinct failed/skipped/cancelled
outcomes, and a summary. Dry-run exposes group/pair boundaries and policy but no execution results.
Install@1 remains compatibility-frozen while its existing human compatibility rows retain skipped
sources. `toCurrentCompatibilityAction` projects `skipped-after-failure` to the existing `skipped`
action for install and flip, and refuses that outcome for uninstall until G4A-01 versions its
contract. Continue never converts a failed batch to success. Redaction applies before any plan,
result, wire value, transcript, or error leaves core.

## Mutation-lock hierarchy and cancellation

The hierarchy accepts normalized unique descriptors with a closed rank and canonical key. Rank is
`artifact-group` before sorted `artifact-member`, then `ledger`, then sorted `live`; descriptors of
the same rank compare by unsigned UTF-16 code units. Acquisition nests in canonical order and
releases in exact reverse order on success, refusal, throw, or cancellation. A duplicate key,
rank inversion, invalid descriptor, or acquisition after scheduling begins refuses before work.

Current acquire/place production supplies exactly the existing placements-ledger target descriptor
at rank `ledger`. It continues to lock the actual `placements.json` target with `realpath:false`, so
proper-lockfile owns `placements.json.lock`, old and new binaries exclude each other, and an absent
ledger target is not created merely to lock. No second production lock, sidecar target, manifest
lock, or artifact-coordinator coupling is introduced here.

`LockPort.withFileLock(path, operation, options?)` gains an optional immutable `{ signal }` request
in the backward-compatible third position. The Node adapter uses
bounded single-attempt proper-lockfile acquisition plus signal-aware bounded retry delays, retaining
the existing stale/update/backoff limits and target identity. Cancellation before or during wait
returns the shared cancellation taxonomy promptly, creates no target/write residue, and cannot run
the callback. After acquisition the hierarchy rechecks the signal before validation and always
releases the lease. The legacy ScanEnv facade forwards the optional request without changing
two-argument callers.

Current execution order is fixed:

```text
prepare immutable plan and exact bindings (unlocked)
-> preview and bulk approval (unlocked)
-> cancellation check
-> acquire canonical hierarchy once
-> cancellation check
-> reread current ledger/live facts
-> validate all preconditions in canonical ID order
-> schedule the exact prepared bindings
-> release in reverse order
```

No lock is first acquired after the scheduler starts. Existing swap/journal functions remain the
per-pair durability implementation.

## Runtime preconditions and no-replan rule

A private bound precondition has a deterministic `precondition:v1:<sha256>` ID, exact operation
IDs, a copied/deep-frozen expected ordinary snapshot, and an observer for the same resource identity.
Adapters populate every mutating operation's `preconditionIds`; the coordinator rejects an empty
mutating-operation set, duplicate/extra registry entry, dangling ID, operation mismatch, or binding
whose covered IDs differ from the plan.

For current acquire/place pairs the normalized snapshot compares every fact the binding will use:

- command, operation, group, pair, tool, skill, scope, and canonical project-root identity;
- the selected ledger pair, including mode, placement path, dev/pinned source facts, and pending
  journal operation/transaction/phase facts;
- live path kind/classification, canonical path, symlink target, dangling state, and content hash or
  other bounded identity used by the planned operation;
- selected source/store content identity needed by that exact binding.

All observations occur under the held compatibility lock before the first pair write. An observation
error or structural mismatch returns one sanitized state refusal, invokes zero bindings, performs no
replan, and leaves plan/result/order unchanged. This is a bounded runtime comparison, not G3B-04's
repository-wide expected revisions, immutable observed-state repository, reducer, or saved-plan
staleness model.

## Verification policy

The inner loop runs changed selectors and focused execution, lock, acquire/place, lifecycle, port,
public API, CLI help/output/exit, and version-contract tests. It also runs `bun run test:smoke`,
`bun run test:smoke:p2-ts04:recovery`, `bun run typecheck`, `bun run lint`,
`bun run lint:boundaries`, `bun run check:p17`, and `git diff --check` in proportion to the edit.

Governance replay is
`bun test scripts/p17-catalog.test.ts tests/ergonomics/phase/EWP-P0A-TS09.test.ts` plus the exact 16
selectors. The major coordinator milestone additionally runs the exact P2-TS04 selector. The
five-minute complete suite runs once through `bun run check` at terminal G3B-02 sign-off and is not
duplicated at every iteration or twice in the same unchanged gate.

while the group receipt records their new honest red extensions; the other ten required-now selectors keep
their signed status and green baseline evidence. Findings `EWP-CF-005` and `EWP-CF-026` remain
`planned` until implementation supplies their behavior and trace evidence.

1. Ready: independent product/schema, architecture/ownership, and trace/test reviewers accept the

2. Test-first: green baselines precede honest reds in P3B-TS01, P3B-TS03, OPT-TS04, WF15,

   dev/promote surface, and flip@4 make focused tests pass without successor work.
4. Targeted/impacted green: all 16 exact selectors, focused tests, recovery smoke, bounded smoke,
   static gates, and the major coordinator P2-TS04 selector pass.
5. Refactor/adversarial review: three implementation partitions are independently reviewed;
   findings receive bounded amendments and exact reruns.
6. Traceability/sign-off: primary entities and required extensions close with committed receipts,
   catalog/checklist validation, terminal static checks, and one full repository suite.
