# P17-G3B-03 Ready plan

## Outcome and exact scope

G3B-03 makes ledger version 2 the only current mutation format, without weakening the already
supported version-1 read contract. It adds a visible and revision-checked ledger migration,
project-registration maintenance, durable logical transactions, bounded resource-fair history,
same-operation recovery and an internal pending-abort primitive, and deterministic `doctor --fix`
for a closed safe-repair allowlist.

The corrected group has exactly 13 primary entities: `COMMAND:doctor`, `D-010`, `EWP-CF-006`,
`EWP-CF-028`, doctor TS01..TS06, `EWP-P3B-T04`, `EWP-P3B-TS04`, and `P2-07`. Its immutable
validation partition is 25 impacted, 9 required now, and 16 downstream. The required selectors are
doctor TS01..TS06, the signed status TS04 and P3B-TS03 replays, and new P3B-TS04. Full `EWP-WF11`
is downstream: G3B-03 proves its ledger/recovery foundation, while the public undo workflow remains
owned by G5-03 after G3B-04's repository-composition foundation.

This is defensive local CLI reliability work. Production accepts no arbitrary executable, network
endpoint, credential, or unbounded filesystem target. Crash fixtures use only parent-created
temporary roots, bounded subprocesses, deterministic Clock/Id ports, and repository code.

## Current boundary and successor exclusions

- Phase 2 already owns strict ledger-v1/v2 codecs, the pure lossless v1-to-v2 migration, logical
  journal schemas, artifact reads, and the exact legacy project-config migration.
- Phase 3A already owns non-mutating version discrimination and correlated status. G3B-03 replays
  status TS04 and changes no status wire version.
- G3B-02 already owns the lock hierarchy, under-lock preconditions, deterministic scheduling, and
  current per-pair transaction boundaries. G3B-03 adds durable ledger-v2 transaction state around
  those current adapters and narrowly admits validated null-pair artifact prerequisites plus the
  global migration gate; existing pair/group/batch semantics otherwise remain unchanged.
- G3B-04 retains domain repositories, immutable observed-state repositories, pure reducers/planners,
  expected repository revisions, ADR 0006, repository-composition fault-injection seams, and
  monolith extraction. G3B-05 retains tool-adapter extraction and G3B-06 retains
  OperationContext/lifecycle propagation.
- Phase 4 retains manifest/lock mutation as ordinary desired-state execution and saved-plan apply.
  Doctor may invoke the already-reviewed exact legacy-project migration and canonical lock
  regeneration only through their normal coordinator paths; it gains no duplicate artifact writer.
- Phase 5 retains public `undo`, its target/scope/all selection, committed-history reversal, and
  ledger-authoritative GC/expiry. G3B-03 exposes only internal same-operation resume and exact
  pending-abort primitives needed to prove reversibility.

No partial WF11, public undo command, arbitrary repair, ledger reset, ambiguous normalization,
install/remove/apply behavior, store deletion, retention-expiry interpretation, saved-plan
execution, new network behavior, or credential handling is introduced here.

## Canonical ledger-v2 mutation boundary

The mutator boundary consumes the canonical `LedgerModel`; it never projects a supported v2 ledger
back into the historical v1-shaped `LedgerFile`. Every current write encodes through
`ledgerV2Codec`. V1 encode remains an explicitly addressable compatibility codec only.

Read and mutation states are exact:

1. An absent ledger is the only empty state. Read-only commands report absence without fabricating a
   durable timestamp. The first real mutation creates canonical v2 directly under the historical
   ledger-target lock.
2. A supported v1 ledger is normalized in memory. Read-only and all dry-run paths preserve its exact
   bytes and expose a visible `migrate-ledger` prerequisite.
3. A supported v2 ledger is decoded, cross-validated, and mutated without losing projects,
   registrations, transactions, history, legacy pair journals, or unknown-but-supported tool IDs.
4. Existing zero-byte, whitespace-only, invalid UTF-8/BOM, truncated, malformed, wrong-kind,
   schema-invalid, cross-reference-invalid, or newer-version ledgers refuse as state errors before
   lock/write/cleanup. A future version receives fixed upgrade guidance and is never guessed.

Every mutating adapter uses immutable copy-on-write transforms. It derives
`projectRegistrations` from the resulting project tree after every pair change and validates exact
equality before encode: one registration for each recorded project root, one canonically sorted
consumer per project pair, retained pinned store facts even when the current mode is dev, and no
extra consumer. Pair and registration updates enter the same atomic ledger replacement.

`place/ledger.ts` remains the compatibility facade for current callers, but its public mutation
shape becomes v2-preserving. The v1-only clone and write path is deleted rather than retained as a
second schema authority. Existing legacy pair journals remain byte-semantic facts inside v2 and are
not renamed or converted opportunistically.

## Visible ledger migration and atomic replacement

`migrate-ledger` is an executable prerequisite operation, not a parser side effect. Its before/after
images are schema-1/schema-2 ledger images, it mutates only ledger state, and it precedes dependent
pair operations. Preview and execution use the same immutable operation ID and migration envelope.

Before decoding or mutating the live target under the historical lock, every caller probes one fixed
ledger-derived recovery pointer. Its path is
`<dataDir>/recovery/ledger/v1-<sha256(canonical-ledger-path)>.json`; recovery never discovers a
transaction by scanning a directory or trusting a path from ledger contents. The strict canonical
internal record contains exact keys for schema/kind, owner token, transaction and operation IDs,
ledger target plus parent identity, pure migration source/target byte and semantic revisions, the
complete canonical migration-journal seed (group/pair identity, intent, context command/workflow,
attempt, preallocated phase timestamps/facts, and before/after images), the expected full
staged/backed-up/live/committed ledger byte and semantic revision for each cursor, derived
transaction-directory basename plus nullable verified identity, stage/backup basenames plus file
identities/revisions, and cursor. The seed is sufficient to reproduce every pending and committed
journal byte without reading an unrecorded clock or ID source. Cursor is one of `prepared`, `staged`,
`backed-up`, `replaced`, `handed-off`, `committed`, or `cleanup`.

The pointer and its private transaction directory are the discoverable durability authority until
handoff to live v2. Each pointer create is exclusive; each transition is compare-and-replace against
the prior pointer revision. The adapter fsyncs a newly created stage/backup file and its transaction
directory, and fsyncs every pointer file and its parent directory before the cursor advances. A
verified matching pre-existing pointer is resumable crash state; only an unrelated, malformed,
symlinked, shared, owner-mismatched, revision-mismatched, or otherwise unverifiable pointer/residue
refuses. No cleanup follows an arbitrary recorded path: basenames and identities must rederive from
the pointer target/transaction.

Under the lock, execution is exact:

1. with no pointer, reread exact v1 bytes, require the planned revisions, recompute the pure Phase-2
   migration, allocate the complete deterministic non-reversible logical migration-journal seed
   with `{kind:"none", retentionResourceIds:[]}`, exclusively create/fsync the `prepared` pointer
   with a null transaction-directory identity, and only then create/fsync the derived private
   transaction directory. Compare-and-replace the pointer with its verified directory identity
   before creating the stage. A crash after pointer creation can therefore create or verify only
   that derived empty private directory; no transaction directory is an undiscoverable orphan;
2. exclusively write/fsync canonical staged v2 containing the migrated legacy projection plus that
   one pending coordinator journal, fsync the transaction directory, validate the full staged
   revisions and separately validate the migrated skills/projects/registrations and preserved
   legacy-journal identities against the pure Phase-2 target, then advance `staged`;
3. exclusively copy the exact original v1 bytes to the derived backup, fsync file and directory,
   verify its identity/revision, then compare-and-replace the staged file with the same pending
   journal advanced to `backed-up`, fsync file/directory, and advance the pointer `backed-up`; the
   durability-only backup is recorded only in the recovery pointer, never in `actual.retained` or
   operation reversibility;
4. rename stage directly over the live ledger, fsync the live parent, and then advance `replaced`.
   There is no two-rename live-missing gap; the crash window is after rename but before parent fsync,
   where recovery accepts only the exact old or exact backed-up revision;
5. reread/decode live v2, require the exact backed-up coordinator journal and migrated projection,
   advance that journal to `live` through atomic ledger replacement plus live-parent fsync, and then
   advance the pointer to `handed-off`.
   Before handoff the pointer wins; after handoff the exact matching live pending journal wins and the
   pointer remains only its cleanup locator;
6. atomically remove the pending entry and append exactly one complete non-reversible committed
   migration journal through atomic ledger replacement plus live-parent fsync, and advance the
   pointer to `committed`; an already matching history ID is success on resume and is never appended
   twice;
7. verify and delete the durability-only backup, fsync its directory, advance `cleanup`, remove any
   verified stage residue and transaction directory, revalidate live v2, then remove/fsync the
   pointer last. An already missing verified backup during committed/cleanup recovery means deletion
   completed and cleanup continues.

Recovery cross-validates cursor and durable state as a closed matrix. `prepared` accepts no stage or
the exact staged revision. `staged` accepts the exact staged file with the backup either absent or
exact, or the exact backup plus exact backed-up stage. `backed-up` accepts original v1 live plus the
exact backed-up stage, or the exact backed-up revision live after rename. `replaced` accepts the
exact backed-up live revision or the exact live-journal revision. `handed-off` accepts the exact
live-journal revision or the exact committed revision. `committed` and `cleanup` accept only the
exact committed live revision with the cursor-permitted verified backup/stage/directory residue
subset. When the one permitted next-state revision is observed, recovery completes its required
fsync and compare-and-replace promotes the cursor; every other combination refuses without cleanup.

`artifacts/ledger-writer.ts` is the single focused private durable adapter for ledger replacement.
Like the existing artifact recovery-file adapter, its Node implementation uses exclusive `wx`
creation, `O_NOFOLLOW` reads, inode/link-count revalidation, private-directory ownership/mode checks,
rename/unlink, and explicit file/directory fsyncs. Its injected test port exposes the same logical
and physical barriers to deterministic fault tests. Generic acquire/place/doctor code may call this
adapter but may not import Node filesystem mutation APIs or recreate a weaker write port.

A crash before replacement leaves exact v1 authoritative. A crash at/after rename resolves old
versus new only from live revision plus the verified pointer, stage, and backup; corrupt/third-party
live bytes refuse. Recovery never treats corruption as absence, downgrades v2, or deletes the only
verified original. Another process cannot complete migration outside the same historical lock; a
previously saved operation whose source revisions no longer match stales rather than becoming a
guessed success.

The committed migration journal retains before/after audit facts but no backup claim and is not a
public undo candidate. First-mutator and doctor paths use the same writer/recovery algorithm and
produce the same pure migrated legacy projection for the same source bytes; their separately
validated coordinator context/history may truthfully differ by invocation identity.

## Logical transactions and internal recovery

Ledger v2 `transactions` contains non-committed `LogicalJournalV1Dto` values keyed by their exact
unique transaction ID. Logical IDs are disjoint across pending transactions and retained history.
The only physical-journal ID reuse is an exact compatibility shadow of that same logical pair
transaction; preserved unmatched legacy journals are separately uniqueness-checked. The durable
phases remain `prepared`, `staged`, `backed-up`, and `live` before a single atomic
pending-to-history commit changes phase to `committed`, sets completion facts, removes the pending
map entry, and appends one complete journal. A logical transaction is never valid in both
collections and history never contains a non-committed journal.

For new v2 pair work, the embedded physical journal and logical journal use the same transaction ID
and are one authority plus compatibility shadow, not two candidates. The exact shadow predicate
requires the same pair membership, transaction ID, start/completion facts, phase, and operation
family: logical install/remove/link-dev/promote map to physical install/uninstall/dev/promote, while
rollback disposition maps to physical rollback. Every new phase creates/advances both values in the
same atomic ledger replacement at the reviewed physical durability boundary.

The logical pending-to-history commit is atomic with the adapter's physical terminal transition.
Promote/dev may retain their matched physical `committed` shadow for current rollback compatibility;
install/uninstall clear/delete theirs according to current behavior. Status/join collapses an exact
matched committed shadow into the logical-history winner and never emits a duplicate or superseded
candidate. A matched pending logical journal wins over its shadow. A migrated unmatched legacy
journal remains legacy-only; its same-operation recovery attaches a matching logical shadow using
the original transaction ID before the next filesystem boundary. A logical pair journal without its
required physical shadow, a mismatched shadow, or one transaction ID across different pairs is
invalid. Commit/cleanup resume treats an already matching history ID as committed and never appends
it twice.

Recovery selection is deterministic:

- A pending logical transaction or legacy pair journal for the selected pair takes precedence over
  committed history. An unrelated pair cannot block, resume, abort, or supply state for it.
- The same operation may resume only when command, pair, and intent identity match and the observed
  resources satisfy the recorded phase-specific recovery predicate. A new invocation does not
  supply an independent phase. Resume increments `context.attempt` exactly once, preserves original
  `startedAt`, and converges without duplicate history.
- A conflicting operation refuses with exact same-operation or pending-abort remediation and
  performs no partial cleanup.
- Internal pending abort validates every recorded before image and backup revision, then atomically
  converts the existing pending logical transaction in place—same transaction ID, no second pending
  entry—to `disposition:"rollback"` and advances its matched physical shadow. It increments attempt,
  preserves original start, sets `parentOperationId` to the forward intent operation ID, and records
  the caller's validated abort command/workflow correlation. The rollback `prepared` state,
  including any owned backup of an edited/unmanaged live value and its verified revision, is durable
  before the filesystem boundary. A crash thereafter resumes rollback only; forward rerun refuses.
  Terminal commit removes the one pending entry and appends exactly one rollback-disposition history
  journal while applying the adapter's physical committed/null/delete transition.
- Missing, stale, shared, mismatched, or unverifiable retained resources make abort unavailable;
  status/doctor report the reason and no best-effort mutation occurs.
- Cancellation before a durable boundary leaves the prior phase authoritative. Cancellation after
  a boundary leaves an exact resumable phase; it never rewrites the transaction as ordinary failure.

G3B-03 exposes these recovery functions to later public selection code but does not select a target
or latest history entry on the user's behalf.

## Deterministic bounded history

The ordinary history budget is **256 complete committed transactions**. A journal is indivisible:
multi-resource transactions are never split, and array position under the ledger lock is canonical
commit order. Wall-clock timestamps, locale, directory order, and incoming object order never
select eviction.

Each journal has one or more resource anchors:

- a placement pair anchor from normalized scope, project-root-or-user, skill, tool, and placement
  path;
- a manifest/lock anchor from its role plus canonical portable token or machine-bound path; or
- the singleton ledger anchor.

Both before and after anchors participate when identity/path changes. A committed transaction with
no mutated anchor is invalid. Anchors are collision-free canonical JSON tuples with explicit domain,
role, scope, user/project-root tag, skill, tool, and canonical location fields; they derive only from
recorded journal data and never filesystem I/O. Tuple strings compare by unsigned UTF-16 code units.

The protected set contains the newly committed journal; the newest journal for every placement-pair
anchor represented anywhere in candidate committed history, including an absent/uninstalled
after-state rather than only current ledger pairs; the newest journal for every anchor referenced by
a pending transaction; and every journal containing at least one `actual.retained` entry whose
`retainUntil !== null`. G3B-03 treats non-null retention as a protection bit and does not interpret
expiry. Effective capacity is `max(256, protectedCount)`, so a busy pair cannot evict the only
reversible state for quieter pairs and protected state cannot make an otherwise valid commit fail.

Remaining slots use breadth before depth. Bucket unprotected journals by anchor; visit depth zero
for every anchor before depth one, then later depths. Within a depth, choose the greater commit
position first and break impossible/equal-position ties by transaction ID in unsigned UTF-16 order.
A multi-anchor journal is selected once. Persist the chosen complete journals in their original
oldest-to-newest commit order. The newest ineligible frontier remains retained while its cleanup is
pending; older history is not falsely exposed as the newest reversible entry.

History eviction and backup disposal are one-victim-at-a-time:

1. commit the new journal, temporarily allowing the ledger to exceed effective capacity;
2. under the ledger lock, recompute and select exactly one deterministic victim;
3. preflight every `role: "backup"` for that victim before deleting any: each path must be in a
   recognized SkillSmith-owned transaction location, match transaction identity and recorded
   path/revision/hash, and be unreferenced by pending, kept-history, legacy-journal, current-live, or
   other retained state;
4. delete only verified transaction-specific backups and fsync their parent directories; an already
   missing verified backup is accepted during recovery;
5. atomically rewrite the ledger without that one journal; and
6. repeat after reread/revalidation until within capacity.

Before deletion, journal and backup remain. After deletion but before ledger rewrite, the complete
journal is the durable cleanup tombstone: status/doctor report missing retention and cannot offer
undo, while retry selects the same victim. After rewrite neither reference nor backup remains. A
cleanup failure or unowned/shared/mismatched/unverifiable backup leaves history over capacity and
stops compaction at that first victim with a deterministic status/doctor finding; it is never
guessed, deleted, repeatedly bypassed, or used to expose an older undo candidate. Under the ledger
lock, every history-producing mutator must finish this pending cleanup before planning/committing new
history. If the exact victim cannot safely converge, the new mutation refuses and leaves the same
tombstone authoritative; read-only inspection remains available.
An absent backup is deletion-complete only when journal/path/transaction ownership validates and the
same journal recomputes as victim against the recognized unchanged ledger revision; otherwise it is
protected/refused with a finding.
`role: "store"` resources are never deleted during compaction. Dropping their reference merely
makes them eligible for later G5 reachability/GC policy.

## Doctor diagnostics, repair planning, and authority

Health checks retain the focused read-only `DoctorPorts`; checks never receive lock, write,
interaction, process, or cleanup capabilities. A separate repair planner consumes owned findings
and canonical artifact envelopes, then emits a deeply frozen deterministic plan from a closed
allowlist:

- `migrate-ledger` for an exact supported v1 ledger;
- `migrate-project-config` for the exact supported legacy project shape through the existing
  lossless editor/coordinator; and
- `write-lock` regeneration only when the selected canonical manifest and available resolution facts
  prove the normal canonical lock output through the shared artifact coordinator.

No finding authorizes install, remove, apply, undo, ledger reset, ambiguous normalization, arbitrary
overwrite/delete, expired-retention disposal, or a standalone migrate command. Manual/ambiguous/
unsafe findings remain non-mutating and retain exact remediation text and their normal exit effect.

Repair operations are ordinary shared executable operations. `CurrentMutatorCommand` and group-ID
validation add `doctor`; `createOperationId`, `createOperationGroupId`, and
`createOperationPlan` validation remain the only identity/ownership/order authorities. The shared canonical
order gains one general refinement: null-pair artifact prerequisites sort before pair-bound live
operations, then retain the existing scope/skill/source/group/tool/kind/ID comparison. The scheduler
accepts a null-pair operation only for `migrate-ledger`, `migrate-project-config`, or `write-lock`
with null skill/source/tool/scope, exact artifact-only mutation flags, empty dependencies, and one
validated binding. Each such operation occupies a standalone singleton group unless it is an
explicit non-doctor prerequisite prefix for the affected live-operation group. Existing
one-operation-per-non-null-pair and empty-dependency rules are unchanged.
For install/uninstall/dev/promote, failure or cancellation of a `migrate-ledger` prefix skips every
later live operation regardless of fail-fast/continue policy; no pair binding starts against v1. A
manifest/lock prerequisite in a non-doctor plan is the first operation of its affected group and
failure gates the rest of that group rather than invoking the normal started-group sibling rule.
For doctor, each null-pair repair is a distinct independent singleton group and the plan uses
continue-on-error plus an independent under-lock revalidation, so one failed repair does not hide
the other completed repair results. This makes
first-mutator migration a real global prerequisite while giving doctor one shared plan rather than a
bespoke repair ordering.

A doctor group identity is exact: `command:'doctor'`; null skill/source/scope; and `target` equal to
the selected normalized ledger, manifest, or lock path. Its operation identity has null pair/tool,
and there is exactly one standalone group/operation per artifact target. Duplicate targets or two
operations for one target refuse during planning.

Every doctor operation in one plan is independent against the same observed current snapshot. The
planner never combines `migrate-project-config` and a dependent `write-lock` for that same artifact
pair in one invocation; canonical lock regeneration becomes eligible on the converged rerun. A
completed batch therefore returns one result per operation without a hidden dependency/skipped
state. `--offline` permits only repairs whose after-image derives from validated local envelopes and
makes no resolver/network call. A resolution-dependent lock finding remains unhandled offline.
Online lock regeneration uses the existing canonical credential-free resolver; source-resolution
failure is exit 5 and performs no guessed write.

Doctor's public exit inventory is exact: health/unhandled finding/repair failure 1; syntax,
option-policy, approval refusal, and noninteractive approval 2; invalid, corrupt, newer, or stale
artifact state 3; source resolution 5; permission/write failure 6; and cancellation 130. Command
spec and contract tests advance together.

Doctor option semantics are checked before project discovery or I/O:

- `--dry-run` requires `--fix`;
- `--yes` and `--dry-run` conflict;
- `--yes` requires `--fix`;
- without `--fix`, doctor is read-only;
- `--fix --dry-run` returns the exact operations and no execution results;
- nonempty execution requires an interactive confirmation or `--yes`;
- a clean zero-operation `doctor --fix` with no unhandled blocking finding is exit 0, prompts nobody,
  reports `No repairs needed`, and emits no synthetic operation; a manual/unrepairable zero-op keeps
  its normal failure/strict effect and reports `No automatic repairs available` instead;
- one nonempty plan receives exactly one bulk prompt, never one prompt per operation;
- preview never prompts and is valid in JSON, `--no-prompt`, and non-TTY modes; a nonempty execute
  plan in those modes refuses with usage exit 2 unless `--yes` is present; an explicit false answer
  is exit 2, cancellation is exit 130; and
- refusal/cancellation before approval performs zero writes.

The declarative option relations and `validateNonMutatingMode` are one consistent authority:
doctor's mode input gains `fix`, dry-run/yes require fix, and yes conflicts dry-run. Registry
preflight and utility-level tests must return the same usage result; the utility cannot continue to
classify fix execution as a non-mutating mode.

After approval, the application supplies the minimum operation-specific lock/write ports to the
repair executor. It revalidates the exact plan under the normal locks and returns one correlated
result per attempted operation. A failed repair never authorizes later unsafe work and reports
sanitized errors. Successful preview is exit 0 unless a separate nonrepairable blocking finding
exists. Execution uses the normal error/strict semantics: warnings fail only under `--strict`, while
error findings or failed repair results fail.

## Doctor health@2 wire contract

`check` remains permanently bound to strict `health@1`. `doctor` always advances to `health@2`,
including invocations without `--fix`, because switching schema by option would make the current
command mapping nondeterministic. Health@1 bytes, schema, mapper, and check goldens remain unchanged.

Health@2 is strict, recursive-unknown-field rejecting, two-space JSON with no terminal LF:

```ts
interface FindingV2Dto extends FindingV1Dto {
  findingId: `finding:v1:${string}`;
}

interface HealthV2Dto {
  schemaVersion: 2;
  experimental: true;
  findings: FindingV2Dto[];
  counts: { ok: number; warning: number; error: number };
  repair: {
    mode: 'not-requested' | 'preview' | 'execute';
    operations: DoctorRepairOperationV1Dto[];
    results: DoctorRepairResultV1Dto[];
  };
  mutation: {
    kind: 'none' | 'preview' | 'applied';
    planned: number;
    changed: number;
    unchanged: number;
    failed: number;
  };
  deprecations?: DeprecationV1Dto[];
}
```

Redaction produces the canonical FindingV1 projection before identity assignment or operation
correlation. Health@2 then assigns every projected finding a unique
`finding:v1:<64-lowercase-hex>` identity over its canonical FindingV1 fields plus its zero-based
occurrence among structurally equal findings. The deterministic registry/finding order makes that
occurrence stable, and the digest can never fingerprint a pre-redaction secret. Health@1 does not
expose or accept this field.

A repair operation has exact keys `operationId`, `kind`, `artifact`, `path`, `before`, `after`, and
`findingIds`. Kind is the three-value allowlist; artifact is `ledger`, `manifest`, or `lock`; path is
the selected normalized path; and sorted unique finding IDs must resolve to health@2 findings that
authorize that exact operation. `operationId` is the shared underlying executable operation's exact
`operation:v1:<64-lowercase-hex>` ID from `createOperationId`; finding authorization is deliberately
not part of operation identity. Preview and execution therefore share the same coordinator identity
and cannot silently substitute work.

Each before/after summary has exact keys `state`, `schemaVersion`, `byteRevision`, and
`semanticRevision`, contains no artifact content, and uses this closed shape:

```ts
type DoctorRepairArtifactSummaryV1Dto =
  | {
      state: 'absent';
      schemaVersion: null;
      byteRevision: null;
      semanticRevision: null;
    }
  | {
      state: 'present';
      schemaVersion: number | null;
      byteRevision: `sha256:${string}`;
      semanticRevision: `sha256:${string}` | null;
};
```

The runtime codec narrows every digest template above to exactly `sha256:[0-9a-f]{64}`.

Cross-validation restricts ledger summaries to schema 1 or 2 with both revisions, canonical
manifest summaries to schema 1 with both revisions, exact legacy manifest summaries to null schema
with both revisions, and lock summaries to schema 1 after repair. A noncanonical/unsupported lock
before-image may have null schema and semantic revision but must retain its exact byte revision.
After-images are always present and canonical. `migrate-ledger` is 1 -> 2,
`migrate-project-config` is null -> 1, and `write-lock` targets a schema-1 lock.

A result has exact keys `operationId`, `outcome`, and `error`; outcome is `changed`, `unchanged`, or
`failed`. Changed/unchanged require `error:null`; failed requires a sanitized exact
`{code,message,remediation}` object. Preview has operations and zero results. Execution results
correlate one-to-one in operation order. `mutation` equals the application outcome summary and is
cross-validated against mode/operations/results.

Mutation cross-validation is exact. Counters are nonnegative safe integers. `not-requested` always
uses `none` with all counters zero. Preview with N operations uses `preview`, `planned:N`, and zero
changed/unchanged/failed; a zero-operation preview uses `none` with zeros. A completed nonempty
execution uses `applied`, `planned:N`, exactly N results, and changed/unchanged/failed counters equal
their result outcomes and sum to N; zero-operation execute uses `none` with zeros. A cancellation
before execution emits the normal exit-130 error contract. Cancellation after execution begins
stops new operations at the next durable boundary and also emits exit-130 error output rather than
a misleading partial health@2 value; already committed work remains truthful durable state and the
remediation is to rerun doctor/status. No partial DTO is presented as a complete one-to-one batch.

Exit handling uses exact finding correlation rather than changing the original counts. Without fix,
every finding is unhandled. In preview, a finding is provisionally handled only when its ID is
referenced by a valid planned operation. In execution, it is handled only when every referencing
operation returns changed or unchanged; a failed/missing result leaves it unhandled. The command
fails for any failed repair result or unhandled error finding, and under `--strict` for any unhandled
warning. Thus a repairable-only preview can exit 0, successful repair does not fail because of its
pre-repair finding, and nonrepairable or failed-repair findings retain their normal failure effect.

The mapper owns and redacts every value before codec validation. Health@2 receives an explicit
Zod-free declaration facade and public-contract inventory tests. No v1-to-v2 migration is
registered because these are output contracts, not persisted input.

Human doctor output renders findings first, then the same ordered preview/result facts and summary.
It uses stable action words, emits `No repairs needed` only for the clean fix no-op, emits
`No automatic repairs available` when unhandled findings have no operation, never prints raw
artifact bytes or backup content, and preserves diagnostics/stderr discipline. Check continues to
use its existing health@1 human/JSON behavior.

## Test-first and fixture partitions

The two existing required selectors, signed status TS04 and P3B-TS03, are replayed green before new
tests. Doctor TS01..TS06 do not yet exist and are created as honest failing selectors. P3B-TS04 is
created and fails only on missing G3B-03 behavior. No red may be a missing
module, syntax error, todo/skip, fake command, impossible fixture, unbounded wait, public undo, or
G3B-04 repository fault seam.

P3B-TS04 owns the dense foundation matrix:

- absent versus zero/whitespace/truncated/malformed/wrong-kind/newer ledger behavior;
- v1 read-only and dry-run byte identity, visible first-mutator and doctor migration, canonical-v2
  equivalence, source-revision staleness, and preserved legacy pair journal identities;
- project-registration derivation across user/project, dev+pinned retention, path changes, and
  unknown supported tool IDs;

The P3B-TS04 worker protocol has a versioned self-check and exact-key plain-data guards. Message
kind, worker role, journal phase, and barrier values are closed; arrays, strings, IPC frames, output,
and reason text are bounded. Each child has at most one pending IPC read. Every message correlates
case, operation, transaction, worker, and barrier IDs before it can release progress. The parent
creates the temporary root plus a worker-only marker; the worker refuses any root/marker/guard it did
not inherit explicitly. Each step deadline is at most 30 seconds, timeout escalates terminate then
kill, every exit is awaited, output is capped, and cleanup runs in `finally`. The worker calls the
real `withLedgerLock` and durable writer. Its injected barrier observer only reports physical
barriers: it cannot replace locking/durability, release production work, or become a production
pause/backdoor.
