# P17-G3A-01 implementation plan

## Outcome and exact scope

P17-G3A-01 adds one immutable, non-mutating correlated status product and the dedicated
`skillsmith status [skill...]` command. The product joins exactly one selected manifest/lock pair,
the canonical v1-or-v2 local ledger projection, and the selected live tool/scope roots under one
closed effective project placement context. After the signed shared preflight resolves project/Git
identity (or the explicit non-Git project fallback below), the status domain reports desired,
locked, ledger, live, recorded verification,
selected-scope shadow, and journal facts without writing, locking, executing a process, accessing
the network, running verification, or reading a clock/ID source.

The primary entities are exactly 13: `COMMAND:status`, `D-008`, `P1-02`, `EWP-P3A-T02`,
`EWP-P3A-T03`, `EWP-CMD-STATUS-TS01..TS06`, `EWP-P3A-TS02`, and `EWP-P3A-TS04`. Required-now and
impacted validations are the same exact eight selectors: the six status command selectors plus
P3A-TS02 and P3A-TS04. Downstream coverage is empty.

The sole direct dependency is signed G2-05. G3A-01 sequentially reuses the signed project context,
artifact discovery/pair selection, manifest/lock/ledger repositories, portable-lock correlation,
adapter registry/inventory, selection provenance, application runtime, exit taxonomy, and wire
registry. It replaces none of those authorities.

Strict exclusions are:

- G3B-03 retains ledger migration execution, reducers/writer, locks, transaction coordination,
  history bounds, recovery, resume, abort, and undo execution. G3A-01 only reads v1/v2, presents
  migration metadata, and describes fixed remediation.
- G3A-02 retains the general agents/list/commands inventory, compact/long modes, fleet-wide
  duplicate analysis, and capability presentation. G3A-01 computes only status-local shadow facts
  for its selected product.
- G5-05 retains the final all-command artifact-option closure. G3A-01 implements the already frozen
  status selector row but does not advance future `EWP-OPT-TS08`.
- No new planner, operation, writer, journal, verification, recovery, mutation, network, prompt,
  approval, or future-command authority is introduced. Operation observation events never become
  durable status state.

## Selected readable context and artifact pair

Status accepts the exact frozen grammar:

```text
skillsmith status [skill...]
  [--file <path> [--lockfile <path>]]
  [-t, --tool <name>]...
  [-s, --scope <system|user|project|managed> | --system | --user | --project | --managed]
  [--check]
  [--json]
```

There is no `--all`, `--dry-run`, approval, force, strictness, batch, repair, verification-run, or
mutation option. Tool selection is repeatable and limited to the four registered tool IDs. Scope is
singular; `--scope` and its four sugar spellings follow the signed consistency relation. Repeated
singular selectors are rejected by the parser. `--lockfile` requires `--file`; the existing pair
resolver continues to reject collision, escape, foreign absolute form, and unresolvable paths.

`selectReadableArtifactContext` is added to the existing artifact-discovery authority and returns
one of these immutable results:

```ts
type ReadableArtifactContext =
  | Readonly<{ readonly state: 'unselected'; readonly reason: 'live-only-scope' }>
  | Readonly<{
      readonly state: 'selected';
      readonly source: 'explicit' | 'discovered-project' | 'project-default' | 'user-default';
      readonly file: string;
    }>;
```

Selection is total and ordered:

1. explicit `--file` wins for every selected scope;
2. an exact project-only selection uses the nearest discovered project manifest, otherwise
   `<projectRoot>/skillsmith.toml`, or `<effectiveCwd>/skillsmith.toml` for explicit project scope
   outside Git with no ancestor manifest;
3. an exact user-only selection uses `$XDG_CONFIG_HOME/skillsmith/skillsmith.toml`;
4. an exact system-only or managed-only selection without `--file` is live-only and selects no
   portable pair because manifest declarations cannot own those scopes;
5. an unscoped invocation uses the nearest discovered project manifest when one exists; otherwise
   a nonnull Git/non-Git ancestor `projectRoot` selects `<projectRoot>/skillsmith.toml` as
   `project-default`; only a context with no project root selects the user manifest as
   `user-default`, whether the selected default path exists or is absent.

A nested discovered manifest selects the portable artifact but never changes the stable project
root or live placement roots. `-C`, Git worktrees, symlink entry paths, and non-Git ancestors all
consume the already-resolved shared project context. The selected file is passed to
`resolveArtifactPair`; its sibling or explicit lock source and both exact resolved paths are
reported. A live-only context represents artifacts as unselected rather than fabricating absent
portable files.

The application layer is the sole pair-resolver owner. It converts the readable context plus raw
CLI `--file`/`--lockfile` inputs through `resolveArtifactPair` exactly once and passes this closed
value to the status reader:

```ts
type StatusArtifactSelection =
  | Readonly<{ readonly state: 'unselected'; readonly reason: 'live-only-scope' }>
  | Readonly<{
      readonly state: 'selected';
      readonly source: 'explicit' | 'discovered-project' | 'project-default' | 'user-default';
      readonly manifestPath: string;
      readonly lockPath: string;
      readonly lockSource: 'sibling' | 'explicit';
    }>;

type StatusProjectPlacementContext =
  | Readonly<{ readonly state: 'unselected' }>
  | Readonly<{
      readonly state: 'selected';
      readonly source: 'shared-project' | 'explicit-non-git';
      readonly root: string;
      readonly identity: string;
    }>;
```

The application projects the resolved pair into newly owned strings before calling the reader. The
reader never sees raw selector or portable-token spelling and never resolves the pair again. It
reads and reports the exact projected paths/source. Full pair portability remains application-local
and is not added to status@1.

The application also freezes project placement identity exactly once. A nonnull shared
`ProjectContext.projectIdentity`/root becomes `shared-project`. Only an exact explicit project-scope
selection with no shared identity uses `realpath(effectiveCwd)` for both root and identity and marks
`explicit-non-git`, matching install/uninstall ledger keys. All other no-project contexts are
`unselected`; an unscoped invocation outside a project does not invent a project root. Artifact
defaulting remains the shared discovery rule based on `effectiveCwd`; it does not define placement
identity. Desired custom-path resolution, ledger project-tree lookup, reported status context, and
live project roots all consume the closed project-placement value.

The single local data location also reuses existing authorities without spelling a home-relative
default: `resolveDataDir({ xdg: ports.xdg }, configuration)` yields the data directory,
`ledgerPathOf(dataDir)` yields the one ledger path, and `storeRootOf(dataDir)` yields the store root
used for store-link classification and retained source-content checks. Status does not duplicate or
hardcode XDG, ledger, or store path policy.

Selected tools use the signed read-command precedence: explicit repeatable CLI tools, then the
effective configuration's tool selection, then all registered tools in registry order. The
application preserves that choice as `explicit`, `effective-config`, or `unbounded-default` rather
than trying to infer it from the resulting four-item array. Selected scopes default to all
contextually readable scopes in signed `SCOPES` order and similarly preserve `explicit` versus
`unbounded-default`. With a selected project-placement context that is all four scopes. Without one
it is exactly system, user, managed: project is omitted from `StatusSelection.scopes`, no project
path/root is resolved or observed, and no project placement row is produced. An exact explicit
`--project` creates the non-Git fallback before scope selection, so project is then readable.

A project-scoped declaration from a selected user or explicit manifest is still decoded as real
portable membership, but is removed by contextual scope availability when project placement is
unselected; its custom path is never resolved. If such declarations are the only candidates,
bounded status and an exact target both return the fixed filter-noop rather than fabricating a null
project identity. A truly all-absent product with nothing removed remains `selected` with zero
entries. This contextual filter performs zero project-root calls.
Explicit targets change `selectionSource` to `explicit-targets`; no targets use `bounded-default`.
`explicit-all` is unrepresentable for status.

Selection preserves the signed scope-first contract. Stage one performs invocation validation and
collects only real decoded manifest/lock/ledger and exact-mappable logical journal membership after applying scope bounds; option,
enum, and cardinality checks are pre-I/O. Stage two applies effective tool/capability bounds, lists
only the selected tool/scope live roots, adds their actual child names/paths, and uniquely resolves
each exact name or canonical placement-path target. A target not resolved after that selected live
listing is usage exit 2 unless a real decoded candidate for that target was removed by contextual
project-scope availability or the tool bound, in which case it is explained exit-0 `filter-noop`.
A lexical `root/target` possibility alone is never membership, so a syntactically valid absent name remains
unmatched. A live-only name under an unselected tool is not probed and cannot justify filter-noop.
No glob grammar is introduced by this group.

Observation is failure-isolated after selection. Unselected scopes, tools, unknown adapters, and
filtered candidates perform no list/stat/read/capability call, so an unreadable Claude managed root
cannot fail `--tool codex --user`. A selected-root failure retains the normal permission/failure
exit. Matching metadata from an unselected portable or ledger row may justify filter-noop but never
authorizes observation of its live root.

A lock entry correlated to a manifest declaration inherits that declaration's tool/scope
qualifiers for filtering. With no declaration, a lock entry correlated to ledger pairs inherits
the union of those pair qualifiers. A lock beside a readable legacy configuration-only manifest
inherits that legacy file's effective tool/scope defaults for filtering only; this can make a
matching lock-only row visible but never creates desired state. Missing legacy defaults fall through
to orphan handling. A truly orphan lock entry is visible only when tool and scope
selection provenance are both `unbounded-default`; any explicit or effective-configuration
narrowing filters it out, even if the resulting value arrays enumerate every known tool and
readable scope. Filtering a Claude-only manifest+lock name with `--tool codex` therefore produces
filter-noop, not a fabricated Codex lock-only drift row.

SKILL.md validity reuses `parseSkillFrontmatter` and the signed placement file predicate. An absent
entry is `missing`. A regular file, or a symlink whose `realpath` ultimately has `pathKind: 'file'`,
is read as bytes, decoded with fatal UTF-8, and passed to `parseSkillFrontmatter`; successful parse
is `valid`, including absent or partial frontmatter. Malformed gray-matter/YAML, invalid UTF-8, a
dangling/file-to-nonfile symlink, or a directory/other node named SKILL.md is `invalid`. Name and
description are not required, directory-name equality is not checked, and adapter/verifier schemas
are never called. Permission/access failures from kind/realpath/read remain actual errors rather
than `invalid`.

An entry name is included exactly when it is present in the selected manifest, selected lock,
ledger top-level user tree, ledger project tree at the exact effective `projectIdentity`, an
exact-mappable selected logical journal, or selected live tool/scope roots. Other manifests, other
ledger project roots, and unselected live roots are
excluded. The full `correlatePortableLock` result is computed once, but report relationship/fact
projection follows the stage-two selection: name-qualified facts for filtered-out entries are
suppressed. The pair-global `manifest-hash-mismatch` fact is retained only when stage two retains
the complete desired/locked name universe. If stage two removes at least one real candidate and
retains none, relationship drift facts are empty, outcome is `filter-noop`, and `--check` exits 0;
zero candidates with nothing removed remains `selected`. Artifact syntax/schema failures
still fail before filtering. This makes filtering diagnostic scope rather than a way for an
unselected Claude-only or orphan lock row to cause Codex `--check` drift.

Relationship display is projected without rerunning correlation: no retained comparable portable
names is `none`, except canonical empty manifest plus absent lock is `missing-lock`; a retained
canonical declaration with absent lock is `missing-lock`; retained
lock-only names are `lock-only`; retained missing/extra facts are `incomplete`; retained stale facts
are `stale`; otherwise a comparable pair is `current`. `missingNames` is exactly the sorted unique
name set from retained `missing-entry` facts. `incomplete` and `stale` each require a nonempty fact
array, so filtering can never leave either state with empty facts or stale missing names. A readable
legacy manifest is explicitly
configuration-only: it reports `sourceVersion: 'legacy'`, `migrationPending: true`, contributes no
desired declarations, and with no lock has relationship `none` and no manifest-only/missing-lock
drift. A lock beside that legacy config remains a real lock-only product. Canonical manifest-only
state retains the normal drift behavior. `summary.migrationPending` is the OR of selected legacy
manifest migration and selected v1-ledger migration; lock state never invents migration.

Placements are the union of selected desired tool/scope intentions, selected ledger pairs, selected
live observations, and exact-mappable logical journal identities. A custom manifest path resolves under home for user scope or the stable
project root for project scope and names the skill directory. A desired-only default-root intention
may retain `path: null`; status does not invent the future mutation destination policy. Ledger and
live paths are always exact canonical paths.

Here and throughout status, canonical placement path means the normalized absolute logical install
path beneath a realpath-normalized placement root, without dereferencing the final placement node.
`StatusLiveObservation.realpath` alone records the dereferenced observed target. Physical-row keys,
exact-path target matching, ledger joins, shadow winner/shadowed paths, and undo argv all use the
logical placement path, so a dev/store symlink joins its ledger placement rather than its target.

A logical journal is exact-mappable only when intent skill/tool/scope are nonnull, its single
mutated live resource resolves to exactly one logical `placementPath`, and a project resource's
machine-bound project root equals the selected project identity (user uses null). Its intent name
and logical path participate in stage-one exact target membership; scope/tool filtering and path
ambiguity use the same rules as other candidates. The journal attaches to the matching physical row
or creates one journal-only row with desired/ledger/live absent, classification absent, and that
nonnull path. A prepared install-from-absent or committed uninstall-to-absent therefore retains its
full journal state/remediation even with no other product member. Selected-context
null/multi-live/multi-resource journals stay in `StatusReport.journals` with reason
`multi-resource` and never invent placement identity; foreign-project journals are excluded below.

Logical `before` uses the unique selected `LiveActualV1Dto`, not the count of all before resource
roles: absent maps to `absent`; present mode dev/pinned maps to that mode; present mode null, missing
unique live actual, or placement mismatch maps to `multi-resource`. A normal transaction that also
records manifest, lock, and ledger before images therefore still reports its meaningful live
before-state.

The physical row key is `(name, tool, scope, projectIdentity-or-null, canonical-path)`. A desired
custom path joins only that exact resolved canonical path. A desired default with `path: null`
attaches to every existing ledger/live candidate having the same name, tool, scope, and project
identity; when no candidate exists it creates exactly one null-path absent intention. Ledger/live
correlation first joins exact canonical paths. Then, for one name/tool/scope/project identity, if
exactly one unmatched ledger path and exactly one unmatched live path remain, status correlates them
into one row whose identity uses the live path and adds `placement-drift`. Every other ambiguity is
left as separate ledger-only/live-only rows; status never guesses. Multiple adapter roots therefore
remain separate by canonical path.

An unknown v2 ledger tool ID is included as a ledger-only row only when
`toolSelectionSource === 'unbounded-default'`; it sorts after registered tools by unsigned UTF-16.
Explicit or effective-configuration narrowing hides it even when the resulting known-tool array
happens to contain all four registered IDs. An unknown tool can never select a live adapter root or
cause an adapter capability call. A truly orphan lock entry is visible only when both
`toolSelectionSource` and `scopeSelectionSource` are `unbounded-default`; otherwise it is filtered.

Entries sort by unsigned UTF-16 name. Placements sort by registered tool order (unknown v2 adapter
IDs after known IDs by unsigned UTF-16), then signed scope order, stable project identity or empty,
then canonical path or empty. Facts use the fixed rank below; string arrays are unique and sorted.

## Live classification, management, and drift

Live physical class is distinct from desired declaration presence and ledger management. A
`--no-save` install with ledger+live state is managed local state that is undeclared; it is not
`unmanaged`. Conversely an ordinary real directory without a ledger pair is physically unmanaged.

Classification is total and ordered:

1. no live path and no ledger pair -> `absent`; no live path with a ledger pair -> `broken`;
2. dangling link, file/special node where a skill directory is expected, missing `SKILL.md`, a
   successfully read but structurally invalid `SKILL.md`, or a live/ledger mode contradiction ->
   `broken`;
3. symlink outside the store -> `dev`;
4. symlink into the store -> `store-linked`;
5. real skill directory with a matching pinned ledger record -> `pinned`;
6. real skill directory without a ledger record -> `unmanaged`.

`brokenReason` is nonnull exactly for `broken` and uses this first-match precedence:
ledger-recorded absence, dangling link, wrong node kind, missing SKILL.md, structurally invalid
SKILL.md, then live/ledger mode contradiction. Read/access failure is still an actual error rather
than a broken reason. Every other classification has `brokenReason: null`.

An untracked external or store symlink retains its useful `dev` or `store-linked` physical class and
receives the table's nonredundant `live-only` fact. A desired but absent placement is `absent`, while
a ledger-recorded missing or invalid placement is `broken`. Existing signed placement classification and inventory
are reused; status adds only the correlated broken/unmanaged interpretation needed by its product.
Recorded verification comes from ledger pinned state and is never freshly executed.

`StatusFact` has only owned normalized scalar fields:

The code order above is the canonical fact rank. Fixed renderer messages are selected by code and
never interpolate an untrusted error. Partial products, lock relationship failures, missing live,
undeclared live, missing ledger, the four drift dimensions, broken live, shadowing/duplicates,
pending journals, and unsatisfied retention are drift. Committed history, migration pending, and
recorded/unrecorded verification labels are informational by themselves.

Code fixes both subject and impact. `manifest-only` is manifest/drift. `lock-only` and every
`lock-*` code are lock/drift. `ledger-only`, `ledger-missing`, and the source/revision/content drift
codes are ledger/drift. `live-only`, `live-missing`, `live-undeclared`, `placement-drift`, and
`broken-live` are live/drift. `shadowed` and `duplicate-live` are shadow/drift. `journal-pending` and
all retention failure codes are journal/drift; `journal-committed` is journal/info.
`ledger-migration-pending` is ledger/info. All four `verify-*` codes are verification/info. No code
may be emitted with any other subject/impact pairing; the strict codec rejects mismatches.

Fact attachment and co-emission are total. `StatusReport.facts` owns only canonical-empty-manifest
plus absent-lock `manifest-only`, pair-global `lock-manifest-hash`, `ledger-migration-pending`, and
facts for unmatched pending journals.
`StatusEntry.facts` owns whole-artifact/name relationship facts: canonical desired plus wholly absent
lock emits `manifest-only`; a lock entry with no canonical manifest authority emits `lock-only`; when
both canonical artifacts exist, retained correlation facts emit `lock-missing-entry`,
`lock-extra-entry`, `lock-source`, `lock-ref`, and `lock-source-path` exactly as applicable. These
three alternatives do not co-emit their umbrella presence code. `StatusPlacement.facts` owns all
local presence, dimensional, classification, shadow, verification, matched-journal, and retention
facts.

For the placement presence table, D/G/L mean desired intention, ledger pair, and observed logical
live node presence after joining. These rows are exhaustive; the listed facts co-emit and no other
presence fact does:

| D | G | L | Presence facts |
|---|---|---|---|
| 0 | 0 | 0 | no row, except one exact journal-only row with no presence fact |
| 0 | 0 | 1 | `live-only` |
| 0 | 1 | 0 | `ledger-only` |
| 0 | 1 | 1 | `live-undeclared` |
| 1 | 0 | 0 | `ledger-missing`, `live-missing` |
| 1 | 0 | 1 | `ledger-missing` |
| 1 | 1 | 0 | `live-missing` |
| 1 | 1 | 1 | none |

The D0/G0/L0 exception exists only for J=1 exact journal identity. It emits no presence fact,
always emits `verify-unrecorded`, and otherwise emits only its journal/retention facts. Pending makes
the placement/entry drift through `journal-pending`; committed is informational and converged when
retention is satisfied or intentionally non-reversible, but unsatisfied/incomplete retention makes
it drift. Journal-only entries and placements count normally in report summary totals.

`broken-live` additionally emits iff classification is `broken`, including ledger-recorded absence
and an untracked invalid node. Thus a ledger-recorded missing row has `live-missing` when declared
or `ledger-only` when undeclared, plus `broken-live`; a no-save ledger+live row has only
`live-undeclared` unless independently broken. Presence never emits a dimensional fact.

Dimensional facts are independent and co-emit in canonical rank only when both compared values are
known and unequal: portable desired/lock relationship emits its three name-field facts; correlated
lock/ledger emits source, revision, and content drift; desired/ledger/live mode or exact logical-path
comparison emits placement drift. Unknown/null comparison data emits no dimensional fact. A
shadowed row emits `shadowed`, each ambiguous duplicate row emits `duplicate-live`, a matched journal
emits exactly its pending/committed code, each unsatisfied retention requirement emits exactly one
code from its aggregate ranked state,
and every placement emits exactly one verify code matching `StatusVerification`.

Each dimension emits at most one fact. Source uses compact canonical JSON tuple
`[host,repository,pathOrNull]`, preserving subgroup/path segments without delimiter ambiguity.
Placement uses compact canonical JSON tuple `[representationOrNull,modeOrNull,logicalPathOrNull]`.
Its expected projection is: representation = desired placement, otherwise ledger placement,
otherwise symlink when ledger mode is dev, otherwise null; mode = pinned when desired is present,
otherwise ledger mode, otherwise null; path = nonnull desired custom path, otherwise ledger logical
placement path, otherwise null. Its actual projection is: representation = live symlink/directory/
file-or-other mapped to symlink/copy/other, otherwise ledger-derived representation; mode = live
class dev->dev, pinned/store-linked->pinned, unmanaged->unmanaged, broken->broken, absent->absent,
otherwise ledger mode; path = live logical placement path, otherwise ledger logical path, otherwise
null. Roots are already normalized, but the final node is never dereferenced.

Representation/path components compare only when both sides are nonnull. Mode compares only when
actual is dev/pinned/unmanaged; broken/absent are carried in the tuple but owned by structural facts.
If any comparable component differs, the one fact carries the complete expected/actual tuples;
simultaneous representation/mode/path mismatches therefore produce one `placement-drift`, not
several. With no comparable unequal component, no placement drift emits. Revision and content use
their exact normalized scalar/hash. Within one fact array, equal
code-rank facts sort by unsigned UTF-16 expected (null as empty), then actual (null as empty), so
multiple journal/retention facts are byte-stable.

Presence fact scalar values are fixed `expected: 'present', actual: 'absent'` for missing facts and
the inverse for `manifest-only`, `lock-only`, `ledger-only`, and `live-only`; `live-undeclared` uses
expected `declared`, actual `undeclared`; `broken-live` uses expected `valid`, actual equal to the
closed broken reason. Dimensional facts carry the normalized expected/actual scalar being compared.
`shadowed` uses expected equal to the winner logical path and actual equal to the current logical
path; `duplicate-live` uses expected `unique` and actual `duplicate`. `journal-pending` uses expected
`committed` and actual equal to its phase; `journal-committed` uses `committed`/`committed`.
Retention facts use expected compact JSON `[resourceIdOrNull,path]` and actual `missing`, `mismatch`,
`unverified`; journal-level `retention-incomplete` uses expected `complete`, actual `incomplete`.
`ledger-migration-pending` uses expected `current-v2`, actual
`source-v1`. Verify facts use expected `recorded` and actual `passed`, `warned`, `skipped`, or
`unrecorded`. The mapper never substitutes prose for these scalar vocabularies.

The existing `correlatePortableLock` result is the sole manifest/lock relationship authority.
Its facts map without reordering: missing/extra entry, manifest semantic hash, source, requested
ref, and source path. Correlated local comparisons are exact:

- source compares the lock canonical source/source path with ledger origin host/repository/skill
  path when both are recorded;
- revision compares lock resolved SHA with ledger origin resolved ref, otherwise pinned `gitSha`
  when nonnull, otherwise pinned `rev`; absence is unknown, not invented drift;
- content compares lock content hash with ledger pinned content hash when both are recorded; G3A-01
  does not hash the live tree;
- placement compares desired symlink/copy intent, ledger mode/path, and observed physical class/path.

An entry is `drift` iff it or one of its placements has a drift-impact fact. Otherwise it is
`converged`. Pair-wide facts such as an empty manifest with an absent lock and ledger migration
metadata live in `StatusReport.facts`; they are not attached to an arbitrary name. Plain status
returns success after a complete product even when drift exists. `--check` returns semantic
drift/exit 7 iff at least one report, entry, or placement fact has drift impact and no actual error
occurred.
`summary.converged`/`drifting` count entry convergence only; pair-global report drift can therefore
produce exit 7 with zero entries and `drifting: 0`, as in canonical empty manifest plus absent lock.

Status-local shadow identity is `(tool, skill-name)`. Only placements with a present or broken live
node participate; desired-only, ledger-only, and truly absent projections cannot shadow. For
selected live user/project placements of the same identity, the current project placement wins and
reports the exact shadowed user path. An absent project intention therefore never shadows a valid
user live placement. Same-tool/same-scope multiple live paths are `duplicate` with no guessed
winner. System/managed collisions and other multi-scope live combinations are also `duplicate`
until G3A-02 supplies general fleet precedence. Different tools never shadow each other.

The runtime codec cross-refines the retention records beyond structural unions: observed revision
kind must equal expected kind; logical role/sourceRole selects the exact content domain below;
legacy structural kind/literal-link-target and hash checks follow the compatibility table; aggregate
requirement state equals the fixed path/structural/revision/content rank; and `satisfied` is
impossible unless every recorded check is satisfied.

A matching pending legacy pair journal or v2 logical transaction always wins over committed
history. Logical eligibility requires exact intent skill/tool/scope and either a matching live
resource path or a multi-resource operation that names the placement; legacy eligibility comes
from the exact ledger pair. Matching candidates sort by effective timestamp descending
(`updatedAt`, otherwise `startedAt`), transaction ID ascending, then format rank logical before
legacy. The first candidate wins; another matching candidate is `superseded`, a nonmatching
exact-placement candidate is `unselected-placement`, and a journal spanning or not mappable to one
placement is `multi-resource`. The same ordering selects committed history only when no pending
candidate exists.

Journal candidates are bounded before precedence: selected tool, scope, effective project identity,
name target, and exact path target apply first. Foreign-project, unselected-tool/scope/name, and
unselected exact-path journals are omitted from entries and `StatusReport.journals` and emit no
fact. Within the bounded product, losing matching candidates are `superseded`; a selected-name
candidate that cannot attach to the selected placement is `unselected-placement`; a selected
multi-resource intent is `multi-resource`. `unselected-placement` is excluded under an exact-path
target. Every retained unmatched pending journal emits report-level `journal-pending` drift;
retained committed history is informational. Thus out-of-context journal state can never change
selection outcome, summary, or `--check`.

Both pending and committed projections retain the owned before-state label. Pending reports resume
as fixed prose and expose abort as the exact argv
`['skillsmith', 'undo', canonicalPlacementPath, '--tool', tool, '--scope', scope]` only when
eligible; otherwise abort is null. A journal attaches to a placement only through an exact nonnull
logical resource path, so the path target remains unambiguous with duplicate name/tool/scope roots.
Committed state is labeled `reverse committed`; its reverse argv uses the same exact-path shape.

Logical requirements enumerate `actual.retained` in signed order and preserve every signed
`resourceId`, role/sourceRole, path, `repositoryRevision`, content hash, and nullable `retainUntil`.
Status reports deadlines without reading a clock or deciding expiry. Path, repository revision, and
content are checked independently. Repository observation preserves the expected revision kind and
uses `hashCanonicalInput('resource', 1, canonicalInput)`: artifact/file input is exact bytes; a
logical symlink resource is compact JSON `["symlink",literalReadLinkTarget]`; a directory resource
is the serialized `projectSourceContent` projection. Content observation is role-specific:
manifest backup uses `hashManifestBytes(exactBytes)`; lock backup validates canonical bytes then
uses `hashCanonicalInput('lock-canonical', 1, exactBytes)`; ledger backup uses
`hashCanonicalInput('resource', 1, exactBytes)`; directory live backup/store uses
`hashSourceContentV1(projectSourceContent(path))`; symlink live backup hashes source content at its
realpath-resolved directory target while its repository revision still hashes the logical link.
Wrong representation makes only the affected check unverified. Eligibility requires both signed
repository and content checks; matching one never compensates for mismatch/unverified in the other.

Logical intent gates precede retained checks:

| Journal state | Intent/before condition | Eligibility before hash checks |
|---|---|---|
| pending, any phase | before `absent` | `eligible`; removing new/staging state restores absence |
| pending `prepared`/`staged` | before `dev`/`pinned` | `eligible` only while current live matches before; no retained resource required yet |
| pending `backed-up`/`live` | before `dev`/`pinned`, intent `none` | `not-reversible` |
| pending `backed-up`/`live` | reversible/conditional | declared and retained ID sets must be equal |
| pending, any phase | before `multi-resource` | `not-reversible` |
| committed | intent `none` | `not-reversible` |
| committed | reversible/conditional | declared and retained ID sets must be equal |

Any failed structural/before-state condition in this table maps to `not-reversible`; its underlying
placement/classification mismatch still emits the normal local drift fact.
An unequal required ID set is `retention-incomplete`; this makes argv null even when the projected
retained array is empty. Once the gate passes, all requirements must be satisfied. Requirement-state
rank is missing, then mismatch, then unverified. Journal eligibility therefore ranks
`not-reversible`, `retention-incomplete`, `retention-missing`, `retention-mismatch`,
`retention-unverified`, then `eligible`; `not-reversible` adds no retention fact (a structural cause
already has its local drift), while the four retention failures are drift. Each retention failure
emits its exact fact and makes argv null.

Legacy requirements are structural when the v1 journal recorded no digest; absence of a hash alone
never becomes unverified. The compatibility table is exact:

| Legacy phase | Before `absent` | Before `dev`/`pinned` |
|---|---|---|
| `prepared`/`staged` | backup absent; live/staging may be removed | backup absent; live matches recorded kind/target; staging is disposable |
| `backed-up` | backup absent; live/staging is disposable | exactly one recoverable before image at live or backup; staging is disposable |
| `live` | backup absent; live/staging is disposable | backup contains the recoverable before image; live/staging is disposable |
| `committed` | install is not reversible; uninstall requires backup | promote requires recorded dev source; dev requires pinned store; other combinations are not reversible |

For a recoverable legacy symlink, exact literal target equality is sufficient; it is not forced
through source-content hashing. For a recoverable pinned directory with recorded content hash, the
selected live/backup directory is checked with `hashSourceContentV1`; committed dev reversal checks
the recorded pinned store path/content hash. Missing, mismatched, or unreadable required paths block
argv under the same aggregate rank. A committed uninstall backup is structurally eligible when its
recorded before kind/target matches because v1 recorded no backup digest. The renderer prints
structural expected/observed kind/link target, resource IDs, both hash/revision checks, paths, and
null/non-null retain-until values, shell-quotes nonnull argv,
and JSON retains exact arrays/null. Status registers or executes none of those commands.

Retention proof is deliberately secondary status data. A required path proven absent is `missing`;
a present path whose retained hash cannot be safely reproduced for any reason—including EACCES,
unstable metadata, unsupported node content, or a source-content projection failure—is
`unverified`, with observed hash null and remediation null. Plain status still renders at exit 0 and
`--check` exits 7 for that drift. Permission exit 6 remains for primary selected manifest, lock,
ledger, or live/SKILL observation, where no partial product may render. Cancellation remains 130 at
every stage and is never converted to unverified.

## Read order, errors, and byte identity

Option enum/cardinality/scope/pair syntax validation occurs before content discovery. The status
reader then performs deterministic manifest, lock, ledger, and live reads in that order. Artifact
absence is data; manifest-only, lock-only, ledger-only, live-only, and all-absent products complete
normally. Only a missing ledger is empty. Existing zero-byte, whitespace-only, invalid UTF-8/BOM,
truncated, malformed, schema-invalid, or newer-version ledger input is state error 3.
After primary live observation, retained resources are probed in their displayed requirement order;
logical order is signed `actual.retained` order and legacy order is backup then store.

An unreadable dimension never becomes absence or drift and no partial product is rendered:

- invalid manifest, lock, or ledger -> state 3;
- permission/access failure -> permission 6;
- selected known tool without required read capability -> capability 4;
- other inventory/content observation failure -> failure 1;
- invalid selector, option, scope, tool, or unmatched explicit target -> usage 2;
- cancellation -> 130.

Cancellation wins. Otherwise the signed numeric actual-error precedence 6, 5, 4, 3, 2, 1 beats
drift 7, which beats success. Because invocation-level validation is pre-I/O and artifact reads are
sequential, status normally returns the first encountered single error; the shared selector still
governs any accumulated live-read failures.

All successful, drift, filter-noop, and refused paths are read-only. After the existing shared
project-context preflight has resolved Git/worktree identity, the focused status domain receives no
process capability. Its tests trap every write, rename, remove, directory creation, symlink, copy,
fsync, lock, subprocess, HTTP, clock, and ID capability; project-context compatibility separately
permits only the signed preflight Git read. They hash manifest, lock, ledger, and live fixture bytes
before and after human, JSON, and check reads. A permission failure while inspecting or reading
`SKILL.md` is exit 6; another read failure is exit 1; neither is classified as broken or rendered as
a partial product. Hostile port throwables—Errors, primitives, accessor/coercion objects, and
proxies—map to fixed secret-safe errors without inspecting a message, cause, stack, getter,
coercion, or trap.

## Application, command, and rendering boundary

`runStatusApplication` joins the existing current read-service registry. It validates the exact
tool/scope/target request, resolves the shared project/context and selected artifact pair, calls
only the focused status reader, and returns `NO_MUTATION`. The generic declarative runtime attaches
the new current-state command; no command-local `commands/status.ts`, program branch, adapter
branch, or alternate runtime is added.

The evolving current-state contract gains the target-registry status rows atomically. Historical
0.7.0 snapshots, the frozen target registry, and the migration ledger are not rewritten. Command
metadata freezes:

- group `discover`;
- primary question `How do desired, locked, ledger, and live states relate?`;
- application/report kind `status`;
- examples `skillsmith status` and `skillsmith status review --tool codex --check`;
- exits 0 successful report, 1 observation failure, 2 usage/unmatched target, 3 invalid artifact,
  4 unavailable read capability, 5 source failure if a signed read dependency reports it, 6
  permission failure, 7 successful drift check, and 130 cancellation.

source, tool source, scope source, outcome, and the fixed filter-noop reason when present, followed

coarse signed selection layer; detailed per-key configuration path provenance remains config output
and is not duplicated here. Human and JSON render the same five selection values for explicit
targets, bounded default, effective-config tools, and filter-noop.
