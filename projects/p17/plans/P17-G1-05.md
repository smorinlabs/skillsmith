# P17-G1-05 implementation plan

P17-G1-05 replaces independent supported, writable, and verification tool lists plus generic
tool-name conditionals with one validated executable tool-adapter registry. Its primary IDs are
`COMMAND:verify`, `EWP-CF-007`, `EWP-CF-036`, `EWP-CMD-VERIFY-TS01` through
`EWP-CMD-VERIFY-TS04`, `EWP-P1-T11`, `EWP-P1-TS09`, and `P2-06`.

The formal dependency, P17-G1-03, is signed off. P17-G1-04 is also signed off and constrains this
group: inventory and verification bundles retain focused ports, no aggregate `ScanEnv` dependency
returns, and registry construction is pure. Required-now validation is exactly the four verify
command contracts plus `EWP-P1-TS09`. `EWP-CMD-AGENTS-TS03`, `EWP-P3B-TS06`, `EWP-WF01`,
`EWP-WF05`, and `EWP-WF07` remain downstream-only.

ADR 0007 records the registry decision. ADR 0006 remains reserved for the later immutable
snapshot/planner/repository decision; numbering follows the canonical architecture plan rather
than implementation order.

## Frozen registry contract

- A `ToolDescriptor` owns immutable `id`, deterministic `order`, positive-safe-integer
  `capabilityVersion`,
  per-operation support, scope support, verification modes, and stable capability/remediation
  facts. The exact built-in order is Claude Code, Codex, Kilo Code, OpenCode.
- The baseline operation matrix distinguishes detection, skill inventory, command inventory,
  diagnostics, install, uninstall, dev, promote, undo, static verification, deep verification, and
  desired-state plan/apply/sync/update. Claude Code and Codex support the full lifecycle; Kilo Code
  and OpenCode support detection/inventory/diagnostics only. Known unsupported operations produce
  capability exit 4; unknown IDs remain usage exit 2.
- All four initial descriptors have `capabilityVersion: 1`; identity is the pair
  `<id>@<capabilityVersion>`, so different IDs may legitimately share version 1. Detection is
  unscoped. Skill inventory, command inventory, and diagnostics support exactly `user`, `project`,
  `system`, and `managed` for all four tools. Static/deep verification uses the explicit `artifact`
  scope and is supported only by Claude Code and Codex. Install, uninstall, dev, promote, undo,
  plan, apply, sync, and update support exactly `user`, `project`, and `custom` for Claude Code and
  Codex and no scopes for Kilo Code or OpenCode. A supported operation must have a nonempty exact
  scope set unless its contract is explicitly unscoped.
- Every adapter has one cohesive inventory bundle containing current detection, roots, and plugin
  directory behavior. Verification, placement, and adaptation are optional bundles. Verification
  bundles own verifier dispatch, verified-against version, mode coverage, gate policy, and rendered
  verification facts. Placement bundles own standard/current/legacy roots, placement discovery,
  duplicate and legacy notices, and lifecycle placement policy. Adaptation remains optional and is
  absent from the four current built-ins.
- `createToolRegistry(adapters)` validates before freezing. It rejects duplicate IDs, duplicate
  order, duplicate adapter identity (`id@capabilityVersion`), malformed versions, descriptor/bundle
  drift, declared verification without a verifier, declared mutation without placement, bundles
  whose operations are not declared, and any mutation bundle on a descriptor declared read-only.
  Capability versions need not be globally unique across different tool IDs.
- Registry lookups and derived projections preserve descriptor order. Adding a fixture read-only or
  write adapter changes generic choices, capability views, and dispatch without editing a generic
  coordinator, renderer, schema owner, or selection validator.

The registry is the sole source for built-in IDs/order, capability facts, verifier availability,
verified-against versions, and mutation availability. `SUPPORTED_TOOLS`, `VERIFY_TOOLS`,
`FLIP_TOOLS`, `VERIFIED_AGAINST`, the public 1.x `Agent` record, and `registry` remain compatible
exports but are derived projections. CLI option/completion metadata, configuration enums, migration
ledger choices, selection policies, verification dispatch, and JSON enum schemas consume those
projections; they do not retain independent built-in arrays.

Generic application, acquire, placement, verification, scan, selection, and renderer modules may
not branch on the four known IDs. Adapter-owned modules may name their own ID. Existing
tool-specific behavior moves behind bundle operations or is returned as structured facts, including
Codex current/legacy roots, duplicate notices, install/promotion verification policy, and the
Claude deep-presence label. Current report and JSON bytes remain unchanged.

Executable static gates cover TypeScript policy values and conditionals in current generic modules.
They explicitly exempt adapter-owned literals, immutable Phase-0/current/target JSON snapshots,
wire goldens, fixtures, documentation, comments, and examples as non-authoritative data. Runtime
derivation and routed fixture operations—not text absence alone—prove the single authority.

## Current verify behavior

`verify <path>` retains plugin and bare-skill target resolution, isolated wrapper creation and
cleanup, static default, additive deep mode, strict warning promotion, repeatable explicit tools,
human/JSON rendering, global `-C`/configuration behavior, live version reporting, and cancellation.
The default set is registry-derived Claude Code plus Codex. Deep requests dispatch static and deep
to both bundles. Automatic absence is tolerated when another requested verifier ran; explicit
absence, no verifier running, or requested deep not running is capability exit 4. Findings exit 1,
usage exits 2, cancellation exits 130, and failure outranks a simultaneous capability gap.

Kilo Code and OpenCode are known names but have no verification bundle. Explicit verification for
either returns the registry-defined capability result rather than an unknown-tool usage error.
Deterministic fake bundles prove static/deep dispatch in the required PR suite; environment-gated
live Claude/Codex tests remain supplementary.

`EWP-P1-TS09` is test-first and covers seven executable families:

1. exact four-tool order, operation/scope matrix, and public capability facts;
2. ID/order/version uniqueness and descriptor/bundle construction rejection cases;
3. derived parity for public compatibility arrays/records, CLI and completion option metadata,
   configuration/schema choices, help facts, capability facts, and verified-against versions;
4. read-only and write fixture adapter registration without generic source edits;
5. known read-only mutation/verification capability exit 4 versus unknown usage exit 2;
6. Claude Code and Codex static-plus-deep bundle dispatch and preserved gate policy; and
7. scoped static bans on independent built-in arrays and known-ID branches in generic modules.

The four command-contract selectors add positive and adversarial current-behavior coverage:

1. TS01: plugin, bare skill, missing, and invalid targets; wrapper byte copy and finally cleanup;
   target recognition and wrapper manifests derive from a registered fixture verifier, making the
   selector red against the current hard-coded Claude/Codex manifest recognition;
2. TS02: automatic/explicit selection, absent tools, both static-plus-deep bundles, and known
   unsupported Kilo/OpenCode capability results;
3. TS03: strict severity plus 0/1/2/4/130 exits, failure-over-capability precedence, and one shared
   exit-policy owner across the application and retained CLI compatibility helper; the current
   duplicate selectors make this authority clause red; and
4. TS04: human/JSON/global-context parity, exact current v1 output, and live-version exact/drift/
   unknown/not-installed behavior without verdict drift; checked-against versions and schema tool
   choices must derive from injected descriptors, making the current static maps red.

Thus all five selectors are genuinely red for named missing production authority while retaining
characterization-green clauses for already shipped behavior; missing files alone are never accepted
as the test-first receipt.

Implementation proceeds in seven ordered slices:

1. Commit the five genuinely red selectors while the current focused verify baseline remains green.
2. Add ADR 0007 and freeze descriptor, bundle, registry-builder, capability, and compatibility
   projection types before parallel migration.
3. Register all four built-ins, derive the legacy `Agent`/tool/version views, and move verifier
   dispatch plus current verify policies behind verification bundles.
4. Move placement roots, discovery, legacy notices, gate policy, and rendered facts behind placement
   bundles; remove `FLIP_TOOLS` literals and generic known-ID branches without changing behavior.
5. Derive selection, configuration, CLI/completion/migration metadata, and current schema enums from
   registry projections; expose stable capability facts for later agents/help/planner consumers.
6. Register read-only and write fixture adapters and close descriptor/bundle and generic-branch
   static gates.
7. Run every required selector, current verify/core/CLI and placement/acquisition regressions, full
   `bun run check`, fresh independent adversarial review, and traceability closure.

After red and interface-freeze commits, parallel ownership is disjoint. Root owns docs/ADR,
registry contracts/builder, public exports, shared application/CLI integration, catalog, evidence,
and commits. A verify owner may change verification bundles/run/types and verify tests. A placement
owner may change built-in placement bundles and acquire/place modules. Shared agent registry,
selection, schema, and public files remain root-owned until the interface commit.

Prohibited scope: final `agents --capabilities` command bytes (`EWP-CMD-AGENTS-TS03`); saved-plan
capability fingerprints and planner staleness (`EWP-P3B-TS06`, `EWP-WF01/05/07`); ADR 0006
snapshot/repository work; G1-06 DTO/codec or JSON redesign; G1-07 operation observation; Phase-2
manifest/lock implementation; Phase-3 planner/status behavior; Phase-6 generated help/manual work;
P3 adapters; new verification modes; removal of 1.x public compatibility exports; and any change to
current report bytes, journals, prompts, exits, or lifecycle semantics.
