# P17-G5-01 Ready plan

## Outcome and immutable scope

G5-01 adds the approved narrow `skillsmith sync --from <scope|path> --to <scope|path>` command for
direct live-location reconciliation. Source state is always read-only. Destination changes are
additive by default, `--delete` is the only destination-only removal authority, `--force` replaces
only an already-selected conflicting destination placement under the existing backup/journal
policy, and `--save` additionally updates one exact destination manifest/lock pair through safe
merge. Sync projects its request and observations into the existing pure placement planner,
artifact planner, deterministic scheduler, execution coordinator, artifact-pair authority, and
placement swap/recovery engine. It does not introduce a synchronization engine, operation kind,
writer, transaction coordinator, journal, scheduler, or artifact schema.

The immutable primary scope is exactly 17 entities:

- command contract `COMMAND:sync`;
- accepted decision `D-007` and retained recommendation `P1-10`;
- phase tasks `EWP-P5-T01` and `EWP-P5-T02`;
- command selectors `EWP-CMD-SYNC-TS01` through `EWP-CMD-SYNC-TS10`;
- phase selector `EWP-P5-TS01`; and
- workflow `EWP-WF10`.

The required-now partition is exactly 12 validations: the ten command selectors, P5-TS01, and
WF10. `EWP-WF13` is the sole downstream obligation and remains primary in dependency-complete

## Endpoint contract

Both `--from` and `--to` are mandatory singular values. Each accepts one canonical scope token or
one path:

- `user` selects the current user's adapter roots;
- `project` selects the effective current `ProjectContext`;
- `system` and `managed` are recognized read scopes, valid only as a source when the selected
  adapter exposes readable inventory there;
- any other value is a path resolved relative to the one top-level effective cwd, then through the
  existing project-context resolver; its exact canonical project root/effective cwd becomes a
  project endpoint; and
- a destination must resolve to writable `user`, `project`, or path-derived project scope.

Missing values, repetition, absent/non-directory paths, unreadable roots, destination
system/managed scope, and unsupported adapter capability fail before mutation. A path spelling is
never interpreted as an artifact path or a custom skill root. `--file` and `--lockfile` remain the
separate destination artifact pair when `--save` is present.

Endpoint identity is frozen before inventory reads. A user endpoint is keyed by its canonical user
roots; a project/path endpoint is keyed by its resolved project identity and canonical root.
`from` and `to` must differ. Symlink aliases, equivalent scope/path spellings, or selected tool
roots that collapse onto the same real location refuse before planning so sync can never stage a
write inside its own source. The source context is never substituted for the command's global
configuration/artifact context, and no process cwd mutation is permitted.

Path endpoints cover project-A to project-B/C workflows. They do not create project directories,
search the home tree, crawl for manifests, or broaden a missing endpoint into user/global scope.

## Selection and pair model

Positionals are skill-name/glob filters over the source inventory. With no positionals, the
mandatory endpoints bound every selected source entry and the report uses
`selectionSource = "bounded-default"`. With positionals, the report uses
`selectionSource = "explicit-targets"`; duplicates are normalized deterministically. There is no
`--all` spelling.

The exact selection rules are:

1. resolve and validate both endpoints and all option relations;
2. resolve the registry-ordered tool set and require source inventory plus destination sync
   capability for every selected tool;
3. observe the complete selected source and destination root membership;
4. apply positional and tool filters only to the source set;
5. treat a valid filter-to-zero result as an explained exit-0 no-op; and
6. never infer deletion from a missing target, unmatched glob, tool filter, or empty source match.

An ambiguous source identity, duplicate runtime winner, aliased root, or unreadable member is an
invocation-level refusal, not a force candidate. A selected source skill is one operation group.
All selected tool pairs for that destination skill report within the group; each pair has an exact
source member, destination member, content observation, and capability fact.

Targetless `--delete` additionally selects destination-only names within the complete endpoint and
tool boundary. Explicit-target mode never converts an unmatched source name into a destination
deletion; this preserves the accepted filter-to-zero rule. Destination-only removal is therefore
possible only from a complete bounded source view plus explicit `--delete`. Each removal remains
one destination-skill group.

## Source observation and byte identity

G5-01 extracts a command-neutral live-fleet observation seam from the signed export reader. Export
continues to request portable proof; live-only sync requests only immutable inventory, ledger,
placement, content, and collision facts. `--save` additionally requests the existing exact portable
proof. This avoids a remote resolution/fetch in ordinary live-only sync and avoids a duplicate
filesystem scanner.

Every selected source member records:

- runtime name, tool, scope, root/path/realpath, placement representation, and visibility;
- exact canonical live content hash, with symlink targets read through a stable realpath;
- the matching ledger pair and pending-journal state when present;
- a source-selection membership hash; and
- only for save, the existing credential-free portable candidate proof from exact managed Git or
  clean Git-dev content.

Source membership and content are execution preconditions on the operations that consume them.
They are reobserved immediately before the applicable group executes. A source change, disappearance,
alias change, selection change, pending journal, or cancellation refuses/fails that group without
writing the source. `--force` cannot authorize any source change.

For live-only sync, a managed, dev, dirty, non-Git, or unmanaged source may supply its exact current
bytes if it is otherwise a valid skill tree. Its logical source uses the existing machine-bound
`local-dev` operation-source variant; this does not imply a symlink destination. For `--save`, every
selected source group must collapse to one exact portable declaration/lock identity across its
tool members. Any unmanaged, dirty, non-Git, mixed-origin, mixed-content, unsupported-scope, or
otherwise nonportable selected member refuses the whole invocation before artifact or live writes.

## Destination planning and operation equivalence

Sync adds a `sync` request/intent variant to the existing pure snapshot-bound placement planner.
The sync module prepares observations and delegates; it does not construct executable operation
semantics independently. The planner emits only existing operation kinds:

- absent destination: `install`;
- managed destination needing content or representation convergence: `update` or `repair`;
- selected differing unmanaged/edited/external destination: a bounded conflict on the applicable
  install/update operation;
- destination-only selected by `--delete`: `remove`; and
- exact destination content/representation: a `noop` diagnostic with no executable live operation.

The destination after-image is an independent store-backed copy or symlink according to exact
portable placement when one exists; a nonportable live-only source defaults to a copy. It never
links the destination directly to the source endpoint. Source material is snapshotted through the
existing immutable store writer and installed through the existing placement swap. A portable
source retains exact canonical origin/SHA/source-path facts in the destination ledger. A
nonportable live-only source produces a normal pinned store/placement record with no fabricated
portable origin; the existing optional-origin ledger shape already represents this state.

The internal `SwapPlan.install` input therefore permits `origin: null` only for a sync operation
whose logical source is machine-bound. The durable ledger schema already makes origin optional.
The swap writer, before/after images, recovery, backup policy, and installed portable origin
behavior remain unchanged. A null origin cannot be serialized into a manifest/lock or presented as
portable provenance.

The durable logical journal must retain that same truthful machine-bound source. The shared
artifact plan codec therefore separates its existing saved-plan matrix from a narrow runtime-
journal matrix:

- saved plans continue to require portable sources for `install` and `update`, byte-for-byte and
  semantically preserving the signed saved-plan contract;
- runtime journals may use `local-dev` for `install` or `update` only when the after-image is a
  pinned copy, has no link target, and its exact content hash equals both the operation source and
  staged store content;
- local journal install starts from an absent live image; local journal update starts from an
  existing selected placement; all normal scope, mutation, identity, before/after, and conflict
  matrix rules still apply; and
- signed promote behavior remains unchanged; it is not admitted to the new local install/update
  case and its existing compatibility representation is retained.

The swap adapter writes no synthetic host, repository, ref, or origin for that case. The staged
pair omits `origin`, and same-operation reconstruction uses its pinned/store record plus the exact
local source retained by the logical journal. Journal decode, ledger round-trip, crash resume, and
ambiguous-residue refusal therefore remain on the existing version-1 journal/version-2 ledger and
placement recovery formats. No ledger codec, journal codec, recovery format, operation kind, or
persisted saved-plan capability is widened.

The operation group ID is derived with command `sync`, the selected destination skill, source
identity/content, destination scope/root, and stable endpoint identity. Each tool pair receives the
normal deterministic pair/operation identities. `createOperationPlan`, canonical ordering,
precondition validation, batch scheduling, and result construction are shared without a sync-only
sort or execution loop. EWP-CMD-SYNC-TS10 directly compares the sync projection against the shared
planner operations and statically rejects a duplicate coordinator/scheduler/writer/planner.

## Conflict, force, delete, and approval

A differing selected destination placement is a conflict. Without force it produces a stable
refusal and no write for that pair. With `--force`, only that exact already-selected destination
may be backed up and replaced. Force never:

- changes endpoint, target, tool, or group selection;
- resolves source ambiguity or source change;
- implies `--delete`, `--save`, `--yes`, or no-prompt;
- bypasses capability, portability, artifact merge, precondition, journal, retention, or
  cancellation safety; or
- converts a failed group/batch to success.

Forced replacement reports the existing closed force projection: requested/applied, conflict type,
exact destination, normal and forced behavior, and required backup. Edited or unmanaged backups are
retained under the already-signed policy. A supplied force flag with no applicable conflict reports
unused and changes nothing.

Delete is an independent selection authority. It removes only exact destination members proved
extra against a complete selected source endpoint; force cannot widen it. Managed exact removal
uses the normal journal/retention path. An edited/unmanaged destination-only member remains a
bounded conflict and requires force in addition to delete. Filter-to-zero never deletes.

Approval is required for a nonempty plan that contains more than one destination-skill group, any
delete, or any forced replacement. A single additive nonconflicting destination group follows the
same prompt-free policy as a normal single install. Interactive approval displays the exact group
and operation IDs; noninteractive execution requires `--yes` when approval is required.
`--no-prompt` never approves. Approval refusal/cancellation happens after the full immutable plan
is known but before locks or writes. `--yes` conflicts `--dry-run`; force/delete/batch remain valid
in dry-run because they change the preview.

## Save and safe artifact semantics

Without `--save`, sync does not select, read, validate, or write a manifest/lock pair. `--file` and
`--lockfile` are usage errors in this mode. This preserves live-only operation even when unrelated
portable state is absent, malformed, or multiply owned.

With `--save`, sync selects exactly one destination pair:

- explicit singular `--file`, with sibling lock by default;
- optional singular `--lockfile`, requiring `--file`;
- otherwise the user default pair for a user destination; or
- otherwise the destination project/path context's discovered/default pair.

Artifact selectors resolve from the top-level effective cwd and never relocate either live
endpoint. The selected pair and selection source are exact in human/JSON output. Exact legacy
destination configuration adds the existing visible `migrate-project-config` prerequisite. Mixed,
empty, malformed, future, or incoherent manifest/lock state refuses before writes.

Save uses the existing portable classifier, lossless manifest editor, lock builder/serializer,
artifact image/precondition logic, artifact-pair controller, and coordinator. Source portable
candidates are projected to the destination scope/tools while retaining canonical source,
requested ref, resolved SHA, source path, content hash, placement, and portable custom path facts.
Compatible declarations merge; existing requested refs and unrelated human content are preserved.
Any selected declaration conflict refuses. Live `--force` is never passed to artifact merge and
cannot overwrite a conflicting declaration.

Additive save leaves destination-only declarations and placements unchanged. Save plus delete
removes only destination declaration tools/names corresponding to the exact live removal set and
rebuilds the complete correlated lock. It never deletes the manifest itself. A declaration remains
until every selected tool in that declaration is removed; unrelated tools and declarations remain.

Artifact operations use exact immutable whole-file before/after images per destination-skill group:

```text
portable add/update group:
  migrate? -> write-manifest -> write-lock -> destination live pair operations

delete group:
  destination live removals -> write-manifest -> write-lock
```

Multiple groups selecting the same pair use the signed G4A-04 collision lane. Every later group
names the latest earlier `write-lock` prefix whose exact after-image it observed. An unavailable
artifact prefix dependency-skips later colliding groups under both fail-fast and continue; it is
not independent work. If an additive group's prefix commits and its later live pair fails,
`--continue-on-error` may execute the next group from that durable prefix. Live-only groups remain
independent under the normal batch policy. Execution never rebases edits, replans, or manufactures
a branch-dependent after-image.

## Execution, partial failure, and recovery

The prepared plan is rendered before any mutation. Dry-run returns that exact plan and performs no
locks, prompt, source snapshot, store write, artifact write, ledger write, live write, or backup.
Execution uses the same plan instance.

Save execution holds the signed order through `withArtifactPairExecutionAuthority`: artifact group,
exact artifact members, placement ledger, then the existing live/store transaction mechanics.
Live-only execution holds the existing ledger/live authority without artifact locks. Under those
locks, shared repositories reobserve exact destination revisions and each applicable source
content/membership precondition before staging. Artifact operations bind to the existing
artifact-pair controller; live operations bind to the command-neutral placement lifecycle and
swap/recovery engine. No executor may call the sync observer or planner after approval.

Groups run in canonical destination-skill order. All tool pairs in a started group report. Default
fail-fast labels later independent groups `skipped-after-failure`; `--continue-on-error` schedules
them and preserves nonzero failure. Cancellation always stops. A successful earlier group remains
durable and truthful. Same-command rerun reads fresh state, resumes only an exact compatible
pending logical/physical transaction through the existing recovery authority, and converges or
refuses ambiguous residue. A different operation cannot claim sync residue.

Every destination mutation uses the existing backup/journal/ledger/store transition. There is no
invocation-wide rollback or `--atomic` promise. Retained before-state/store/backup references remain
available for G5-03 undo and G5-04 GC; G5-01 does not add undo/GC selection or retention policy.

## Command grammar and output contract

The live CommandSpec becomes exactly:

```text
sync [skill...]
  --from <scope|path>          required, singular
  --to <scope|path>            required, singular, distinct from from
  -t, --tool <name>            repeatable, registry-ordered
  -f, --force                  bounded destination conflict only
  --delete                     exact destination-only selection
  --save                       select/update destination portable pair
  --file <path>                singular; requires save
  --lockfile <path>            singular; requires file and save
  --dry-run                    non-mutating exact preview
  -y, --yes                    execution approval; conflicts dry-run
  --continue-on-error          later independent group scheduling
  --json                       strict sync@1 report
```

Required/repeated/conflicting relations are registered once and validated before project/tool/
inventory/network/prompt/write activity. Global cwd/config/color/verbosity/no-prompt/debug behavior
remains shared. There is no scope shorthand, all, strict, check, prune, locked, no-save, retry,
atomic, positional manifest, or saved-plan option.

The strict version-1 report is one immutable projection shared by human and JSON renderers:

```ts
interface SyncReportV1Dto {
  readonly schemaVersion: 1;
  readonly kind: "skillsmith.sync";
  readonly command: "sync";
  readonly mode: "dry-run" | "execute";
  readonly state: "ready" | "refused" | "completed" | "partial";
  readonly endpoints: {
    readonly from: SyncEndpointV1Dto;
    readonly to: SyncEndpointV1Dto;
  };
  readonly artifactPair: null | {
    readonly manifestPath: string;
    readonly lockPath: string;
    readonly lockSource: "sibling" | "explicit";
    readonly selectionSource: "explicit" | "destination-project" | "destination-user";
  };
  readonly options: {
    readonly force: boolean;
    readonly delete: boolean;
    readonly save: boolean;
    readonly dryRun: boolean;
    readonly continueOnError: boolean;
  };
  readonly selection: SyncSelectionV1Dto;
  readonly operations: readonly PlanOperationV1Dto[];
  readonly checks: readonly PlanCheckV1Dto[];
  readonly diagnostics: readonly PlanDiagnosticV1Dto[];
  readonly approval: {
    readonly required: boolean;
    readonly outcome: "not-required" | "pending" | "approved" | "refused" | "cancelled";
  };
  readonly groups: readonly SyncGroupResultV1Dto[];
  readonly effects: readonly SyncEffectV1Dto[];
  readonly summary: SyncSummaryV1Dto;
}
```

Endpoint output identifies normalized kind/scope, selected input, and canonical project root when
applicable. Selection records bounded-default/explicit-targets, selected/filter-noop, exact
targets/tools/group IDs, and source/destination membership counts. Group results record skill,
group ID, per-tool source/destination, action, execution outcome, skip/failure reason, stable force
projection, backup outcome, and artifact/live drift. Effects record exact role
`manifest|lock|ledger|store|live|backup`, action, operation ID, destination group, and
planned/succeeded/failed/cancelled/not-run outcome. They never expose raw exceptions, credentials,
unselected roots, journal internals, or source acquisition arguments.

The sync report codec validates operations/checks/diagnostics through the existing strict
`contracts/v1/plan.ts` report projection, as apply already does; this is distinct from the saved-
plan artifact codec and does not copy or weaken either schema. The artifact codec change is limited
to truthful runtime-journal validation described above and leaves its saved-plan matrix unchanged.
The contracts/v1 subpath and root public declarations expose the additive DTO/codec without
changing historical bytes. JSON stdout is one value; diagnostics remain stderr. Human and JSON
report identical selection, operation, force, delete, artifact, scheduling, and exit facts.

Exit classes are: 0 for successful/noop/filter-noop/dry-run; 1 for execution, integrity, or partial
failure; 2 for grammar, endpoint choice, unsafe conflict, missing approval, or nonportable save;
3 for invalid persisted artifact/ledger or stale precondition; 4 for unsupported selected tool or
destination capability; 6 for permission denial; and 130 for cancellation. Cancellation wins;
otherwise any actual 1-6 failure remains nonzero.
