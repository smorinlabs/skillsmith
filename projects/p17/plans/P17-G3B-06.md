# P17-G3B-06 Ready plan

## Outcome and exact scope

G3B-06 completes the Phase-3B consumption side of ADR 0009. The existing immutable
`OperationContext`, closed event registry, failure-isolated `ObservationEmitter`, deterministic
operation plan, coordinator/scheduler, journal-v1 model, placement transactions, and recovery
engines remain authoritative. This group connects those existing authorities without adding a
second observation, workflow, transaction, or recovery framework.

The immutable catalog scope is exactly two primary entities:

- `EWP-P3B-T07` — propagate `OperationContext` through planners, adapters, the coordinator,
  journal, rollback, and recovery; and
- `EWP-P3B-TS07` — the sole required selector for causal lifecycle sequences, correlation,
  attempt identity, observer isolation, and proof events never control state.

The validation partition contains only `EWP-P3B-TS07`. There is no downstream coverage owned by
this group. Signed `EWP-CF-038` remains primarily owned by G1-07 and closes here only through its
recorded secondary group. Signed `EWP-P1-TS11` remains a compatibility selector; its deliberate
Phase-3B deferral checks are narrowed but its primary ownership is not transferred.

Formal dependencies remain exactly signed G3B-02 and G1-07. Signed G3B-03, G3B-04, and G3B-05 are
preservation baselines for journal/recovery, pure planning/repositories, and registry-bound
lifecycle execution. Current commands, options, public reports, wire codecs, human/JSON bytes,
exit behavior, mutation results, durability, rollback, and recovery semantics remain unchanged.

This is authorized, credential-free local work for the open-source Skillsmith CLI. Tests use
hermetic ports, temporary directories, deterministic clocks/IDs, fixture registries, and synthetic
artifacts only.

## Architecture review verdict

The architecture is sound and needs bounded propagation, not a rewrite. The accepted before/after
is:

| Concern | Before | After | Confidence |
|---|---|---|---:|
| Planner boundary | Application owns observation, while pure planners know nothing about it | Planners stay port-free; orchestration emits `plan.created` after a plan returns | 99% |
| Operation identity | Scheduler executes deterministic operation IDs without an observation context | Scheduler derives one child context for each actually started planned operation | 98% |
| Transaction identity | Journals have transaction and intent IDs but synthesize context facts | Existing scalar fields describe a transaction context whose parent is the planned operation | 98% |
| Event ownership | Mutator events are absent | One existing lifecycle authority emits each fact exactly once | 98% |
| Recovery attempts | Some durable paths increment attempts without typed observation | Recovery reconstructs the transaction context and increments once per invocation | 96% |
| API propagation | Internal lifecycle and binding seams omit observation | Optional internal `ObservationBundle` propagation; no public/wire expansion | 97% |

The plan explicitly rejects AsyncLocalStorage, global context, an event bus, middleware/decorators,
a telemetry SDK, an observer queue, a lifecycle/workflow engine, a second coordinator, a new
journal version, persisted event arrays, a generic metadata bag, and public command/report/schema
changes.

## Frozen causal identity hierarchy

There are exactly three context levels:

```text
command context
  operationId = CLI invocation ID
  parentOperationId = null

planned-operation context
  operationId = ExecutableOperation.operationId
  parentOperationId = command context.operationId
  groupId/pairId = planned deterministic IDs

transaction/recovery context
  operationId = LogicalJournalV1Dto.transactionId
  parentOperationId = LogicalJournalV1Dto.intent.operationId
  groupId/pairId = journal intent IDs
```

All three reuse the invocation's focused clock and the same failure-isolated emitter. Observation
identity never participates in plan semantics, preconditions, state revisions, transaction IDs,
journal validation, or result calculation.

### Plan identity

`plan.created.planId` is exactly:

```text
plan:v1:<sha256(canonicalPlanningString(operationPlan))>
```

The helper is pure and private. The plan ID is not added to `OperationPlan`, a public report, a
saved-plan DTO, or any persisted artifact. Re-emitting the same immutable plan produces the same
ID; changing observation context, timestamps, verbosity, or observer behavior cannot change it.

`plan.created` is emitted once after successful plan construction, including an empty or dry-run
plan. A refusal or failure before a valid plan exists emits no plan event. Dry-run emits no
operation, transaction, or recovery events because no binding starts.

### Planned-operation identity

The scheduler owns planned-operation derivation because it alone knows which validated binding
actually starts. It creates the child context immediately before invoking that binding. Cancelled
or `skipped-after-failure` results synthesized for unstarted work receive no fabricated
`operation.started` or `operation.completed` pair.

The operation event kind is the immutable `ExecutableOperation.kind`. Completion maps results as:

| Execution result | Observation outcome | Error code |
|---|---|---|
| `succeeded` | `success` | `null` |
| `failed` | `failure` | sanitized execution error code |
| `cancelled` after start | `cancelled` | `cancelled` |
| `rolled-back` | `success` | `null` |
| `skipped-after-failure` | no event because the binding never started | n/a |

Mutation operation completions set `standaloneCount`, `bundledCount`, and `resultCount` to `null`.
`rolled-back` means the requested rollback operation reached its durable disposition;
`transaction.rolled-back` carries the transaction reason and direction.

The scheduler completes the span in every normal, failed, cancelled, or thrown binding path without
using the span or emitter return value in a decision. A thrown cancellation
(`signal.aborted`, `cancelled`, `ABORT_ERR`, or `AbortError`) completes with outcome `cancelled` and
code `cancelled`; every other thrown binding completes with outcome `failure` and code
`safeErrorCode(error) ?? 'execution-threw'`. The identical semantic error is then rethrown.

### Transaction and recovery identity

The transaction context uses `transactionId` as its own operation ID and the forward semantic
operation ID as its parent. This resolves the signed pending-abort rule without a schema change or
self-parent relationship.

- **Forward:** attempt 1; command/workflow are canonical facts derived from the immutable command
  and operation, independent of observer presence. The existing journal clock supplies persisted
  `context.startedAt`; the transaction event context separately captures fresh event timing.
- **Forward resume:** retain transaction ID, parent, command, workflow, group, and pair; increment
  attempt exactly once per recovery invocation; use fresh event clocks while preserving the
  original persisted `startedAt`.
- **Pending abort/rollback:** retain transaction ID and forward-operation parent; replace
  command/workflow with the validated abort caller; increment once; preserve original `startedAt`;
  change only already-authorized disposition, phase, and context fields.
- **Rollback resume:** retain transaction ID, forward-operation parent, rollback command/workflow,
  and original `startedAt`; increment once per invocation.
- **Post-commit cleanup:** reuse the terminal transaction context and attempt. Do not rewrite
  committed history merely to record observation or cleanup.

New journals unconditionally write `context.parentOperationId = intent.operationId`, whether or not
an observer is supplied. Existing valid journal-v1 records with a null parent remain readable;
event reconstruction uses
`journal.context.parentOperationId ?? journal.intent.operationId`. Backfill occurs only while an
already-authorized pending transaction is being mutated. Committed history is never rewritten only
for correlation. Observation-enabled and observation-omitting callers produce identical new journal
bytes under the same deterministic transaction ports. This group intentionally corrects incomplete
parent/attempt bookkeeping; it does not promise byte identity with the pre-G3B-06 incomplete bytes.

One narrow internal `beginTransactionRecoveryAttempt` primitive updates a pending logical journal
and its matching physical shadow together. It does not weaken `advanceLogicalTransaction` identity
checks and does not create a second recovery authority.

## Single event ownership

Every lifecycle fact has one owner:

| Event family | Sole owner |
|---|---|
| `command.*` | existing shared CLI runtime; unchanged |
| `plan.created` | acquire runner after complete plan creation; lifecycle/read application service after placement/doctor planning |
| mutating `operation.*` | execution scheduler around actually started bindings |
| `tool.detection.*` | one new private generic acquisition wrapper reusing the existing typed detection semantics |
| `tool.verification.*` | existing `runVerify` observation seam using the available root or operation bundle |
| `transaction.stage.*` | physical durable swap or ledger-migration transition authority |
| `transaction.committed` | physical authority after durable committed state is acknowledged |
| `transaction.rolled-back` | physical rollback authority after rollback is durably acknowledged |
| `recovery.*` | placement/ledger recovery wrapper around one resume, rollback, or cleanup invocation |

`executeRepositoryLifecycleV1` is not a transaction-event owner. Its `stage/commit/rollback/cleanup`
vocabulary composes repositories and does not prove the journal's physical phase transitions.
Emitting there would duplicate or mislabel facts.

Adapters do not gain observer-aware interfaces. Existing generic detection and verification
wrappers receive the bundle. Tool-specific code remains behind the signed registry bundles, and no
known-tool branch is introduced.

## Internal propagation boundary

Add one private `packages/core/src/execution/observation.ts` module. It owns only:

- deterministic private plan-event ID derivation and `plan.created` emission;
- planned-operation context derivation from a root bundle and an immutable operation;
- transaction/recovery context construction from a closed scalar identity
  (`transactionId`, operation/group/pair IDs, command, workflow, and attempt);
- operation-result to observation-outcome/error projection; and
- small begin/complete helpers that keep counts and error normalization consistent.

It is not exported from the public core index and does not read state, repositories, adapters,
process streams, environment variables, persisted files, or artifact/journal DTOs. Placement and
ledger-migration owners project their journal data into the closed scalar input.

Observation never enters package-root public options or reports. `InstallOptions`,
`UninstallOptions`, `FlipOptions`, `DoctorRepairExecutionRequest`, current execution request/binding
signatures, and generated public declarations remain unchanged.

Internal propagation uses source-module-only `*Observed` entry points and private structural
sidecars that are never re-exported from the package root:

- lifecycle application services call observed install/uninstall registry kernels and emit
  placement plans before preview/execution;
- doctor read service emits the repair plan and calls an observed doctor executor;
- observed coordinator/scheduler entry points accept the root bundle separately from the unchanged
  request and binding shapes;
- a private per-operation execution sidecar receives the derived planned-operation bundle without
  adding fields to the immutable plan or result;
- acquisition/placement execution kernels carry that sidecar bundle through verification, journal
  construction, physical phases, rollback, and recovery; and
- existing package-root and direct compatibility entry points omit observation while preserving
  results, outputs, exits, and the same new canonical journal bytes.

No observation field enters `OperationPlan`, `ExecutableOperation`, `OperationExecutionResult`,
public reports, ledger DTOs, journal DTOs, saved plans, manifests, locks, or renderer models.

## Durable transaction sequences

### Successful placement/acquisition transaction

For an actually executed journaled operation, the exact causal sequence is:

```text
operation.started
transaction.stage.started(prepared)
transaction.stage.completed(prepared, success)
transaction.stage.started(staged)
transaction.stage.completed(staged, success)
transaction.stage.started(backed-up)
transaction.stage.completed(backed-up, success)
transaction.stage.started(live)
transaction.stage.completed(live, success)
transaction.stage.started(committed)
transaction.stage.completed(committed, success)
transaction.committed
operation.completed(success)
```

Stage completion acknowledges the canonical durable phase marker. The current write-ahead swap may
persist `backed-up` before the live-to-backup rename and `live` before the staging-to-live rename;
therefore completion does not claim that a later physical rename has finished. A physical failure
after a successful marker does not retroactively emit a second failure completion for that stage.
Recovery reports the actual subsequent work. A marker write that itself fails completes with
`failure` or `cancelled`, includes a normalized code, and is not followed by a success completion.
Later forward markers are absent unless recovery actually advances them.

Record-only repair transactions may move directly from prepared to committed internally, but the
observable sequence still reports only stages that the durable authority actually acknowledges; it
does not invent filesystem work.

### Rollback and recovery

Recovery emits one span per transaction attempt, not one span per public batch call:

```text
recovery.started(resume | rollback | cleanup)
  zero or more actual transaction stage pairs
  optional transaction.committed or transaction.rolled-back
recovery.completed(outcome, errorCode)
```

`transaction.rolled-back.reasonCode` comes from the normalized durable failure/cancellation reason,
not a free-form exception message. A successful rollback recovery completes with observation
outcome `success` even though the original forward operation result remains failed. Observation does
not rewrite that original result.

Repeated recovery of an already terminal transaction emits only the recovery work actually
performed; it does not replay historical stage events. Cleanup after commit emits `cleanup` recovery
events and never fabricates a new transaction commit. A committed-journal sweep emits one cleanup
span inside each recovered transaction's per-target authority and emits none for a zero-target
sweep. Transaction terminal durations use fake-clock monotonic elapsed time from the current
transaction-attempt event context.

### Ledger migration

Ledger migration remains owned by the canonical ledger writer. A narrow optional synchronous
post-durable cursor-transition notification is added at the writer's already-authoritative
recovery-pointer transition, and the placement adapter maps only durable journal phases
`prepared/staged/backed-up/live/committed` to typed events. The writer does not import observation,
await observers, render output, or expose event semantics. Notification throws are contained and
ignored by the writer, and the callback does not accept promises. It is separate from the existing
awaited `afterBarrier` fault-injection seam, which retains its exact crash-test semantics. Migration
`live` maps to the authoritative handed-off durable-live transition, not the earlier `replaced`
cursor, and notifications occur only for a newly completed cursor transition—not for a cursor that
recovery merely proves was already complete.

## Observer isolation and semantic independence

The existing emitter remains the only observer-failure boundary. Throwing, rejecting, slow, and
never-settling observer ports must produce identical:

- operation plans and plan hashes;
- execution results and ordering;
- human stdout/stderr and JSON stdout;
- exit classes;
- journal, ledger, and recovery bytes;
- transaction/recovery decisions; and
- final live/store/artifact state

to a no-op observer under the same deterministic ports.

No emitter call may appear as a condition, returned semantic value, promise dependency, persisted
value, state-reducer input, retry choice, rollback choice, or recovery choice. Observation spans may
only be passed back to `complete` in unconditional cleanup paths.
