# P17-G4A-03 Ready plan

## Outcome and exact scope

G4A-03 activates `skillsmith init` as the one-manifest bootstrap command. It resolves one
manifest destination from the shared project context, derives a declaration-empty canonical
skeleton from explicit and effective defaults, delegates create/replace/migrate/noop/refusal
classification to the signed Phase-2 `planInitManifest` authority, projects a real immutable
`OperationPlan<'init'>`, and executes its sole manifest operation through the shared coordinator.
Dry-run returns the same immutable operation without acquiring a mutation lock or writing. Init
never creates, updates, removes, or migrates a lockfile, placement, store, or placement ledger.

The immutable primary scope is exactly ten entities:

- `COMMAND:init`;
- accepted finding `EWP-CF-041` and retained recommendation `P1-05`;
- command selectors `EWP-CMD-INIT-TS01..TS05`; and
- phase task/selector `EWP-P4A-T04` and `EWP-P4A-TS04`.

The exact required-now validation partition is the five init command selectors,
`EWP-OPT-TS03`, `EWP-OPT-TS04`, signed `EWP-P2-TS05`, and `EWP-P4A-TS04`.
`EWP-OPT-TS05` and `EWP-WF03` remain immutable downstream obligations. The former belongs to the
Phase-6 generated-help owner and the latter to dependency-complete G4B-03 because WF03 invokes
future `plan` and `apply` and proves clean-clone reproduction. This group does not activate either
downstream target.

Formal dependencies are signed: G2-04 supplies the pure request/skeleton/migration classifier at
accepted implementation pin `5c902f700a14a83e33118d183e9eef08bab2c308`; G3B-03 supplies
durable recovery and interruption behavior at `7b7d285eee051e24c7e5d7624c33e4cd5a2e9ac6`;
G3B-04 supplies immutable observations, revisions, pure plans, and execution bindings. Signed
Phase 1 supplies the declarative command/application/renderer runtime, and signed Phase 2 supplies
project context, artifact selection, readers, lossless edits, codecs, and the one-member artifact
coordinator. Existing G4A work is a compatibility baseline, not a replacement dependency or a
source of init-specific policy.

All work is local, credential-free product/reliability development. Tests use temporary homes,
Git worktrees, XDG trees, manifests, sibling locks, ledgers, live roots, deterministic filesystem
ports, injected barriers, and synthetic canaries only.

## User-visible contract

The activated grammar is exactly:

```text
skillsmith init
  [--file <path>]
  [-t, --tool <name>]...
  [-s, --scope <user|project> | --user | --project]
  [-f, --force] [--dry-run] [--json]
```

There are no positionals, aliases, `--lockfile`, live-import, export, prune, approval, batch,
network, plan-file, or confirmation options. Exact preflight rules are:

- `--file` and `--scope` are singular; repeated occurrences exit 2;
- any two scope forms conflict even when they spell the same scope, before project/config/artifact
  reads or mutation;
- unknown tool/scope exits 2; recognized `kilo-code`/`opencode` tools and recognized read-only
  `system`/`managed` effective scope exit capability 4 for init before artifact coordination; mixed
  writable/read-only tool sets also refuse rather than dropping members; repeated writable tools
  deduplicate in registry order;
- `--force` and `--dry-run` may combine because force changes classification and dry-run changes
  execution only;
- init has no approval boundary, so force never requires or implies `--yes`; and
- inherited `-C`, `--config`, JSON, quiet/verbosity, color, no-prompt, and signal behavior continue
  through the shared runtime without local parsing or process control.

Destination selection consumes one resolved `ProjectContext`:

1. explicit `--file` wins and resolves from `effectiveCwd` without changing project identity;
2. explicit user scope selects `$XDG_CONFIG_HOME/skillsmith/skillsmith.toml`;
3. explicit project scope selects the Git root only when `projectKind === "git"`; every non-Git
   context selects `effectiveCwd/skillsmith.toml`, even when an ancestor manifest supplied a
   discovered non-Git project identity;
4. without explicit scope, a Git context selects the shared Git root; otherwise init selects the
   XDG user manifest; and
5. human and JSON output name the selected manifest and its derived sibling lock path, while
   execution authority contains only the manifest path.

Nested cwd inside one Git worktree is invariant. A nested non-Git cwd beneath an ancestor
`skillsmith.toml` still initializes its effective cwd when project scope is explicit. A
deliberately explicit artifact path never
rebases project live roots, ledger project identity, or placement containment. An existing nested
discovered manifest is not an automatic init destination: default project initialization remains
at the shared Git root, while `--file` is the explicit route to another artifact.

## Skeleton defaults and legacy intent

Init constructs a Phase-2 `InitManifestSkeletonInput` from the normal effective configuration, but
keeps destination selection and persisted defaults separate:

- explicit `--tool` supplies `defaults.tools` and outranks every configured tool layer;
- otherwise a nonempty effective scalar/plural tool selection supplies `defaults.tools`;
- otherwise init runs the shared adapter detection for the writable Claude/Codex family only and
  persists the detected nonempty set in registry order; zero detected writable tools leaves the
  field absent, while a detection error refuses rather than pretending no default exists;
- explicit scope supplies `defaults.scope`; otherwise a representable effective user/project scope
  supplies it, while destination fallback alone does not invent a persisted scope;
- effective portable `path` is included only with its effective user/project scope;
- an effective credential-free canonical `registry.default` is included; and
- absent values remain absent, so the minimal skeleton is exactly `version = 1\n`.

CLI-selected tools and scope are the only `legacyIntent.requireMatch` fields. Configured or detected
defaults do not override values already present in an exact legacy project file: bare init migrates
that file losslessly. Explicit `--tool` or scope that conflicts with the corresponding legacy field
refuses with state exit 3 instead of discarding either intent. An explicit file controls location
only and adds no default intent.

The selected target may also be a configuration layer. Effective-config resolution gains only a
bounded automatic-project exclusion: when the automatically discovered project config is also the
init target, only semantically valid canonical or exact safely migratable legacy bytes participate
as configuration. Every other unchanged target snapshot—mixed, empty, malformed, unknown, future,
unsafe legacy, or canonical-shaped but semantically invalid—is omitted from automatic config
merging and passed unchanged to `planInitManifest`. The planner therefore owns replaceable invalid
classification, the exact unsafe-legacy refusal, and future refusal even under force. The exclusion
never applies to an explicit `--config` or
`SKILLSMITH_CONFIG` layer. If explicit config and `--file` identify one canonical or exact-legacy
path, the application shares the one owned byte snapshot between configuration and artifact roles;
if they identify one invalid path, config parsing refuses with state 3 even under force. The same
one-snapshot rule applies when an automatic canonical/legacy project layer is also the target.
System, user, environment, other-project, and noncolliding explicit-config precedence remains
unchanged. This is one extension of the existing resolver, not an init-specific duplicate merge
algorithm or a force bypass around configuration validity.

An explicit or effectively configured `kilo-code`/`opencode` tool, a mixed writable/read-only tool
set, or effective `scope = system|managed` returns capability 4 before operation planning or locks.
Unknown CLI values return usage 2. A syntactically valid but nonportable configured path that
cannot enter the skeleton returns the signed init invalid-request refusal; an invalid registry
identity or other invalid/unreadable configuration layer returns state 3. Init never silently persists an
unrepresentable default. Force authorizes replacement of the selected
manifest conflict only and does not bypass invalid CLI input, unsafe legacy conversion, future
schema, path safety, permissions, concurrent change, or cancellation.

## Pure classification and result matrix

The application observes the selected path once as absent or an owned ordinary-file byte snapshot,
then calls `planInitManifest` without modifying or reimplementing its matrix:

| Current selected manifest | Without force | With force |
|---|---|---|
| absent | `create-manifest` | `create-manifest` |
| exact safe legacy | `migrate-project-config` | same migration; force is irrelevant |
| unsafe/nonportable legacy | refusal | same refusal |
| canonical semantically equal to requested skeleton | `noop` | same noop |
| canonical different or semantically invalid | existing-manifest refusal | `replace-manifest` |
| mixed, empty, malformed, or unknown | existing-manifest refusal | `replace-manifest` |
| future version | future-manifest refusal | same refusal; force cannot downgrade |

Create and migration require no additional approval. Replacement requires force but not yes. Noop
is byte-, mode-, sibling-, live-, and ledger-identical and performs no coordination. Refusal is
zero-write and does not provision parents, create recovery records, or acquire mutation locks.

The pure input remains path-free and authoritative for canonical bytes, exact lossless migration,
manifest-byte/semantic hashes, shape precedence, fixed safe errors, and caller-data ownership.
G4A-03 adds no second skeleton renderer, shape classifier, TOML migration, or manifest serializer.

Two existing digest domains remain deliberately distinct. `InitManifestBeforeImage.byteHash` and
`InitManifestWriteImage.byteHash` use Phase-2 `hashManifestBytes` (`manifest-bytes`) and flow to the
init domain result/report. `OperationImage.manifest.byteHash`, the new opaque image `byteHash`,
resource preconditions/revisions, actual-before execution images, and
`opaqueManifestBackup.expectedResourceDigest` use
`hashCanonicalInput("resource", 1, bytes)`. Manifest semantic hashes continue to use
`hashManifestSemantics`. The projection owns one copy of the observed current bytes and the planned
after source, computes both byte digests from those same bytes without rereading, and never copies a
manifest-bytes digest into an operation/resource field or vice versa.

## Shared operation plan and the opaque before-image gap

Every mutating init result becomes exactly one canonical `OperationPlan<'init'>` operation:

| Init result | Shared operation |
|---|---|
| `create-manifest` | `write-manifest`, absent before, canonical after |
| `replace-manifest` | `write-manifest`, exact present before, canonical after |
| `migrate-project-config` | `migrate-project-config`, legacy before, canonical after |
| `noop` or refusal | no executable operation |

The plan uses `bounded-default` selection, no tool/scope placement identity, one deterministic
group/operation ID, manifest-only mutation flags, no checks, and exact revision preconditions. A
replace operation carries the existing bounded `destination-exists` conflict with the exact
manifest resource as target, normal `refuse`, forced `backup-and-replace`, and backup `required`.
Create, migrate, and noop carry no conflict. Init joins `CurrentMutatorCommand`; it does not add an
executable operation kind because `write-manifest` and `migrate-project-config` already own the
physical effects.

One signed model gap must close truthfully. Current `OperationImage` can represent an absent,
canonical, or legacy manifest, but force replacement may have a mixed, empty, malformed, unknown,
or semantically invalid canonical before-image. G4A-03 adds one closed `opaque-manifest` image with
only machine-bound location, structural shape
`canonical | mixed | empty | malformed | unknown`, and exact resource-domain byte digest. It contains no source
bytes, parsed value, semantic claim, or secret-bearing error. Legacy is always represented by the
existing parsed legacy image and future always refuses before operation planning; neither is valid
as opaque. `createOperationPlan` validates opaque only as a `write-manifest` before-image; no other
operation may produce or consume it. Canonical/legacy images retain their existing strict shape and
snapshot requirements.

The shared execution scheduler mirrors that closure rather than treating opaque as a generic
artifact. It permits the image only as the same-location before of `write-manifest`. It permits a
null-pair `destination-exists` conflict only when `plan.command === "init"`, the operation is
`write-manifest`, the before image is present, and target/normal/forced/backup exactly match the
selected manifest policy. Init create and migration remain conflict-null, and every non-init
artifact prerequisite retains the signed conflict-free rule. The execution coordinator maps an
opaque image to its `manifest-bytes` resource at the same location; it never falls through to
ledger identity. All prior placement, pair, lock, ledger, group, and binding validation is
unchanged.

`opaque-manifest` is an in-memory `OperationImage` variant only. It is not added to `PlanImageV1`,
`SavedPlanV1`, or the strict saved-plan codec: additive enum growth would break persisted v1 and
belongs to a future version only if plan/apply ever needs it. G4A-03 changes no saved-plan type,
codec, repository, bytes, or fixture. The existing codec cannot represent the runtime-only image,
and init exposes no save-plan route. Previously valid operation plans remain valid.

The successful command report carries one immutable `init@1` result projection whose `action` is
`create-manifest | replace-manifest | migrate-project-config | noop`, selected manifest path,
before state/shape/digests, canonical after digests, and nullable operation ID. The first three
actions have an executable operation ID and canonical after image; noop has a present canonical
before image, `after: null`, and `operationId: null`. Refusal is not a fifth success result: it is a
closed `InitFailure` normalized through the shared human/JSON error envelope. The same result
projection and operation object are used for dry-run and successful execution; only report-level
dry-run, force-applied, and effect-outcome facts differ.

Every successful report also carries the shared `BoundedForceEffect`. Create, migrate, and noop
report requested force as unused with null conflict fields. Replacement dry-run reports the stable
destination conflict with `requested: true`, `applied: false`; successful execution reports that
same conflict with `applied: true`. Failed or cancelled execution cannot claim application. This is
constructed by `createBoundedForceEffect`, not by an init-specific force DTO.

No report or error includes original manifest bytes, local configuration values unrelated to the
skeleton, recovery paths, raw errors, live paths, ledger paths, or authentication data.

## Manifest-only execution and durability

Execution binds the approved operation to the signed one-member coordinated human-file authority.
It does not call the pair executor, acquire the sibling lockfile compatibility target, or acquire a
placement-ledger lock. The binding:

1. observes the exact manifest with the `resource` digest domain and validates the operation
   before-image;
2. enters the existing artifact central lock plus the selected manifest member lock;
3. reobserves with the same `resource` digest in the closed edit callback immediately before
   staging and requires the exact approved path/state/revision/digest/mode without replanning;
4. for create, requires absence and writes copied canonical bytes at owner-only mode;
5. for migration, invokes the sole lossless `migrate-legacy` edit and proves the exact planned
   canonical after-image;
6. for replace, requires the same exact byte digest/shape and preserves the existing mode while
   installing the planned canonical bytes;
7. stages, fsyncs, no-replace installs, recovers, rolls back/finalizes, and cleans up through the
   existing private recovery protocol; and
8. returns a normal `OperationExecutionResult` consumed by the shared scheduler/observer path.

The runtime binding uses the same opaque manifest resource mapping for `actualBefore`, precondition
coverage, and execution results. Scheduler validation receives the enclosing command so the init
conflict exception cannot be inferred from an operation shape alone.

The one-member coordinator already observes ordinary files with a `resource` digest and performs no
TOML parse. Its actual blocker is `recordFor` applying `validateCandidateBytes` to every backup
before-image. The source-internal request therefore gains only
`opaqueManifestBackup: { expectedResourceDigest }`, supplied exclusively by a validated init
`replace-manifest` conflict for any present before shape, including a semantically valid canonical
manifest. Before creating a recovery record it must match the role's exact present resource digest;
otherwise it refuses stale state. A bare boolean or a create/migrate/noop operation, normal
non-init manifest/config/lock caller, absent before-image, wrong path, or wrong digest domain is
invalid at binding construction. Runtime `opaque-manifest` operation images remain closed to the
opaque force-replacement shapes already enumerated above; the backup authority is broader only
because an otherwise canonical old manifest may contain secret-looking comments that must be moved
without disclosure.

For this one authorized case, `recordFor` skips only UTF-8 and sensitive-sink validation of the old
backup bytes. Candidate after bytes still pass the existing strict UTF-8, sensitivity, canonical
manifest, and exact-hash validation. This deliberate old-byte policy is required for force to
replace malformed non-UTF8 and unknown files: the exact old file is moved, not rendered, into the
owner-only transaction directory, its recovery record stores digest/mode/identity but no content,
and no report/log/error includes it. Credential canaries are therefore recoverable without a new
secret sink or disclosure.

The existing invalid-lock replacement branch remains a distinct `invalid-lock` opaque observation
using `observeOpaqueLockFile` and its `lock-canonical` digest. Init never toggles or reuses that
branch: its provisional, final-guard, backup, rollback, and recovery observations all retain
`observeArtifactFile(..., "resource")`. Shape is not reimplemented in the coordinator. The init
application calls the signed Phase-2 classifier exactly once while producing the immutable plan.
`createOperationPlan`, scheduler validation, and binding construction reject hostile shape/action/
digest/path combinations before coordination. At execution, the exact resource revision/digest
proves the approved bytes are unchanged; create checks absence, replace installs the already-planned
candidate, and migration alone reapplies the signed lossless edit then compares its candidate to the
planned after image. No execution callback invokes a planner or changes an operation. The
coordinator independently owns only exact path/resource-revision and safe backup/install mechanics.
Config save and every existing caller omit `opaqueManifestBackup` and retain strict old-byte
validation.

Dry-run does not enter this execution path. Cancellation before commit returns 130 with original
bytes durable; cancellation after a durable commit reports the after state consistently. A stale
or concurrent writer returns state exit 3 without overwriting the peer. Permission is 6. Ordinary
coordinator/recovery failure is 1 unless the canonical error taxonomy identifies invalid/stale
state as 3. A crash at every one-member coordinator boundary converges by the signed recovery
algorithm to exact before or exact after and leaves no unowned residue.

Sibling lockfile bytes, existence, mode, and identity; placement/live roots; store; placement
ledger; journals outside the artifact coordinator; and every unrelated manifest remain unchanged.
The bounded defaults probe calls only existing writable-tool adapter detection. It does not scan or
import skills/commands, read placement contents into declarations, inventory the fleet, call the
network, or resolve sources.

## Wire and human output

The strict additive success DTO uses these closed unions exactly:

```text
ManifestByteDigest = ArtifactDigest produced by hashManifestBytes (manifest-bytes domain)
ManifestSemanticDigest = ArtifactDigest produced by hashManifestSemantics

AbsentBeforeV1 =
  { state: "absent"; shape: null; byteHash: null; semanticHash: null }

PresentBeforeV1 =
  { state: "present";
    shape: "canonical" | "legacy" | "mixed" | "empty" | "malformed" | "unknown";
    byteHash: ManifestByteDigest; semanticHash: ManifestSemanticDigest | null }

ReplaceBeforeV1 =
  { state: "present";
    shape: "canonical" | "mixed" | "empty" | "malformed" | "unknown";
    byteHash: ManifestByteDigest; semanticHash: ManifestSemanticDigest | null }

CanonicalAfterV1 =
  { state: "canonical"; byteHash: ManifestByteDigest;
    semanticHash: ManifestSemanticDigest }

InitResultV1 =
  | { action: "create-manifest"; operationId: string;
      before: AbsentBeforeV1; after: CanonicalAfterV1 }
  | { action: "replace-manifest"; operationId: string;

      before: PresentBeforeV1 & { shape: "canonical";
        semanticHash: ManifestSemanticDigest };
      after: null }

ManifestResourceV1 =
  { kind: "manifest-bytes"; location: { kind: "machine-bound"; path: string } }

InitForceEffectV1 =
  | { requested: boolean; applied: false; conflictType: null; target: null;
      normalBehavior: null; forcedBehavior: null; backup: null }
  | { requested: true; applied: boolean; conflictType: "destination-exists";
      target: ManifestResourceV1; normalBehavior: "refuse";
      forcedBehavior: "backup-and-replace"; backup: "required" }

InitEffectsV1 = [
  { role: "manifest"; action: "create" | "replace" | "migrate" | "unchanged";
    operationId: string | null; outcome: "planned" | "succeeded" | "not-run" },
  { role: "lock"; action: "not-written"; operationId: null; outcome: "not-run" },
  { role: "live"; action: "not-written"; operationId: null; outcome: "not-run" },
  { role: "ledger"; action: "not-written"; operationId: null; outcome: "not-run" }
]

InitV1Dto {
  schemaVersion: 1
  kind: "skillsmith.init"
  reportVersion: 1
  dryRun: boolean
  requested: {
    tools: BuiltInToolId[]
    explicitTools: boolean
    toolSource: "explicit" | "config" | "detected" | "none"

    explicitScope: boolean
    file: string | null
    force: boolean
  }
  defaults: {
    tools: BuiltInToolId[] | null
    scope: "user" | "project" | null
    path: string | null
    registryDefault: string | null
  }
  artifactSelection: {
    outcome: "selected"
    selectedBy: "explicit-file" | "project" | "user"

    lockPath: string
    lockSource: "sibling"

  result: InitResultV1
  force: InitForceEffectV1
  effects: InitEffectsV1
  summary: { changed: 0 | 1; unchanged: 0 | 1 }

```

The strict codec cross-validates the remaining action relationships rather than accepting their
cross-product:

| Result action | Manifest effect | Summary | Force effect |
|---|---|---|---|
| create | same ID, `create`, planned iff dry-run else succeeded | changed 1, unchanged 0 | no conflict; requested mirrors request |
| replace | same ID, `replace`, planned iff dry-run else succeeded | changed 1, unchanged 0 | exact destination conflict; applied iff not dry-run |
| migrate | same ID, `migrate`, planned iff dry-run else succeeded | changed 1, unchanged 0 | no conflict; requested mirrors request |
| noop | null ID, `unchanged`, not-run | changed 0, unchanged 1 | no conflict; requested mirrors request |

The last three effects occur once each in fixed `lock`, `live`, `ledger` order. The force target
must equal `artifactSelection.manifestPath`; result/effect operation IDs must equal the immutable
plan operation ID. Replacement before-shape excludes legacy and future; canonical uses the normal
manifest image when semantically valid and opaque only when semantic normalization fails. The DTO
rejects every other action/before/after/effect/force/outcome/count/path combination.

The codec also rejects impossible selection projections. Successful tool arrays contain only
`claude-code | codex`, are unique in registry order, and `requested.tools` equals
`defaults.tools ?? []`. `toolSource: explicit` requires `explicitTools: true` and a nonempty array;
`config` or `detected` requires `explicitTools: false` and a nonempty array; `none` requires
`explicitTools: false`, an empty requested array, and null default tools. `requested.force` equals
`force.requested`. `explicitScope: true` requires nonnull requested scope; configured user/project
scope may be nonnull with `explicitScope: false`; in either case `requested.scope` equals
`defaults.scope`, while automatic destination fallback leaves both null. `requested.file` is the
normalized selected path exactly when `selectedBy` is `explicit-file`, equals `manifestPath`, and
is null for project/user selection. These are schema refinements, not renderer-only assumptions.

Planning refusal returns `Result.err(InitFailure)` with the signed init reason/exit class and no
success DTO, operation, or effects. Execution failure/cancellation returns a sanitized
`InitFailure` carrying the attempted manifest effect and shared execution outcome for the error
renderer, but never serializes a successful `init@1` document. In `--json` mode the single shared
error envelope is written to stdout exactly once and diagnostics remain on stderr; human failure
uses stderr. Dry-run does not alter refusal classification or stream placement.

Human success names create/replace/migrate/noop, the manifest path, the sibling path that remains
untouched, before/after digest facts, force requested/applied/conflict/backup facts, and whether the
operation was planned or applied. Quiet suppresses successful human output only. Help and
completion are generated from the same `CommandSpec`. Downstream EWP-OPT-TS05 retains final
documentation/help-inventory ownership, but current command help and completion must already expose
the exact activated grammar.
