# P17-G3B-01 implementation plan

## Outcome and exact scope

P17-G3B-01 introduces one deeply immutable runtime planning domain for executable operations,
required checks, planner diagnostics, bounded conflicts, and execution results. It migrates the
current install, uninstall, dev, and promote planning/dry-run paths so preview and execution consume
the same canonically ordered operation identities. The existing install, uninstall, and flip action
unions remain compatibility report DTOs only; they are projections of planning diagnostics and
execution results and are never executable work.

The group also completes the accepted Phase-3B portion of the existing dev/promote surface:
target-or-all validation, user/project scope selection and sugar, exact scoped target resolution,
explicit selection provenance, and real approval of the already-planned bulk operation set.
Compatibility `--rollback` continues to call the current rollback engine. Existing verification,
dirty-source, store-retention, crash-recovery, and no-residue behavior is preserved.

The primary entities are exactly 21: `COMMAND:dev`, `COMMAND:promote`, `D-009`, `EWP-CF-002`,
`EWP-CF-025`, `EWP-P3B-T01`, `EWP-P3B-T03`, `EWP-CMD-DEV-TS01..TS06`,
`EWP-CMD-PROMOTE-TS01..TS06`, `EWP-P3B-TS01`, and `EWP-P3B-TS02`. The 15 required-now validations
are the twelve command selectors, `EWP-OPT-TS04`, and the two Phase-3B selectors. The 17 downstream
validations named by the corrected catalog include `EWP-WF05`; they remain pristine and are not
created, executed, or advanced by this group.

The sole direct dependency is signed G3A-02. The group reuses G1's project/selection, application,
interaction, registry, exit, wire, and observation authorities plus G2-05's exact saved-plan v1
persistence contract. It changes neither the frozen saved-plan bytes nor the public install@1,
uninstall@1, or flip@2 compatibility versions. Dev/promote move to the separately versioned flip@3
contract described below.

## Cross-group validation boundary

Several required selectors intentionally cover a workflow that later groups extend. G3B-01 closes
only the clauses owned by its two phase tasks:

- `EWP-CMD-DEV-TS04` and `EWP-CMD-PROMOTE-TS04` prove canonical group construction, scope-aware
  selection, approval, explicit-all/filter-noop provenance, and the planned fail-fast/continue
  policy value. They do not claim the future coordinator has executed a failing multi-group batch.
  G3B-02 owns the deterministic scheduler, skipped-after-failure results, continuation after an
  actual failure, cancellation, and partial-pair execution mechanics under `EWP-P3B-TS03`.
- The operation domain can represent batch policy, but G3B-01 does not expose
  `--continue-on-error`. G3B-02 adds the option together with its real scheduler semantics; no
  user-visible no-op option is shipped here.
- `EWP-CMD-DEV-TS05` and `EWP-CMD-PROMOTE-TS05` prove current `--rollback` routing, operation-plan
  equivalence, option conflicts before discovery/I/O, and compatibility projection. The future
  public `undo` command and shared undo engine remain G5-owned.
- `EWP-WF05` is downstream under G5-03, where its complete direct-undo command sequence can execute.
  G3B-01 replays the existing focused dev/promote/verify/status/rollback characterization instead.
  No placeholder undo command, fake success, skipped required assertion, or premature G5 entity is
  introduced.
- `EWP-OPT-TS04` adds only the operation-model/bounded-force invariants relevant here. The actual
  command-specific force surfaces remain with their owning install/uninstall and downstream groups.

This boundary is an implementation sequencing rule, not a weakening of the consolidated contract.
The catalog's downstream relations remain the closure mechanism for later scheduler and undo work.

## Runtime planning domain

The new `packages/core/src/planning` boundary owns semantic vocabulary, immutable types, canonical
ordering/identity, deep-freeze construction, and current-report compatibility mapping. Persistence
continues to live in `artifacts/plan-types.ts` and `artifacts/plan-codec.ts`.

The public runtime shape is conceptually:

```ts
interface OperationPlan<TCommand extends string> {
  readonly domain: 'skillsmith.operation-plan';
  readonly schemaVersion: 1;
  readonly command: TCommand;
  readonly selection: OperationSelection;
  readonly batchPolicy: 'fail-fast' | 'continue-on-error';
  readonly operations: readonly ExecutableOperation[];
  readonly checks: readonly PlanCheck[];
  readonly diagnostics: readonly PlanningDiagnostic[];
}

type CurrentMutatorOperationPlan = OperationPlan<
  'install' | 'uninstall' | 'dev' | 'promote'
>;

interface ExecutableOperation {
  readonly operationId: string;
  readonly groupId: string;
  readonly pairId: string | null;
  readonly kind: ExecutableOperationKind;
  readonly dependencyMetadata: Readonly<{
    readonly domain: 'skillsmith.operation-dependency';
    readonly schemaVersion: 1;
    readonly operationIds: readonly string[];
  }>;
  readonly skill: string | null;
  readonly source: OperationSource | null;
  readonly tool: SupportedTool | null;
  readonly scope: 'user' | 'project' | null;
  readonly before: OperationImage;
  readonly after: OperationImage;
  readonly reason: Readonly<{ code: string; message: string }>;
  readonly selectionSource: 'explicit-targets' | 'explicit-all' | 'bounded-default';
  readonly preconditionIds: readonly string[];
  readonly requiredCheckIds: readonly string[];
  readonly reversibility: OperationReversibility;
  readonly mutates: MutationFlags;
  readonly conflict: BoundedConflict | null;
}

interface OperationExecutionResult {
  readonly operationId: string;
  readonly outcome: 'succeeded' | 'failed' | 'cancelled' | 'rolled-back';
  readonly actualBefore: OperationImage;
  readonly actualAfter: OperationImage;
  readonly force: BoundedForceEffect | null;
  readonly error: SanitizedExecutionError | null;
}
```

`ExecutableOperationKind` uses the accepted vocabulary: install, update, remove, link-dev, promote,
move-scope, adapt, repair, write-manifest, write-lock, migrate-project-config, and migrate-ledger.
`planning/vocabulary.ts` is the neutral semantic literal authority;
`artifacts/plan-types.ts` aliases its `PlanOperationKindV1` to that authority while its codec's
accepted values and serialized bytes remain unchanged. The runtime domain never imports a wire DTO
or parser. An explicit runtime-to-persistence mapper interface is defined and parity-tested here,
but constructing a complete `SavedPlanV1` or executing one remains G4B work. The public names do not
collide with observation's broader `OperationKind`/`OPERATION_KINDS` event vocabulary.

`OperationSource`, `OperationImage`, precondition/check references, reversibility and retention use
closed readonly domain unions that cover the same semantic facts as G2-05 without importing DTOs.
`BoundedForceEffect` is a closed union containing `requested`, `applied`, `conflictType`, selected
`target`, `normalBehavior`, `forcedBehavior`, and `backup`. Commands without force use null. A
force-capable command always returns the union: no flag is requested:false/applied:false, a supplied
flag with no applicable conflict is requested:true/applied:false with null conflict facts, and an
applicable conflict carries every nonnull target/behavior fact whether applied or refused.
`SanitizedExecutionError` is a
closed redacted `{ code, message, remediation }` record with no raw cause, file object, environment,
or unbounded details. Private compatibility sidecars may retain a legacy `SkillSmithError` only long
enough for current exit projection and never place it in a plan, immutable result, or wire DTO.

Operations contain only dispatchable work. Verification/source/capability/precondition work is a
check. Noop, skip, refusal, conflict, and warning are diagnostics. Failure and rollback are results,
not operation kinds. Every result references one real operation ID; a diagnostic may reference a
group/pair/operation when one exists but cannot fabricate an executable operation for a refusal.

All IDs are deterministic, collision-safe encodings of canonical semantic identity, never array
position, wall time, randomness, locale ordering, or unredacted source material. Groups sort by
scope order, skill, then source identity; pairs sort by registry tool order and placement identity;
operations sort by group, pair, operation-kind order, then ID. Dependencies must reference earlier
operations in the same plan and cycles, duplicates, dangling IDs, or cross-domain metadata refuse
construction. Comparison is unsigned UTF-16 code-unit comparison.

Construction copies ordinary input values and recursively freezes every returned record and array.
Functions, accessors, proxies, cycles, exotic prototypes, sparse arrays, symbol keys, and budget
overflow refuse. The domain accepts only normalized, redacted semantic strings. Mutation traps prove
that callers cannot alter a plan, dependency, diagnostic, check, selection, image, conflict, or
result after construction.

## Current mutator migration

Each current runner gains a plan-then-project seam without adding the future coordinator:

1. Existing source/target discovery and classification constructs frozen group/pair candidates.
2. Pure current-mutator adapters project candidates to one `CurrentMutatorOperationPlan` plus private execution
   bindings keyed by operation ID. Bindings hold only the current runner's existing pair/source
   inputs and are not public or persisted.
3. Dry-run walks that operation plan and produces compatibility results without invoking mutating
   ports. Execution walks the same operation identities through the current sequential runner and
   returns `OperationExecutionResult[]` keyed to those identities.
4. One compatibility mapper combines plan diagnostics and execution results into existing
   `InstallReport`, `UninstallReport`, or `FlipReport` rows. Renderers and current v1/v2 codecs see
   the same documented fields and ordering as before, except the accepted scope/selection changes.
5. Phase tests capture both paths at the seam and require byte-for-byte equality of normalized
   operation/check/diagnostic identity and order. Execution-only actual results are separately
   asserted and never back-propagated into the plan.

The private binding map is built atomically with the plan and validated for one-to-one executable
coverage. No operation can execute without a binding; no binding can exist without an operation.
Dry-run cannot call a binding. Existing per-pair verification and journal/swap functions remain
unchanged behind bindings until their later extraction groups.

Install/uninstall migration is limited to projecting their current decisions and routing their
existing dry-run/execution loops through operation identity. It preserves current scope, source,
continue, force, result, and exit behavior. It does not add manifest/lock persistence, public plan
files, or a new install/uninstall option.

Dev/promote migration replaces `PairPlan[]` plus `preResults[]` as the authoritative work model.
`PairPlan` may remain private compatibility input during the staged refactor, but public/current
planning returns operations and diagnostics. `FlipAction` stays renderer-facing only.

## Dev/promote selection, scope, and approval

Dev/promote accept exactly targets xor `--all`. An empty invocation, targets plus all, and an
unmatched explicit target refuse with usage exit 2 before approval or mutation. A selected filter
that legitimately produces no eligible placement is an exit-0 diagnostic with explicit
`filter-noop` metadata and never widens.

Scope is singular user/project through `--scope`, `--user`, or `--project`; conflicting or repeated
singular spelling refuses before discovery. Unscoped explicit names and paths reuse the G1
selection authority: one match across the current user/project universe selects uniquely, the same
name in both scopes refuses as ambiguous, and exact path plus contradictory scope refuses. Absent
`dev --source` creation defaults to project inside the selected project context and user otherwise.
Explicit project scope outside Git uses the already signed canonical effective-cwd project fallback.

`--all` spans eligible user plus current-project placements unless narrowed. Canonical group order
is user before project, then skill, then tool registry order. `selection.source` is
`explicit-targets` or `explicit-all`; `bounded-default` is unrepresentable for these mutation
commands. The selection retains exact tools, scopes, selected identities, and filter-noop outcome.

The placement planner uses the existing adapter `roots(..., scope, ctx)` capability and the existing
ledger `getPairAt`/`setPairAt`/`deletePairAt` scope-key authority. It does not add tool branches or
infer project identity from a placement path. The application service resolves project context and
scope once and passes normalized scope/project facts to core planning.

Approval occurs after immutable planning and before any execution binding is invoked. Single noop
or refusal-only products do not prompt. A mutating bulk plan calls the existing injected
`InteractionPort.confirm` once with stable group/operation counts and scope facts. `--yes` resolves
that confirmation affirmatively through the current CLI interaction authority. JSON,
noninteractive, or no-prompt without authorization refuses before writes. `--dry-run` and
`--yes` remain conflicting under the signed non-mutating-mode policy and never prompt.

## Bounded conflict and compatibility rules

The runtime conflict type represents the complete accepted EWP-CF-025 authority so later mutators
can share it, but G3B-01 does not add force to dev or promote. A conflict always names one already
selected target, normal behavior, forced behavior, and backup policy. Force cannot select an
ambiguous target, expand selection, imply approval, skip checks, change operation identities after
preview, bypass capability/portability/journal/retention rules, or turn a failed result into success.
Compatibility projections report requested/applicable/applied/conflict/backup facts consistently.

Current human bytes and flip@2 JSON bytes remain stable for all characterized legacy cases. The
structured dev/promote plan facts use a strict flip@3 codec and registry entry; flip@2 remains a
frozen compatibility mapper/fixture and is never changed additively. Flip@3 adds scope and selection
source, selected identities/filter-noop, operations, checks, diagnostics, batch policy, and
separately correlated results using redacted DTOs. Install@1 and uninstall@1 remain unchanged.

## Failure, cancellation, and effect boundary

All option and relation validation precedes project discovery, filesystem reads, interaction, or
mutation. Planning errors retain the shared exit taxonomy. Cancellation wins with exit 130.
Planning and dry-run receive no write, lock, network, prompt, clock, random-ID, or generic-process
capability beyond existing bounded observation needs. Execution retains the current narrow runner
ports and existing lock/journal behavior.

No partial report is fabricated for invocation-level validation, ambiguity, project-context,
approval, or plan-construction failure. Per-pair current execution failures remain separately keyed
results. The future scheduler will decide which later groups execute after a failure; this group
only retains the batch-policy value and current sequential compatibility.

## Test-first partitions

The first implementation step captures one signed green baseline receipt for `EWP-OPT-TS04`, then
creates four planned acceptance files and all 14 absent selectors as honest failing tests. The
substantive G3B-01 extension to `EWP-OPT-TS04` is committed in the same test-first change and must
also fail for the missing operation/conflict behavior. No red receipt may be an import error, empty
placeholder, skipped assertion, fake undo, or successor-owned scheduler behavior. Fixtures remain
inline until a reviewed ownership amendment names an exact fixture path.

- Dev TS01..TS03: state machine, source/destination/name/path/tool/scope validation, and verification
  gates.
- Dev TS04..TS06: scoped/all selection and approval, dry-run/JSON/rollback compatibility, immutable
  plan equality, crash/source/store retention, and residue parity.
- Promote TS01..TS03: scoped placement convergence, provenance/dirty policy, and per-tool verify
  mode.
- Promote TS04..TS06: scoped/all selection and approval, planned batch policy, dry-run/JSON/rollback
  compatibility, partial multi-tool planning characterization, hashes/store reuse/recovery/residue.
- P3B TS01: snapshot matrix maps every existing action/disposition/outcome to exactly one of
  operation, check, diagnostic, or result and proves compatibility projection.
- P3B TS02: shuffled-input/property determinism, collision-safe IDs, dependency validation,
  deep-freeze mutation traps, and dry-run/execution operation equality.
- OPT TS04: operation conflict shape and force/approval/dry-run separation, without advancing any
  downstream command selector.

Focused characterization replays existing acquire/place/application/CLI/output/wire tests after
each affected partition. Iteration then runs typecheck, Biome on changed files, boundary lint, P17
catalog validation, and the bounded five-test smoke lane. The focused P2-TS04 recovery smoke runs
after execution-seam changes and again at targeted and terminal gates. The five-minute full
repository suite is reserved for terminal G3B-01 sign-off because this group modifies high-traffic
mutator paths.

## Strict exclusions

- G3B-02 retains lock hierarchy, coordinator, deterministic execution scheduler, actual
  fail-fast/continue behavior after failures, cancellation scheduling, and partial-pair transaction
  mechanics.
- G3B-03 retains ledger v2 writes/migration, project registrations, canonical writer, journals,
  recovery/history, resume/abort, and doctor repair.
- G3B-04 retains repositories, versioned observed snapshots, fully pure end-state planners,
  expected revisions, ADR 0006, and monolith extraction.
- G3B-05 retains complete tool-specific placement/verification migration and known-tool-branch
  removal. G3B-06 retains OperationContext propagation and lifecycle events.
- G4 retains manifest/lock persistence, saved-plan construction/execution, declarative plan/apply,
  and final persistence closure of EWP-CF-002. G5 retains public undo and final shared batch command
  behavior.
- No new saved-plan schema, wire parser, option matrix, exit selector, interaction implementation,
  tool registry, runtime composition root, repository abstraction, lock, journal format, ledger
  writer, public command, or network behavior is created here.

## Gate sequence

1. Ready: independent product/schema, architecture/ownership, and trace/test reviewers accept this
   plan, exact ownership, commands, exclusions, and the cross-group validation boundary.
2. Test-first: the 14 absent selectors plus the extended option selector fail for the intended
   missing behavior after a recorded green dependency baseline.
3. Minimal implementation: immutable domain, current-mutator seams, and scoped dev/promote surface
   make focused selectors pass without successor work.
4. Targeted/impacted green: all 15 required-now selectors, focused characterization, static gates,
   and smoke pass.
5. Refactor/adversarial review: compatibility action unions are presentation-only, no duplicate
   authorities or successor leakage remains, and independent review findings are remediated.
6. Traceability/sign-off: exact receipts, final ownership, catalog closure, terminal static gates,
   and one full repository suite are pinned to committed revisions.
