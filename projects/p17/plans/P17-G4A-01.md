# P17-G4A-01 Ready plan

## Outcome and exact scope

G4A-01 makes the existing `install` and `uninstall` commands desired-state-first without adding
another lifecycle verb or another transaction framework. A resolved install saves complete portable
intent to one manifest/lock pair before independently attempting each selected tool placement.
Uninstall removes live placements independently but retains portable intent until every selected
removal in that declaration group succeeds. `--no-save` is the explicit live-only escape hatch.

The immutable catalog scope is exactly 23 primary entities:

- command contracts `COMMAND:install` and `COMMAND:uninstall`;
- decision `D-006`, finding `EWP-CF-020`, and retained recommendation `P1-09`;
- command selectors `EWP-CMD-INSTALL-TS01..TS08` and
  `EWP-CMD-UNINSTALL-TS01..TS07`;
- phase task/selector `EWP-P4A-T01` and `EWP-P4A-TS01`; and
- temporary live-only workflow `EWP-WF02`.

The validation partition is exactly 18 required-now and impacted validations with no downstream
coverage: the 15 install/uninstall command selectors, P4A-TS01, WF02, and signed compatibility
workflow WF14. Full first-installation workflow WF01 is not in this group: its unchanged release
workflow closes in dependency-complete G6-04.

Signed G3B-03 through G3B-06 remain authoritative for durable journals/recovery, immutable
snapshots and pure planning, registry-owned lifecycle behavior, and causal observation. Signed
Phase-2 artifact discovery, lossless manifest editing, portable lock encoding, repositories, pair
coordination, and lock hierarchy remain authoritative. G4A-01 composes and minimally extends those
seams; it does not replace them.

This is authorized, credential-free local work for the open-source Skillsmith CLI. Tests use
temporary directories, fixture registries, hermetic Git remotes, deterministic clocks/IDs, and
synthetic artifacts only.

## Product value and before/after

The work has high product value because the shortest lifecycle commands become reproducible by
default:

| Concern          | Before                                                        | After                                                                                     |
| ---------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Install intent   | Live placement and local ledger only                          | Complete portable declaration and exact lock intent, plus independent live placement      |
| Uninstall intent | Live removal and local ledger only                            | Declaration/lock retained through partial removal, then removed after the group completes |
| Temporary work   | Every install is implicitly live-only                         | `--no-save` explicitly requests a live-only change without inspecting portable state      |
| Destination      | Snapshot is selected primarily from placement scope           | Explicit file, then unique declaration owner, then new destination by effective scope     |
| Ambiguity        | Portable ownership is not part of install/uninstall execution | Dual owners refuse with exit 2 before any write; force cannot override                    |
| Output           | No exact portable effect                                      | Save mode, exact pair or explicit none, per-group effects, drift, and scheduling outcome  |

This unlocks later Phase-4 plan/apply and sync work because install/uninstall finally produce the
same manifest, lock, operation, and result vocabulary those commands consume. It also gives
Phase-5 update/undo/GC a truthful distinction among declared, live, and local-ledger state.

## Architecture verdict

The accepted design activates existing abstractions rather than introducing new ones:

1. use the existing artifact discovery snapshot and `selectManifestDestination`;
2. resolve the exact selected pair once and pass it into acquisition snapshot reading;
3. use existing manifest edits and portable lock serialization;
4. emit existing `write-manifest` and `write-lock` operation kinds through the pure acquisition
   planner;
5. activate the existing operation dependency metadata in the scheduler;
6. hold the existing artifact group/member locks before ledger/live execution;
7. add one lease-bound pair commit method to the existing artifact coordinator; and
8. project the richer domain result through additive install/uninstall v2 wire codecs.

The plan explicitly rejects a generic desired-state service, repository base class, unit of work,
pipeline, workflow engine, second coordinator, second scheduler, new journal format, composite
manifest layer, invocation-wide atomicity claim, or duplicated artifact editor/serializer.

## Frozen save-mode clarification

The consolidated plan contains two phrases that are contradictory for `--no-save`: every mutation
names a selected artifact pair, while no-save rejects artifact selectors and must not discover or
write portable state. G4A-01 resolves this narrowly:

- `saveMode = "desired-state"` selects and reports one exact pair;
- `saveMode = "live-only"` sets `artifactPair = null`, reports selection `none/no-save`, reports
  portable state as not inspected or changed, and performs no portable owner discovery or
  artifact-content read;
- each affected placement reports drift as `not-evaluated` with the conditional future effect
  `depends-on-selected-manifest`; and
- `--no-save` conflicts with both `--file` and `--lockfile`.

This is a wording correction, not a product-scope change. “Always report the selected pair” means a
saving execution reports its pair; no-save explicitly reports that no pair was selected. Unrelated
malformed or dual-owner portable files therefore cannot make a valid no-save operation fail.

Dry-run preserves the same selection rule. A saving dry-run resolves and reports the prospective
exact pair and effects but writes nothing. A no-save dry-run reports `artifactPair = null`,
selection `none/no-save`, and drift `not-evaluated` without portable discovery. Only a later
`status` command may establish whether live and selected desired state actually differ.

## Command option and usage contract

The current single declarative command registry gains only the already-approved options:

### Install

- singular `--file <path>`;
- singular `--lockfile <path>`, requiring `--file`;
- `--no-save`, conflicting with `--file` and `--lockfile`; and
- singular `-p, --path <dir>`.

Existing rules remain: `--ref` requires exactly one source and conflicts with an inline `@ref`
even when equal; `--path` requires exactly one source and one effective tool (automatic tool
selection is valid only when it resolves exactly one); `--deep` conflicts `--no-verify`; `--yes`
conflicts `--dry-run`; any two scope forms conflict even when equivalent; repeated singular
`--file`, `--lockfile`, `--ref`, or `--path` are usage errors; duplicate tools deduplicate in
registry order; and force never resolves selection, ownership, portability, verification,
capability, or approval errors.

### Uninstall

- singular `--file <path>`;
- singular `--lockfile <path>`, requiring `--file`;
- `--no-save`, conflicting with `--file` and `--lockfile`; and
- `--continue-on-error`.

Existing rules remain: `--all-scopes` conflicts with any singular scope form; `--yes` conflicts
`--dry-run`; any two singular scope forms conflict even when equivalent; repeated singular
`--file` or `--lockfile` are usage errors; force changes only bounded selected-removal conflicts;
and approval remains separate from force.

Approval is required only for multiple resolved declaration groups or a force plan containing
backup-and-replace. A normal single install or managed uninstall is prompt-free. A non-TTY
approval case requires `--yes`; `--no-prompt` never grants approval. `--no-prompt` remains valid
with dry-run, while `--yes` does not.

All new relations are declared in the shared registry and enforced before project resolution,
source acquisition, ownership lookup, or mutation. Help, completion, migration-ledger comparison,
and option-contract tests consume the same registry; command modules do not duplicate the rules.

## Artifact destination and ownership

Saving install/uninstall resolves one declaration-name set, takes one discovery snapshot, and calls
the existing destination selector with this precedence:

1. explicit singular `--file`, with sibling lock unless an explicit `--lockfile` is also supplied;
2. the one selected-project/project-root/user manifest already declaring the resolved name;
3. exit-2 refusal naming every owner when two candidates declare the name;
4. for a new install declaration, project scope selects
   `<projectRoot>/skillsmith.toml`; and
5. for a new install declaration, user scope selects
   `$XDG_CONFIG_HOME/skillsmith/skillsmith.toml`.

The selected artifact path never relocates project live roots or ledger identity. An explicit
project file may intentionally own a user-scoped declaration. A request whose resolved declarations
belong to different manifests refuses before mutation because one invocation has one artifact pair.
Two sources resolving to the same manifest declaration name also refuse before mutation; force
cannot convert that ambiguity into sequential replacement.
Every candidate is shape-checked before ownership is inferred. Exact legacy project configuration
adds the existing visible `migrate-project-config` prerequisite; mixed, empty, malformed,
nonportable, or unknown shapes refuse without writes.

Uninstall uses `mode = "remove"` and never invents a destination for an absent declaration. A
truly absent live/ledger/declaration target is an exit-0 noop. A declared-only/live-absent target is
not the same case: it removes desired-state intent after the selected group is proven complete. An
explicit absent `--file` still reports that exact requested pair with both artifacts `not-write`;
it does not create either file.

## Persistent install intent

A resolved saving install group persists the complete requested declaration, independent of which
tool placements happen to succeed locally:

- credential-free canonical source identity and selected skill name;
- requested ref, or resolved full SHA when `--pin` is set;
- the complete unique nonempty requested tool list;
- effective user/project scope;
- `placement = "copy"` for `--direct`, otherwise canonical symlink default; and
- a normalized `./project-relative` or `~/home-relative` custom path.

The lock records source resolution, requested ref, resolved SHA, source path, content hash, and the
manifest semantic hash. It never records placement paths.

Force, strict/deep/no-verify, continue/fail-fast, approval, dry-run, JSON, quiet/verbose/debug,
transaction IDs, journals, store paths, literal acquisition input, credentials, and skipped gate
policy do not persist. A skipped verification remains a local ledger fact. A default-saving custom
path that is absolute, drive/UNC-qualified, escaping, store/ledger/dev-owned, or otherwise
nonportable refuses before mutation and recommends a portable path or `--no-save`.

After source identity/reference/content resolution succeeds, install commits the complete
declaration/lock pair before its selected live pairs. If one live pair then fails, successful pairs
remain committed and missing pairs are declared-but-missing drift. Same-operation rerun converges
only the incomplete work. A source that fails before resolution writes nothing.

## Uninstall intent and retention

For each selected declaration/target group:

- live removals remain per tool/scope and retain the existing store/source-checkout and backup
  policy;
- the declaration and its lock entry remain byte-for-byte present while any selected removal
  fails, is cancelled, or is skipped;
- after every selected removal succeeds or is already acceptably absent, remove exactly those tools
  from the manifest declaration; when declared tools remain, retain the existing lock entry and
  regenerate only the lock's root `manifestHash` against the reduced manifest declaration;
- only when no declared tools remain does the coordinated pair update perform sequential
  lease-held manifest and lock commits to remove the declaration and corresponding lock entry
  without peer-writer interleaving;
- the lossless manifest writer preserves defaults, registry data, comments, formatting, and the
  manifest file itself; the canonical lock is regenerated with all remaining entries, including a
  valid zero-entry lock when the last entry is removed;
- uninstall never implicitly deletes a manifest and never creates an absent empty manifest; and
- exact legacy project configuration is migrated only as an explicit prerequisite to a real
  removal, never merely to record absence.

Default scheduling marks later independent target groups `skipped-after-failure`;
`--continue-on-error` permits them to run. Cancellation stops remaining work. Successful earlier
groups remain committed. Within an incomplete group, successfully removed placements are
`desired-without-live` until rerun because portable intent is retained. No invocation-wide rollback
or `--atomic` surface is claimed.

## Operation plan and dependency semantics

G4A-01 uses the existing operation vocabulary and activates its existing dependency field.
Planning remains pure and execution never replans under lock.

Each saving install group whose declaration changes contains:

```text
migrate-project-config? -> write-manifest -> write-lock -> every tool placement operation
```

When the complete declaration already matches but its lock entry is absent or stale, the group
contains only `write-lock -> every tool placement operation`. Rewriting the human manifest solely
to manufacture a dependency edge is forbidden. When both declaration and correlated lock entry
already match, the group is an unchanged artifact group and its live operations need no artifact
write dependency. These are the only two omissions from the full saving-install chain.

Each saving uninstall group contains:

```text
migrate-project-config? -> every selected tool removal operation
every selected tool removal operation -> write-manifest -> write-lock
```

No-save groups contain only live/ledger operations. Artifact operations have null pair identity;
live operations retain one deterministic pair identity per tool/scope. The two artifact operations
describe their own manifest and lock before/after images. Each uses the existing artifact-pair
coordinator with `keep` for the other member, so its reported before/after image matches one
physical commit. The outer lease prevents a peer writer from interleaving between the sequential
manifest and lock operations. No paired-operation executor or second transaction coordinator is
added.

The canonical plan builder performs a deterministic stable topological order using the existing
operation comparator only as the ready-node tie-break. Dependencies may point in either direction
relative to the initial comparator order. It rejects dangling, duplicate, self, cross-group, or
cyclic dependencies. The scheduler:

- starts an operation only after every dependency has the exact outcome `succeeded`;
- returns `skipped-after-failure` without starting an unmet dependent;
- continues independent tool-pair operations within the current group;
- applies fail-fast/continue policy only between declaration/target groups;
- returns cancelled for all unstarted work after cancellation; and
- preserves exact result coverage/order and emits no lifecycle events for unstarted work.

This is the minimum required activation of a field already present in every operation. No generic
DAG library, worker pool, retry policy, or new scheduling model is added.

G4A-01 proves normal sequencing, ownership ambiguity/zero-write preflight, exact-pair exclusion,
under-lock revision refusal, recovery of each individual artifact or placement operation, existing
placement/ledger crash resume and opposite-operation refusal, fail-fast/continue/cancellation

## Exact artifact lock and commit seam

Saving execution acquires locks in the already-signed order:

```text
artifact central/group -> artifact compatibility members -> ledger -> live transaction locks
```

`withArtifactGroupLock` remains the artifact-group authority. Its unforgeable
`ArtifactGroupLockLease` keeps its public shape unchanged. The concrete lease retained privately by
`coordinator.ts` carries the exact pair, operation/barrier identity, signal, active state, and
member-held state. One source-internal `commitArtifactPairWithLease` function accepts that lease and
the existing mutation request, validates the exact pair/active state, calls the same internal
validation/replay/recovery/commit logic as `commitArtifactPair`, and returns the same
`ArtifactPairMutationResult`. It is not re-exported from `artifacts/index.ts`, the package root, or
public declarations.

The public `commitArtifactPair` and source-internal lease path share the same private commit body so
there is one commit implementation. The public function preserves its current lock acquisition,
observable result, and recovery behavior for existing callers. The lease-bound path:

- cannot name a different pair;
- cannot run before compatibility members are held;
- does not reacquire central or member locks;
- retains overlap recovery, parent provisioning, external-writer replay, CAS checks, cancellation,
  crash records, rollback, and cleanup;
- permits sequential manifest-then-lock commits while rejecting concurrent, nested, expired, or
  pre-member-acquisition use; and
- never exposes coordinator internals or a reusable lock token.

Acquisition supplies a small command-local `LockPort` adapter to the existing execution lock
hierarchy. Its artifact-group descriptor enters `withArtifactGroupLock`, both exact canonical
artifact-member descriptors acquire the manifest and lock lease members once, and its ledger
descriptor delegates to the existing ledger lock. The active lease remains private to the
acquisition execution binding. No lock is introduced after scheduling begins.

No-save supplies only the existing ledger lock descriptor and never constructs artifact
coordinator ports.

### Missing-parent compatibility-lock amendment

The accepted hierarchy exposed one concrete compatibility gap during step 8: the production member
lock creates a sibling lock object and therefore requires the artifact target's parent directory to
exist. A first user-scoped save or an explicit nested destination may legitimately have an absent
parent. Creating that parent before the signed snapshot would make dry-run and execute observe
different authorities; requiring it to preexist would regress the accepted destination behavior;
and creating it while acquiring the member lock would make the command's own generic revision
precondition refuse because the expected absent parent became a directory.

The bounded resolution preserves both first-save behavior and the generic precondition contract:

- acquisition opts into one source-internal coordinator seam while the authentic exact-pair central
  lease is active and before either compatibility member is requested;
- before the first lock or provisioning mutation, acquisition validates the complete descriptor
  target set (central/group, both artifact members, and ledger): no target may equal or be an
  ancestor of another, and no proper-lock sidecar (`<target>.lock`) may equal or be an ancestor of
  another descriptor target. The source-internal coordinator seam repeats the artifact-pair subset;
  pair equality and every existing alias refusal remain in force;
- the coordinator exclusively creates only the missing parent segments needed for the two exact
  targets, in deduplicated ancestor-first order, fsyncs the affected directories, and records
  lease-private path, identity, mode, parent, and nearest-preexisting-ancestor facts only for an
  exclusive creation that succeeded; an EEXIST path is never claimed by the receipt;
- an opaque lease-bound receipt can be authenticated only through another source-internal
  coordinator seam; it is not added to `ArtifactGroupLockLease`, `coordinator-types.ts`, artifact
  indexes, package-root exports, or public declarations;
- after both compatibility members are released, an execution that made no physical artifact
  commit removes receipt-owned directories deepest-first only when every recorded identity is
  unchanged and the directory is still empty, then fsyncs the surviving parent;
- a successful changed commit or an error proved durable-after consumes the cleanup authority and
  retains the now-required parents; unchanged, precondition-refused, cancelled-before, lock-refused,
  and durable-before paths remain eligible for cleanup; and
- preexisting/EEXIST, nonempty, replaced, retargeted, or otherwise unproved directories are never
  removed. A process crash between exclusive creation and cleanup may leave only the same empty,
  mode-0700 parent residue already admitted by the coordinator's signed provisioning boundary; it
  may not leave a portable artifact, recovery record, or reusable authority. Successful reverse
  cleanup restores the created namespace and artifact-byte absence, not the nearest existing
  directory's historical timestamps: mkdir, rmdir, and fsync necessarily change filesystem
  metadata that this authority neither snapshots nor promises to restore.

The acquisition controller may normalize exactly one self-authored revision delta while that
receipt and lease are active: the original manifest or lock target was absent, the target remains
absent, and the only changed revision facts are its direct parent changing from absent to the
receipt-created same-identity directory and the deterministically derived absence/revision digests.
The coordinator must also revalidate every receipt-owned segment and the nearest preexisting
ancestor before accepting that equivalence. A target appearance, wrong resource/domain/path,
unreceipted directory, foreign or expired lease/receipt, identity or mode change, changed ancestor,
or any additional represented revision delta refuses before mutation. Unrelated sibling entries are
intentionally not revision facts: this matches the existing present-parent revision rule that
ignores sibling/link-count churn, and a foreign sibling merely makes reverse cleanup retain the
now-nonempty directory. The wrapper returns the original frozen expected revision only after this
proof, so the generic execution precondition comparator and all non-artifact preconditions remain
unchanged.

Focused evidence must cover shared, distinct, and nested missing parents; partial provisioning and
lock-acquisition failures; cancellation; unchanged and durable-before cleanup; changed and
durable-after retention; identity replacement and foreign nonempty directories; forged, foreign,
and expired receipts; target appearance and every non-parent revision delta; equality, ancestor,
and sidecar-ancestor conflicts across central, member, and ledger descriptors; member-release-
before-cleanup ordering; crash residue/retry convergence; no-save nonconstruction; and the exact
`central -> scaffold -> members -> ledger -> preconditions -> operations` hierarchy.

## Snapshot and repository boundary

The acquisition reader accepts a private discriminated artifact projection:

```ts
type AcquisitionArtifactSnapshot =
  | {
      mode: "selected";
      pair: ResolvedArtifactPair;
      manifest: /* existing exact observed manifest state */;
      lock: /* existing exact observed lock state */;
    }
  | { mode: "none" };
```

The selected branch uses the existing stable artifact reader with the exact pair for repository
IDs, observations, operation locations, and preconditions. This prevents a pure plan from reading
one pair and committing another. The none branch is not an absent filesystem observation: it reads
no artifact path, supplies no fabricated target/parent identity or revision, and contributes no
artifact expected revision, location, precondition, operation, or result. Ledger/live/store/
capability state continues through the existing acquisition readers. This is a private
acquisition-specific projection in `acquire/plan.ts`/`execute.ts`, not a new generic snapshot or
repository framework.

Artifact destination discovery and pair resolution occur after source/name resolution but before
any plan or write. Invocation-level syntax, dual ownership, split ownership, invalid shapes,
nonportable saved paths, and invalid pair selectors all refuse before live/artifact mutation.

## Wire, domain report, and human output

Strict install/uninstall v1 codecs remain registered and byte-compatible. They keep their existing
schemas, formatting, enum sets, and explicit mappers. G4A-01 adds `install@2` and `uninstall@2` to
the existing contracts/v2 entry point and advances only current CLI mappings/renderers to v2.
Legacy v1 mappers remain typed against their frozen legacy report shapes and continue producing the
exact historical v1 bytes. A rich v2 report is never silently downgraded to v1 because its
desired-state, selection, drift, force, and scheduling facts are not representable there.

The version boundary is explicit in the domain as well as the wire:

- existing `InstallResult`, `InstallReport`, `UninstallResult`, `UninstallReport`, and
  `UninstallAction` remain frozen legacy shapes used by the v1 mappers;
- the legacy report shapes accept only absent/`1` domain `reportVersion`, while new
  `CurrentInstallResult`, `CurrentInstallReport`, `CurrentUninstallResult`, and
  `CurrentUninstallReport` require `reportVersion: 2`;
- the current uninstall action union is the frozen legacy union plus `skipped`; an unstarted
  scheduler row is never encoded as noop, refusal, failure, cancellation, or a missing row;
- current acquisition/application services, human/JSON renderers, and v2 mappers use only the
  current report types;
- the v1 mappers accept only the legacy types and also refuse a runtime `reportVersion: 2` value,
  preventing casted JavaScript from silently dropping v2 facts; and
- `toCurrentCompatibilityAction` remains the frozen legacy compatibility edge and continues to
  refuse uninstall skipped projection, as signed P3B-TS01 requires. Current uninstall v2 result
  construction does not call it for scheduler-only rows.

Uninstall's human action enum adds `skipped`; `executionOutcome` preserves the exact scheduler
fact. V2 requested input adds `batchPolicy: "fail-fast" | "continue-on-error"` and install
`path: string | null`. The summary adds group-level
`desiredState: { changed, unchanged, retained, notWritten, failed }` counts so a declared-only

credential-bearing source input remains redacted before encoding. The wire report is a bounded
projection of the existing immutable plan/results; it does not expose the whole plan as a second
public transaction model.

facts have null conflict/target/behavior/backup fields; conflict type is exactly
`unmanaged-target | modified-managed-target | destination-exists | source-changed`; target is the

`refuse / backup-and-replace / required`, while source-changed requires
`refuse / replace / none`. The v2 codec mirrors that discriminated union recursively and strictly.

`current-renderers.ts` changes only its uninstall stderr projection: scheduler-only skipped rows
produce no warning/error, as their canonical v2 action/outcome and summary are already rendered on
stdout and the earlier failed row owns the nonzero exit. It does not learn artifact semantics.
`acquireExitCode` stops accepting either report generation and instead accepts its actual minimal
structural input, `Readonly<{ results: readonly { error?: SkillSmithError }[] }>`, so frozen v1 and
current v2 reports share the same unchanged error/exit precedence.
The existing CLI install/uninstall golden files remain immutable v1 fixtures. The owned JSON test
checks them through explicit v1 mappers/codecs, then checks current rendering separately against
exact v2 facts; current rendering is no longer compared to v1 goldens.

The v2 codecs are strict, schema-version 2, conservative, and have no implicit v1-to-v2 decoding
migration. V1 and v2 are separate named public contracts; the current command mapping selects v2.

Human output derives from the same domain facts:

- saving success prints `Saved desired state:` and the exact manifest/lock paths;
- saving dry-run prints `Would save desired state:` and the same pair;
- no-save prints `Portable desired state: not inspected or changed (--no-save)` plus the
  conditional consequence that a later apply follows whichever manifest is selected then;
- ambiguity/refusal prints no success heading and leaves stdout/JSON structurally truthful;
- per-group artifact effects and skipped-after-failure are visible without inferring from reason
  strings; and
- quiet/verbose/debug and JSON stdout/stderr rules remain owned by the shared runtime.
