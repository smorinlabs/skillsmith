# P17-G5-03 Ready plan

## State and boundary

P17-G5-03 adds one public `undo` lifecycle for scope-aware pending abort and eligible committed
reversal. It extends the already-signed Phase-3B transaction/history/recovery foundation and the
Phase-1 selection/application/runtime foundations. It does not create a second transaction engine,
guess the latest operation globally, reinterpret retention, or implement update reversal.

The group has exactly 13 required-now validations:

- signed impacted replays `EWP-CMD-DEV-TS05` and `EWP-CMD-PROMOTE-TS05`;
- new undo selectors TS01, TS02, and TS04 through TS09;
- `EWP-P5-TS03`, `EWP-WF05`, and `EWP-WF11`.

`EWP-CMD-UNDO-TS03`, `EWP-CMD-UPDATE-TS07`, and `EWP-WF09` remain downstream under
P17-G5-05 because all three require update-to-undo lock restoration. They remain reciprocal
secondary coverage for G5-03 and are not executed or advanced here.

## Public request and selection contract

The exact command is `skillsmith undo <skill...> | --all` with repeatable `--tool`, one
`--scope user|project` or matching `--user`/`--project` sugar, `--dry-run`, `--yes`,
`--continue-on-error`, and `--json`.

Validation happens before context discovery or I/O:

- no target and no `--all` is usage exit 2;
- positional targets conflict with `--all`;
- `--yes` conflicts with `--dry-run`;
- scope sugar is exclusive and must agree with `--scope`;
- repeated singular scope values refuse;
- unknown tools are usage errors and registered tools without undo capability are capability exit 4.

Candidate observation is bounded to user plus current-project history. Outside a project, project
scope requires an explicit valid project context and is never inferred. An unscoped name matching
both user and current-project history is ambiguous; explicit scope or one exact placement path
selects one. Explicit unmatched targets refuse and never widen. `--all` spans both writable scopes
unless narrowed and reports `explicit-all`. Active tool/scope filters that reduce a valid all-set to
zero are a successful explained no-op.

For each selected pair, an attached pending logical or preserved legacy journal wins over committed
history. Otherwise the newest retained committed journal for that exact pair anchor is selected.
An ineligible newest candidate refuses; undo never skips it to expose an older action. Repeated
names, paths, transaction IDs, or multi-anchor matches deduplicate to one canonical group without
merging different scopes/tools.

Disposition is part of candidate identity. A forward pending transaction is eligible for durable
conversion to rollback. A rollback pending transaction is eligible only to resume that same
rollback and retains whether it originated as pending abort or committed reversal through its
transaction/operation/parent linkage. The newest committed rollback for the selected parent is an
explained `already-reversed` no-op when its restored image remains current; it is never reversed
again and selection never falls through to the older forward history row. Missing or inconsistent
origin linkage refuses as invalid state.

## Immutable observation and plan

New private `undo` modules produce a deeply immutable observation and pure plan:

- `observe.ts` reads the canonical ledger, user/current-project placement facts, status journal
  correlation, retained-resource probes, capability facts, and migration state through focused
  ports/repositories;
- `plan.ts` consumes only that observation plus the normalized request and composes the shared
  snapshot-bound placement planner to create stable group, operation, precondition, check, and
  diagnostic identities;
- `types.ts` closes requests, candidate facts, plan groups, execution results, and errors;
- `execute.ts` consumes the exact approved plan through the shared placement-plan executor and
  revalidates it under the canonical lock;
- `index.ts` is the private domain entrypoint.

`undo` is added to the shared `CurrentMutatorCommand` and immutable-plan validator. Like dev and
promote, undo prohibits bounded-default selection. The existing retained-history rollback request,
planner overload, validator, and placement-plan execution input are generalized from dev/promote to
undo; no private planning or execution substitute is permitted. Alias projections continue to use
the same rollback plan and executor with `reportOp: rollback` compatibility output.

Each actionable group is labeled exactly `abort-pending` or `reverse-committed` and records source
and active transaction IDs, source and active operation IDs, parent operation ID, disposition,
phase, execution mode (`convert-to-rollback` or `resume-rollback`), operation family,
scope/tool/pair identity, before-state class, eligibility, retention requirements, and exact public
operation IDs. An `already-reversed` selection records the same disposition/parent facts as a
non-actionable no-op rather than manufacturing an executable group. Planning is deterministic under
input permutation and does not allocate clocks/IDs until a genuinely new executable group starts;
resumption reuses the existing rollback identities.

Version-1 ledger reads and dry-runs remain byte-identical and visibly prefix the shared
`migrate-ledger` operation. The first real undo performs the same signed migration under the
existing ledger lock. A migration race stales the approved plan; a legacy pending pair journal is
preserved and remains selectable only for same-operation resume or pending undo.

## Pending abort execution

Logical forward pending abort uses the signed Phase-3B sequence:

1. reobserve the selected journal, current resources, and retained resource revisions;
2. durably begin one recovery attempt with command `skillsmith-undo` and workflow `undo`;
3. call `abortPendingLogicalTransactionAfterRecoveryAttempt` to convert the same transaction ID to
   rollback disposition at `prepared` while preserving start time and parent operation identity;
4. persist that prepared rollback before any physical mutation;
5. dispatch exact placement or move-scope recovery through the existing physical authority;
6. atomically reach committed rollback history, remove pending state, and finish cleanup.

An already-pending rollback bypasses the forward-only abort reducer and resumes physical rollback
with the existing transaction/operation/parent identities. This applies both to a crash after
forward-pending conversion and to a crash during a fresh committed reversal. Missing, stale, shared,
mismatched, unowned, or unverifiable before/retained state refuses without best effort.
Cancellation before a durable boundary leaves the old phase authoritative; after a boundary it
leaves one resumable rollback phase. A crash after conversion may resume rollback only; rerunning
the forward command refuses. Pending state always wins over an older committed candidate.

A preserved v1 legacy pair journal has no logical transaction entry and never enters the v2 abort
reducer. A real mutation first performs the signed byte-preserving v1-to-v2 migration when needed,
then the existing legacy placement recovery path rolls back that same pair journal without
fabricating a logical transaction or changing its ID/schema. Crash/retry resumes the legacy path.

An overlapping standalone artifact-pair recovery record is not selected or reinterpreted by
target-bound undo. It blocks with the coordinator's exact same-operation remediation and must first
converge through that owning command. Undo never guesses correlation from artifact paths or mutates
the recovery-record format in this group.

## Committed reversal execution

Committed promote, dev, install, and uninstall reversal creates one new rollback-disposition
transaction; it never edits or removes the original committed history row. The new transaction has
fresh operation/transaction identity, the original operation as parent, and the original forward
intent orientation: `intent.before` remains the state to restore and `intent.after` remains the
state being reversed. The rollback reducer owns the inversion; undo must not invert the intent a
second time. The approved current image must equal the original `intent.after`, the new
`actual.before` records that current image, and the new `actual.after` records the restored original
`intent.before`. The original retained resources remain required to restore that prior state.

The canonical swap terminal seam becomes rollback-origin aware. Converted pending abort preserves
its signed terminal projection. A fresh committed reversal is distinguished by its active operation
and parent linkage and commits `actual.before` as the approved current/original-after image and
`actual.after` as the physically restored parent-forward-before image. It never substitutes current
state for restored state merely because the disposition is rollback. Swap crash tests prove both
origins at every durable phase and refuse inconsistent linkage.

The canonical repository/coordinator/swap authorities stage, commit, roll back, recover, and clean
the inverse work. Retention and current-resource revisions are revalidated before staging. An
edited current copy is preserved through the existing backup policy. Successful reversal appends
one complete committed history row. A pending instance resumes that same inverse transaction. Once
committed, another undo reports `already-reversed` with zero mutation when the restored image still
matches; it never reverses the rollback or falls back to older history. Stale, inconsistent, or
unrestorable state refuses without falling back to older history.

Update reversal and portable lock restoration are deliberately recognized but refused as
downstream-not-yet-available in this group. G5-05 owns UPDATE-TS07, UNDO-TS03, and WF09 and will add
that exact operation-family composition without changing G5-03 selection semantics.

## Application, approval, output, and exit policy

`undo-service.ts` normalizes the parser request, prepares once, presents one exact bulk preview,
and executes the same frozen plan after approval. Dry-run never prompts or writes. Interactive
refusal and cancellation perform no migration, ledger, live, artifact, or cleanup write. JSON and
`--no-prompt` require `--yes` for changing execution.

The exact preview contains ordered group and operation IDs. The application context gains no raw
filesystem/network/process bag; it composes existing focused runtime and artifact coordinator
ports. Mutation counts derive from exact operations/results, including truthful partial success.

`undo@1` is a strict named codec and report with:

- `kind`, `schemaVersion`, and `command` identity;
- selection source/outcome, targets, tools, scopes, and project context;
- mode and approval state;
- ordered groups with transaction/action/phase/before/eligibility/retention facts;
- disposition, source/active/parent linkage, execution mode, and `already-reversed` no-op facts;
- exact public operations, checks, results, effects, diagnostics, and summary;
- no internal journal object, capability object, stack/cause, credential, or mutable reference.

Human and JSON render the same facts. Usage/capability/state/failure/permission/cancellation remain
numeric exits 2/4/3/1/6/130 through shared application exit policy. Default scheduling stops later
groups after the first actual failure; `--continue-on-error` continues independent groups while a
real error still determines the final exit.

## Implementation-discovered ownership amendment — fresh reversal compatibility shadow

The first implementation pass proved that fresh committed reversal cannot safely publish through
the canonical placement swap while the compatibility-shadow codec treats every rollback
disposition as the interrupted-forward `rollback` physical operation. A committed reversal must
keep the parent's forward intent orientation, while its physical journal describes the inverse
operation that restores that intent's before-image. Reusing the interrupted-forward rollback path
is not an alternative: that path restores an existing backup and cannot materialize retained
dev/store state for a completed promote, dev, install, or uninstall.

The amendment adds exactly six paths:

- `packages/core/src/artifacts/ledger-codec.ts` and
  `packages/core/tests/artifacts/codec.test.ts` own the origin-aware shadow predicate and hostile
  cross-reference coverage;
- `packages/core/src/artifacts/ledger-history.ts` and
  `packages/core/tests/artifacts/ledger-writer.test.ts` own dependency-closed bounded retention and
  cleanup/crash coverage;
- `packages/core/src/status/read.ts` and `packages/core/src/status/types.ts` own one private
  lifecycle-history observation mode that skips unrelated manifest/lock reads while reusing status
  ledger/live/retention/join authority. The already-owned status read test proves that mode.

No registry, artifact schema/DTO, history-capacity, placement-runner, ledger-writer production, or
recovery-record path is added. The exact manifest changes from 78 paths at initial Ready to 84
paths: 38 production, 20 focused tests, 5 selectors/fleet, 19 signed compatibility owners, and 2
governance owners. Catalog ownership is 86 paths including this plan and its evidence record.

The codec distinction is structural and closed:

- a converted pending abort has rollback disposition with `parentOperationId` equal to its own
  operation ID and keeps the signed physical `rollback` shadow;
- a fresh committed reversal has rollback disposition with a distinct non-null parent operation,
  whose retained committed forward journal must match the rollback intent orientation, approved
  current image, and retained resources exactly;
- its sole allowed physical shadow is derived from the preserved forward before/after images for a
  committed `install`, `remove`, `link-dev`, or `promote` parent: absent forward-before restores
  through `uninstall`, development forward-before through `dev`, non-development placement before
  with absent forward-after through `install`, and non-development placement before with placement
  forward-after through `promote`; managed store-linked state normalizes consistently with pinned,
  while update, repair, move-scope, unmanaged/unrestorable, and non-placement orientations refuse;
- missing, pending, rollback, duplicate, mismatched, or otherwise inconsistent parent linkage is
  invalid ledger state, never a reason to accept another shadow operation.

Bounded history preserves that invariant transitively. Committed-history operation IDs are unique,
pending operation IDs are unique within the pending map, and a distinct-parent fresh rollback
child's operation ID cannot collide with committed history; every such parent reference resolves
exactly one committed forward row. The signed compatibility case where a legacy pending-forward
snapshot reuses its committed operation ID remains readable but never supplies fresh-parent
authority. Every protected fresh-rollback child protects its exact committed-forward parent, and fair
selection admits a child only with its parent as one deterministic unit, raising effective capacity
when required. Visible cleanup-frontier rows are dependency-closed; a parent cannot be a victim
while a surviving child depends on it. Shared retained-backup cleanup authorizes only the complete
excluded dependency closure and removes that closure together, so ordinary writes and
crash/restart never publish a child without its parent. The public capacity constant and
one-victim API remain unchanged.

Undo status observation uses a request-only `lifecycle-history` unselected-artifact mode. It is
valid only for an empty status-target set with bounded-default selection, a unique nonempty subset
of user/project scopes, exact project placement provenance whenever project is included, and a
unique caller-bounded set of known tools. Explicit scope/tool filters retain their existing source
labels; command-default tools and command-default user/current-project scopes use the existing
unbounded label within this lifecycle-only universe.
The mode reads the ledger, selected live roots, and retention probes exactly once through current
status authority, reads no manifest/lock path or bytes, and projects the existing wire-compatible
unselected artifact summary. It does not widen public status CLI grammar or change `status@1`.

Canonical forward placement shadows must preserve later reversal authority instead of hardcoding
`reversibility: none` and an empty retained set. For committed install/remove/link-dev/promote with
a non-absent forward before-image, the logical intent carries the approved operation's conditional
pair resource ID and `actual.retained` carries exactly one matching source-content resource:

- development before-image: role `store` in the journal's existing source-content retention class,
  exact machine-bound development source/link target, exact recorded content/resource digest, and
  null `retainUntil`;
- pinned or managed store-linked before-image: role `store`, exact retained store path, exact
  content/resource digest, and null `retainUntil`.

The retained resource ID is the operation's pair ID. Missing path, digest, ownership/orientation,
or ID parity is never fabricated: the journal remains visibly retention-incomplete and status
refuses reversal. Status probes the same ID/path/digest and current live image before reporting
eligible. A fresh install or fresh link-dev whose approved before-image is absent is the exact
zero-retention exception: its forward journal carries `none`/empty retention, and committed status
is reversible only when the current live image exactly matches its recorded forward after-image;
its inverse is removal. No other `none` journal becomes reversible. Swap and status tests plus TS02
prove all four command families and hostile missing/mismatched retained state.

Fresh reversal creates its logical rollback in memory and atomically publishes that journal with
the inverse physical shadow at the first write-ahead placement boundary. It never persists a
logical pending placement journal without its required pair shadow. A crash after that boundary
resumes the inverse physical shadow through normal placement resume; a converted pending abort
continues through the existing backup-restoring rollback path. Focused codec and swap/recovery tests
must cover every allowed mapping, invalid linkage/orientation, the atomic first boundary, and resume
at every durable phase before the amendment is accepted as implemented.

Four implementation-free selector assertions are corrected without changing their paths, IDs, or
behavioral scope. TS01 expects the exact shared inverse sequence `migrate-ledger`, then `remove` for
its legacy pending dev whose before-image is absent; no synthetic rollback/restore operation kind is
added. That preserved v1 forward-pending pair journal has no published rollback transaction to
resume, so TS01 reports `convert-to-rollback` and routes through the signed legacy backup-restoring
path without fabricating a logical transaction. For pending-abort candidates, a journal already
carrying rollback disposition reports `resume-rollback`. This distinction does not change a fresh
committed-forward reversal candidate's `resume-rollback` mode; its first atomic write publishes the
new distinct-parent rollback child and inverse physical shadow. TS08 keeps JSON aliases strict
flip@4 and stderr-clean, compares their operations/checks/
diagnostics to direct undo, then separately invokes the human alias and requires the structured
deprecation warning to name `skillsmith undo` and the frozen removal version. Because operation,
pair, check, and precondition identities intentionally include machine-bound project, source, store,
ledger, and live locations, the direct and alias dry-runs use the same seeded fleet and each proves
that its snapshot is unchanged before their exact equality is asserted; comparing separate
`mkdtemp` fleets would test different semantic identities rather than shared routing.
