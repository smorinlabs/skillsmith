# P17-G2-02 implementation plan

## Scope and prerequisites

P17-G2-02 owns the pure portable-resolution artifact authority: the closed version-1 hash domain
registry and framing algorithm, manifest semantic and exact-byte digests, the strict canonical
portable-lock model and serializer/reader, pure manifest/lock relationship classification, and a
portable source-content projection/hash over injected read capabilities.

Its primary IDs are exactly:

- `D-004`;
- `EWP-CF-027`;
- `EWP-P2-T03`;
- `EWP-P2-TS03`.

P17-G2-01 is signed off at `944c41118cf0cc4710fb671a658d3fac443d7754`, with accepted
implementation pin `0751951bbb413dd80f5dc6e67eec8725d18c9735`. Phase 2 is active and its entry
gate is passed. G2-02 consumes G2-01's normalized manifest, semantic projection, credential-free
source identity, requested-ref validation, and source-relative path rules without reparsing or
creating a competing model.

Required-now validations are exactly:

```sh

bun test tests/ergonomics/phase/EWP-P2-TS03.test.ts --test-name-pattern EWP-P2-TS03
```

## Ownership and overlap boundaries

### G2-01 input authority

G2-01 remains the sole owner of strict manifest reading, normalized manifest values, source/ref/
path validation, and `projectManifestSemantics`. G2-02 hashes that exact projection. It does not
reparse TOML, reorder raw declarations independently, reinterpret legacy manifests, or introduce a
second semantic model.

### G2-02 pure artifact authority

G2-02 owns:

- a closed public runtime registry for all seven version-1 hash domains and one generic hasher;
- exact manifest-semantic and manifest-bytes canonical inputs;
- the portable lock v1 immutable model, strict reader, canonical serializer, digest, and pure
  relationship state;
- a portable source-content v1 immutable model, canonical projection, serialization, and digest;
- stable, secret-safe state errors for these pure boundaries.

It uses injected read and metadata capabilities only. It performs no write, lock acquisition,
staging, replacement, recovery, repository persistence, process execution, or CLI rendering.

### G2-03 coordination boundary

G2-03 owns generalized human-artifact editing, artifact-group coordination, absent-target locking,
exact external-writer guards, safe replan/refusal, staged writes, pair atomicity, crash recovery,
SIGINT behavior, and shared recursive redaction. It must call G2-02's pure lock/hash authority and
must not add a second lock serializer.

### G2-05 codec and compatibility boundary

G2-05 owns the reusable artifact-codec registry, versioned repositories, migrations, compatibility
inventory, and the policy for interpreting legacy ledger/store hashes. It registers/adapts G2-02's
lock authority rather than cloning it.

`packages/core/src/place/store.ts::contentHashOf` is a compatibility-only, unversioned digest used
by existing ledger v1 records, integrity checks, and store paths. G2-02 must not replace, wrap,
delegate, or silently reinterpret it. One fixed regression pins its current result for a
non-executable `SKILL.md` containing the byte `z` to
`sha256:e6701e2073659fd193452d2a55dc7d457f33d4719fbc7ea24e3b010d22a2ebc7`. The new
`source-content` authority exists alongside it until G2-05 performs an explicit version-aware
migration.

### Later hash projections

G2-02 publishes the `resource`, `selection-set`, and `capability` domain names and can hash
caller-supplied canonical bytes in those domains. Their canonical-input builders and models belong
to later planner/executor groups and are not invented here.

## Closed hash schema v1

### Public authority

The public runtime surface is centered on these exact names:

- `HASH_SCHEMA_VERSION`;
- `HASH_DOMAINS`;
- `hashCanonicalInput`;
- `parseArtifactDigest`;
- `hashManifestSemantics`;
- `hashManifestBytes`.

`HASH_SCHEMA_VERSION` is exactly `1`. `HASH_DOMAINS` is a frozen tuple in this exact order:

1. `manifest-semantic`;
2. `manifest-bytes`;
3. `lock-canonical`;
4. `source-content`;
5. `resource`;
6. `selection-set`;
7. `capability`.

Public types include `HashSchemaVersion`, `HashDomain`, `ArtifactDigest`, and `ArtifactHashError`.
An `ArtifactDigest` is branded only after exact runtime validation. All published constants and
normalized products are recursively frozen.

The exact callable surface is synchronous and uses the existing core `Result` type only where
caller data can refuse:

```ts
hashCanonicalInput(
  domain: string,
  schemaVersion: number,
  canonicalInput: string | Uint8Array,
): Result<ArtifactDigest, ArtifactHashError>

parseArtifactDigest(value: unknown): Result<ArtifactDigest, ArtifactHashError>

hashManifestSemantics(manifest: NormalizedManifestV1): ArtifactDigest

hashManifestBytes(source: string | Uint8Array): ArtifactDigest
```

These functions never throw for caller-data validation. `hashManifestSemantics` is total for a
G2-01 normalized manifest; `hashManifestBytes` is total for its typed input. The generic function
returns an error before hashing an unsupported domain/schema. Every `Uint8Array` is synchronously
copied before hashing, so later caller mutation cannot alter the result. A string is encoded with
the WHATWG `TextEncoder` UTF-8 algorithm, including its specified U+FFFD replacement of an unpaired
UTF-16 surrogate; callers requiring exact external bytes use `Uint8Array`.

`ArtifactHashError` is exactly:

```ts
interface ArtifactHashError {
  readonly code: 'artifact-hash';
  readonly reason: 'unknown-domain' | 'unsupported-hash-schema' | 'invalid-digest';
  readonly field: 'domain' | 'schemaVersion' | 'digest';
  readonly message: string;
}
```

The reason/field/message mapping is total and fixed:

| Reason | Field | Message |
|---|---|---|
| `unknown-domain` | `domain` | `artifact hash domain is unsupported` |
| `unsupported-hash-schema` | `schemaVersion` | `artifact hash schema is unsupported` |
| `invalid-digest` | `digest` | `artifact digest is invalid` |

### Exact framing and digest grammar

For domain `D`, schema version 1, and canonical input bytes `B`, the hashed byte sequence is
exactly:

```text
UTF8("skillsmith:" + D + ":v1") || 0x00 || B
```

SHA-256 is serialized as exactly `sha256:` followed by 64 lowercase hexadecimal characters.
String canonical input is encoded once as UTF-8; `Uint8Array` input is copied and hashed byte for
byte. No newline, length prefix, BOM, normalization, platform encoding, or implicit stringify is
added by the generic hasher. Unknown runtime domains, unknown schema versions, malformed digests,
uppercase hex, alternate algorithms, surrounding whitespace, and non-64-byte hex forms refuse.

Golden vectors hard-code the exact framed bytes and digest for all seven domains over the same
`fixture` byte input, plus binary input containing NUL and invalid UTF-8. Tests compute neither the
expected prefix nor the expected digest with the production helper.

### Manifest canonical inputs

`hashManifestSemantics` accepts a G2-01 `NormalizedManifestV1`. Its canonical bytes are exactly the
UTF-8 encoding, with no trailing LF, of `JSON.stringify(projectManifestSemantics(manifest))`.
G2-01's projection already establishes schema field order, sorted names/tools, explicit null
sentinels, and normalized sources/refs/scopes/placements/paths. G2-02 neither reparses the manifest
nor defines an alternate projection/serializer. Tests pin both the exact JSON bytes and digest.

Formatting, comments, raw TOML key/declaration/tool ordering, permissions, and newline form do not
change the semantic digest. Every version/default/registry/declaration/name/source/ref/tools/scope/
placement/path addition, removal, or semantic change does. A raw ordering change that normalizes to
the same value remains equivalent.

`hashManifestBytes` accepts only caller-supplied exact string or `Uint8Array` bytes and uses the
`manifest-bytes` domain. Presentation edits change this digest. It is local concurrency evidence
only and is never stored in a portable lock.

## Portable lock v1

### Immutable model and public API

The public surface adds:

- `LOCK_VERSION`;
- `readPortableLockSource`;
- `serializePortableLock`;
- `hashPortableLock`;
- `correlatePortableLock`.

Public types include `PortableLockV1`, `PortableLockSkillV1`, `PortableLockStateError`,
`PortableLockRelationship`, and its closed reason/fact types. The serializer accepts a normalized
lock value and validates/owns/freezes a fresh copy before producing bytes. The reader returns only
a recursively frozen normalized lock or a state error. No public constructor accepts a literal
clone URL, runtime path, store path, credential-bearing acquisition string, or IO capability.

The exact callable surface is synchronous:

```ts
readPortableLockSource(
  source: Uint8Array,
): Result<PortableLockV1, PortableLockStateError>

serializePortableLock(
  lock: Readonly<PortableLockV1>,
): Result<string, PortableLockStateError>

hashPortableLock(
  lock: Readonly<PortableLockV1>,
): Result<ArtifactDigest, PortableLockStateError>

correlatePortableLock(
  manifest: NormalizedManifestV1,
  lock: PortableLockV1 | null,
): PortableLockRelationship
```

No function throws for data validation. The reader synchronously owns a copy of the input bytes,
decodes with fatal UTF-8, and compares canonical re-encoded bytes to that owned copy. Invalid UTF-8
is malformed; a UTF-8 BOM is explicitly noncanonical. The serializer returns the canonical
JavaScript string whose UTF-8 encoding is authoritative. It and `hashPortableLock` validate and
copy the complete typed value rather than trusting a fabricated mutable object. Correlation is
total only over a G2-01 normalized manifest and a normalized lock returned/accepted by this
authority; malformed bytes refuse before it is called.

The normalized v1 model is:

```ts
interface PortableLockV1 {
  readonly version: 1;
  readonly hashSchemaVersion: 1;
  readonly manifestHash: ArtifactDigest;
  readonly skills: readonly PortableLockSkillV1[];
}

interface PortableLockSkillV1 {
  readonly name: string;
  readonly source: string;
  readonly requestedRef: string | null;
  readonly resolvedSha: string;
  readonly sourcePath: string;
  readonly contentHash: ArtifactDigest;
}
```

Names are unique and sorted with the same explicit UTF-16 code-unit comparator used by the
manifest projection. `manifestHash` must be an exact artifact digest and is the
`manifest-semantic` digest by contract. `resolvedSha` is exactly 40 lowercase hexadecimal
characters; lock schema v1 deliberately records Git SHA-1 and does not guess a 64-hex future form.
`contentHash` is an exact `source-content:v1` digest by contract.

### Canonical source/ref/path correlation

The lock `source` is a credential-free, total, unambiguous textual projection of G2-01's
`CanonicalSourceIdentity`: always `<host>/<repository>`, including `github.com`, followed by
`//<source-relative-path>` when the canonical identity has a non-null path. The reader treats the
first segment as the host and the remaining pre-`//` segments as the repository, requires at least
two repository segments, validates by the exact G2-01 source-identity grammar, and requires
reserialization to reproduce the same string. It never guesses host versus GitHub shorthand from a
dot in a segment. Thus `{ host: 'github.com', repository: 'acme/tools', path: null }` is exactly
`github.com/acme/tools`, and `{ host: 'git', repository: 'acme/tools', path: 'skills/a' }` is
exactly `git/acme/tools//skills/a`.

The spelling contains no scheme, transport user, `.git` suffix, query, fragment, credentials,
literal acquisition input, or local path. Validation feeds exactly `https://` plus the lock-source
string to G2-01 `normalizeSourceIdentity`, compares the resulting object field-for-field with the
expected identity, and then requires explicit-host reserialization to reproduce the original lock
spelling. The transport prefix is validation-only and never retained or serialized. This makes a
single-label host such as `git` total without asking G2-01's shorthand parser to interpret the bare
lock spelling.

`requested_ref` is omitted entirely when the manifest ref is null. When present it must pass the
existing G2-01 requested-ref validator and must reproduce the exact normalized ref.

`source_path` is `.` when the source identity's path is null. Otherwise it is exactly the normalized,
nonempty relative POSIX path accepted by G2-01's source-identity grammar, without a leading `./`,
and must equal the path embedded in the canonical source identity. Absolute, drive, UNC, backslash,
empty, dot-segment, traversal, whitespace/control, and noncanonical forms refuse. Placement-path
reserved-name rules for local store/ledger/dev destinations are not applied to a legitimate path
inside a source repository.

### Exact canonical TOML bytes

The one canonical spelling is:

```toml
version = 1
hash_schema_version = 1
manifest_hash = "sha256:<64 lowercase hex>"

[[skills]]
name = "<name>"
source = "<canonical source>"
requested_ref = "<requested ref>"
resolved_sha = "<40 lowercase hex>"
source_path = "<canonical source path or .>"
content_hash = "sha256:<64 lowercase hex>"
```

Root keys occur exactly in the shown order. Entries are sorted by name. Entry keys occur exactly
in the shown order, except `requested_ref` is absent rather than empty/null when the normalized ref
is null. There is one empty line before every `[[skills]]` block, which also produces exactly one
empty line between adjacent blocks. An empty lock ends immediately after `manifest_hash`. Bytes use
LF only and exactly one final LF. Comments, CRLF, BOMs, alternate whitespace, reordered keys or
entries, single/literal/multiline strings, and missing/extra final newlines are noncanonical;
version/hash-schema token errors follow the more specific reader precedence below.

The canonical TOML basic-string encoder rejects unpaired UTF-16 surrogates and ASCII control/DEL
characters, escapes `"` as `\"` and `\` as `\\`, and emits every other Unicode scalar directly as
UTF-8. It never chooses an alternate escape. Field validators remain stricter where required.

`hashPortableLock` hashes the exact canonical serialization, including its one final LF, in the
`lock-canonical` domain. A checked-in fixture pins both bytes and digest.

### Strict version-first reader

The reader uses this exact precedence:

1. own the bytes; zero length is `empty-lock`;
2. fatal UTF-8 decoding failure is `malformed-lock`; a leading BOM is `noncanonical-lock`;
3. TOML parser failure, including duplicate assignments/tables and syntactically invalid leading-
   zero/unsafe integer forms, is `malformed-lock`; a parsed trivia-only document is `empty-lock`;
4. discriminate the parsed root `version` value and its source token;
5. for v1, discriminate `hash_schema_version` and its source token;
6. validate exact v1 keys, types, values, names, and ordering;
7. reserialize and require exact byte equality, otherwise `noncanonical-lock`.

At step 4, `version` must be one positive safe base-10 integer token matching `[1-9][0-9]*`. A
valid future integer version returns `unsupported-lock-version` before unknown future keys are
considered. Missing, float, exponent, signed, zero, negative, unsafe, string, or boolean forms are
`invalid-version`, and no v0 migration exists.

For version 1, `hash_schema_version` receives the same integer-token treatment. Any valid integer
other than 1 returns `unsupported-hash-schema`; malformed forms return an invalid-field error.
Only then does strict v1 decoding require exactly the three root keys and exactly the entry keys
described above. Unknown or missing keys, wrong types, duplicate names, invalid sort order,
noncanonical source/ref/path/SHA/digest, empty/malformed input, and TOML duplicate-key/table errors
refuse. Finally, normalized parse -> serialize bytes must equal the original bytes exactly; a
mismatch is `noncanonical-lock` before relationship classification.

Accordingly, comments, whitespace, key/entry order, quote spelling, and final-LF differences that
remain syntactically and semantically valid reach step 7 and are `noncanonical-lock`. A signed,
float, exponent, underscored, or otherwise noncanonical version/hash-schema token is an invalid
version/field when the parser accepts it, not a generic canonical-byte mismatch. Parser-rejected
numeric spellings remain `malformed-lock`.

### Stable secret-safe error contract

`PortableLockStateError` has `code: 'portable-lock-state'`, `exitCode: 3`, a closed `reason`, an
optional stable field path, and a fixed message. Reasons are exactly:

- `empty-lock`;
- `malformed-lock`;
- `invalid-version`;
- `unsupported-lock-version`;
- `unsupported-hash-schema`;
- `unknown-field`;
- `missing-field`;
- `invalid-field`;
- `duplicate-name`;
- `noncanonical-lock`.

Errors never echo the rejected source text, string value, bytes, URL, path, ref, digest, or nested
parser error. Field paths use stable schema labels such as `version`, `hash_schema_version`,
`skills[2].source`, and `skills[2].content_hash`.

The reason/field/message mapping is fixed. `unknown-field` uses only `root` or `skills[]` rather
than echoing an attacker-chosen key; missing/invalid fields use the expected canonical schema path.

| Reason | Field | Message |
|---|---|---|
| `empty-lock` | omitted | `portable lock is empty` |
| `malformed-lock` | omitted | `portable lock is malformed` |
| `invalid-version` | `version` | `portable lock version is invalid` |
| `unsupported-lock-version` | `version` | `portable lock version is unsupported` |
| `unsupported-hash-schema` | `hash_schema_version` | `portable lock hash schema is unsupported` |
| `unknown-field` | `root` or `skills[]` | `portable lock contains an unknown field` |
| `missing-field` | expected schema path | `portable lock is missing a required field` |
| `invalid-field` | expected schema path | `portable lock field is invalid` |
| `duplicate-name` | `skills[].name` | `portable lock skill name is duplicated` |
| `noncanonical-lock` | omitted | `portable lock bytes are not canonical` |

## Manifest/lock relationship

`correlatePortableLock(manifest, lockOrNull)` accepts only a G2-01 normalized manifest and a
successfully read/normalized lock or null. Malformed, noncanonical, and unsupported lock bytes have
already refused at the reader and can never be mislabeled stale.

The exact fact and result unions are:

```ts
type PortableLockFact =
  | { readonly reason: 'missing-entry'; readonly name: string; readonly field: 'skills.name' }
  | { readonly reason: 'extra-entry'; readonly name: string; readonly field: 'skills.name' }
  | { readonly reason: 'manifest-hash-mismatch'; readonly field: 'manifest_hash' }
  | { readonly reason: 'source-mismatch'; readonly name: string; readonly field: 'source' }
  | {
      readonly reason: 'requested-ref-mismatch';
      readonly name: string;
      readonly field: 'requested_ref';
    }
  | {
      readonly reason: 'source-path-mismatch';
      readonly name: string;
      readonly field: 'source_path';
    };

type PortableLockRelationship =
  | { readonly state: 'missing-lock' }
  | {
      readonly state: 'incomplete';
      readonly missingNames: readonly string[];
      readonly facts: readonly Extract<
        PortableLockFact,
        { readonly reason: 'missing-entry' | 'extra-entry' }
      >[];
    }
  | {
      readonly state: 'stale';
      readonly facts: readonly Exclude<
        PortableLockFact,
        { readonly reason: 'missing-entry' }
      >[];
    }
  | { readonly state: 'current' };
```

Every result, facts array, and missing-names array is recursively frozen. Facts use this total rank:
`missing-entry`, `extra-entry`, `manifest-hash-mismatch`, `source-mismatch`,
`requested-ref-mismatch`, `source-path-mismatch`; facts of the same reason sort by name with the
manifest comparator. The manifest-hash fact has no name. `missingNames` uses that comparator and
exactly equals the names in `missing-entry` facts.

The closed precedence is:

1. null lock -> `missing-lock`;
2. one or more manifest names absent from the lock -> `incomplete` with stable sorted missing names;
3. otherwise, any extra lock name, manifest-hash mismatch, source mismatch, requested-ref mismatch,
   or source-path mismatch -> `stale` with stable sorted facts;
4. otherwise -> `current`.

If any name is missing, `incomplete` wins. Its facts contain exactly every missing entry and every
extra entry; manifest-hash and entry-local mismatches are deliberately not evaluated until the
name sets are complete. The lock reader has already rejected duplicates, bad SHA/digest/source/path
values, and incomplete entry shapes. G2-01 normalized manifests always contain a canonical source,
so a fabricated noncanonical manifest input is a programmer error rather than a portable
relationship state.

Relationship comparison is by unique manifest name. Source is compared with the exact canonical
text projection, requested ref with null/omission equivalence, and source path with
`declaration.source.path ?? '.'`. The stored manifest hash is compared with the freshly computed
`manifest-semantic` digest. Formatting-only manifest changes remain current; every semantic change
causes manifest-hash staleness even when the entry-local fields happen to remain equal. Facts use
closed reason codes and sorted names/field labels, never raw values.

## Source-content v1

### Public surface and injected capabilities

The public surface adds:

- `SOURCE_CONTENT_EXCLUSIONS_VERSION`;

- `serializeSourceContentProjection`;

Public types include `SourceContentProjectionV1`, its closed directory/file/symlink entry union,
`SourceContentReadPort`, and `SourceContentError`. The focused read port is a `Pick` of existing
`FileReadPort` and `FileMetadataReadPort` capabilities: directory listing, byte read, link read, and
lstat-like metadata with kind/mode/identity. No production port extension is needed.

The exact projection types are:

```ts
interface SourceContentProjectionV1 {
  readonly version: 1;
  readonly exclusionsVersion: 1;
  readonly entries: readonly SourceContentEntryV1[];

type SourceContentEntryV1 =
  | { readonly path: string; readonly type: 'directory' }
  | { readonly path: string; readonly type: 'symlink'; readonly target: string }
  | {
      readonly path: string;

```

The exact callable surface is:

```ts
type SourceContentReadPort = Pick<FileReadPort, 'listDir' | 'readBytes' | 'readLink'> &
  FileMetadataReadPort;

projectSourceContent(
  ports: SourceContentReadPort,
  root: string,
): Promise<Result<SourceContentProjectionV1, SourceContentError>>

  projection: Readonly<SourceContentProjectionV1>,

hashSourceContentV1(
  projection: Readonly<SourceContentProjectionV1>,
): Result<ArtifactDigest, SourceContentError>
```

No function throws for caller data, filesystem refusal, or projection validation. The projector
copies every listing and byte buffer before the next observation/await and returns owned strings/
arrays only. The serializer validates and owns a fresh recursively frozen copy before returning the
canonical string. Hashing validates through that serializer, then applies the fixed domain.

Serializer validation requires exactly the root keys `version`, `exclusionsVersion`, and `entries`;
both versions exactly 1; an array of unique strictly UTF-8-path-sorted entries; exactly the
schema-ordered keys for each discriminated entry type; valid canonical path/target strings; and no
extra own keys. File entries require a boolean `executable`, a non-negative safe integer `length`,
canonical padded base64 `bytes`, and decoded byte length equal to `length`. Input object insertion
order is irrelevant because the owned projection is rebuilt in schema order; entry array order is
normative and an unsorted array refuses.

The input root is capability context and never enters the projection. The root must remain a
directory throughout the read but is not itself an entry. Every child directory, including an empty
directory, is an entry. An empty root projects `entries: []`.

### Exact projection and canonical JSON

The recursively frozen projection serializes as exactly
`UTF8(JSON.stringify(the schema-ordered owned projection))`, with no trailing LF. All path/target
strings reject unpaired surrogates before JSON serialization. ECMAScript `JSON.stringify` therefore
solely determines quote, backslash, control, and Unicode scalar emission; no HTML escaping,
ASCII-only rewriting, slash escaping, replacer, indentation, or alternate `\u` choice is allowed.
The smallest projection is:

```json
{"version":1,"exclusionsVersion":1,"entries":[]}
```

Entries are sorted by the unsigned lexicographic UTF-8 bytes of their NFC-normalized relative POSIX
path. Equal normalized path bytes are a collision and refuse. Entry objects use exactly these field
orders:

```json
{"path":"empty","type":"directory"}
{"path":"link","type":"symlink","target":"run.sh"}
{"path":"run.sh","type":"file","executable":true,"length":2,"bytes":"eAo="}
```

File bytes use standard RFC 4648 base64 with required `=` padding and no line wrapping. `length` is
the exact non-negative safe byte length and must agree with decoded bytes. A file is executable iff
`(metadata.mode & 0o111) !== 0`; all other permission bits, uid/gid, timestamps, inode numbers, and
platform metadata are excluded. `hashSourceContentV1` hashes these exact JSON bytes in the
`source-content` domain.

### Portable paths and Unicode

Every directory entry name and accumulated path is normalized to Unicode NFC before comparison and
serialization. Raw siblings or accumulated paths that normalize to the same value refuse. A path
uses `/` only and contains nonempty segments other than `.` or `..`. Absolute POSIX, backslash,
drive, UNC, traversal, NUL/control/DEL, empty, and invalid/unpaired-surrogate forms refuse. Directory
enumeration order and the host path separator cannot affect bytes.

### Symlinks

Symlinks are read with `readLink` and never followed. A target is NFC-normalized, uses POSIX `/`,
and is stored as a canonical literal relative target. Absolute, drive, UNC, backslash, NUL/control/
DEL, empty raw, and unpaired-surrogate targets refuse. The platform-independent segment algorithm
then:

1. splits only on `/` and rejects every empty segment, including repeated or trailing separators;
2. removes each `.` segment;
3. for `..`, pops a preceding ordinary segment when present, otherwise preserves one leading `..`;
4. joins the stack with `/`, emitting `.` when the stack is empty;
5. resolves that canonical literal stack against the link's containing projected directory and
   rejects any result that escapes the source root.

Thus `a//b` and `a/` refuse, `a/./b` becomes `a/b`, and `a/..` becomes `.`. Changing the canonical
target changes the projection/digest, while changing bytes behind a symlink does not because the
target is never followed.

### Exclusions and unstable reads

`SOURCE_CONTENT_EXCLUSIONS_VERSION` is exactly 1.
`SOURCE_CONTENT_EXCLUSIONS_V1` is the frozen tuple `['.git']`. A child whose NFC-normalized basename
is exactly `.git` and its entire subtree are excluded before metadata or content access. No other
ignore rule exists: `.github`, `git`, `.DS_Store`, editor files, hidden files, and OS-specific
metadata are hashed normally.

The projector refuses rather than omits unstable state. Existing metadata kind `dir` maps to
projection type `directory`; the only accepted metadata kinds are exactly `dir`, `file`, and
`symlink`. Root metadata must be `dir`. `other` is `unsupported-entry` for a child; no socket, FIFO,
device, or guessed fallback enters a digest. A file mode must be a non-negative safe permission
integer so its executable fact is defined.

The exact observation sequences are:

- initial root: read metadata once; absent, non-`dir`, null identity, invalid mode, or initial
  metadata failure is `invalid-root`;
- directory/root after that: metadata A -> copied listing A -> metadata B -> recursively observe
  children in normalized UTF-8 path order -> copied listing B -> metadata C; all metadata facts and
  normalized child-name sets must match;
- file: metadata A -> copied bytes A -> metadata B -> copied bytes B -> metadata C; all metadata
  facts and both byte arrays must match exactly;
- symlink: metadata A -> copied raw target A -> metadata B -> copied raw target B -> metadata C;
  all metadata facts and both raw target strings must match exactly before normalization.

Every child discovered in either directory pass must be accounted for. After the initial-root
step, `absent`, changed identity/kind/mode, changed listing, unequal paired bytes/targets,
byte-length inconsistency, or any metadata/list/read/readlink failure is `unstable-read`. This
detects every difference observable across the paired reads; no unlocked reader can promise to
detect an adversarial ABA mutation that restores all observed facts between observations.

`SourceContentError` has `code: 'source-content'`, a closed reason, a required stable non-value
field, and a fixed message. Reasons are exactly `invalid-root`, `unsafe-path`,
`normalization-collision`, `unsafe-symlink`, `unsupported-entry`, `unstable-read`, and
`invalid-projection`. It never echoes a filesystem root, literal target, file bytes, or rejected
raw value.

The public error has a required non-value-bearing field, and its mapping is exact:

```ts
interface SourceContentError {
  readonly code: 'source-content';
  readonly reason:
    | 'invalid-root'
    | 'unsafe-path'
    | 'normalization-collision'
    | 'unsafe-symlink'
    | 'unsupported-entry'
    | 'unstable-read'
    | 'invalid-projection';
  readonly field:
    | 'root'
    | 'projection'
    | 'version'
    | 'exclusionsVersion'
    | 'entries'
    | 'entries[].path'
    | 'entries[].target'
    | 'entries[].type'
    | 'entries[].executable'
    | 'entries[].length'
    | 'entries[].bytes';
  readonly message: string;
}
```

| Reason | Field | Message |
|---|---|---|
| `invalid-root` | `root` | `source content root is invalid` |
| `unsafe-path` | `entries[].path` | `source content path is unsafe` |
| `normalization-collision` | `entries[].path` | `source content paths collide after normalization` |
| `unsafe-symlink` | `entries[].target` | `source content symlink target is unsafe` |
| `unsupported-entry` | `entries[].type` | `source content entry type is unsupported` |
| `unstable-read` | `entries` | `source content changed while it was read` |
| `invalid-projection` | `projection` or exact non-value-bearing schema field above | `source content projection is invalid` |
