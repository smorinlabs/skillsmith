## Artifact selection and semantic preflight

Update always selects exactly one existing portable pair. Selection follows the shared artifact
pair authority:

- singular explicit `--file`, with sibling lock by default;
- optional singular `--lockfile`, requiring explicit file; or
- the one discovered selected project/user manifest under the current ProjectContext rules.

The manifest must exist and be canonical or an exactly supported readable legacy state. Mixed,
empty, malformed, future-version, ambiguous-owner, nonportable, noncanonical lock, and incoherent
manifest/lock state refuse before remote discovery or mutation. Update never creates a new
manifest, searches the home/repository tree for multiple manifests, persists a lockfile override,
or lets artifact location rebase live project roots.

One pure semantic preflight runs before project/tool/artifact reads where the answer is available:

- `--all` conflicts any positional target;
- mutation and dry-run require targets or `--all`;
- targetless `--check` is valid and equivalent in membership to `--all --check`;
- `--check` conflicts `--dry-run` and `--yes`;
- `--dry-run` conflicts `--yes`;
- `--ref` is singular and requires exactly one positional declaration target, never `--all` or a
  target glob that can select more than one declaration;
- `--pin` requires either an explicit ref or an existing selected moving declaration;
- lockfile requires file; file and lockfile are singular; and
- no-prompt/noninteractive bulk execution requires `--yes` before discovery or I/O. Explicit all,
  more than one target, or a wildcard target is conservatively bulk-capable.

`--strict`, `--pin`, `--ref`, `--tool`, and `--continue-on-error` remain meaningful in check and
dry-run because they change candidate evaluation, verification, selected pairs, or scheduling.
No-prompt remains a valid noninteraction assertion in every mode and never grants approval.

## Declaration-first selection

Selection occurs over unique manifest declarations before expanding tools. Targets are exact names
or globs over declaration names. `--tool` then restricts the nonempty tool set inside each selected
declaration. This prevents a two-tool declaration from becoming a false ambiguous target and keeps
one declaration equal to one operation group.

Selection provenance is exact:

- targetless check is `bounded-default` over every eligible declaration in the selected manifest;
- `--all` is `explicit-all` over the same eligibility set;
- positional targets are `explicit-targets`;
- an explicit target/glob with no match is an explained selection no-op and never widens;
- a valid target whose tool filter selects zero pairs is an explained filter no-op; and
- duplicate target spellings and overlapping globs deduplicate to canonical declaration order.

Known read-only tools remain recognized and return capability exit 4 when selected for update.
Unknown tools are usage errors. The effective tool order comes only from the adapter registry.
Selection never silently drops a declared tool, changes scope, selects an undeclared live
placement, or uses ledger records as alternate portable declarations.

## Exact remote-ref authority and candidate policy

The current `GitPort.resolveRemoteRef` returns only a SHA and asks for tag and branch rows together,
preferring tags. It cannot truthfully distinguish a moving branch/default from a fixed tag or
resolve a branch/tag name collision. G5-02 adds a separate high-level exact ref inspection
authority; it does not change the historical SHA-only method used by acquisition.

The additive Git result is a closed immutable fact:

```ts
interface GitRemoteRefInspection {
  readonly kind: "default" | "branch" | "tag" | "sha";
  readonly requestedRef: string | null;
  readonly resolvedSha: string;
}
```

Production uses exact `git ls-remote` patterns and full 40-hex validation. A null ref inspects
remote HEAD and is moving `default`. A full SHA is fixed and requires no network for classification
(acquisition may still fetch that exact object). A non-SHA name is
resolved against exact branch and tag namespaces; an annotated tag is peeled. If the same spelling
exists as both a branch and tag, inspection refuses as ambiguous instead of applying preference.
Missing refs, malformed/credential-bearing results, offline state, timeouts, cancellation, and Git
errors retain structured source/network/ref failure classes and never become `current`.

The new method is an additive optional compatibility capability on aggregate `GitPort` only for
legacy fake compatibility. Update's dependency boundary narrows it back to required before any
remote work and returns capability exit 4 if a supplied runtime lacks it. Production and every
update success-path fixture supply it; absence is tested as a deliberate failure. There is no
fallback to SHA-only `resolveRemoteRef`. Existing acquisition `resolveRemoteRef` behavior and its
audited fake parity remain byte- and behavior-identical.

Candidate rules are:

1. A manifest null ref (remote default) and an exact branch ref are moving.
2. Exact tags and full SHAs are fixed and are skipped by ordinary bulk or explicit-name update when
   no new ref is supplied.
3. `--ref <moving-ref>` changes manifest intent to that moving ref and resumes tracking.
4. `--ref <fixed-tag>` changes manifest intent to that tag; later bulk updates skip it.
5. `--pin` with an existing moving ref resolves once and changes manifest intent to the full SHA.
6. `--ref <ref> --pin` resolves the explicit ref once and stores the full SHA as manifest intent.
7. The lock always records the full resolved SHA and source-content hash, even when manifest intent
   remains moving.
8. A candidate exists when selected lock intent changes, selected live/ledger/store state must
   converge to the resulting exact pin, or both. A rerun therefore repairs a committed-lock/
   incomplete-live partial result even when the remote head has not advanced again.
9. An unchanged moving ref with converged selected pairs is current. A fixed declaration skip is
   reported separately from current and never counted as an available change.

Each candidate retains current manifest intent, current lock pin, classified ref kind, proposed
manifest intent, proposed exact pin, change reason, and selected tool pairs. No ref classification
uses name spelling heuristics such as `v*`.

## One source materialization and portable byte identity

For every selected candidate that requires remote evaluation, the update preparation owns one
attempt-scoped materialization. It reuses the existing credential-free source identity,
`resolveRemoteSource`, Git port, sparse subtree selection, and cleanup authority. Inspection binds
the proposed candidate to its full SHA. Acquisition either fetches that inspected SHA directly or
fetches the exact inspected namespace and requires the peeled `FETCH_HEAD` SHA to equal it. A ref
that advances between inspect and fetch fails closed; update never substitutes the new head or
replans. The same exact materialization then supplies:

- resolved full SHA and source path;
- `projectSourceContent` projection;
- `hashSourceContentV1` comparison;
- adapter verification input; and
- execution staging after approval.

It is not fetched once for discovery, again for verification, and a third time for execution.
Execution receives an opaque prepared-source binding and revalidates inspected SHA, fetched SHA,
source path, and content hash before staging; it cannot substitute a different tree. Check/dry-run/refusal/cancellation
always clean attempt-scoped materialization. Execution moves/copies only through the existing
content-addressed store authority, and cleanup failure is visible with the correct permission or
failure class.

Source identity uses the signed source-content hash domain. Candidate comparison is sensitive to
file bytes, executable mode, entry type, safe symlink target, and empty directories, while Windows,
macOS, and Linux projections of the same portable tree produce the same digest. Legacy
`contentHashOf` is not used for portable candidate discovery.

## Verification policy

Update makes the previously implicit TS05 policy explicit by adding
`update: "static" | "static+deep"` to `VerificationGatePolicy`. Built-in values equal the minimal
pinned-mutation policy already used by promote: Claude Code is static and Codex is static+deep.
Registry validation requires static support and requires deep support whenever update policy is
static+deep. This is an adapter fact, not a tool-name branch.

Each selected tool pair runs the existing verifier and `evaluateVerificationGate` against the
exact candidate materialization. `--strict` promotes warning/inconclusive results to blocking
failure; normal failure always blocks. Check and dry-run perform the gate without durable writes so
their output contains an observed, not guessed, outcome. Execution first constructs immutable
operations plus blocking verification checks, then confirms the exact operation/check set when
required, then runs those checks against the held materialization, and only then executes. Approval
refusal or cancellation invokes no verifier. A blocked pair remains represented in the approved
immutable plan but its operation is terminally blocked/skipped; verification never deletes or
regenerates operations after approval. If every pair in a declaration is blocked, its artifact/live
operations do not execute. Partial verification remains pair-local and truthful; portable intent
never silently shrinks its declared tools.

This is the D-011 order: plan, confirm when required, verify, execute. A bulk noninteractive request
lacking required approval is rejected at semantic preflight before candidate discovery, so
verification cannot become an accidental prompt bypass. `--yes` applies only to the already
constructed immutable operation/check set. There is no `--deep`, `--no-verify`, or persisted
verification policy on update.

## Shared reconciliation and per-declaration artifact projection

Update prepares one immutable `OperationPlan<'update'>`. The shared reconciliation preparation is
generalized only where necessary to accept:

- command `update`;
- exact target/all/bounded-default selection metadata;
- fail-fast or continue batch policy chosen before preview;
- declaration name membership in addition to existing tool/scope filters;
- supplied current/proposed declaration and pin facts; and
- exact per-declaration artifact transitions.

The pure desired/current placement logic, operation vocabulary, operation/group/pair identities,
checks, diagnostics, ordering, and source/live/store preconditions remain shared. Update never
calls a planner after approval.

One declaration is one group. A group contains its exact selected artifact transition plus every
selected tool placement:

```text
moving ref, unchanged manifest intent:
  write-lock -> selected tool update/repair operations

explicit ref or pin transition:
  write-manifest -> write-lock -> selected tool update/repair operations
```

The manifest editor losslessly changes only the selected declaration's ref when needed. The lock
builder replaces exactly that declaration's pin and root manifest semantic hash while retaining
all other entries. Comments, ordering, whitespace, mode, defaults, registry, unrelated
declarations, requested refs, tools, scopes, placement, and paths remain exact.

Multiple selected declarations share one pair and therefore use the signed G4A-04 collision lane.
Planning carries each exact after-image forward as the next before-image; every later group names
the latest earlier terminal `write-lock` prefix. If an earlier artifact prefix fails, later
colliding groups are dependency-skipped under both scheduling policies. If the prefix succeeds and
a later live pair fails, continue may start the next group from the durable prefix. No runtime
rebase, conditional after-image, invocation finalizer, or global lock operation is allowed.

Artifact and placement effects remain in the same group. A single invocation-wide lock write would
falsely commit failed declarations and violate CF-005/CF-026. A group whose exact pin is already in
the lock but whose selected live pair is stale has no artifact operation, still uses the current
pair revision as a guard, and performs only the needed live operation.

## Exact execution, partial state, and retained history

`createFreshReconcileExecutionPlanV1` and `executeValidatedReconcilePlanV1` are generalized from
apply-only typing to the closed `apply | update` reconciliation command set. Their canonical-plan,
batch-policy-only derivation, binding validation, precondition, cross-group prefix, result coverage,
and cancellation rules do not weaken. `executeValidatedReconcilePlan` is factored so fresh apply
and update share source preparation, snapshot capture, artifact/ledger/live binding, lock hierarchy,
and coordinator execution rather than copying it.

Update artifact binding admits the already-supported exact lossless manifest edit and canonical
lock replacement actions. Physical placement execution uses the existing `update` operation kind,
store materialization, logical transaction, swap, backup, ledger, and crash recovery authorities.
It emits no update-specific journal, transaction, store layout, or compatibility shadow.

A started group reports all selected pairs unless cancellation stops it. Tool-pair success is not
rolled back by a sibling failure. Default fail-fast skips later groups; continue schedules later
independent groups; colliding groups still require the exact artifact prefix. Cancellation always
stops. An actual error stays nonzero, and a successful prior group remains durable and truthful.

The old content-addressed store entry, before-image, and committed logical transaction history are
retained under the signed bounded-history policy. Focused G5-02 units prove that the prior exact
resolution can be selected from retained history and that normal bounded-history eviction rules
remain deterministic. The combined UPDATE-TS07 selector is not reinterpreted or executed here: its
normative prior-store-retention-and-undo behavior, UNDO-TS03, and WF09 remain dependency-complete
G5-05 coverage after G5-03 lands.

Same-command rerun observes fresh manifest/lock/live/ledger state, resumes only an exact compatible
pending operation through the existing recovery authority, and converges remaining work. A
different command/identity cannot claim update residue. No whole-invocation rollback or atomicity
promise is added.

## Check, preview, approval, and exit behavior

All three modes derive from the same prepared candidate set, immutable operations and checks, and
report vocabulary:

- `--check` performs no durable write, prompt, ledger/store mutation, or user-root temp residue;
  exits 0 when current/skipped/filter-noop and 7 when at least one successfully evaluated change is
  available;
- `--dry-run` performs the same evaluation and renders the exact execution plan but exits 0 on
  changes;
- execution approves exactly the prepared operation/check set, then evaluates verification against
  its held source binding and executes without replanning.

Dry-run operations, checks, diagnostics, group IDs, artifact before/after facts, and candidate facts
equal execution's pre-approval report. Check/dry-run contain terminal observed verification facts;
execution shows pending verification at approval and advances those same check IDs to observed
terminal facts only after approval. Operations are never removed or regenerated. Check/result/effect
outcomes alone advance from planned to terminal states.

Approval is required when more than one declaration group will mutate. One exact declaration group
is prompt-free. Interactive approval names exact group and operation IDs; `--yes` approves only the
already prepared plan. Noninteractive/no-prompt bulk execution without yes is a usage refusal
before discovery. Refusal/cancellation runs no verifier. Check/dry-run never prompt and perform
verification before rendering their required observed outcomes.

Exit precedence is the signed global taxonomy: 0 success/current/noop/filter-noop/dry-run; 7 only
for successfully evaluated check-mode changes; 1 execution, verification, or integrity failure; 2
grammar, unsafe conflict, unresolved selection, or missing approval; 3 invalid/unreadable
manifest/lock/ledger state or stale execution guard; 4 unavailable update/tool capability; 5
source/network/ref/resolution failure; 6 permission/filesystem denial; 130 cancellation. Cancellation
wins, otherwise any actual 1-6 error wins over drift 7 through the shared exit selector.

## Command grammar and report contract

The live CommandSpec becomes exactly:

```text
update [skill...]
  --all                       explicit whole eligible declaration set
  --file <path>               singular selected manifest
  --lockfile <path>           singular, requires file
  -t, --tool <name>           repeatable registry-ordered pair filter
  --check                     non-writing 0/current or 7/change evaluation
  --dry-run                   non-writing exact plan, exit 0 on change
  --ref <git-ref>             singular; exactly one positional declaration
  --pin                       freeze existing/explicit moving resolution to SHA intent
  --strict                    warning/inconclusive verification blocks
  -y, --yes                   approval; conflicts check and dry-run
  --continue-on-error         later independent declaration scheduling
  --json                      strict update@1 report
```

Global cwd/config/color/verbosity/no-prompt/debug behavior remains shared. There is no scope
selector, force, locked, prune, no-save, no-verify, deep, retry, atomic, positional manifest, saved
plan, outdated alias, or diff alias.

The strict update@1 report owns one human/JSON fact model:

```ts
interface UpdateReportV1Dto {
  readonly schemaVersion: 1;
  readonly kind: "skillsmith.update";
  readonly command: "update";
  readonly mode: "check" | "dry-run" | "execute";
  readonly state: "current" | "changes-available" | "ready" | "refused" | "completed" | "partial";
  readonly artifactPair: {
    readonly manifestPath: string;
    readonly lockPath: string;
    readonly lockSource: "sibling" | "explicit";
    readonly selectionSource: "explicit" | "discovered-project" | "project-default" | "user-default";
  };
  readonly options: {
    readonly all: boolean;
    readonly ref: string | null;
    readonly pin: boolean;
    readonly strict: boolean;
    readonly continueOnError: boolean;
  };
  readonly selection: UpdateSelectionV1Dto;
  readonly candidates: readonly UpdateCandidateV1Dto[];
  readonly operations: readonly PlanOperationV1Dto[];
  readonly checks: readonly PlanCheckV1Dto[];
  readonly diagnostics: readonly PlanDiagnosticV1Dto[];
  readonly approval: {
    readonly required: boolean;
    readonly outcome: "not-required" | "pending" | "approved" | "refused" | "cancelled";
  };
  readonly groups: readonly UpdateGroupResultV1Dto[];
  readonly effects: readonly UpdateEffectV1Dto[];
  readonly summary: UpdateSummaryV1Dto;
}
```

Candidate rows include current/proposed requested ref, classified kind, resolved SHA, content hash,
transition `preserve|track|pin`, and outcome `current|available|skipped-fixed|failed`. Group rows
include one skill/group ID, exact selected tools, verification mode/gate, action, terminal outcome,
skip/failure reason, and artifact/live drift. Effects identify manifest, lock, store, ledger, live,
and backup roles by operation/group. The codec validates embedded operations/checks/diagnostics
through the existing plan report vocabulary, enforces selection/group/candidate/summary identity,
and rejects unknown fields recursively.

The report never serializes clone URLs, credential material, local fetch directories, raw
exceptions, unselected roots, journal internals, or store internals. JSON stdout is exactly one
canonical value and diagnostics use stderr. Human and JSON modes report identical artifact,
selection, ref/pin, verification, group, scheduling, effect, and exit facts.
