# P17-G1-07 implementation plan

## Scope and prerequisites

P17-G1-07 owns operation-scoped observation, correlation, recursive redaction, and the existing
quiet/verbose/trace/debug behavior. Its primary IDs are `EWP-CF-038`, `EWP-P1-T13`, and
`EWP-P1-TS11`.

The formal dependency is P17-G1-03, signed off at
`cd7ec024dc9beef0872dfd06eaa72024fffe2966`. G1-04 supplies focused `ClockPort`/`IdPort` and the
application context, G1-05 supplies tool authority, and G1-06 supplies canonical JSON output.
Those signed groups are preservation constraints, not additional lifecycle dependencies.

Required-now validation is exactly `EWP-P1-TS11`. `EWP-P3B-TS07` remains downstream-only and owns
live planner, coordinator, transaction, journal, rollback, recovery, retry, and resume propagation.

## Frozen boundary

### ADR and public core authority

Add ADR 0009 and one public core observation module. Public exports include:

- immutable `OperationContext` and its construction/derivation inputs;
- the exact event-kind tuple, event payload map, and `ObserverEvent` discriminated union;
- `ObserverPort`, `noopObserver`, and the best-effort emission helper;
- observation verbosity types and pure recursive redaction;
- focused operation clock/ID inputs without exposing process, filesystem, environment, or CLI IO.

The observation module must not import Commander, CLI renderers, concrete stream IO, persistence
schemas, or a telemetry SDK. Existing `Logger`/`noopLogger` remain a deprecated 1.x compatibility
facade; new domain/application code may not depend on them.

### OperationContext

`OperationContext` is a recursively frozen value/capability bundle:

- `operationId: string`, `parentOperationId: string | null`, `command: string`, and
  `workflow: string`;
- `groupId: string | null` and `pairId: string | null`;
- `attempt: number`;
- `clock: Readonly<Pick<ClockPort, 'wallNowIso' | 'monotonicMilliseconds'>>`;
- `startedAt: string` and `startedMonotonicMilliseconds: number`.

Public construction is exactly:

```ts
createOperationContext(input: {
  command: string;
  workflow: string;
  clock: Pick<ClockPort, 'wallNowIso' | 'monotonicMilliseconds'>;
  id: Pick<IdPort, 'nextId'>;
  operationId?: string;
  parentOperationId?: string | null;
  groupId?: string | null;
  pairId?: string | null;
  attempt?: number;
}): OperationContext

createChildOperationContext(
  parent: OperationContext,
  input: { command: string; workflow: string; id: Pick<IdPort, 'nextId'> },
): OperationContext

withOperationTarget(
  context: OperationContext,
  target: { groupId: string | null; pairId: string | null },
): OperationContext

nextOperationAttempt(context: OperationContext): OperationContext
```

All supplied strings must already be trimmed, non-empty, free of ASCII control characters, and at
most 256 UTF-16 code units; values are rejected rather than normalized. `attempt` must be a positive
safe integer. `pairId` may be non-null only when `groupId` is non-null. Wall time must be canonical
UTC ISO (`new Date(value).toISOString() === value`); monotonic time must be finite and non-negative.
Clock and ID functions must be non-proxy functions. A generated ID is validated by the same rule.

Fresh construction without `operationId` calls `nextId('operation')` exactly once. Supplying an
explicit ID consumes no ID and is the frozen downstream resume seam. Child construction consumes
one ID, sets `parentOperationId` to the parent's operation ID, resets target IDs to null and attempt
to 1, and captures new start times. `withOperationTarget` consumes no ID or clock, preserves start
and attempt, and accepts already-derived deterministic IDs from the future planner; G1-07 does not
invent a hashing algorithm. `nextOperationAttempt` consumes no ID, increments attempt, retains all
identity/target fields, and recaptures both start times. It throws on overflow.

Direct constructors throw `TypeError` on invalid input. Production action construction is contained
by the existing normalized failure boundary: no command event is promised before a valid context
exists, and construction failure produces the usual sanitized human/error-envelope failure with
exit 1. Current actions create one context and pass the same identity through runtime and
application context.

Help/version remain zero-discovery: their context uses only the focused real clock/ID adapters and
must not compose project, filesystem, process, Git, HTTP, or configuration capabilities.

### Exact typed event registry

The initial registry contains exactly these 15 kinds, in this order:

1. `command.started`
2. `command.completed`
3. `plan.created`
4. `operation.started`
5. `operation.completed`
6. `tool.detection.started`
7. `tool.detection.completed`
8. `tool.verification.started`
9. `tool.verification.completed`
10. `transaction.stage.started`
11. `transaction.stage.completed`
12. `transaction.committed`
13. `transaction.rolled-back`
14. `recovery.started`
15. `recovery.completed`

Every event owns these common fields in order: `kind`, `operationId`, `parentOperationId`, `command`,
`workflow`, `groupId`, `pairId`, `attempt`, `occurredAt`, `monotonicMilliseconds`. They are copied
from the context except the two event timestamps, which are captured from its injected clock.

The exact kind-specific payload map is:

| Kind                          | Required fields after common fields                                                                               |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `command.started`             | none                                                                                                              |
| `command.completed`           | `outcome`, `exitClass`, `errorCode`, `durationMilliseconds`                                                       |
| `plan.created`                | `planId`, `operationCount`                                                                                        |
| `operation.started`           | `operationKind`                                                                                                   |
| `operation.completed`         | `operationKind`, `outcome`, `errorCode`, `standaloneCount`, `bundledCount`, `resultCount`, `durationMilliseconds` |
| `tool.detection.started`      | `toolId`                                                                                                          |
| `tool.detection.completed`    | `toolId`, `outcome`, `errorCode`, `resultCount`, `durationMilliseconds`                                           |
| `tool.verification.started`   | `toolId`, `modes`                                                                                                 |
| `tool.verification.completed` | `toolId`, `modes`, `verdict`, `errorCode`, `durationMilliseconds`                                                 |
| `transaction.stage.started`   | `transactionId`, `stage`                                                                                          |
| `transaction.stage.completed` | `transactionId`, `stage`, `outcome`, `errorCode`, `durationMilliseconds`                                          |
| `transaction.committed`       | `transactionId`, `durationMilliseconds`                                                                           |
| `transaction.rolled-back`     | `transactionId`, `reasonCode`, `durationMilliseconds`                                                             |
| `recovery.started`            | `transactionId`, `recoveryKind`                                                                                   |
| `recovery.completed`          | `transactionId`, `recoveryKind`, `outcome`, `errorCode`, `durationMilliseconds`                                   |

`outcome` is exactly `success | failure | cancelled | skipped`. Command `exitClass` is the existing
closed `CommandExitClass`; command outcome is `cancelled` only for exit 130, `failure` for exit
classes 1..6, and `success` for success or drift. `errorCode` is `string | null`: it is null for
success/skipped and a normalized non-empty code for failure/cancelled. `reasonCode` is non-null and
normalized. Counts are non-negative safe integers. Durations are finite non-negative milliseconds.

`operationKind` is derived from the exact frozen tuple
`inventory, diagnostics, install, update, remove, link-dev, promote, move-scope, adapt, repair,
write-manifest, write-lock, migrate-project-config, migrate-ledger`. Current list-skills and
list-commands summaries emit paired `operation.*` events with `inventory`; current health scan uses
`diagnostics`. `standaloneCount`, `bundledCount`, and `resultCount` are non-null for current
inventory reads, allowing the legacy adapter to reproduce its exact summary, and null for
diagnostics/future mutating kinds.

Each verification `modes` value is a non-empty frozen owned array containing each member of
`static | deep` at most once and in canonical request order: exactly `['static']` or
`['static', 'deep']` for current commands. A verification span covers the one current checker call,
which receives all requested modes atomically; G1-07 does not claim a separate duration for work the
checker does not expose separately. Verification `verdict` is
`pass | warn | fail | inconclusive | unavailable | skipped`. Detection outcomes use the common
outcome union and zero results represent unavailable without inventing a fifth outcome.
Verification error code is null for pass/warn/skipped and normalized non-null for
fail/inconclusive/unavailable. Transaction/recovery completion follows the common outcome/error-code
rule. `transaction.committed` is implicitly successful; rollback uses its required reason code.
`stage` is exactly `prepared | staged | backed-up | live | committed`, matching the current journal
phase vocabulary without importing a journal schema. `recoveryKind` is `resume | rollback | cleanup`.

`toolId` is a generic registry identity matching `/^[a-z][a-z0-9-]*$/`, not a hard-coded built-in
union. A registry-bound emitter receives the validated tool IDs and rejects IDs absent from it;
fixture registries therefore supply their own `registry.ids` without generic edits.
Transaction/recovery IDs follow the general normalized scalar rule. Event
payloads contain no preformatted message, stack, cause, raw exception, arbitrary metadata bag,
secret-bearing environment, or IO capability.

Registry types are derived from one immutable runtime tuple/map. Construction rejects unknown
kinds, malformed scalars, non-finite timing, mismatched payload fields, accessors, proxies, exotic
objects, and caller mutation. Emitted events and nested data are frozen owned values.

G1-07 emits command lifecycle and current scan/inventory/tool-detection events. It defines the
remaining event contracts for downstream use but does not fabricate plan, transaction, journal, or
recovery events before their owners exist. Current `verify` emits one verification span around each
registry-selected tool checker call; failures before target resolution and checker selection emit
only command completion.

### Event construction and independent spans

Typed low-level builders validate and freeze events and throw `TypeError` on malformed input. Domain
and runtime code receives only this registry-bound, failure-isolated facade:

```ts
interface ObservationEmitter {
  begin<K extends StartedKind>(
    context: OperationContext,
    input: StartedInput<K>,
  ): ObservationSpan<K> | null;
  complete<K extends StartedKind>(
    span: ObservationSpan<K> | null,
    input: CompletedInput<K>,
  ): void;
  emit<K extends InstantKind>(
    context: OperationContext,
    input: InstantInput<K>,
  ): void;
}

createObservationEmitter(input: {
  observer: ObserverPort;
  toolIds?: readonly string[];
}): ObservationEmitter
```

The factory validates, clones, de-duplicates, and freezes `toolIds`; malformed or duplicate entries
throw `TypeError`. Omitting `toolIds` binds an empty tool registry, which is sufficient for
zero-discovery help/version command events. Current application composition passes the validated
tool registry's `ids`; generic test registries pass their own `ids`. Every tool start/complete input
is checked against the bound set. An absent ID or an ID outside the set fails internal construction
and is dropped without invoking the observer. The returned span is opaque and branded to its
originating emitter. Pair identity (`operationKind`, detection `toolId`, verification `toolId` plus
`modes`, transaction ID plus stage, or transaction ID plus recovery kind) is copied from the span into completion; callers
supply only completion-only fields and cannot change pair identity. A span from another emitter is
dropped. Direct low-level event builders enforce structural/scalar rules and throw; registry
membership and same-emitter span authority are deliberately owned by the facade.

Each begin captures its own wall/monotonic start and returns a frozen span with context, start time,
and the paired completion kind. Nested tool/operation/transaction spans therefore do not reuse the
command start. Completion captures a new clock value and subtracts its own start. Invalid/throwing
clock output, malformed payload, negative duration, or event-construction failure drops that event
attempt and returns null/void; it never escapes into a domain result. Low-level builders remain
directly testable and throwing, while production helpers are failure-isolated.

### Best-effort observation and error authority

`ObserverPort` is exactly
`{ observe(event: ObserverEvent): void | PromiseLike<void> }`. Production helpers invoke it
synchronously in authored lifecycle order, catch synchronous throws, safely attach a rejection
handler to returned thenables, return `void` without awaiting, and never read an observer result.
Async completion order is deliberately outside the contract; invocation order is deterministic and
no rejection is unhandled. The production CLI sink is synchronous, so production diagnostic order
matches lifecycle invocation order and cannot produce late output. A hanging third-party observer
cannot block the command. Observer failure can never change a `CommandOutcome`, diagnostic,
rendered report, exit class, transaction decision, or later event attempt.

An observation event is never the sole representation of an error. Command/application failures
remain structured `CommandOutcome` diagnostics or the canonical error envelope; completion events
may repeat only a normalized error code and outcome. Events are not persisted and are never read by
state, planning, execution, or recovery code.

### Recursive redaction

Redaction is pure, non-mutating, cycle-safe, and accessor/proxy-safe over nested ordinary objects,
null-prototype records, and arrays. It preserves own enumerable string-key and array order and
returns owned recursively frozen data with null-prototype object records.

Any key containing `authorization`, `cookie`, `credential`, `password`, `secret`, or `token`
case-insensitively replaces its whole value with `[REDACTED]` without visiting that value. In all
other string values, the full matching credential substring is replaced by `[REDACTED]` for these
global patterns: `Bearer` plus one or more non-whitespace characters; `gh[pousr]_` plus at least
eight ASCII alphanumeric/underscore characters; and `sk-` plus at least eight ASCII
alphanumeric/underscore/hyphen characters.

Exact safe markers are `[UNDEFINED]`, `[BIGINT]`, `[SYMBOL]`, `[FUNCTION]`, `[ACCESSOR]`,
`[PROXY]`, `[EXOTIC]`, `[CIRCULAR]`, `[NON_FINITE]`, `[MAX_DEPTH]`, `[MAX_NODES]`, and `[UNSAFE]`.
`-0` remains `-0`. If any traversed object or array has any own symbol key, enumerable or not, that
whole value becomes `[SYMBOL]`; symbol keys are never stringified and no synthetic string key is
invented. Dates, maps, sets, typed arrays, and non-ordinary prototypes become `[EXOTIC]`. Depth
beyond 32 and nodes beyond 4,096 stop deterministically with their markers. Shared non-cyclic
references are cloned at each position; cycles use `[CIRCULAR]`.

Proxy detection uses `node:util.types.isProxy` before any reflective operation. A proxy is replaced
wholesale. Properties are inspected only through own descriptors; accessors become `[ACCESSOR]`
and are never invoked. Own-key, descriptor, or prototype failure replaces the whole value with
`[UNSAFE]`. Correlation IDs and normalized error codes remain unless their value itself matches a
secret pattern.

All CLI observation rendering consumes only redacted event data. Debug must not print a raw stack,
cause, environment, request object, or unredacted exception.

### One CLI diagnostic and verbosity policy

The shared CLI runtime resolves the already-declared global options once:

- `--quiet` -> `quiet`;
- no verbosity flag -> `normal`;
- one `-v`/`--verbose` -> `verbose`;
- two or more verbose occurrences -> `trace`;
- `--debug` -> `debug` (and wins over verbose when both are present).

Existing preflight conflicts remain exact: quiet conflicts with verbose and debug; verbose and debug
may coexist. No option, alias, environment variable, command, or persisted setting is added.

Normal mode preserves all accepted current stdout/stderr bytes and emits no observation detail.
Quiet suppresses rendered human stdout but never human error/warning/deprecation stderr; it does not
suppress JSON. Verbose renders stable command/operation/plan detail events to stderr. Trace also
renders tool/transaction/recovery detail. Debug renders the complete recursively redacted structured
event to stderr. Observation lines are newline-terminated and deterministic apart from injected
IDs/times.

Human report stdout is otherwise identical across normal/verbose/trace/debug. JSON stdout is the
same single canonical G1-06 document at every verbosity, including quiet. All observation detail
and non-envelope diagnostics are confined to stderr; canonical JSON success/error documents remain
on stdout. Renderer warnings and canonical errors remain visible in quiet mode.

The diagnostic grammar is exact and uncolored:

- verbose detail kinds are command, plan, and operation events and render
  `detail: <kind> operation=<id> command=<command>` followed by non-null kind-specific fields in the
  payload-table order;
- trace includes every kind and renders
  `trace: <kind> operation=<id> parent=<id|-> group=<id|-> pair=<id|-> attempt=<n> at=<ISO> monoMs=<n>`
  followed by every kind-specific field in table order, using `-` for null;
- debug includes every kind and renders `debug: <compact-json-event>`, with common then
  kind-specific property order and explicit nulls.

Each diagnostic is exactly one LF-terminated stderr line. Strings are JSON-escaped when needed so a
field cannot inject a second line. Detail/trace scalar rendering omits quotes only for the safe token
class `[A-Za-z0-9._:/@+-]+`; all other strings stay JSON-quoted. The sole array payload, `modes`, is
rendered as compact JSON with no spaces (for example `["static","deep"]`). Color is never applied
to observation lines.

### Current integration and compatibility

The shared atomic bundle is exactly
`{ context: OperationContext; emitter: ObservationEmitter }`. The generic action factory creates
one bundle for every action, including context-free actions through focused clock/ID dependencies,
and adds it as a required `observation` member of `RuntimeExecutionRequest`. Full
`ApplicationContext` also gains the same required `observation` bundle by reference; the focused
context-free object contains only that bundle. The runtime, not the application, emits
`command.started` before the application and exactly one `command.completed` after success,
returned failure, throw, missing application, missing renderer, renderer failure, or cancellation.
Completion uses injected monotonic duration and the final semantic exit/error code.

Neither the bundle nor `ApplicationContext` receives format, quiet, verbosity, diagnostic policy,
or CLI IO. Domain/application event production is identical at every presentation level. Only the
CLI runtime/sink filters or renders observations.

Operation identity is frozen at the action factory, before runtime execution:

- every ordinary non-version action uses `command = spec.path` and
  `workflow = spec.application`;
- the bare root is therefore `skillsmith` / `rootHelp`, the config root is
  `skillsmith config` / `configHelp`, explicit help is `skillsmith help` / `help`, and completion is
  `skillsmith completion` / `completion`;
- the explicit version command, any action redirected by inherited `-V/--version`, and the eager
  root version path all use the canonical pair `skillsmith version` / `version`;
- command aliases always use the owning spec's canonical `path`; `reportKind`, an alias spelling,
  and raw argv never define either identity field.

`command.completed.errorCode` is derived without rendered-text parsing. For a classified runtime
failure (returned/thrown error, missing application/renderer, or renderer failure), its normalized
`RuntimeFailure.code` wins. For a structured `CommandOutcome` whose exit class is neither success
nor drift, the first diagnostic with severity `error` wins; warning/info diagnostics are not error
identity. When no error diagnostic exists, use the exact exit-class fallback:
`failure -> command-failed`, `usage -> usage`,
`state -> state`, `capability -> capability`, `source -> source`, `permission -> permission`, and
`cancelled -> cancelled`. Success and drift always use null. Thus strict warning failures and
doctor/check outcomes without an error diagnostic deterministically use `command-failed`.

Current agents/list/commands/doctor scan paths replace free-form `logger.debug/warn` calls with typed
inventory/detection events. `DetectOptions`, `ListSkillsOpts`, `ListCommandsOpts`, and
`CheckRunContext` retain their deprecated `logger` field and add one optional atomic
`observation?: { context: OperationContext; emitter: ObservationEmitter }` field. Production services
always pass observation. If both are supplied, observation wins and logger is not invoked; if only
logger is supplied, `observationFromLegacyLogger(logger, activity, toolIds)` supplies a private
frozen synthetic context and an emitter bound to the current selected tool IDs. Its context is
exactly: `operationId = legacy-observation`, `parentOperationId = null`,
`command = legacy-scan`, `workflow = activity`, `groupId = pairId = null`, `attempt = 1`,
`startedAt = 1970-01-01T00:00:00.000Z`, and `startedMonotonicMilliseconds = 0`; its fixed clock
returns those same zero values and no ID function is called. `activity` is exactly one of `detect`,
`list-skills`, `list-commands`, or `diagnostics`.

That private adapter receives typed, redacted events but ignores their common synthetic identity
when it reproduces the existing debug/warn strings exactly. The identity is never sent to a
caller-supplied `ObserverPort`, persistence, or command output. Neither input uses `noopObserver`.
Logger metadata cannot enter an event. List summaries map to paired `operation.*` inventory events,
detection messages map to `tool.detection.*`, and health cross-scope inventory forwards the same
observation pair.

`VerifyOptions<ToolId>` adds the same optional atomic `observation` bundle. Inside `runVerify`, no
tool event is attempted until `resolveTarget` succeeds and the exact `toolSet` and `modes` are
computed. In selected-tool order, it begins one `tool.verification` span immediately before checker
resolution/invocation, using the selected `toolId` and a frozen clone of the requested `modes`. A
missing checker completes `fail` / `generic` and returns the existing generic error. Immediately
after an invoked checker settles, `runVerify` completes the span before returning an error or
pushing a verdict. A rejected/thrown checker completes `fail` / `generic`, then preserves the
existing throw behavior or the existing aborted-signal `Result.err` behavior. A returned `err`
completes `fail` with its `SkillSmithError.code`, then returns the same error. Observation failure
never changes cleanup or short-circuit behavior; later selected tools receive no events after the
first verification failure.

For a returned `ToolVerdict`, completion mapping uses this exact precedence:

1. `available === false`, or empty modes with top-level `skipReason === 'not-installed'` ->
   `unavailable` / `not-installed`;
2. any mode with `status === 'error'` and `skipReason === 'timeout'` ->
   `inconclusive` / `timeout`;
3. any mode with `status === 'error'` and `skipReason === 'exec-error'` ->
   `inconclusive` / `exec-error`;
4. any mode with `status === 'skipped'` and `skipReason === 'not-installed'` ->
   `unavailable` / `not-installed`;
5. any mode with `status === 'skipped'` and `skipReason === 'timeout'` ->
   `inconclusive` / `timeout`;
6. any mode with `status === 'skipped'` and `skipReason === 'exec-error'` ->
   `inconclusive` / `exec-error`;
7. summary verdict `fail` -> `fail` / `verification-failed`;
8. summary verdict `warn` -> `warn` / null;
9. summary verdict `pass` -> `pass` / null;
10. summary verdict `inconclusive`, including an available result with empty modes ->
    `inconclusive` / `verification-inconclusive`.

Current code has no structured path that maps to event verdict `skipped`; that registry member is
reserved for downstream callers. The mapping reads only the structured result and never rendered
text. Pre-aborted input, target-resolution/wrapping failure, or an empty selected tool set produces
no verification event. A missing checker after selection follows the paired `generic` rule above.
Command completion remains the error authority.

Production process writes remain owned by `CliRuntimeIo`; command modules and core observation code
cannot import process streams. G1-06 DTOs, renderer bytes, JSON kinds/versions, and terminal framing
do not change.

### Context-free actions, preflight, and lifecycle order

Parser-owned `-h/--help` is not a command action and emits no lifecycle event. Its configured output
writer applies quiet suppression but never creates project/runtime ports; verbose/debug add no
events to parser help. Root/config/help application actions and completion are ordinary runtime
actions and receive focused operation context. Quiet suppresses their human stdout. JSON behavior
is unchanged where supported.

Eager `-V/--version` remains zero-discovery but now uses pure root relation validation and a focused
clock/ID operation factory before runtime execution. Therefore eager `--version -qv` and
`--version --quiet --debug` intentionally change from the signed TS07 bypass to usage exit 2; TS07
is updated in the G1-07 test-first commit. Quiet version emits no stdout; normal bytes are unchanged;
verbose/trace/debug add only stderr observation. Operation-context construction failure uses the
sanitized human failure path because eager version has no JSON contract.

For a valid context, `command.started` is attempted immediately before application lookup.
Applications run, failures are classified, and the selected renderer/failure renderer first
produces an in-memory output value. Exactly one `command.completed` is then attempted with the final
semantic exit class and normalized code, immediately before rendered output is emitted and before
the exit port is called. Missing application, returned failure, thrown application, missing
renderer, renderer throw, cancellation, drift, and success all follow that order. Observer failure
does not affect classification or suppress the completion attempt. Parser/preflight and context
construction failures occur before a valid lifecycle and emit no command events.

## Validation design

`EWP-P1-TS11` is one executable selector with these families:

1. exact immutable event registry, payload closure, public type/runtime parity, and context
   construction/derivation rejection;
2. fake clock/ID command lifecycle order, correlation, wall timestamps, durations, group/pair,
   child, and stable-ID/new-attempt behavior;
3. synchronous and asynchronous observer failure isolation for application success/failure,
   renderer failure, and scan events, while errors remain outcomes/envelopes;
4. recursive redaction canaries in nested records/arrays/value patterns, input immutability, cycles,
   proxies, getters, exotic values, and zero secret/accessor leakage;
5. migrated current scan/inventory typed events, no free-form domain logger calls, and registered tool
   identity;
6. direct runtime quiet/normal/verbose/trace/debug output policy, separate stream assertions, and
   deterministic injected event summaries;
7. spawned human and JSON matrix with options before/after subcommands, `-v`, `-vv`, `--debug`,
   quiet conflicts, quiet error preservation, one parseable JSON stdout value, and no secret leak;
8. static ownership: no new domain Logger dependency, direct command/process output, event
   persistence, observation-driven branch/state decision, telemetry/trace/log surface, or Phase-3B
   propagation.

The static family uses parsed imports/AST rather than raw word regexes. `Logger` type imports are
allowed only in `env/logger.ts`, `observation/logger-compat.ts`, the three public scan option files,
`doctor/types.ts`, public export facades, and tests; `.info/.warn/.debug` calls on Logger are allowed
only in `logger-compat.ts`. Core observation modules cannot import `place`, `acquire`, persistence
schemas, CLI, or process streams. Existing persistence/coordinator directories cannot import the
observation module in G1-07. Observation helper return values are `void`, and AST checks reject their
use in conditions, returns, assignments that feed outcomes, or recovery/state branches.

CLI process stdout/stderr imports remain confined to the existing `runtime/io.ts`, normalized error
boundary, and entrypoint allowlist. The new diagnostic sink receives `CliRuntimeIo` and cannot import
`process`. Future-only plan/transaction/recovery event kind literals are allowed only in the event
registry, type fixtures, and TS11—not in current place/acquire/repository modules. Package manifests
must not add telemetry/logging dependencies or scripts, and command/spec inventories must not add an
option or command.

Characterization clauses freeze existing parser conflicts, normal current output, G1-06 JSON bytes,
help/version zero-discovery, and structured error behavior before authority tests turn green.
Tests inject clock/ID and capture stdout/stderr separately; they do not compare ambient IDs/times,
merge streams, require empty debug stderr, change JSON DTOs, or demand future transaction/recovery
events from absent systems.
