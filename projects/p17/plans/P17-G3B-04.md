# P17-G3B-04 Ready plan

## Outcome and exact scope

G3B-04 separates observation, planning, execution, and persistence without replacing the signed
durability engines. It introduces private domain repositories, one versioned immutable
`ObservedStateSnapshotV1`, port-free pure planners, exact expected revisions including revisioned
absence, a coordinator-owned revision cursor, immutable ledger reducers, compatibility shells, and
staged extraction of acquisition and placement runners.

The immutable catalog scope is exactly three primary entities:

- `EWP-CF-035` — separate immutable snapshots, pure planning, and repository writes;
- `EWP-P3B-T05` — ADR 0006, repositories, snapshots, reducers, planners, revisions, and extraction;
  and
- `EWP-P3B-TS05` — the required architecture/behavior selector.

The immutable validation partition is exactly four impacted validations. `EWP-P3B-TS05` is the
sole required-now selector. `EWP-WF06`, `EWP-WF11`, and `EWP-WF13` remain downstream under their
future groups and are not run, reassigned, or advanced here.

P17-G3B-02 remains the sole formal catalog dependency. Signed G3B-03 implementation
`7b7d285eee051e24c7e5d7624c33e4cd5a2e9ac6` and sign-off
`ea31bd6c4c1aef92dcbc80426fcb601741f959ca` are the accepted integration baseline. This group wraps
and extracts the canonical ledger writer/recovery/history foundation; it does not reopen or fork
it.

This remains authorized, credential-free local work for the open-source Skillsmith CLI. Tests use
repository code, hermetic ports, temporary roots, bounded local subprocesses, deterministic
fixtures, and synthetic sensitive-data canaries only.

## Normative architecture

[ADR 0006](../../../docs/adr/0006-immutable-observed-state-and-repositories.md) is the controlling
decision. The exact private dependency direction is:

```text
domain models/codecs/focused ports
  -> behavior-specific domain repositories
  -> immutable observed-state reader/snapshot
  -> pure planners
  -> immutable plans/preconditions
  -> execution coordinator and revision cursor
  -> domain write adapters
  -> existing physical durability engines
```

Application services and compatibility shells compose above the pipeline. Repositories never call
one another. Planners receive no ports or repositories. Status receives read-only state access.
Execution never invokes a planner. The execution coordinator owns cross-domain locks,
preconditions, scheduling, and revision advancement. The artifact coordinator and canonical ledger
writer remain separate physical authorities.

Two current dependency reversals close before broader extraction:

1. ledger history moves from `place/history.ts` to `artifacts/ledger-history.ts`, leaving the old
   path as a compatibility re-export with no policy; and
2. legacy action vocabulary moves to `planning/legacy-action.ts`, so foundational planning no
   longer imports acquisition or placement runners.

Executable ESLint/static checks prohibit repository-to-repository imports, planner effects,
execution-to-planner-implementation imports, status write capabilities, artifacts-to-place imports,
and new cycles across the owned source graph.

## Ordinary-data ownership

`state/ownership.ts` owns one bounded private ordinary-data traversal for planning and execution
preconditions. It:

- owns every accepted array/object rather than freezing caller-owned containers;
- rejects proxies, accessors, symbol keys, exotic prototypes, non-enumerable properties, sparse
  arrays, cycles, unsupported primitives, non-finite numbers, and depth/node-budget overflow;
- applies the existing sensitive-material/property rules through caller-provided policy; and
- deeply freezes the resulting owned graph.

Planning and execution map traversal failures into their existing domain-specific errors. Codec,
redaction, status, inventory, registry, and wire-contract boundaries keep their local validation or
freezing semantics; no universal cloning framework is introduced.

The default budget remains the signed planning/precondition budget: 20,000 nodes and depth 64.
Changing that budget is outside this group unless a focused killing test proves a necessary
compatibility correction.

## Revision contract

`ExpectedRevisionV1` is a closed private union for `manifest`, `lock`, `ledger`, `live`, `store`,
`project`, and `capabilities`. Every member has schema version 1, domain, stable resource identity,
and `absent` or `present` state.

Present revisions preserve the applicable facts:

- manifest, lock, and ledger: exact byte revision plus semantic revision;
- live placement: normalized location, path representation, resource revision, and content
  revision when meaningful;
- store: normalized location, resource revision, content revision, and snapshot identity;
- project: canonical project-context semantic fingerprint; and
- capabilities: ordered relevant adapter/capability fingerprint.

Absence is revisioned, never represented by `null` alone. It includes normalized target identity,
target kind `absent`, normalized parent identity, parent kind, and the stable parent metadata
identity or explicit absent-parent identity. A domain-separated digest covers the closed record.
Creation refuses when the target appears, the parent changes, or an unexpected/special node is
observed.

No revision contains a clock value, random ID, mutable object identity, formatted message, or open
unversioned object.

## ObservedStateSnapshotV1

The private snapshot is an exact deeply frozen record with:

```text
schemaVersion: 1
snapshotId: snapshot:v1:<sha256>
project
manifest
lock
ledger
live[]
store[]
capabilities
```

Each component includes its exact revision and immutable planning facts. Live/store arrays use
canonical resource order. The snapshot contains no repositories, ports, callbacks, mutable maps,
class instances, errors, renderers, or CLI flags.

The reader performs one deterministic two-pass consistency check:

1. derive the closed resource list from the normalized request/project selection;
2. read every component and revision in canonical order;
3. reread the same ordered revision vector; and
4. return only if the vectors are exactly equal.

Any mismatch returns closed `snapshot-changed`; it never returns mixed state or loops internally.
The snapshot ID is the domain-separated digest of the canonical revision vector. Equivalent
vectors produce the same ID without consulting a clock or ID port.

The reader reuses existing artifact repository, canonical ledger, placement, store, project, and
capability authorities. It does not duplicate codecs, source normalization, tool policy, or status
join policy.

## Pure planner contract

Current mutators receive synchronous port-free planners with the conceptual signature:

```text
create<Command>Plan(request, snapshot) -> immutable OperationPlan
```

The planner never reads a repository, filesystem, Git, process, environment, network, clock, ID
port, lock, or interaction port. It does not mutate request/snapshot and does not reread state.

Plans record the approved snapshot ID and exact expected-revision preconditions. Existing semantic
operation/group/pair ID constructors remain authoritative and clock/random-free. Snapshot ID does
not enter operation IDs; explicit preconditions own staleness so unrelated state does not churn
semantic operation identity.

For one request/snapshot pair:

- repeated planner calls are deeply equal and canonically ordered;
- dry-run, displayed preview, approval, and fresh execution use the exact operation set;
- execution never silently invokes the planner; and
- stale state requires a newly generated and displayed plan.

Compatibility result projection remains an edge concern. `planning/legacy-action.ts` owns only the
closed literal vocabulary; current acquisition/place result aliases and the compatibility mapper
consume it without reintroducing a planning-to-runner import.

## Domain repositories and logical staging

The five behavior-specific repositories are manifest, lock, ledger, live placement, and store.
Their contracts live in `state/repositories.ts`; domain adapters remain close to existing mechanics.

Every repository:

- owns exact reads and revision comparison for its domain;
- accepts domain-specific immutable edits;
- creates a logical immutable stage record against one expected revision;
- exposes coordinator lifecycle operations for stage, commit, rollback, and cleanup;
- returns exact before/after revisions and a `changed` fact; and
- maps expected failures into a closed domain result.

Logical staging does not claim physical durability. Existing artifact coordination, ledger
replacement/recovery, live swap, and store mechanics retain physical stage/backup/rename/fsync and
cleanup protocols. No repository reimplements a codec, registry, lock hierarchy, recovery record,
or writer.

The following designs are explicitly prohibited:

- generic CRUD or `Repository<T>`;
- a universal unit of work;
- dependency-injection container;
- ORM or event store;
- a fourth coordinator;
- a second codec/registry authority;
- merged artifact/ledger crash state machines; or
- public repository/snapshot interfaces.

## Coordinator revision cursor

Execution initializes an immutable resource-revision cursor from the approved snapshot. Under the
existing lock hierarchy, every referenced resource is reobserved and must match the cursor before
its operation starts.

Cursor transitions are exact:

1. unstarted, skipped, or pre-stage refusal — unchanged;
2. successful commit — advance only revisions proven by its receipt;
3. complete rollback — restore/retain the proven before revisions;
4. failure after a durable boundary — the physical adapter/recovery path must resolve it to a
   committed or rolled-back receipt before later work; and
5. indeterminate or unreadable state — stop the group and fail closed.

A cursor never advances from an in-memory model or guessed result. G3B-03's mandatory durable
reread after a started operation remains controlling. Successful pairs may advance truthfully when
a later pair fails; the group does not claim invocation-wide atomicity.

## Immutable ledger reducers and compatibility

Canonical ledger changes are copy-on-write reducer operations over `LedgerModel`. Reducers receive
no effect port, clock, ID source, persistence callback, or mutable context and return a validated
new frozen model or a closed error.

`withLedgerPairAt`, `withoutLedgerPairAt`, logical transaction reducers, project-registration
derivation, and history selection are reused or relocated to neutral ownership. The mutable
`LedgerFile` projection and `SwapCtx.ledger/persist` closure survive only inside a bounded
compatibility shell while current callers migrate, then lose production mutation authority.

The canonical G3B-03 writer remains the only ledger replacement, recovery, and bounded-history
cleanup engine. Existing version-1 read/migration behavior, logical/physical journal compatibility,
rollback direction, cancellation, and crash results remain unchanged.

## Runner extraction and size ratchet

Extraction is vertical, not cosmetic:

- `acquire/plan.ts` and `place/plan.ts` own pure planning;
- `acquire/execute.ts` and `place/execute.ts` bind plans to repositories/coordinator execution;
- `acquire/recovery.ts` and `place/recovery.ts` own compatibility recovery routing; and
- `acquire/run.ts` and `place/run.ts` become thin request/report orchestration shells.

At Ready, the no-growth baselines are 3,955 lines for `acquire/run.ts` and 2,917 lines for
`place/run.ts`. Test-first pins those maxima while also checking responsibility/import movement.
There is no arbitrary global maximum and no requirement to split the cohesive artifact coordinator
or ledger writer solely because they are large.

## Compatibility and successor exclusions

This gate preserves current CLI behavior, application-service results, public types, exit classes,
and human/JSON bytes. It adds no public export and owns no `packages/cli/**`, `src/index.ts`, or
`public-types.ts` path. Any need to change those surfaces is a blocker requiring a recorded ownership
amendment and compatibility review; it is not inferred from this plan.

G3B-04 does not implement:

- saved-plan apply or desired-state manifest/lock mutation;
- public undo, sync, update, GC, or retention-expiry policy;
- adapter extraction or known-tool policy changes (G3B-05);
- OperationContext or observation propagation (G3B-06);
- new commands, options, outputs, wire versions, codecs, DTOs, or persisted schemas;
- network behavior, credential handling, arbitrary filesystem targets, or external-system testing;
  or
- downstream workflow ownership for WF06, WF11, or WF13.

## Implementation ownership and sequence

After test-first and interface freeze, work may proceed in parallel with disjoint write ownership:

1. `/root/g3b04_state_snapshot` — ordinary-data ownership, revision/snapshot types, read
   repositories, consistent state reader, and focused state/status tests;
2. `/root/g3b04_planner_extraction` — neutral legacy action vocabulary, pure acquisition/place
   planners, compatibility parity, and planner tests;
3. `/root/g3b04_repository_execution` — ledger/live/store repositories, immutable reducer
   integration, revision cursor, execution/fault tests, and dependency-cycle closure; and
4. root integration owner — ADR/docs/lint, shared application/runner integration, recovery shells,
   ownership, aggregate selectors, reconciliation, and commits.

No agent modifies another partition without root reassigning the path. The final adversarial
reviewer is independent of all implementers.

Implementation order is:

1. commit Ready architecture and ownership;
2. add executable P3B-TS05 characterization/red tests and bind the catalog target;
3. freeze shared interfaces after independent red-test review;
4. close dependency reversals and ordinary-data ownership duplication;
5. implement revisions, snapshot reader, and pure planners;
6. add domain repository adapters and coordinator revision cursor;
7. migrate runner compatibility shells and remove mutable production authority;
8. refactor by responsibility without changing public behavior;
9. replay required, impacted, static, smoke, and recovery-smoke gates;
10. run independent architecture/adversarial review; and
11. run one terminal full repository gate before sign-off.

## Verification policy and Ready exit

Ready changes documentation and lifecycle metadata only. Required verification is:

- deterministic catalog/checklist generation;
- P17 catalog/P0A-TS09 governance tests;
- `bun run check:p17`;
- Markdown/JSON/diff hygiene; and
- independent scope and architecture review.

No runtime, smoke, recovery, P2-TS04, or full repository suite is required for Ready because no
production/test behavior changes. Test-first begins with the exact selector and standard smoke.
Recovery smoke joins as soon as coordinator, recovery, lock, barrier, durable I/O, or cancellation
behavior changes. The complete suite is reserved for a major integration milestone and terminal
sign-off.

Ready advances only P17-G3B-04 to `ready`, passes its Ready gate, and advances only
`EWP-P3B-T05` to `ready`. `EWP-CF-035` and `EWP-P3B-TS05` remain `planned`; no implementation,
validation, downstream workflow, or later lifecycle gate is credited.
