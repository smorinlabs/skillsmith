# P17-G4B-02 Ready plan

## Outcome and scope

G4B-02 activates `skillsmith apply` as the sole declarative convergence executor. Fresh apply
prepares the same immutable desired/current operation set as `skillsmith plan`, displays it,
obtains approval when changes exist, acquires the existing mutation locks, revalidates current
state, and executes those exact operation IDs and dependencies through the signed coordinator.
Saved apply decodes one reviewed saved-plan v1 artifact, validates only its referenced
compatibility and state facts, and executes that exact recorded operation set without prompting or
replanning. Its `--dry-run` and `--check` modes validate and render the exact saved operations
without writing.

The primary scope is exactly 31 entities:

- `COMMAND:apply`, decisions `D-002` and `D-014`, recommendation `P1-08`, findings `EWP-CF-009`,
  `EWP-CF-015`, and `EWP-CF-042`, and Phase-4B tasks `EWP-P4B-T03` and `EWP-P4B-T04`;
- command selectors `EWP-CMD-APPLY-TS01..TS14` and `EWP-CMD-PLAN-TS11`;
- option gate `EWP-OPT-TS09`;
- phase selectors `EWP-P4B-TS02`, `EWP-P4B-TS03`, and `EWP-P4B-TS07`; and
- workflows `EWP-WF06`, `EWP-WF07`, and `EWP-WF08`.

The required-now partition is exactly 29 selectors. Twenty-two are new G4B-02 primaries: apply
TS01..TS14, plan TS11, option TS09, P4B-TS02/03/07, and WF06/07/08. Seven are already-signed
dependency replays: plan TS06..TS10, plan TS12, and WF15. `EWP-WF13` is the sole downstream
obligation and remains planned under G5-05.

G4B-01 is signed and supplies the strict saved-plan v1 artifact, canonical projection,
deterministic desired/current planner, immutable observations, scoped resource/selection/
capability preconditions, owner-only writer, and plan report/renderers. Signed Phase 2 and Phase 3
supply canonical artifact readers, repositories, operation identities, scheduler, lock hierarchy,
under-lock revalidation, artifact/live/ledger execution authorities, and lifecycle events. G4B-02
composes those authorities; it does not replace them.

All work is authorized local open-source CLI development. Tests use temporary HOME/XDG/data,
project, store, ledger, live, and plan paths; hermetic local fixtures; `fixture.invalid` identities;
synthetic canaries; deterministic clocks and IDs; and bounded local child processes only.

## Command and mode contract

The activated grammar is:

```text
skillsmith apply
  [--file <path>] [--lockfile <path>]
  [-t, --tool <name>]...
  [-s, --scope <user|project> | --user | --project]
  [--locked] [--prune] [--yes] [--continue-on-error]
  [--dry-run | --check] [--json]

skillsmith apply --plan <path> [--dry-run | --check] [--json]
```

There are no positionals or command aliases. In fresh mode, `--dry-run` and `--check` are
compatibility views of the same fresh prepared product used by `plan`; they conflict with each
other and with `--yes`. `--no-prompt` remains inherited and asserts noninteraction; it never grants
approval. `--lockfile` requires `--file`, scalar selectors are singular, tool filters are
repeatable without duplicate values, and scope spellings are mutually exclusive.

Saved mode treats explicit selection of the plan artifact as prior authorization and therefore
does not prompt. It rejects `--file`, `--lockfile`, tool/scope filters and sugars, `--locked`,
`--prune`, `--yes`, and `--continue-on-error` before discovery or mutation. JSON and inherited
output/context controls remain allowed. Saved dry-run and check conflict; dry-run returns 0 for a
valid exact plan, check returns 0 for valid empty work and 7 for valid nonempty work, and either
returns 3 for stale or incompatible authorization. No saved mode changes the plan file.

Usage/refusal checks finish before project discovery, plan reads, source access, prompting, locks,
or writes. Exit classes retain the shared precedence: 0 success/valid empty, 1 execution or
integrity failure, 2 usage, 3 stale/invalid state, 4 unsupported capability, 5 source failure, 6
permission failure, 7 valid drift, and 130 cancellation. Errors 1..6 and cancellation outrank
drift. Partial results never convert a real error into 7.

## Minimal architecture

Exactly four focused seams are permitted:

1. Extract one `prepareReconcilePlan` use case from the current plan application flow. It selects
   and observes one artifact context, resolves allowed pins, creates one immutable
   `ReconcilePlanProduct`, and builds its saved projection. `plan` and fresh `apply` consume this
   same product; neither reconstructs operations from rendered DTOs.
2. Add one saved-plan validation module. It reads through the existing registered v1 artifact
   codec/repository, checks schema/executor/hash compatibility, resolves portable tokens or exact
   machine bindings, observes only referenced resource/selection/capability facts, and returns a
   validated remapped operation plan plus fresh execution guards. It never invokes the planner.
3. Add one reconciliation execution adapter. It binds every exact operation one-to-one to the
   existing artifact, placement, store, and ledger authorities, then invokes the existing
   coordinator/scheduler. It may extract narrow binding factories from current controllers but may
   not add a second coordinator, command-local transaction engine, journal format, or arbitrary
   dependency model.
4. Add a thin apply application service and report contract. The service partitions modes,
   requests fresh approval, invokes validation/execution, and maps shared outcomes/exits. One
   small structured approval-preview extension may carry the exact operation IDs/order to the
   interaction boundary; core does not import a CLI renderer and no broad interaction framework is
   introduced.

`CurrentMutatorCommand` gains `apply`; no new operation kind, saved-plan schema version, hash
domain, artifact grammar, lock hierarchy, scheduler, or recovery state is introduced.

## Fresh apply boundary

Fresh apply prepares once. The human/JSON preview, approval request, immediate revalidation, and
execution all refer to the same immutable operation IDs, order, before/after images, dependencies,
checks, diagnostics, selection, and prune authority. An unchanged plan exits 0 without prompting.
An interactive changing plan prompts with No as the default. Rejection or cancellation occurs
before mutation and leaves manifest, lock, ledger, live, store, and configuration bytes unchanged.
A noninteractive changing plan requires `--yes`; `--no-prompt` alone refuses.

Approval never bypasses a conflict, capability, integrity, selection, or state refusal. After
approval, the existing lock hierarchy is acquired and every operation actual-before and relevant
precondition is observed again. Any mismatch refuses instead of replanning behind the displayed
selection. `--prune` remains the separate deletion authority; filters, an empty manifest, an
unsupported adapter, ambiguity, or filter-to-zero never widen selection.

Default lock resolution remains visible in the prepared operation set. G4B-02 executes an already
planned `write-lock` operation through existing artifact authorities, but does not define the
terminal lock update/reproduction policy owned by G4B-03.

## Saved-plan validation and exact execution

Saved apply first decodes the strict v1 artifact and checks its executor schema, hash schema and
domains, operation/check/precondition graph, and capability requirements. Every portable token is
resolved from the current invocation/project/tool context using one closed resolver. A
machine-bound location must match its recorded binding and associated preconditions; mismatch
returns state 3 with regeneration guidance.

Staleness is scoped:

- a formatting/comment-only manifest edit remains valid because authorization compares the
  semantic manifest fact; execution then binds a fresh current byte revision for under-lock CAS;
- a semantic manifest change, selected canonical lock change, referenced source/live/store/ledger
  fact change, selected-set membership change, relevant capability version change, or incompatible
  executor/hash domain is stale;
- unrelated resources, unselected declarations, and unrelated adapter capabilities do not stale
  the plan; and
- complete-set prune/delete operations retain the complete selected-set fingerprints recorded by
  the plan rather than degrading to per-item checks.

Validation reconstructs the executable internal plan without changing any ID, ordering edge,
image, selection source, reason, mutation flag, or reversibility fact. The executor creates exactly
one binding per recorded operation and executes only those bindings. Missing, duplicate,
ambiguous, unsupported, or changed bindings refuse. Saved dry-run/check stop after exact
validation/rendering and never lock or write. Saved execution retains the plan artifact
byte-identically.

## Ordering, failures, output, and portability

The signed scheduler remains authoritative for dependency ordering and safe parallelism.
Fail-fast is the fresh default; `--continue-on-error` applies only to fresh independently schedulable
groups. Failed groups report truthful per-operation/per-tool results and a fresh rerun observes
current state and converges remaining work. Saved execution uses its recorded batch semantics and
cannot be widened by a CLI batch override.

`ApplyReportV1` is a strict versioned projection containing the mode, selected artifact or saved
plan, exact operations/checks/diagnostics, approval state, validation state, per-operation results,
summary, and exit-relevant state. Human and JSON output consume that one projection. The report and
all diagnostics are recursively redacted through the existing boundary. Credential URLs,
environment values, secret canaries, temporary/recovery/store internals, and raw nested errors do
not reach plan files, streams, reports, journals, backups, temporaries, or partial-failure residue.

Portable plans contain no local absolute path and bind deterministically on a compatible current
machine/project. Machine-bound plans retain explicit reason/path/precondition facts and useful
refusal guidance. G4B-02 proves binding, refusal, and redaction. G4B-03 retains full machine-A to
machine-B reproduction and crash-recovery coverage.

## Explicit exclusions

G4B-02 does not add or change:

- saved-plan schema v2, hash domains, operation vocabulary, artifact grammar, or plan writer;
- another planner, scheduler, coordinator, lock hierarchy, transaction engine, journal, or
  command-specific durability mechanism;
- terminal lockfile resolution/update policy, every-boundary crash recovery, or machine-A to
  machine-B reproduction owned by G4B-03;
- sync, update, undo, GC, generated-help, or Phase-5/6 behavior;
- arbitrary cross-group dependencies, implicit selection widening, or unmanaged deletion; or
- public-network, real-account, real-credential, third-party-system, or destructive testing.
