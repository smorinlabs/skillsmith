# P17-G3B-05 Ready plan

## Outcome and exact scope

G3B-05 completes the consumption side of ADR 0007. The validated `ToolRegistry` remains the sole
capability authority; existing inventory, verification, and placement bundles remain the only
tool-specific implementation owners. Generic lifecycle selection, planning, execution, and human
rendering receive narrow registry/bundle inputs instead of closing over production globals.

The immutable catalog scope is exactly two primary entities:

- `EWP-P3B-T06` — complete tool-specific lifecycle ownership behind registered bundles; and
- `EWP-P3B-TS06` — the sole required selector.

The immutable validation partition contains only `EWP-P3B-TS06`. There is no downstream coverage
owned by this group. Signed `EWP-CF-036` remains a secondary trace whose primary implementation
owner is G1-05. G3B-05 closes the deferred lifecycle/fingerprint proof without reopening the
registry decision or advancing `EWP-WF01`, `EWP-WF05`, or `EWP-WF07`.

The sole formal dependency is signed G3B-01. Signed G1-05 is the registry baseline; signed G3B-04
is the immutable snapshot/planner/execution baseline. Current public commands, report schemas,
wire codecs, human/JSON bytes, durability, recovery, and exit behavior remain unchanged.

This remains authorized, credential-free local work for the open-source Skillsmith CLI. Tests use
hermetic ports, temporary roots, fixture adapters, deterministic operation plans, and synthetic
data only.

## Architecture review verdict

The current architecture is sound but incompletely consumed. No new adapter framework is needed.
The accepted before/after is:

| Concern | Before | After |
|---|---|---|
| Registry access | Generic lifecycle modules import production `toolRegistry`/`FLIP_TOOLS` | Production composition supplies a narrow registry projection to generic kernels |
| Placement policy | Generic code interprets root order and rebuilds project/legacy/duplicate logic | Existing placement bundles own scope-aware root facts, list, resolution, duplicates, and notices |
| Verification gates | Install and promote repeat mode and verdict reduction | One pure policy/evaluation helper; command wording and error mapping stay local |
| Rendering | Lifecycle renderers query the production registry | Renderer calls receive adapter facts or a narrow registry projection; result/wire shapes stay fixed |
| Capability staleness | Mutation snapshots hash the complete registry | Snapshots bind only used adapter/operation/mode/scope requirements |
| Fixture tools | Selection/planning validation is built-in-only | Internal generic kernels accept registered string IDs; public wrappers default to built-in types |

The plan explicitly rejects a `LifecycleBundle`, DI container, plugin loader, renderer DSL,
workflow/policy engine, inheritance hierarchy, root-topology framework, transaction rewrite, or
public schema redesign.

## Registry-bound lifecycle authority

One private structural authority is accepted:

```text
LifecycleToolRegistry = Pick<ToolRegistry,
  'ids' | 'get' | 'toolsFor' | 'capability'>
```

Consumers may narrow this further. They may not copy IDs, operation facts, versions, or bundle
dispatch into new maps. Production wrappers default to `toolRegistry`; tests and embeddings may
provide another validated registry.

The registry is injected through existing dependency composition:

- lifecycle application services derive known/allowed tools and capability remediation from it;
- acquisition and placement runners use it for selection, roots, hints, verification, and result
  facts;
- snapshot authorities derive relevant capability requirements from it;
- planning canonicalization receives registry order for non-built-in fixture IDs; and
- renderer functions or factories receive only the registry/fact projection they need.

No service locator or ambient mutable registry is introduced. Compatibility exports
`SUPPORTED_TOOLS`, `VERIFY_TOOLS`, and `FLIP_TOOLS` remain immutable derived 1.x views, but generic
lifecycle kernels no longer use them as hidden authority.

## Fixture typing boundary

Internal lifecycle and planning types become generic in `ToolId extends string`, with the current
built-in type as the default. The widening is bounded:

- public command wrappers, current reports, ledgers, codecs, and generated declarations continue
  to expose the existing built-in unions;
- generic kernels can carry a novel validated fixture ID through selection, immutable operation
  planning, verification, placement, private dry-run/execution binding, and rendering;
- operation identity remains tool-string based and unchanged;
- planner validation accepts only syntactically valid IDs supplied by its registry context; and
- ordering follows descriptor order, with stable lexical fallback only for data outside a supplied
  registry context.

There is no unsafe cast seam and no second fixture-only operation model. Novel fixture execution
ends at a private hermetic prepared binding/coordinator result; it never enters the built-in-fixed
public reports, swap plan, ledger, journal, artifact codecs, or saved-plan DTO. Production
Claude/Codex replays prove the real durable lifecycle. Public `SupportedTool` and `FlipTool` are not
globally replaced with unconstrained `string`.

## Scope-aware placement ownership

`PlacementBundle` is extended additively. Existing 1.x adapter source compatibility is retained;
new scope-aware behavior is optional at the public extension boundary but normalized by registry
construction into one complete runtime shape.

The additive adapter surface and its normalized private runtime shape are:

```text
PlacementRootFact {
  path
  role: destination | alternate
}

PlacementBundle additions {
  rootFacts?(env, scope, ctx) -> PlacementRootFact[]
  listScoped?(env, ctx, storeRoot, scope) -> PlacementInventory
  resolveScoped?(env, ctx, storeRoot, skill, scope) -> PlacementResolution
}

RegisteredPlacementBundle {
  rootFacts
  listScoped
  resolveScoped
  noticeForRoot
}
```

The normalized runtime bundle owns:

- ordered root facts for a requested scope, including destination/current versus noncanonical or
  legacy role;
- scope-aware listing and resolution;
- duplicate detection and exact duplicate reason;
- notices associated with the selected root;
- the default destination root; and
- the complete standard-root set used to distinguish ledger-owned custom paths.

Built-in Claude and Codex adapters implement the complete shape. Registry construction normalizes
older external adapters exactly once: existing `roots`, `list`, `resolve`, and `noticeForRoot`
remain callable; a missing role declaration treats the first root as destination and every later
root as ordinary alternate; user-scope legacy methods retain their exact behavior; other scopes
use the neutral shared placement primitives across all declared roots; multiple present roots are
a duplicate and block destination mutation; and no legacy wording is invented unless the adapter's
existing `noticeForRoot` returns it. Generic lifecycle modules consume only the normalized runtime
shape and never apply a second fallback or guess a tool name.

Normalization preserves the legacy methods as a structural superset, rejects duplicate root paths,
and requires exactly one destination whenever the root-fact result is nonempty.

After migration:

- acquisition no longer uses `[0]` as destination policy or `.slice(1)` as legacy policy;
- placement planning no longer reconstructs project-scope list/resolve/duplicate behavior;
- uninstall uses the same adapter resolution path as install/dev/promote;
- path ownership enumerates adapter root facts and adapter notices; and
- `standardRoots` is deprecated as a compatibility alias and has no independent policy.

Shared physical `classifyPlacement` and `listPlacements` primitives remain neutral and reusable.
Custom destination classification and cross-scope target selection remain generic because they are
ledger/command policy, not tool policy.

## Verification gate consolidation

The existing `VerificationBundle` remains the only owner of verifier dispatch, available modes,
gate policy, checked-against version, target manifests, and renderer facts. No lifecycle bundle is
added.

One private pure helper may be introduced for:

- resolving requested lifecycle mode from `gatePolicy` and the command request;
- reducing `pass`, `warn`, `fail`, and `inconclusive` under strict/non-strict policy; and
- returning structured gate status, verdict, actual mode, and whether execution may continue.

Acquisition and placement keep command-specific exception handling, messages, error classes, and
report assembly. Finding summaries remain local unless a shared helper has two behavior-identical
consumers. Verification execution remains in `verify/run.ts` and adapters.

## Structured renderer facts

Human renderers remain pure presentation functions. They receive a narrow registry projection or
already-selected immutable adapter facts; they do not import the production registry.

- install consumes the adapter-provided static notice;
- verify consumes the adapter-provided deep coverage suffix; and
- flip renders the actual verification mode recorded by the immutable plan/check or gate result,
  never re-deriving it from a tool ID or production registry.

No public report or wire field is added. The current production renderer registry supplies the
production adapter authority, while TS06 can inject fixture facts directly. Existing human and JSON
goldens must remain byte-identical.

## Relevant capability fingerprints

The public complete capability snapshot and its existing `createCapabilityStateReaderV1` used by
status/agents remain unchanged. Mutation staleness receives a separately named private reader and
relevant-capability model:

```text
RelevantCapabilityQueryV1 {
  schemaVersion: 1
  tool
  operation
  scope
}

RelevantCapabilityFactV1 {
  schemaVersion: 1
  tool
  capabilityVersion: positive integer | null
  operation
  scope
  supported
}

RelevantCapabilitySnapshotV1 {
  schemaVersion: 1
  facts[]
}
```

Queries are registry-ordered, duplicate-free, deeply frozen ordinary data. Verification mode is
represented by the used operations: static requires `verify-static`; static-plus-deep requires both
`verify-static` and `verify-deep`. Lifecycle work also queries the command operation and the
selected user/project/custom scope.

Snapshot authorities construct the exact query set after selection and before planning. The
canonical frozen queries produce a query-set digest that is part of the capability resource ID, so
two different requirement sets can never alias the same resource. A separately named private
`createRelevantCapabilityStateReaderV1` receives the validated registry plus immutable queries and
resolves their current facts on every observation. A missing adapter produces a null version and
unsupported fact rather than disappearing from the query set. Execution reobserves the same
queries through the bound repository. The capability revision remains one semantic expected
revision in the immutable snapshot vector, but its value contains only relevant current facts.

`ObservedStateSnapshotV1`, `ObservedStateRepositoriesV1`, and `readObservedStateSnapshotV1` become
generic in their capability model with the existing complete public DTO as the default. Status
continues to use the unchanged full reader/default model. Acquisition and placement explicitly use
the private relevant model; no cast bridges the two.

Consequences:

- changing a used adapter's `capabilityVersion` stales the plan;
- removing support for the used operation/mode/scope stales or refuses the work;
- adding, removing, or changing an unrelated adapter does not change the relevant revision;
- operation IDs remain independent of capability revisions; and
- status continues to use the existing full capability reader and public capability product.

G3B-05 also supplies a cast-free built-in-only mapping from supported relevant facts to the existing
saved-plan `CapabilityPreconditionV1` shape. Fixture facts remain private and never enter the fixed
`PlanToolV1` union. Phase 4 owns saved-plan persistence, application, option policy, and stale exit
behavior; this group proves only deterministic relevant versus unrelated semantics.

## Static authority gates

`EWP-P3B-TS06` rejects:

- executable comparisons, switches, includes checks, or keyed policy maps for Claude, Codex, Kilo,
  or OpenCode outside adapter-owned modules and the built-in registry composition;
- direct built-in adapter imports outside `agents/registry.ts`;
- independent built-in capability/version/writeability matrices;
- executable reads from production `toolRegistry`, `SUPPORTED_TOOLS`, or `FLIP_TOOLS` inside
  registry-parameterized kernel bodies; a production wrapper/default-parameter composition may
  name the registry once;
- root-ordinal destination/legacy policy (`[0]`/`slice(1)`) outside adapters/compatibility
  normalization; and
- renderer lookups against the production registry.

Fixed wire unions, compatibility type aliases, historical goldens, fixtures, documentation, adapter
literals, and the derived 1.x projections themselves are explicitly allowed. The static test is
semantic support for runtime fixture routing, not a text-only completion claim.

## Test-first selector

The exact command is:

```text
bun test tests/ergonomics/phase/EWP-P3B-TS06.test.ts --test-name-pattern EWP-P3B-TS06
```

The selector contains ten executable families:

1. static known-tool branch, direct-import, global-authority, and root-ordinal policy bans;
2. registry-bound selection distinguishing unknown usage 2 from known unsupported capability 4;
3. a novel writable fixture adapter through immutable install/uninstall/dev/promote planning;
4. fixture private dry-run/execution-binding identity and exact adapter-owned placement routing,
   without ledger/journal/swap/codec persistence;
5. fixture static/deep verification policy and strict gate reduction;
6. adapter-provided install, flip, and verify human facts without production registry lookup;
7. exact Claude/Codex roots, notices, lifecycle behavior, and static/deep verification parity;
8. effect-free Kilo/OpenCode mutation and verification capability exit 4;
9. relevant capability fingerprint determinism, used-version/operation/scope staleness, and
   unrelated-adapter validity; and
10. public type, current wire, human/JSON golden, compatibility-export, and operation-ID parity.

Missing planned files alone cannot form the red receipt. Characterization clauses for signed
registry, lifecycle, immutable planning, current bytes, and exits remain green; each red must name
a concrete missing runtime or architecture authority.

## Implementation slices

1. **Selector only:** commit TS06 and fixture adapters with actionable red families and green
   characterization.
2. **Registry/capability interface:** add the narrow registry authority, normalized placement
   bundle shape, relevant capability requirements/fingerprint, and generic planning-order context.
3. **Selection and snapshot binding:** inject registry authority into lifecycle application,
   acquisition/place snapshot readers, and planner validation without changing execution behavior.
4. **Placement migration:** move scope-aware root/list/resolve/duplicate/notice behavior fully into
   Claude/Codex bundles; remove generic root-order assumptions and repeated uninstall discovery.
5. **Verification/rendering migration:** share pure gate evaluation, inject renderer facts, and use
   actual recorded flip verification mode.
6. **Compatibility/refactor:** remove obsolete duplicate helpers, prove old adapter compatibility,
   preserve bytes and derived 1.x exports, and run focused/impacted validation.
7. **Adversarial and terminal:** independent review, correction replay, smoke, package/static gates,
   then the reserved complete repository suite before sign-off.

Parallel implementation begins only after the selector and registry/capability interface commits.
Root owns shared types, catalog/evidence, integration, and commits. Placement and
verification/rendering work may proceed in parallel only with disjoint ownership.

## Required replay and milestone policy

During iteration run the TS06 selector, directly affected focused tests, and standard smoke. Replay
these signed selectors before impacted-green when their surfaces change:

- `EWP-P1-TS09` — registry and generic branch authority;
- `EWP-CMD-AGENTS-TS03` — complete capability presentation;
- `EWP-CMD-VERIFY-TS02` — exact verifier selection/deep behavior;
- `EWP-P3B-TS05` — immutable snapshot/planner/repository authority; and
- G3B-01 planning/lifecycle selectors affected by generic tool typing and ordering.

Recovery smoke is required only if an authorized change reaches coordinator, journal, ledger,
swap, or recovery mechanics. Those paths are not owned initially. The full repository suite is not
an iteration command; it runs once at the terminal G3B-05 milestone and again only after a terminal
correction that changes relevant product/test behavior.

## Explicit exclusions

G3B-05 does not add Kilo/OpenCode mutation, a production adapter, adaptation, a verification mode,
dynamic plugin loading, manifest/lock desired-state mutation, plan/apply command behavior, saved-plan
persistence/application, workflow sign-off, operation observation, public schema/codec versions,
new CLI options, output redesign, ledger migration, transaction/lock scheduling, journal/recovery
behavior, or a public generic repository/adapter framework.

The following remain intentionally separate: tool verifier implementations; adapter root modules;
neutral placement primitives; selection semantics; command-specific messages; transaction,
coordinator, journal, swap, and recovery authorities; public compatibility projections; and fixed
wire DTOs/goldens.

## Ready acceptance

Ready requires independent confirmation that:

- the 56-path manifest is sufficient but bounded;
- fixture generic typing does not widen current public/wire contracts;
- placement compatibility normalization has one final runtime authority;
- relevant capability observation cannot be invalidated by unrelated adapters;
- renderers preserve current bytes without a new DSL or report field;
- every red family is executable and implementation-free; and
- no G3B-06, Phase-4, workflow, or release ownership is stolen.

Only after Ready acceptance may TS06 be committed.
