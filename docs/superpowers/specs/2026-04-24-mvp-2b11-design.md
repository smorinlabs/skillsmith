# SkillSmith MVP-2b.1.1 design — "Plugin-scope + slash commands (+ managed scope + origin)"

**Status:** Approved 2026-04-24
**Scope:** Small patch on top of `v0.3.0` closing the plugin-scope discovery gap and adding slash-command listing as a separate primitive. Also extends `Scope` with `managed` and adds an `origin` field to `SkillEntry` / new `CommandEntry`.
**Release framing:** Internal milestone (`v0.3.1`, no public release).
**Prerequisite:** `v0.3.0` (MVP-2b.1) tagged.

## 1. Why

MVP-2b.1 shipped `skillsmith list` with `scope: 'system' | 'user' | 'project'`. Testing against a real machine exposed three gaps:

1. Claude Code's `/skills` UI shows 47 skills; SkillSmith reports 1. The 46 missing are 25 plugin-bundled skills + 21 slash commands. Plugin skills are a real scope missing from our model; slash commands are a distinct primitive.
2. Claude Code's actual `PluginScope` has 4 values (`managed | user | project | local`). `managed` is a real enterprise/MDM precedence tier and belongs on the skill-scope enum too.
3. A skill can come from three different management systems — hand-placed files, a plugin's bundled `skills/` directory, or an org-pushed managed-settings policy. Without an `origin` field, we can't tell users which system a skill comes from, and we can't answer "is this skill enabled right now?" reliably.

Per research in `research/skillsmith-skill-install-paths.md` (Claude Code section) and direct inspection of `~/c/claude-code/src/utils/plugins/{schemas,installedPluginsManager,managedPlugins,pluginPolicy}.ts`:

- All plugins (user/project/managed/local scope) share one cache directory: `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`. Scope is metadata on the install entry, not a separate install path.
- **Enablement** is per-scope: each scope reads its own `enabledPlugins` map from a different settings file. A plugin present on disk at user scope but with `enabledPlugins[id] = false` in `~/.claude/settings.json` is **installed but disabled**.
- **`local` scope** = enablement via `<repo>/.claude/settings.local.json` (gitignored). From the listing perspective, these are project-scope skills with provenance `pluginScope: 'local'`.

## 2. Scope (deliverables)

### 2.1 Type additions

**`Scope` enum — 4 values:**

```ts
export const SCOPES = ['system', 'user', 'project', 'managed'] as const;
export type Scope = (typeof SCOPES)[number];
```

- `managed` is new. Represents enterprise/MDM-enforced precedence. For Claude Code, `managed` skills arrive from policy-pushed `enabledPlugins` or from platform managed-settings paths (`/Library/Application Support/ClaudeCode/managed-settings.json` on macOS, `/etc/claude-code/managed-settings.json` on Linux, `C:\ProgramData\ClaudeCode\managed-settings.json` on Windows).
- `local` (Claude Code's session-only scope for `<repo>/.claude/settings.local.json`) is **not** added to our `Scope` enum. Users see these skills at `scope: 'project'` with `origin.pluginScope: 'local'` preserving provenance.

**`Origin` tagged union:**

```ts
export type PluginProvenanceScope = 'user' | 'project' | 'managed' | 'local';

export type Origin =
  | { kind: 'standalone' }                                   // plain files on disk
  | {
      kind: 'plugin';
      pluginId: string;                                      // "foo@marketplace"
      pluginVersion: string;                                 // version segment of cache path
      pluginScope: PluginProvenanceScope;                    // how the plugin is installed/enabled
    }
  | { kind: 'policy' };                                      // pushed via managed-settings.json
```

**`SkillEntry` extension** — two new fields:

```ts
export interface SkillEntry {
  // ...existing: name, path, realpath, tool, scope, root, frontmatter
  origin: Origin;                                            // NEW
  enabled: boolean;                                          // NEW
}
```

- `enabled` is always `true` for `origin.kind === 'standalone'` (a file on disk in a real scope root is always active).
- For `plugin` origin: `enabled` reflects whether the matching `enabledPlugins[pluginId]` in the correct settings file is `true`. Absent/`false` → `enabled: false`.
- For `policy` origin: `enabled` is always `true` (policy is the precedence tier, not a toggle).

**New `CommandEntry` type — parallel to `SkillEntry`:**

```ts
export interface CommandEntry {
  name: string;                                              // filename without .md
  path: string;                                              // absolute .md path
  realpath: string;
  tool: SupportedTool;
  scope: Scope;                                              // user | project (no system/managed for cmds in MVP)
  root: string;
  frontmatter: Frontmatter | null;                           // YAML frontmatter of the .md
  origin: Origin;
  enabled: boolean;
}
```

Key differences from `SkillEntry`: commands are single `.md` files (not directories with `SKILL.md` inside), and they don't exist at `system`/`managed` scope.

### 2.2 New `@skillsmith/core` public API

```ts
export type {
  Origin,
  PluginProvenanceScope,
  CommandEntry,
  ListCommandsOpts,
} from './public-types.ts';

export { listCommands } from './commands/list-commands.ts';

// existing listSkills signature unchanged; behavior expanded
```

### 2.3 New CLI command

```
skillsmith commands [<glob>...] [--tool <name>]... [--scope <s>] [--user] [--project]
                    [--long] [--json] [--enabled | --disabled]
```

- No alias (`cmds` considered, skipped — keep the surface tight).
- `--scope` choices: `user | project` only. `system` and `managed` rejected with exit 2 (commands don't have those scopes).
- `--enabled` / `--disabled` — mutually exclusive filters. Neither → show both.

### 2.4 `list` changes

- `--scope` choices gain `managed` (now `user | project | system | managed`).
- `--enabled` / `--disabled` filters added (same semantics as `commands`).
- Output grows new columns in `--long` mode: `origin` and, when origin is plugin, `<plugin>@<version>`. JSON gets `origin` + `enabled` fields (schema bumps to `schemaVersion: 2` — experimental so bumping is fine).

## 3. Architecture

### 3.1 New core module: `plugins/`

Centralizes plugin-registry reading. All four agents reuse it (though only claude-code has content for MVP-2b.1.1).

```
packages/core/src/plugins/
  types.ts              # PluginInstallation, PluginEnablement (internal)
  installed.ts          # readInstalledPlugins(env): parses ~/.claude/plugins/installed_plugins.json
  enablement.ts         # resolveEnablement(env, pluginId, cwd): reads 4 settings layers, returns {enabled, enabledAt}
  discover.ts           # discoverEnabledPlugins(env, cwd): returns the joined data ready for consumers
```

- `installed.ts` schema-validates with zod. Returns `{ version, plugins: Array<{id, scope, installPath, projectPath?, version}> }`.
- `enablement.ts` reads the right settings file per scope:
  - `managed`: platform-dependent `managed-settings.json` (macOS, Linux, Windows paths).
  - `user`: `~/.claude/settings.json`.
  - `project`: `<cwd>/.claude/settings.json`.
  - `local`: `<cwd>/.claude/settings.local.json`.
  Returns `{enabled: boolean, source: 'managed' | 'user' | 'project' | 'local' | 'none'}` (latest-wins across layers is not applied here — each installation entry is resolved against its own scope's settings file).
- `discover.ts` joins: returns `Array<{installation: PluginInstallation, enablement: PluginEnablement, cachePath: string}>`. `listSkills` and `listCommands` iterate this list to generate plugin-origin entries.

### 3.2 Agent interface extension

```ts
interface Agent {
  // existing
  readonly tool: SupportedTool;
  readonly installHint: string;
  detect(env, signal?): Promise<Result<InstallRecord[], SkillSmithError>>;
  getSkillRoots(env, scope, ctx): readonly string[];          // existing — now also handles 'managed'

  // NEW
  getCommandRoots(env, scope, ctx): readonly string[];
  getPluginSkillDir(installPath): string | null;              // e.g. join(installPath, 'skills')
  getPluginCommandDir(installPath): string | null;            // e.g. join(installPath, 'commands')
}
```

- For claude-code: `getPluginSkillDir` = `<installPath>/skills`, `getPluginCommandDir` = `<installPath>/commands`.
- For codex/opencode/kilo-code: both return `null` for now. When those ecosystems grow a plugin model we add them.
- `getSkillRoots('managed', ctx)` for claude-code returns `[]` (managed plugins surface through origin=plugin+pluginScope=managed, not through a separate skill root); for codex it could return `/etc/codex/skills` if we want (currently under `system`).

### 3.3 `skills/walk.ts` behavior change

Two new data sources feed the walker:

1. **Standalone skills** (existing) — scan `getSkillRoots(env, scope, ctx)` for each scope. These get `origin: {kind: 'standalone'}`, `enabled: true`.
2. **Plugin-bundled skills** (new) — for each discovered plugin, compute `agent.getPluginSkillDir(installation.installPath)`, scan it the same way. These get `origin: {kind: 'plugin', pluginId, pluginVersion, pluginScope: installation.scope}`, `enabled: <from enablement resolver>`. The `scope` field is mapped from `pluginScope`: `'local' → 'project'`, others pass through. `root` = the plugin's skill dir. `tool` = the agent being scanned.

Policy-pushed skills (if managed-settings pushes a skill directly rather than via a plugin) are out of scope for MVP-2b.1.1 — `origin: 'policy'` is defined in the type but not produced by any walker yet. Keeps the type forward-compatible without building a discovery path for rare territory.

### 3.4 `commands/walk.ts` (new)

Parallel to `skills/walk.ts` but targets a different file shape:

```ts
walkCommandDir(env, { tool, scope, root }): Promise<CommandEntry[]>
```

- `env.listDir(root)` returns entries.
- For each `name.md` file (not a directory), read it, parse frontmatter via the same `parseSkillFrontmatter` helper (frontmatter format is identical), build `CommandEntry`.
- Ignore files that don't end in `.md`.
- `.md` files at top level only — no recursion for MVP.

### 3.5 `scan/list-commands.ts` (new)

Orchestrator parallel to `listSkills`:

```ts
listCommands(env, opts: ListCommandsOpts): Promise<Result<CommandEntry[], SkillSmithError>>
```

Iterates `tools × scopes`, calls `agent.getCommandRoots(env, scope, ctx)` for standalone dirs, plus `agent.getPluginCommandDir(installation.installPath)` for each discovered plugin. Applies glob / scope / enabled filters. Dedupes by `realpath`.

### 3.6 Enablement resolver (the subtle part)

For each plugin installation entry, we need to decide whether it's enabled:

```
switch (installation.scope) {
  case 'user':    return user settings.json#enabledPlugins[id]
  case 'project': return <installation.projectPath>/.claude/settings.json#enabledPlugins[id]
  case 'local':   return <installation.projectPath>/.claude/settings.local.json#enabledPlugins[id]
  case 'managed': return platform managed-settings.json#enabledPlugins[id]
}
```

- `true` → enabled.
- `false` → disabled (Claude Code honors explicit-false).
- missing / no file / parse error → **disabled** (conservative; don't assume).

For project/local scopes, the `projectPath` field on the installation entry must match the caller's `cwd` (walked up to repo root via existing `findProjectConfig` helper). If the caller's `cwd` is outside the installation's `projectPath`, treat the entry as not-applicable — skip it entirely (it's a different project's install).

### 3.7 JSON schema bump

- `list-json.ts` and new `commands-json.ts` emit `schemaVersion: 2` (experimental) with new `origin` + `enabled` fields.
- Existing consumers reading `schemaVersion: 1` will fail validation — acceptable because the schema was marked experimental in MVP-2b.1.
- Doctor JSON stays at `schemaVersion: 1` (unchanged).

### 3.8 ESLint zone additions

- `packages/core/src/plugins/**` may be imported by `skills/**`, `commands/**`, `scan/**`, `doctor/**`, `agents/**`. May NOT import from any of those (it's a leaf).
- `packages/core/src/commands/**` same boundary rules as `skills/**`.

### 3.9 Exit code mapping

No new exit codes needed. Enablement filter conflicts (`--enabled --disabled`) exit 2 via the existing scope-resolver pattern, extended.

## 4. CLI behavior

### 4.1 `skillsmith list` changes

```
skillsmith list [<glob>...] [-t --tool <name>]... [-s --scope <s>]
                [--user] [--system] [--project] [--managed]
                [--duplicates] [--long] [--json]
                [--enabled | --disabled]
```

- `--managed` shorthand flag added (mirrors `--user`, `--system`, `--project`).
- `--enabled` / `--disabled` mutually exclusive; if both, exit 2. Neither → show both.
- `--long` output gains `origin` and (when plugin) `pluginId@pluginVersion` columns.
- Default human output groups by tool/scope (unchanged), then by origin within scope when mixed.

### 4.2 `skillsmith commands` (new)

```
skillsmith commands [<glob>...] [-t --tool <name>]... [-s --scope <s>]
                    [--user] [--project]
                    [--long] [--json]
                    [--enabled | --disabled]
```

- `--scope` choices: `user | project`. `system` or `managed` exits 2.
- Positional glob matches against command `name` (filename without `.md`).
- Human output parallel to `list`:
  ```
  # claude-code
    user:
      ci-audit            standalone   Use when the user asks about "GitHub Actions"...
      brainstorming       plugin:superpowers@5.0.7   You MUST use this before any creative work...
    project:
      (none)
  ```
- JSON: `{schemaVersion: 1, experimental: true, commands: CommandEntry[]}`.

## 5. Success criteria

1. `./skillsmith list --tool claude-code --json` on the reporter's machine returns **≥26 skills** — 1 standalone user skill + 25 enabled plugin-bundled skills. Disabled `superpowers` plugin yields `enabled: false` entries.
2. `./skillsmith commands --tool claude-code --json` returns the 21 standalone user commands + N plugin-bundled commands.
3. `./skillsmith list --scope managed` runs cleanly (empty for typical users, non-empty on MDM-managed machines).
4. `./skillsmith list --disabled` surfaces the disabled `superpowers` entries.
5. `./skillsmith list --user --system` still exits 2 (existing scope-conflict behavior preserved).
6. All 8 `doctor` checks still pass; none affected by the new metadata.
7. `bun run check` — all green.
8. Library consumers can read `{origin, enabled}` via `@skillsmith/core` types without an import change (both exported from the public surface).

## 6. Out of scope

- Managed-settings.json reading on Linux and Windows paths — implemented but only exercised on the macOS path; Windows tests deferred to Phase 2 (Windows CI).
- `origin.kind: 'policy'` production path — the type exists but no walker emits it. Used in Phase 2 when we add a policy-aware scanner.
- Codex/opencode/Kilo plugin models — their `getPluginSkillDir` returns `null`. When those ecosystems grow real plugins we fill them in.
- Nested skill directories inside plugin caches — we scan top-level `<installPath>/skills/*/SKILL.md` only.
- `install`/`uninstall` at `--scope=managed` or `--scope=plugin` — MVP-2c explicitly refuses both.
- Plugin-contributed healthcheck scripts — Phase 2 per MVP-2b spec.

Tag `v0.3.1` internally after all of the above pass.
