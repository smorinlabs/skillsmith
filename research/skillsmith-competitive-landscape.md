# SkillSmith enters a crowded, commoditizing market

**The cross-tool AI skills installer space is already contested by at least a half-dozen shipping products.** Vercel Labs' `npx skills` (40+ agents supported, 579K installs on its top skill), Microsoft's `apm` (enterprise-grade, Microsoft-stewarded), GitHub Copilot's official `copilot plugin install … @awesome-copilot`, Smithery's pivot into skills, and independents like `skild.sh`, `skillpm`, and antfu's `skills-npm` all shipped in roughly the last four months. The baseline feature set SkillSmith proposes — tool-aware install, format adaptation, GitHub-style identifiers, manifest + apply — is now table stakes, not differentiation. However, the pain that motivated SkillSmith is real and unresolved: developers are quoted across GitHub issues, Reddit, HN, and dev blogs describing a "Tower of Babel" of six-plus rule formats, scope bugs where `--scope user` silently writes project-scoped configs, ~50% skill auto-activation rates, broken `plugin update` commands, and no clean uninstall path anywhere. Standards are consolidating under the Linux Foundation's Agentic AI Foundation (AAIF) — **MCP, AGENTS.md, and Anthropic's Agent Skills spec are converging** — which both shrinks the "adaptation" value prop over 12 months and creates an opening for a neutral, high-polish reference implementation. The winning positioning is probably not "another `npx skills`" but rather **governance, trust, and authoring quality** on top of the emerging standards.

## The competitive landscape in one picture

The market decomposed cleanly into four tiers during this research. At the top, **direct cross-tool installers** already ship with broad agent coverage. Below them, **MCP registries** (Smithery, mcp.so, GitHub MCP Registry, the official modelcontextprotocol.io registry) handle the tool-connectivity side. Then **per-tool native marketplaces** (Claude Code `/plugin`, Cursor Marketplace, Cline MCP, Continue Hub, Copilot CLI) own the last mile inside each IDE. Finally, **awesome-list curation** (awesome-mcp-servers at ~85K stars, awesome-cursorrules at ~39K, awesome-claude-code at ~38K) serves as human-readable discovery. SkillSmith would enter at the top tier — the most crowded and fastest-moving.

The central finding is that **the "write-once, install-everywhere" thesis is no longer blue ocean**. As of April 2026, a developer wanting to install a skill across Claude Code + Codex + Cursor + Kilo can run a single `npx skills add owner/repo` command today. The same developer needing enterprise governance, SARIF output, and Unicode-injection scanning can run `apm apply` today. The same developer wanting AI-skill-adjacent MCP installation can run `npx add-mcp` or `smithery mcp add`. SkillSmith's concrete roadmap items — TOML manifest, cross-project sync, existence detection, deterministic adaptation with LLM fallback — each map to features a competitor either has, is experimenting with (`npx skills experimental_sync`), or could ship in a sprint.

## What each AI-native tool does, and what to steal

The surface area across Claude Code, Codex, Cursor, Kilo, Cline, Continue, Windsurf, Factory, Copilot, Aider, llm CLI, Zed, and JetBrains reveals a tangled stack of at least **seven config formats** (plain Markdown, MD+YAML frontmatter, MDC, pure YAML, TOML, JSON, Python entry-points) and **four unit abstractions** (rules, skills, modes/agents, plugins). Two open specs are quietly winning: **SKILL.md with YAML frontmatter** (Anthropic origin, adopted by Codex, Kilo, Cursor, Copilot, Vercel) and **AGENTS.md** (stewarded by the Linux Foundation's AAIF, adopted by Codex, Cursor, Windsurf, Zed, Factory, Warp, Copilot, Aider, goose, opencode, and ~60,000 repos per the AAIF launch materials).

**Claude Code** exposes the richest conceptual vocabulary and also the richest bug surface. Skills live at `~/.claude/skills/<name>/SKILL.md` (user) or `.claude/skills/` (project); plugins extend this with `.claude-plugin/plugin.json` bundling skills, commands, subagents, hooks, and MCP servers. The official registry is `anthropics/claude-plugins-official`; the anthropics/skills repo showcases `pdf`, `docx`, `xlsx`, `skill-creator`, and `webapp-testing`. Install happens via REPL (`/plugin install name@marketplace`) or an under-documented `claude plugin` CLI. **There is no official `claude skill install <url>` for standalone SKILL.md directories outside of plugins** — this is the clearest gap SkillSmith could fill, and the gap is already being filled by `npx skills`.

**OpenAI Codex CLI** reads `~/.codex/AGENTS.md`, `~/.codex/config.toml`, and scans `~/.codex/skills/` using a directory layout **identical to Anthropic's SKILL.md spec** — a material signal that the Agent Skills format is becoming a de facto cross-vendor standard. **Kilo Code** (kilo.ai) reads the same SKILL.md spec at `.kilo/skills/` and explicitly supports compat fallback to `.claude/skills/` and `.agents/skills/`; its marketplace at github.com/Kilo-Org/kilo-marketplace has no UI yet — a weakness SkillSmith could exploit if it prioritized Kilo. **Cursor** launched its plugin marketplace in Feb 2026 with one-click install, mixing MDC rule files, SKILL.md skills, and MCP config under `.cursor-plugin/plugin.json`.

**Cline** leans entirely on MCP plus `.clinerules`, with in-IDE marketplace install backed by github.com/cline/mcp-marketplace. **Continue.dev** is the most package-manager-like of the bunch — YAML assistants compose from "blocks" imported as `owner/slug@version` via hub.continue.dev, with mustache-interpolated inputs and overrides. **Windsurf** reads `.windsurf/rules/*.md` with YAML frontmatter (`trigger: always_on|manual|model_decision|glob`) plus AGENTS.md. **Factory/Droid** ships `/droids` TUI for interactive skill creation with import from Claude Code subagents. **GitHub Copilot** is the most structurally ambitious, with separate `.github/instructions/*.instructions.md`, `.github/prompts/*.prompt.md`, `.github/agents/*.agent.md`, and SKILL.md dirs, all installable via `copilot plugin install`. **Simon Willison's llm CLI** uses a pure Python/pluggy model with `llm install <pkg>` wrapping `pip install` — a clean prior art for a language-native plugin system. **Zed** falls back through a priority chain (`.rules` → `.cursorrules` → `.windsurfrules` → `.clinerules` → `CLAUDE.md` → `AGENTS.md`), which is itself a minor pattern worth stealing: **read what the user already has, rather than demanding a new file**.

**Patterns worth stealing from this tier:** Continue's `owner/slug@version` identifier plus `uses:` import semantics; Copilot's kinded plugin items (`kind: prompt|agent|instruction|skill|hook`); Zed's "read whatever rule file exists" graceful fallback; Factory's Claude Code subagent import with tool/model auto-mapping; Kilo's compat-path fallback so the same directory works for multiple agents.

## Adjacent package managers: ten patterns SkillSmith should adopt

Twenty-two distinct patterns surfaced across npm/pnpm, pipx/uv, Homebrew, VS Code, lazy.nvim, Helm/ArgoCD, asdf/mise, and Cargo. The ten with the highest leverage for SkillSmith, ranked by directness of fit:

**The declarative manifest plus apply/check/cleanup triad** (Brewfile, Helm `upgrade --install`, kubectl apply, lazy.nvim, Cargo) is the non-negotiable core UX. Steal Brewfile's three-verb split: `apply` installs missing and upgrades outdated, `check` dry-runs and exits nonzero on drift (perfect for CI hooks), `cleanup --force` prunes extras with an explicit safety gate. See [docs.brew.sh/Brew-Bundle-and-Brewfile](https://docs.brew.sh/Brew-Bundle-and-Brewfile) and [argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/).

**The Brewfile multi-backend installer module** is the defining architectural metaphor for a cross-tool installer. A single Brewfile already declares `brew "ffmpeg"`, `cask "firefox"`, `vscode "ms-python.python"`, `npm "typescript"` — one manifest, many backing package managers, each with its own installer/checker/dumper. SkillSmith's targets (claude, cursor, codex, kilo) should be implemented as Brewfile-style backend modules from day one; retrofitting is brutal.

**GitHub user/repo identifiers plus pluggable taps** (Homebrew taps, lazy.nvim plugin specs, Scoop buckets) give zero-infrastructure distribution: anyone with a GitHub repo is a publisher. Layer Cargo's `[registries]` pattern on top for private enterprise registries with separate auth files and sparse-HTTP indexes — see [doc.rust-lang.org/cargo/reference/registries.html](https://doc.rust-lang.org/cargo/reference/registries.html).

**Lazy loading with activation triggers** (lazy.nvim's `event`/`cmd`/`ft`/`keys`, VS Code's `activationEvents`) is the AI-agent-specific killer pattern. **An agent with 50 skills installed shouldn't pay 50× the context-window tax.** Skills should declare `activationFiletypes`, `activationKeywords`, `activationCommands` in frontmatter; the agent host exposes only triggered skills. This directly addresses the Claude Code docs' own warning that description budgets truncate skill metadata when users install too many skills.

**Lockfiles for reproducibility** (lazy-lock.json, Cargo.lock, uv.lock) are standard but critical: `skillsmith.lock` should pin `{user, repo, sha, manifest-hash}` plus a system fingerprint a la Brewfile.lock.json.

**Scope precedence with `list` introspection** (mise's layered configs, asdf's `asdf current` showing the source file) — `skillsmith list` must show not just what's installed but **which config declared it**, resolving the #1 future support ticket: "why is this skill here?"

**Ephemeral no-install execution** (`npx`, `uvx`, `pipx run`) powers `skillsmith run owner/skill` for one-off trials and CI jobs. Critically, steal **npx's interactive prompt before downloading from an unfamiliar publisher** — it's a proven anti-typosquat mitigation that competitor installers lack.

**Doctor command with plugin-contributed checks** (brew doctor, mise doctor, nvim `:checkhealth`) — essential for a cross-tool tool. `skillsmith doctor` verifies each target agent is detected, its skills dir is writable, installed files aren't orphaned, manifest matches lockfile, and lets individual skills contribute their own health checks via a plugin hook.

**Team manifest plus opt-in cross-machine sync** — two orthogonal sync stories. `skillsmith.toml` committed to repo is the team manifest (like `.vscode/extensions.json` recommendations). A separate `skillsmith sync` with account-backed storage handles user-global skills across personal machines (like VS Code Settings Sync). **Critical lesson from VS Code: never sync user prefs into project/container scopes.** See [code.visualstudio.com/docs/configure/settings-sync](https://code.visualstudio.com/docs/configure/settings-sync).

**Isolated per-skill directories with entry-point symlinks** (pipx's venvs, mise's direct-PATH over asdf's shims). Each skill at `~/.skillsmith/skills/<user>/<repo>@<sha>/` with its own dependencies, only entry points symlinked into tool-specific locations. Enables conflict-free coexistence and guaranteed-clean uninstall — directly solving the Claude Code issue #30138 complaint that "disabled doesn't mean uninstalled."

Honorable mentions not in the top ten but worth the effort: Helm values-file layering for skill configuration (`values.toml` → user → project → env → `--set`); lifecycle hooks modeled on Helm's pre-install/post-install/pre-upgrade annotations; version compatibility ranges (`engines` in VS Code, `since-build/until-build` in JetBrains plugins); drift detection via `check --exit-code` for CI pre-commit hooks; git-ref pinning with partial clones (lazy.nvim style); and extension-pack meta-skills for curated bundles (VS Code's `extensionPack` field).

## User pain points, organized and quoted

The research surfaced verbatim pain from GitHub issues, Substack, dev.to, HN, Reddit, and Cursor forum, concentrated in ten themes. Every quote below is real and linkable.

**Format fragmentation is described as a "digital Tower of Babel."** The Layer5 blog writes: *"When you switch tools or collaborate with a team using different agents, you're stuck translating the same core instructions into multiple formats… Every time a rule changes — like updating your deployment command or linting standard — you have to update it in multiple places, hoping you don't miss one"* ([layer5.io/blog/ai/agentsmd-one-file-to-guide-them-all](https://layer5.io/blog/ai/agentsmd-one-file-to-guide-them-all/)). A Data Science Collective article adds: *"Claude wants CLAUDE.md. Cursor wants .cursorrules… GitHub Copilot wants .github/copilot-instructions.md. Windsurf wants .windsurf/rules. Google's Jules wants JULES.md. The content is almost identical across all of them. But you're copying and pasting the same instructions into five different files"* ([medium.com/data-science-collective](https://medium.com/data-science-collective/the-complete-guide-to-ai-agent-memory-files-claude-md-agents-md-and-beyond-49ea0df5c5a9)). The rulesync author puts it concretely: *"This creates the need to manually 'synchronize' rule files between tools every time rule content is changed"* ([dev.to/dyoshikawatech](https://dev.to/dyoshikawatech/rulesync-published-a-tool-to-unify-management-of-rules-for-claude-code-gemini-cli-and-cursor-390f)). The rule-porter author frames the lock-in angle: *"if you've invested time writing good .mdc rules in Cursor, those rules are locked in… None of that translates to Claude Code's CLAUDE.md"* ([dev.to/nedcodes](https://dev.to/nedcodes/rule-porter-convert-cursor-rules-to-claudemd-agentsmd-and-copilot-4hjc)). Very common signal.

**Scope confusion is a shipping bug in Claude Code itself.** Issue #16728 documents: *"MCP servers added with --scope user do not actually apply user-wide… The --scope user flag now writes to ~/.claude/.claude.json under projects['<path>'].mcpServers… Misleading flag: --scope user doesn't mean 'user-wide'. Issue #8288 asks for basic diagnosability: *"Users cannot determine if an MCP server is configured at local, project, or user scope… it was impossible to understand this was due to directory-based MCP loading"* ([issues/8288](https://github.com/anthropics/claude-code/issues/8288)). Issue #5963: *"MCP servers added with project scope work correctly during Claude Code execution… but do not appear in claude mcp list output"* ([issues/5963](https://github.com/anthropics/claude-code/issues/5963)). Inventive HQ's config guide concedes: *"This file is at ~/.claude.json, NOT inside the ~/.claude/ directory. **Scope shadowing between user and project is inconsistent.** Issue #44207: *"When a project has its own .claude/skills/ directory, skills from the global ~/.claude/skills/ directory are not loaded… Global skills in ~/.claude/skills/ are ignored entirely (not just name-conflicting ones — all of them)"* ([issues/44207](https://github.com/anthropics/claude-code/issues/44207)). Docker's MCP Horror Stories: *"When a developer innocently asks their AI assistant to 'check the open issues,' the agent reads the malicious issue, gets prompt-injected, and follows hidden instructions to access private repositories and leak sensitive data publicly"* ([docker.com/blog/mcp-horror-stories-github-prompt-injection](https://www.docker.com/blog/mcp-horror-stories-github-prompt-injection/)). **Discoverability is weak despite thousands of repos.** Claude Code's own docs concede the problem: *"All skill names are always included, but if you have many skills, descriptions are shortened to fit the character budget, which can strip the keywords Claude needs to match your request"* ([code.claude.com/docs/en/skills](https://code.claude.com/docs/en/skills)). Build-to-Launch: *"Skill counts climbed into the hundreds. Community repos got shared. Template packs appeared. Most of them are silently broken. **Top five pain points, ranked by frequency and intensity:** (1) format fragmentation forcing copy-paste across 5+ files; (2) scope semantics that silently write to the wrong place and are then undiscoverable; (3) silent-failure installs where nothing errors and nothing runs; (4) no robust update path, with manual cache deletion as the documented workaround; (5) unresolved supply-chain trust where community installers compound the risk rather than mitigate it.

## Feature ideas for SkillSmith, tied to evidence

**Features to steal from competitors.** From Vercel's `npx skills`: the `-a <agent>` and `-a '*'` flag ergonomics, install telemetry feeding a public leaderboard for discovery, and experimental sync — but ship sync as GA, not experimental. From APM: transitive skill dependencies, org-policy inheritance via `apm-policy.yml`, SARIF output for CI, and `pack/unpack` for air-gapped enterprise delivery. From Continue.dev: `owner/slug@version` identifiers with `uses:` imports, mustache-interpolated inputs (`${{ inputs.X }}`) and secret references for skill config. From Smithery: ephemeral API-key injection for skills that wrap paid services. From Copilot plugins: `kind:` tagging (`prompt | agent | instruction | skill | hook`) inside a single plugin bundle. From llm CLI: PyPI-style plugin distribution for skill backends, so new target tools (future AI agents) can be added by third parties without SkillSmith releases. From Neon's add-mcp: auto-detect which agents are installed and only install to those by default. From Kilo Code: compat-path fallback so a SkillSmith-installed skill also works with a stock `.claude/skills/`-reading tool.

**Unmet needs with direct evidence.** Four opportunities have explicit user demand that no shipping competitor fully addresses.

First, **signed, verified, auditable skills**. Given the AuthZed CVE-2025-6514 precedent and the Docker/Stacklok supply-chain warnings, there is a clear opening for a "verified publisher" tier analogous to npm's provenance attestations. SkillSmith could require signed releases, publish SBOMs, sandbox scripts on first install, and expose a `skillsmith audit` command that diffs an installed skill's tree against its signed manifest hash. None of Vercel skills, APM, Smithery, or the smaller clones does all of this. Target users: any enterprise that already blocks `npx` in CI.

Second, **true cross-tool uninstall with lifecycle hooks.** Claude Code issues #30138 and #11240 explicitly request pre-/post-install and pre-/post-uninstall hooks with automatic cleanup. Helm hooks and npm lifecycle scripts are mature prior art. A SkillSmith skill manifest that declares `[hooks] postinstall = "..."` and `preuninstall = "..."` with explicit security prompts (these run arbitrary code, so require user approval on first install) would directly address the orphan-config pain quoted from multiple issues and guides.

Third, **scope-aware `list` with source-file attribution.** asdf's `asdf current` shows the config file path that decided each tool's version. Claude Code users can't answer "why is this skill here?" today (issue #8288). `skillsmith list` should show skill name, SHA, scope (user/project/workspace), the config file path that declared it, and the set of agents it's currently registered with. This is a low-effort feature with outsized support-burden impact.

Fourth, **activation triggers in SKILL.md frontmatter.** The Claude Code docs' own warning that description budgets get truncated means users who install many skills silently degrade Claude's ability to match them. Borrow lazy.nvim's trigger semantics: `activationFiletypes`, `activationKeywords`, `activationCommands`, `activationGlobs`. SkillSmith can implement this client-side by toggling skill files in/out of the active scope based on cwd, open file, or user command — a layer above each agent's native loading. This directly compresses context-window overhead, which maps to user-visible cost and quality.

**Features to be skeptical about.** An LLM-fallback format adapter (proposed for SkillSmith Phase 2) is strategically risky: each round-trip converts metadata losslessly at best, but introduces probabilistic regressions and makes support tickets much harder to diagnose. The three shipping converters (rule-porter, cursor-rules-to-claude, Vooster) are all deterministic, and the AAIF-backed convergence on AGENTS.md + SKILL.md means the space of required conversions is shrinking monthly. Consider deferring the LLM fallback until there's evidence of a conversion pair where deterministic rules demonstrably fail.

## Risks and threats

**Five ecosystem risks rank high on probability × impact.** First, Vercel's `npx skills` continues to entrench — with one skill at 579K installs, Vercel-brand distribution, and visible iteration velocity (v1.5.1 within days of publish), the default answer to "how do I install a cross-tool skill?" in developer chatter is already `npx skills`. Probability: ~95%. Second, GitHub Copilot's `copilot plugin install … @awesome-copilot`, now GA, is positioned to become the default for the ~80% of developers already on GitHub; VS Code's native Agent Skills support as of April 2026 closes the loop. Probability: ~85%. Third, standards convergence on AGENTS.md plus SKILL.md erodes "format adaptation" as a differentiator — if every target agent reads the same two file formats, adaptation degenerates to path mapping, which every competitor already does. Probability: ~70% in 12 months. Fourth, Microsoft APM owning the enterprise segment via SARIF, GitHub Rulesets, Unicode-injection scanning, and the Microsoft org brand: for any large buyer comparing a free MS-backed OSS tool to SkillSmith, APM will win on procurement defaults. Probability: ~65%. Fifth, native package managers absorbing skills (antfu's `skills-npm`, pixi experiments) — if `npm install` auto-symlinks skills via prepare scripts, a dedicated installer becomes redundant for JS/Python-native repos. Probability: ~60%.

**Lower-probability but higher-impact scenarios** include Anthropic shipping an official `claude skill install <url>` that also populates `.codex/skills/` and `.cursor/rules/` (currently ~40% likely in 12 months; would be existential), and MCP's spec absorbing skills as a resource type (~25% but changes SkillSmith's substrate entirely).

**Potential allies, not threats**: Smithery's focus is MCP, not skills — a partnership framing of "Smithery for tool connectivity, SkillSmith for procedural knowledge" is natural and neutral. Anthropic itself **donated Agent Skills as an open standard** (March 2026) and explicitly wants ecosystem adoption rather than lock-in, which means a neutral installer is complementary to Anthropic's interests. The Linux Foundation's AAIF (Anthropic, OpenAI, Block co-founders; AWS, Google, Microsoft, Cloudflare, Bloomberg platinum members) is the standards venue to watch and contribute to — a TOML-manifest specification proposal into AAIF would be both a moat (first-mover on governance format) and a credibility signal.

**On demand validation:** JetBrains' State of Developer Ecosystem 2025 reports 85% of developers regularly use AI tools; the AI Pulse January 2026 update shows Claude Code awareness at 57% (up from 31% in April 2025) with 18% adoption, while Cursor remains very popular in the same cohort — implying substantial multi-tool overlap. Stack Overflow's 2025 Developer Survey (49,000+ developers) shows 84% using or planning to use AI tools and 51% of pros using AI daily, but favorability dropping to 60% (from 70%+ in 2023–24) and 66% frustrated by "AI solutions almost right but not quite." The demand is real, but so is dissatisfaction — which cuts both ways: users will try a new installer, and users will churn quickly if it doesn't work.

## Open strategic questions for the SkillSmith team

**What is the differentiator that isn't copied within a sprint?** Vercel can flip sync from experimental to GA, add TOML support, and match SkillSmith's CLI surface quickly. Defensible moats plausibly come from (a) a verified-publisher + signed-skills trust layer; (b) authoring and test infrastructure (skill linting, activation-trigger validation, dry-run harness); (c) deep enterprise policy ergonomics simpler than APM; or (d) vertical curation (SkillSmith for data engineering, SkillSmith for SRE). Which one does the team commit to?

**Is the business model tenable?** Every serious competitor is open source — Vercel, Microsoft APM, Smithery CLI, skild, skillpm, antfu skills-npm. Going closed-source is likely fatal. A freemium model (OSS core plus a hosted private registry and policy layer) is plausible, but APM already gives the policy layer away for free and Smithery already runs the registry. The honest answer may be that SkillSmith as a pure installer is a community-value project, not a $100M outcome — in which case the strategic question is whether the team is building a brand/DX wedge that leads into a different product (authoring IDE, skill-quality benchmarking, enterprise governance).

**Which target tools should be first-class vs. long-tail?** Claude Code + Codex + Cursor are obligatory. Kilo Code is a genuine opportunity (Kilo's own marketplace has no UI yet, per its docs). Copilot should be supported but Copilot users will prefer `copilot plugin install` by default. Aider, Zed, JetBrains AI Assistant have no native installer and therefore higher relative value from SkillSmith — these are strategic "last mile" targets.

**Should SkillSmith contribute to AAIF now or later?** Submitting a TOML-manifest skill-packaging proposal to AAIF early (before a competitor does) would be a low-cost strategic move with outsized credibility upside. The risk is that AAIF picks APM's YAML format or Vercel's JSON lockfile as the standard, closing off SkillSmith's ergonomic choice.

**What is the migration story from existing tools?** `rule-porter`, `cursor-rules-to-claude`, and Vooster's converter each handle one direction. SkillSmith should bundle a first-class `skillsmith import` command that reads `.cursorrules`, `.clinerules`, `.windsurfrules`, `CLAUDE.md`, and `.github/copilot-instructions.md` and emits a canonical SKILL.md + AGENTS.md layout. This is a credible user-acquisition wedge aimed at the "Tower of Babel" pain quoted across multiple sources.

**What's the naming question?** "SkillSmith" collides semantically with Smithery, skild, skillpm, SkillsMP, skillport, skillshare (runkids), and Vercel skills. A distinct name reduces confusion and SEO friction; the team should pressure-test the name before public launch.

## Conclusion

The honest read is that SkillSmith as specified ships into a market where the incumbent (Vercel's `npx skills`) owns the mainstream, the enterprise flank is claimed (Microsoft's `apm`), the distribution flank is claimed (GitHub Copilot + VS Code), and the standards layer is consolidating under AAIF in ways that shrink the adaptation value prop over the next 12 months. The space is not dead, but winning requires picking a sharper wedge than "better `npx skills` with TOML." The three most defensible wedges that emerged from the evidence are **trust and signed skills** (grounded in the AuthZed CVE and Docker horror-stories material), **activation-triggered lazy loading** (grounded in Claude's own description-budget docs and lazy.nvim's prior art), and **scope-aware introspection with lifecycle hooks** (grounded in the long catalogue of Claude Code scope and uninstall bugs). The genuinely novel insight from the research is that **AI agent skills are close enough to Neovim plugins that the lazy.nvim design — activation triggers, declarative specs, partial-clone git references, lockfiles, plugin-contributed healthchecks — is the most underappreciated prior art in the ecosystem, and no competitor has yet borrowed it**. SkillSmith's strongest differentiated move is to treat skills like lazy.nvim treats plugins, wrap that in Brewfile-style multi-backend modules, and layer a verified-publisher trust tier on top. Everything else on the roadmap is table stakes — necessary to ship, insufficient to win.
